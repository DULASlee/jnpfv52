🔑 第一个关键决策：Skills 的组织模型

继承文档中"A2A协议 + 事件溯源 + MCP工具生态 + 统一IR"的设计范式，但需要决定 Skills 之间如何组织。

A

严格流水线模型

8 个 Skills 按 SDLC 阶段严格串行，前一个完成才触发下一个。类似于现有的 5 阶段 Pipeline Orchestrator。

Pros

  • 流程清晰可控
  • IR 单向演进，无冲突
  • 实现简单，心智负担低

Cons

  • Bug修复需要"回退"到早期阶段
  • 无法并行（如 UI + DB 同时设计）
  • 灵活性差，变更成本高
B

事件驱动 + DAG 依赖图

每个 Skill 是独立 Agent，通过 A2A 事件总线通信。Skills 之间声明数据依赖（DAG），满足依赖即自动触发，不强制串行顺序。

Pros

  • 最大并行度（UI + DB + 架构可同时进行）
  • Bug修复自然融入（修改事件触发下游重算）
  • 与文档中 A2A 设计范式完美对齐

Cons

  • 需要依赖图引擎（拓扑排序 + 变更传播）
  • 并发写入 IR 需要冲突解决
  • 调试复杂度较高
C

分层 + 子流水线混合

将 8 个 Skills 分为 3 层（认知层/设计层/执行层），每层内用 DAG 并行，层间严格串行。Bug修复 Skill 可跨层切入。

Pros

  • 兼顾可控性和灵活性
  • 层间明确的质量门（gate）
  • 每层可以独立迭代升级

Cons

  • 层间串行可能成为瓶颈
  • 分层粒度需要仔细权衡
  • 设计决策多一层抽象
