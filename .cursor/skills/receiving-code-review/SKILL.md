# Receiving Code Review — 处理审查意见

## 核心原则

**先核实，再实施。** 技术正确性优先于社交礼貌。

## 响应流程

```
1. READ    — 完整阅读，不立即反应
2. UNDERSTAND — 用自己的话复述要求（或提问）
3. VERIFY  — 对照代码库核实建议是否成立
4. EVALUATE — 对本项目是否合适？
5. RESPOND — 技术确认或有理有据的反驳
6. IMPLEMENT — 逐条修复，每条单独验证
```

## 禁止回应

- ❌ 「您说得对！」「好建议！」（表演式）
- ❌ 未核实时说「马上改」

## 应做回应

- ✅ 复述技术要求
- ✅ 提出澄清问题
- ✅ 用技术理由反驳（若建议不当）
- ✅ 直接动手改，用代码说明

## 不清楚的条目

**全部条目理解清楚之前，不要开始改任何一条。**

```
✅ 「我理解 1、2、3、6。4 和 5 需要澄清：[具体问题]」
❌ 先改 1、2、3、6，4、5 以后再说
```

## 外部审查者意见

实施前检查：
1. 对本代码库技术上是否正确？
2. 是否破坏现有功能？
3. 当前实现是否有历史/兼容原因？
4. 审查者是否掌握完整上下文？

若建议不当 → 用技术理由 push back，必要时与用户确认。

## YAGNI 检查

审查者要求「正规实现某功能」时 → 先 Grep 是否真有调用方。无调用 → 建议删除而非过度实现。

## 实施顺序

1. 阻塞项（崩溃、安全）
2. 简单项（拼写、import）
3. 复杂项（重构、逻辑）
4. 每条改完单独验证（`dotnet build` / 相关测试）

## 与 requesting-code-review 配对

- `requesting-code-review` — 发起审查
- `receiving-code-review` — 处理返回意见
- 修复后必要时再次 `requesting-code-review`
