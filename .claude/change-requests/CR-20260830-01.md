## 1. 业务理由（v1 → v2 重置原因）

### 1.1 Phase 8 反查触发的 3 类真问题

| # | 问题 | v1 误判 | v2 正确判定 |
|---|------|---------|------------|
| **P-A** | Skill v1.0 缺少 Target Schema Contract | "SchemaChange=Yes = 17 处真实迁移" | **17 处全是列名代理绕过**（F_ApplyUser→F_InputPerson），等于把命名问题下沉运行时 |
| **P-B** | NO-CHANGE 证明机制缺失 | "154 张表 NO-CHANGE = 治理成熟度" | **NO-CHANGE 没找到改动 ≠ 符合目标**，应证明 8 维度合规 |
| **P-C** | 性能验证完全缺失 | "加索引 = 性能提升" | **禁止逻辑推理**，必须 Before/After 测量 |

### 1.2 v1 CR 的过度现代化倾向（必须删除）

| v1 提出（错误） | 修正（v2） |
|--------------|----------|
| base_user 垂直拆分（1 拆 5） | **暂不做**（破坏动态配置链路） |
| datetime → datetime2 全库改 | **新表规范 + 旧表分领域迁移** |
| nvarchar(50) GUID → bigint | **不做**（JNPF 低代码平台 GUID 必要） |
| Temporal Tables 启用 | **暂不做**（与现有 f_delete_mark 写入路径冲突） |
| Row-Level Security | **暂不做**（过度现代化，ITenantFilter 已够） |
| Outbox Pattern / Event Sourcing | **不进入本 CR**（属未来架构演进） |
| CQRS / Domain Boundary | **不进入本 CR** |
| 外键约束（FK）渐进加严 | **暂不做**（JNPF 应用层维护完整） |

### 1.3 真正必须修的 P0 项（5 项）

| # | 项目 | 原因 |
|---|------|------|
| **P0-1** | base_user 安全模型 | 密码字段过短（暗示 MD5）+ f_account 无 UNIQUE + f_tenant_id 可 NULL |
| **P0-2** | tenant 隔离硬保证 | SaaS 核心，ITenantFilter 应用层已做，DB 层 NOT NULL 缺失 |
| **P0-3** | 账号唯一约束 | UNIQUE(f_tenant_id, f_account) 防重复 |
| **P0-4** | Schema Migration Governance 三分类 | 纯技术改名 / 业务语义变化 / 低代码动态字段 混为一谈 |
| **P0-5** | NO-CHANGE 证明机制（IRON-TABLE-01） | 防止虚假完成 |

### 1.4 Skill v1.0 必须升级（核心）

**v1.0 缺陷**：缺少 Target Schema Contract + 5 条 Iron Laws。

**v2.0 必须新增**：

```
IRON-TABLE-01  No Change ≠ No Action           没有变化必须证明符合目标状态
IRON-TABLE-02  Mapping Is Not Migration        字段映射不能替代 Schema Migration
IRON-TABLE-03  Every Table Needs Target Contract   每张表必须有 Target Schema Contract
IRON-TABLE-04  Security Boundary First         身份/租户/权限审计优先于一切
IRON-TABLE-05  Performance Claim Requires Measurement   加索引≠性能提升
```
