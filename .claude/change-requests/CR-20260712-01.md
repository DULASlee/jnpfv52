# CR-20260712-01：编排器 Finalize 修复 PM 终评门控逃逸

> **状态：** 待审批 → 审批后标 `workflow-state.json` `cr-approved`
> **铁律触发：** 需求分析子链铁律第六条（保护方法修改前 MUST CR）+ 实现完整性禁令一（禁止给门控开逃逸通道）
> **保护方法：** `RequirementAnalysisOrchestrator`（编排器）

## 一、根因（运行时证据 · pipeline 343）

`RequirementSpecPmReviewed` IR 事件 ×3，score = 0 / 0 / 40，verdict 全 `fail`（threshold=85）。
但 `AnalysisCompleted(finalized=true)` 仍被写入 ×3，`canRunDesign=true`。

**结论：** PM 终评门控在自动主链被完全绕过——这是门控逃逸（禁令一），343 的"业务真绿"是假的。

## 二、缺陷定位（确证）

| # | 缺陷 | 位置 | 性质 |
|---|---|---|---|
| **D1** | 编排器 Finalize 先跑、PM review 后跑且 verdict 被丢弃 | `RequirementAnalysisOrchestrator.cs:401-414`（round3）/ `:207-211`（ForceRefinalize）/ `:231-236`（auto>3rounds） | 门控逃逸 |
| **D2** | 自动主链无 force 留痕逃生口（仅手动 API 有） | `SkillsApiService.cs:242-249` 有 vs 编排器无 | 逃生口缺失 |
| **D3** | 02 附录 E loader 按 stage 过滤，343 澄清答案被丢弃 | `AnalystSkillService.cs:870` `LoadRequirementClarificationAppendicesAsync` | 渲染数据丢失（非保护方法，本 CR 一并修） |

## 三、修复方案（自定默认实现）

### D1 + D2 修复（编排器 · 保护方法）

**原则：PM review 先于 Finalize；fail 阻断 Finalize；forceConfirm 留痕作逃生口（对齐手动 API `SkillsApiService.ConfirmRequirementSpecAsync:242-249` 既有语义）。**

1. `ReviewRequirementSpecAsync` 改为返回 `Task<PmSpecReviewResult>`（暴露 Score/Verdict/Gaps）。
2. 三处 Finalize 分支（401-414 / 207-211 / 231-236）改为：
   - 先调 `ReviewRequirementSpecAsync` 拿 review。
   - `review.Verdict == "pass"`（即 score≥85）→ 进 Finalize（enableFinalization:true）。
   - `review.Verdict == "fail"`：
     - 默认 `enableFinalization:false`（不物化、不写 AnalysisCompleted）。
     - `options.ForceConfirm == true` 时才 enableFinalization:true，并在 IR 事件 payload 写 `forceConfirm:true` + `forceReason`（留痕，对齐手动 API line 259/277）。
   - 返回 `Status = "pm-review-failed"`（fail 且未 force 时），供前端/调用方识别。

3. `RequirementAnalysisOrchestratorOptions` 增 `bool? ForceConfirm` + `string? ForceReason` 字段。

**不引入第二源（禁令二）：** PM 终评仍是唯一评分源；forceConfirm 仅是逃生口，不改评分逻辑。

### D3 修复（非保护方法 · 一并修）

`LoadRequirementClarificationAppendicesAsync`（AnalystSkillService.cs:870）放宽 stage 过滤：除三个 round 常量外，兼容历史 `"requirement"` stage；缺失 round 时从 setId 反推或标 round=0。确保 343 的 ClarificationAnswered 真写进附录 E。

## 四、不改的部分（防止越权）

- 不改 PM Skill 评分逻辑（`PmSkillService.ReviewSpecAsync` / `ParseSpecReviewResult`）——评分源唯一。
- 不改手动 API `ConfirmRequirementSpecAsync` 既有 forceConfirm 语义——编排器对齐它，不反向改它。
- 不改 28 号渲染器结构——仅修 loader 数据来源。
