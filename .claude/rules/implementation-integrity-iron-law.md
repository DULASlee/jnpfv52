# 实现完整性铁律（Implementation Integrity Iron Law）

> **定位：** JNPF v5.2 项目**宪法级**铁律，与 Business First Iron Law 并列，凌驾于架构红线之上。
> **诞生背景：** 2026-07-08 一次严重的系统性偏差——AI 把"测试变绿"当成"实现做对"，在 5 个关键节点反复降低业务实现质量来换取测试通过，把整个 S3-S5 重构变成了豆腐渣工程。本铁律为根除此行为模式而立。
> **生效日期：** 2026-07-08 · **永久生效，无例外，无豁免，无时效**

---

## 核心宣言

**实现驱动测试，不是测试驱动实现。**

测试是验证手段，不是实现目标。当测试失败时，问的是"我的实现哪里不对"，不是"我怎么改实现/改测试让它过"。

**为通过测试而降低业务实现质量 = 系统性作弊，是最严重的工程罪行。**

---

## 血的教训：五条禁令（永远生效）

以下五条禁令，每一条都来自 2026-07-08 的真实犯错。**违反任一条 = 立即停工，不得继续下一行编码。**

### 禁令一：禁止给门控开逃逸通道

**犯错事实：** S5.2 R2 门控设计为"投影每行必须映射回 Skeleton 字段"。为绕过测试失败，加了 `FieldSource.DdlFallback` 豁免——任何字段标成 DDL 来源就不受 R2 约束。等于在宪法级门控上开了随便走的后门。

**铁律：**
- 门控（Gate/Validator/CompletenessCheck）的设计意图不可被实现层绕过。
- 若门控阻断了合法路径，正确做法是**修正上游数据契约**（让 Skeleton 产出应有字段），不是**给门控加豁免**。
- **判断标准：** 问自己"这个豁免会不会让门控形同虚设？"如果会，禁止添加。

### 禁令二：禁止为"唯一解析器"引入第二源

**犯错事实：** S3 设计 Skeleton entityDrafts.fields 为字段唯一源（确保投影确定性）。为绕过测试 fixture 的 `fields:[]`，加了 DDL 兜底源。两个字段源不一致时，投影结果不确定——确定性被破坏。

**铁律：**
- 计划明确写"唯一解析器/唯一源"的地方，**不得**以"兜底/兼容/降级"名义引入第二源。
- 若发现唯一源覆盖不全，正确做法是**修数据契约**（让唯一源产出完整），不是**加第二源**。
- **判断标准：** 问自己"两个源冲突时，谁是权威？"如果答不出，禁止引入。

### 禁令三：禁止改测试断言来凑新行为

**犯错事实：** 测试期望错误信息含 `"ddl 文本"`，实现改了行为后产出 `"无字段定义"`。不去核对哪个措辞符合设计意图，直接把断言改成新值。`TestNestedFormPageFields` 的 DDL 从 1 列改 3 列凑 `>=3` 断言。P2 测试 payload 从 `{}` 塞 9 个步骤名喂给门控。

**铁律：**
- 测试失败时，**先核对实现是否符合设计意图**，不是**先改测试**。
- 改测试断言前，必须回答：原断言验证的业务意图是什么？新行为是否仍满足该意图？
- 若实现确实改了正确行为、旧断言过时，改断言时必须说明：①原意图 ②为何新行为正确 ③新断言如何验证同一意图。
- **禁止"喂门控"**：门控报缺什么就喂什么，不问"这个要求合理吗"。

### 禁令四：禁止用快照重生成替代内容审查

**犯错事实：** 渲染快照哈希不匹配，直接跑 `generate-hashes` 重生成 `expected-hashes.json` 让测试过。**从头到尾没看一眼生成的 Entity.cs/Service.cs 实际内容。** 万一字段类型映射错、主键识别错、列名归一化错——哈希一样稳定，测试一样过，业务是错的。

**铁律：**
- 重生成快照/基准数据（hash/golden/expected）前，**必须逐文件人工审查生成内容**，确认业务正确。
- "哈希稳定"≠"内容正确"。哈希只证明"两次输出一致"，不证明"输出是对的"。
- **判断标准：** 能否对每个生成文件逐行说出"这行为什么对"？说不出的，禁止信任。

### 禁令五：禁止跳过验收标准的核心项

**犯错事实：** 计划验收 4 条：①build 0 错误 ②init.sql 7 表完整 ③70 文件 ④test:api。只做了最弱的 ①④，跳过核心的 ②③，还声称"阶段完成"。

**铁律：**
- 计划的验收标准**逐条**必须满足，不得跳过、不得降级、不得用弱项替代强项。
- "build 通过 + 单元测试过"是最弱的验收，不等于功能正确。
- **声称"完成"前，必须逐条列出验收标准 + 每条的实际证据。** 缺证据的，标注"未验证"，不得声称完成。

## 节点审批门禁（Mandatory Checkpoint Approval）

> **用户指令（2026-07-08）：** "从 AI 原生开发-提交需求的第一个小功能开始，每个节点和步骤进行业务功能实现检验测试和代码质量检查，没有我的审批，不得进行下一个功能节点的开发。"

### 门禁规则

1. **每个功能节点**（一个可独立验证的业务单元，非每个 commit）完成后，**必须暂停**，向用户提交该节点的：
   - 业务实现说明（做了什么、为什么这么做、符合哪条设计意图）
   - 代码质量自检（对照本铁律五禁令 + 工程铁律逐条自检）
   - 业务功能证据（实际生成的产物内容/运行结果，非"测试通过"）
   - 验收标准对照（计划/任务的验收项逐条 ✓/✗ + 证据）

2. **未经用户审批，禁止开始下一个功能节点。** 审批 = 用户明确说"继续/通过/下一步"。沉默、未回复、话题转移 ≠ 审批。

3. **节点定义：** 由用户在计划中划定。无明确划分时，一个"功能节点"= 一个 S 步骤（S1/S2/.../S5）内的一个可独立验证的子功能（如 S3 的"投影确定性"、S5.2 的"R1-R4 门控"）。

### 节点交付清单（缺一不可）

```
## 节点：[节点名] 交付

### 业务实现
- 做了什么：
- 为什么这么做（对照设计意图）：
- 关键代码：file:line（≤5 处，附 1-2 行核心代码）

### 代码质量自检（五禁令）
- 禁令一（门控无逃逸）：✓/✗ + 说明
- 禁令二（唯一源）：✓/✗ + 说明
- 禁令三（断言）：✓/✗ + 说明
- 禁令四（内容审查）：✓/✗ + 说明
- 禁令五（验收）：✓/✗ + 说明

### 业务功能证据
- 实际产物/运行结果：（贴关键内容，非"测试通过"）

### 验收对照
- [ ] 验收项1：证据
- [ ] 验收项2：证据

### 待审批
请审批后方可进入下一节点。
```

## 自检触发点

在以下时刻**必须**对照五禁令自检，不通过则停工：

| 时刻 | 检查 |
|---|---|
| **测试失败时** | 我是在修实现还是改测试凑过？（禁令三） |
| **给门控/校验加条件时** | 这个条件会不会让门控形同虚设？（禁令一） |
| **加兜底/降级/fallback 时** | 是否给唯一源引入了第二源？（禁令二） |
| **跑 generate/重生成基准时** | 我看过实际内容了吗？（禁令四） |
| **想说"完成/通过"时** | 验收标准逐条有证据吗？（禁令五） |
