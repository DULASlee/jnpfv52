# JNPF 低代码开发专属准则

> 编码/配置任务生效。覆盖平台原生能力边界意识、非侵入扩展、升级兼容等低代码开发核心红线。
> 与 `.claude/rules/architecture-redlines.md`（架构铁律）互补——架构铁律管"代码怎么写对"，本准则管"什么时候不该写代码"。

---

## 准则 1: 开发前先对齐

**不默认假设需求，优先确认平台原生能力边界，不盲目写代码。**

| # | 动作 | 反模式 |
|---|---|---|
| 1.1 | 接到需求先判断：是否可通过表单设计器、流程设计器、数据字典、权限配置等原生配置化能力实现 → **优先走零代码方案** | 上来就写 Custom Service |
| 1.2 | 确认需求对应的官方扩展方式：代码生成器+分部类 / 自定义表单控件 / 插件 / 事件订阅 / 独立业务模块 | 不查文档就自己发明扩展点 |
| 1.3 | 需求涉及平台原生能力修改 → **必须先明确告知升级风险与替代方案**，禁止默认修改平台源码 | 直接改 framework/ 或核心 Service |
| 1.4 | 需求有歧义 → 列出**所有可行路径 + 优缺点**，确认后再动手 | 凭猜测选一条路走下去 |

**关联红线：** R3（Codegen Boundary）、R5（Module Boundary）

---

## 准则 2: 配置优先，最简实现

**能用配置实现的绝不写代码，能用原生能力的绝不自定义，最小化代码量。**

| # | 动作 | 反模式 |
|---|---|---|
| 2.1 | 优先复用平台内置服务 API（用户、权限、流程、文件、字典）— 不重复实现原生已有能力 | 自己写一套 UserService |
| 2.2 | 代码生成器可覆盖的场景 → 严格遵循生成规范，不额外增加抽象、封装、预留扩展 | 在生成代码上套 Repository 模式 |
| 2.3 | **不为未明确要求的场景做兼容** — 不预留扩展点，不添加未请求的功能与配置 | "以后可能会用"的抽象 |
| 2.4 | 自定义代码仅实现平台原生能力**无法覆盖**的业务逻辑，保持逻辑最简、依赖最少 | 用自定义代码替换原生功能 |

**关联规则：** YAGNI（Technical Preferences）、jnpf-frontend-rules.md Component Selection

---

## 准则 3: 非侵入式扩展

**绝对不触碰平台原生代码，所有修改仅通过官方扩展点落地。**

| # | 动作 | 反模式 |
|---|---|---|
| 3.1 | **严禁修改**平台原生目录源码：后端核心引擎、系统服务、前端平台组件、设计器核心逻辑 | 直接改 `framework/` 下的 `.cs` |
| 3.2 | 代码生成器输出 → **禁止直接修改**；必须通过分部类、继承、事件订阅扩展，避免重新生成时被覆盖 | 在 `generated/` 目录改代码 |
| 3.3 | 仅修改用户自定义的业务代码与配置，不调整平台原生的配置项、表结构、接口定义 | 改系统表 `BASE_*` 结构 |
| 3.4 | 自定义模块、控件、插件遵循平台目录结构与命名规范 → 不与原生命名空间、组件名冲突 | 在 `JNPF.` 命名空间下创建类 |
| 3.5 | 表单、流程配置修改**仅针对需求指定的字段与节点**，不调整无关配置 | 顺手"优化"整张表单配置 |

**关联红线：** R3（Codegen Boundary）、R5（Module Boundary）

---

## 准则 4: 闭环验证交付

**先定义完成标准，交付前完成平台兼容性与功能验证。**

| # | 动作 | 反模式 |
|---|---|---|
| 4.1 | 把模糊需求转化为可验证的交付标准，**必须包含**：平台兼容性 + 版本升级兼容性要求 | "看起来没问题"就算完成 |
| 4.2 | 校验逻辑是否符合平台扩展规范，是否存在侵入原生代码的风险 | 不检查就声称完成 |
| 4.3 | 涉及接口/数据 → 验证平台统一鉴权、数据权限是否正常生效 | 用 `[AllowAnonymous]` 跳过权限 |
| 4.4 | 涉及流程/表单 → 验证全流程流转、字段联动、数据提交完整性 | 只测 happy path |
| 4.5 | 无法验证兼容性的场景 → **必须提前说明风险与适用边界** | 隐瞒兼容性风险 |

**关联规则：** Supreme Iron Law（E2E 证据）、testing.md、Phase 5 Verify

---

## 准则 5: 平台核心强制红线

**以下规则为最高优先级开发约束，违反需先输出风险提示。**

| # | 红线 | 对应架构红线 |
|---|---|---|
| 5.1 | **数据操作**：优先使用 SqlSugar ORM + 内置数据服务 API。禁止直接修改系统表结构（`BASE_*`、`FLOW_*`）。禁止裸写 SQL 操作系统核心表 | R7 |
| 5.2 | **权限体系**：所有业务接口、数据访问 MUST 接入平台统一权限体系（`[SecurityDefine]` / `[AllowAnonymous]`），不得自行实现鉴权逻辑 | R8 |
| 5.3 | **流程引擎**：流程流转规则 MUST 通过流程设计器配置，禁止硬编码流程节点、审批人与跳转逻辑 | R3 |
| 5.4 | **前端扩展**：自定义表单控件 MUST 兼容平台表单设计器，不得破坏设计器拖拽配置能力 | jnpf-frontend-rules.md |
| 5.5 | **升级兼容**：所有二开代码 MUST 保证平台版本升级时，无需修改原生代码即可正常运行。不得依赖平台内部未公开 API | R3 |

## 审查检查清单（code-reviewer 子代理使用）

```
✅ 低代码准则自查：
- [ ] 方案是否优先考虑了零代码/配置化路径？（准则 1）
- [ ] 是否有不必要的代码抽象或预留扩展？（准则 2）
- [ ] 是否触碰了平台原生目录或系统表结构？（准则 3）
- [ ] 交付标准是否包含平台兼容性要求？（准则 4）
- [ ] 是否遵守了 5 条强制红线？（准则 5）
```
