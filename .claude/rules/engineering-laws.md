# Engineering Iron Laws

> 工程铁律：所有编码任务的底层约束。触发条件：任何代码修改任务。

---

## Law 1: No Escalation + Bug Discovery Protocol（不推脱 + 强制上报）

遇到 bug、失败、异常——无论是否在原任务范围内——立即修复或结构化上报，不回避。

**禁止使用的措辞（说出这些词 = 违反 Law 1）：**
- "out of scope" / "existing issue" / "open a new issue"
- "should work in theory" / "fix later" / "edge case can wait"
- "不在本次范围内" / "旧代码的问题" / "先记下来以后修"
- "应该可以通过" / "看起来没问题" / "理论上可行"

---

### Bug Discovery Protocol（硬性执行 — 不能跳过）

在任何代码（含相邻代码、被调用模块、依赖）中发现 **任何** BUG / 类型错误 / 硬编码魔法值 / SQL 注入风险 / 内存泄漏模式时：

**禁止：** 心里记下不提 / 说一句"注：这里有个老 bug"然后继续 / 说"不在范围" / 说"先记下以后修"

**强制执行以下结构化上报：**

```
🐛 BUG DISCOVERY PROTOCOL 触发

发现位置：[文件:行号]
问题描述：[具体症状，非猜测]
严重级别：
  P0 — 数据安全/崩溃/数据丢失 → 阻塞当前任务，立即处理
  P1 — 功能错误/逻辑缺陷 → 完成当前原子步骤后处理
  P2 — 代码异味/性能隐患 → 记录后继续，后续审批
  P3 — 样式/文案 → 记录后继续

建议修复：[具体代码级方案，不是"建议排查"]

审批请求：请确认修复方案 / 暂缓（理由）/ 升级优先级
```

**级别动作（不可自行降级）：**

| 级别 | 动作 |
|---|---|
| **P0** | 不等审批，先修复再汇报。修复后 MUST 触发 test-runner 验证。 |
| **P1** | 暂停当前编码，等待用户审批修复方案。获批后立即修复。 |
| **P2/P3** | 记录到 todo_write（标记 pending），继续当前任务。Step 7 报告中必须列出所有 P2/P3 项。 |

**NEVER** 发现 P0/P1 问题后沉默继续。推说"旧代码问题"而不上报 = 直接违反 R10 红线。

### 补充：发现错误但无法立即修复的处理

如果修复预估 ≥ 15 分钟（当前会话无法快速完成）：

1. 仍然 MUST 执行 Bug Discovery Protocol 上报
2. 给出具体代码级修复方案（不是"建议排查"）
3. 写入 `.claude/memory/pending-issues.md`，包含完整协议内容
4. 绝对不允许发现错误后沉默或跳过

## Law 2: Verification is Completion（验证即完成）

**核心原则：** 没有新鲜验证证据，不准声称任何状态。

### Gate Function — 5 步验证协议

声称任何状态之前，完成这 5 步：

1. **IDENTIFY** — 什么命令能证明这个声称？
2. **RUN** — 执行完整命令（本次、实时，不是上次的结果）
3. **READ** — 读完整输出，检查 exit code，数失败数
4. **VERIFY** — 输出是否确认了你的声称？
   - 否 → 用证据说明实际状态
   - 是 → 带着证据做出声称
5. **CLAIM** — 带证据声称结果

跳过任何一步 = 说谎，不是验证。

### 按声称类型验证要求

| 声称 | 需要的证据 | 不够的证据 |
|---|---|---|
| 测试通过 | 测试命令输出：0 failures | 上次跑过、"应该通过" |
| 构建成功 | build 命令：exit 0 | linter 通过、日志看起来正常 |
| Bug 已修 | 复现原始症状：通过 | 改了代码就假设修好了 |
| 代码审查通过 | code-reviewer 子代理报告：0 严重 | 自己觉得没问题 |
| 子代理完成 | 检查 VCS diff + 验证变更 | 信任子代理的"成功"报告 |
| 需求已满足 | 逐项对照计划清单 | "测试通过，阶段完成" |

### 红旗词（说出这些词 = 没有证据）

- "should" / "probably" / "seems to" / "looks like"
- "应该可以通过" / "看起来没问题"
- 在验证之前表达满意（"Great!" / "Done!" / "完美!"）

### 合理化借口 → 真相

| 借口 | 真相 |
|---|---|
| "应该没问题了" | 跑命令，别猜 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "linter 通过了" | linter ≠ 编译器 |
| "子代理说成功了" | 独立验证 |
| "部分检查够了" | 部分证明不了任何事 |
| "我累了" | 疲惫 ≠ 免检 |

---

## Law 3: Honest Reporting（诚实报告）

不确定就说出来，不编造。NEVER 为了显得周全而捏造内容。主动报告在相邻代码中发现的问题。

---

## Law 4: No Shortcuts（不走捷径）

- NEVER 写 TODO、伪实现、吞异常的 try-catch
- NEVER 不分析根因就随机改动
- NEVER 跳过边界情况（null、并发、错误路径）
- 三行相似代码 > 过早抽象
- **硬失败：** `guard-write` L11 · Cursor `guard-placeholder` · `.githooks/pre-commit` 拦截 `TODO: implement` / `NotImplementedException` 等；例外 `// placeholder-ok: <理由>`
