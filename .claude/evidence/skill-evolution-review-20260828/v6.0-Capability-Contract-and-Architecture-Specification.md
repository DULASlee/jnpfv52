## 1. v4.0 实际能力（继承基线）

### 1.1 v4.0 是什么

一个**证据驱动的 .NET 类级诊断与重构决策系统**（非技术清单）：

- **P0 五维取证先行**：Code/Runtime/Arch/Test/Risk，缺 P0 则 P1..P10 全封锁

## 4. v6.0 Architecture

### 4.1 架构总览

```
v4/v5 协议（继承）
    ↓
P0 五维取证 → 16 维 Finding → GO/STOP/NEED
    ↓
(若当前类证据不足)
    ↓
Context Expansion（v6 新增）
    ↓
判断缺失哪一种上下文（调用/DI/Ownership/数据流/跨层）
    ↓
获取 Level 0/1/2 上下文
    ↓
重新判定 GO/STOP/NEED
```

### 4.2 核心组件

1. **Context Model**：五种上下文类型（调用/DI/Ownership/数据流/跨层）的形式化定义
2. **Context Expansion Rules**：触发条件、终止条件、成本评估规则
3. **Level 0/1/2 Acquisition**：上下文获取机制（人工/静态信息/工具）
4. **Decision Integration**：跨类证据接入 GO/STOP/NEED 决策

### 4.3 与 v4 的关系

- **继承**：v4 的 P0 取证 / 16 维 Finding / GO/STOP/NEED / Semantic Budget / Convergence 全部继承
- **扩展**：新增 Context Expansion 机制，允许获取跨类证据
- **纪律**：Context Expansion 不替代 P0，不弱化 GO/STOP/NEED 三门判定

## 5. Context Expansion 模型

### 5.1 核心原则

**Evidence Expansion ≠ Scope Expansion**

- ❌ 错误：发现一个潜在问题 → 扫描整个解决方案
- ✅ 正确：发现一个潜在问题 → 判断缺失哪一种上下文 → 只扩展必要上下文 → 重新判断

### 5.2 最小必要上下文原则

**只获取解决当前 Finding 所必需的最小跨类上下文。**

判断标准：
- 该上下文是否直接影响当前 Finding 的 GO/STOP/NEED 判定？
- 如果不获取，能否安全地标记为 NEED EVIDENCE 并停止？
- 获取该上下文的成本（时间/复杂度/准确性）是否合理？

### 5.3 Context Expansion 触发条件

**只有当以下三个条件同时满足时，才允许 Context Expansion：**

1. Finding 真实存在（不是 False Positive）
2. 当前类证据不足（无法安全判定 GO/STOP/NEED）
3. 缺失的上下文直接影响判定（不是"可能有用"）

### 5.4 Context Expansion 终止条件

> ⚠️ **2026-08-28 Patch v2 横幅**：下列 5 条为 Pre-Patch 表述，现行判停协议 = `R1-Operationalization-Patch.md` v2 §3.1 STOP-1~5（映射见 `Context-Expansion-Rules.md` 横幅）；其中第 3 条"成本超过收益"已删除，第 5 条场景冻结为 NEED EVIDENCE + Escalation（Patch §4.0）。§5.2 第 3 问"成本是否合理"同理由 Patch §1.2 分档 Budget 取代。

**以下任一条件满足时，必须停止 Context Expansion：**

1. 已获得足够证据 → 重新进入 GO/STOP/NEED 判定
2. 达到 Level 上限 → 若 Level 0/1 无法满足，标记 NEED EVIDENCE（Level 2 未实现）
3. 成本超过收益 → 上下文获取成本 > Finding 修复收益 → STOP
4. 跨模块边界 → 涉及跨模块依赖 → STOP（避免跨模块传染）
5. 无法获取 → 上下文不可获取（如运行时行为） → NEED EVIDENCE

## 6. Level 0 / Level 1 / Level 2

### 6.1 Level 0（人工提供）

- **目的**：验证 v6 决策模型本身
- **方式**：人工描述调用链 / DI 注入 / ownership 链
- **成本**：最高，但最灵活
- **适用**：验证阶段，成本可接受

### 6.2 Level 1（静态信息）

- **目的**：利用已有静态信息进行有限上下文扩展
- **方式**：从接口签名 / DI 注册代码 / 项目结构推断
- **成本**：中等
- **适用**：大部分跨类场景

### 6.3 Level 2（工具辅助）

- **目的**：自动化取证
- **方式**：Roslyn call-graph / DI-registration / data-flow
- **成本**：最低（一旦实现），但需开发
- **适用**：大规模解决方案

### 6.4 优先级与证明义务

**优先级：Level 0 → Level 1 → Level 2**

**必须先证明 Level 0/1 无法满足，才能主张 Level 2。**

## 7. Decision Model

### 7.1 继承 v4 三门判定

v6 **完全继承** v4 的 GO/STOP/NEED 三门判定逻辑：

- **GO (Allow Modify)**：Finding evidenced ∧ Contract violation ∧ single-point boundary ∧ gates pass ∧ regression path exists ∧ no Contract expansion
- **STOP (Must Stop)**：sufficient evidence to decide NOT to do now（10 种 disjunctive 条件）
- **NEED EVIDENCE**：insufficient evidence to decide（可能真实存在，但证据不足）

### 7.2 v6 新增：Context Expansion 后的重新判定

v6 唯一新增的是：**当当前类证据不足时，允许通过 Context Expansion 获取跨类证据，然后重新进入三门判定。**

```
v4 协议：当前类证据 → GO/STOP/NEED
v6 协议：当前类证据 → (若不足) → Context Expansion → 跨类证据 → GO/STOP/NEED
```

### 7.3 三种判定路径

- **路径 A：STOP → Context Expansion → GO**（跨类证据支持在当前类修复）
- **路径 B：STOP → Context Expansion → NEED EVIDENCE**（需运行时证据，Level 2 未实现）
- **路径 C：STOP → Context Expansion → STOP**（跨类证据仍不支持 GO，正确拒绝局部修）

## 13. 三个核心问题的正面回答

### ① v4 到底是什么？

一个**证据驱动的 .NET 类级诊断与重构决策系统**（非技术清单）：P0 五维取证先行 → 16 维 Finding → Risk 分级 → GO/STOP/NEED 三门 → 最小语义预算 → 单提交 → 验证 → 收敛。有正式规格+计划文档，4 个跨技术性质 Golden，并经六问 Calibration Review 落地 M1/M2/M3。**v4.0 = 唯一成熟且有证据链的版本，已在 `81bc1dce` 冻结。**

### ② v5 到底增加了什么？

新增 **P2 ORM 行为查表 / P3 数据量敏感度 / P4 影响面(数据源追溯)** 三个**后处理步** + 3 张 reference。全部挂在 v4 既有维度(D3-D10)之上，"在 Findings 识别后叠加"。**0 个真正新能力域**，净性质是 C 规则细化 + D 文档新增。**把 v5.0 称作一次"版本升级"存在拔高，它更像 v4.0 的一次增量校准。**

### ③ v6 到底准备把 Skill 提升到什么新的能力层级，以及为什么值得做？

v6 准备把 Skill 从**"单类人工判断"升级为"解决方案级自动取证决策"**：

- **新增能力**：D11 跨类生命周期分析 + Context Expansion 机制 + Level 0/1/2 上下文来源 + 跨类 Finding 接入决策门
- **为什么值得做**：v4/v5 整条协议是单类视野，对跨类 ownership / DI 生命周期 / 数据量传播等结构性无法回答。v6 通过 Context Expansion 获取跨类证据，让 Skill 能基于跨类证据下判断
- **核心挑战**：如何有纪律地获取最小必要上下文，而不是无限制扫描整个解决方案（Evidence Expansion ≠ Scope Expansion）

**这才是 v6.0 的真实目标（架构级），不是"再加一维"。**
