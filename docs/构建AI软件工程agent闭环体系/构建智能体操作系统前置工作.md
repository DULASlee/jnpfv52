是的，而且我认为**这一步应该放在 AI Engineering OS v1.1 正式施工之前**。但不是让你现在花大量时间“清理干净”，那会掉进一个很大的坑。

我更建议：

> **先做 Harness Inventory + Authority Classification + Quarantine，暂时不做大规模删除。**

这样最快，也最安全。

---

# 一、你现在其实不是“需要清理”，而是需要“收权”

你现在的环境大概是：

```text
用户级 Harness
├── Superpowers
├── ECC Skills
├── 其他全局 Rules
├── 其他全局 Skills
└── 其他 MCP

项目级 Harness
├── AGENTS.md
├── 项目 Rules
├── 项目 Skills
├── 项目 MCP
├── 历史 Rules
├── 历史实验 Skill
└── 各种细碎配置

+
AI Engineering Control Plane 1.0
+
AgentOS
+
Expert Agent
```

真正危险的不是“东西多”。

而是：

> **现在谁拥有最终解释权不一定完全明确。**

所以我们现在不需要立刻删 100 个东西。

首先建立：

# Harness Authority Map

---

# 二、第一原则：千万不要现在“大扫除”

我非常不建议：

```text
删除所有 Superpowers
删除 ECC
删除旧 Rules
删除旧 Skills
删除 MCP
重新安装一套
```

这是非常危险的。

因为你现在根本还不知道：

```text
哪些东西真的有用
哪些只是重复
哪些是项目特有约束
哪些是历史遗产
哪些被某些 Workflow 隐式依赖
哪些 MCP 其实非常好用
```

如果一次清掉：

> **很可能为了“架构整洁”丢掉真正有价值的工程能力。**

---

# 三、我们应该采用“四步清理法”

非常简单：

```text
Inventory
   ↓
Classify
   ↓
Quarantine
   ↓
Migrate / Retire
```

不是：

```text
Inventory
↓
Delete
```

---

# 四、第一步：Inventory —— 先全部登记，不判断对错

把当前环境中的：

```text
User-level
Project-level
```

全部扫描出来。

但只登记：

```text
名称
位置
类型
来源
用途
是否正在使用
依赖谁
```

例如：

| Item        | Scope        | Type  | Purpose         | Status  |
| ----------- | ------------ | ----- | --------------- | ------- |
| Superpowers | User         | Skill | Workflow        | Active  |
| ECC         | User         | Skill | Coding          | Active  |
| Serena      | User/Project | MCP   | Code Navigation | Active  |
| ecc-memory  | User/Project | MCP   | Memory          | Active  |
| xxx.md      | Project      | Rule  | Legacy          | Unknown |
| xxx         | Project      | Skill | Refactor        | Unknown |

**这个阶段不要删。**

---

# 五、第二步：Classification —— 分类才是真正关键

我建议以后所有 Harness 项目都归入下面 7 类：

```text
1. GOVERNANCE
2. WORKFLOW
3. DOMAIN SKILL
4. CAPABILITY
5. MEMORY
6. ADVISORY
7. LEGACY
```

例如：

### GOVERNANCE

```text
AI Engineering Control Plane
Project Constitution
Approved Project Rules
```

---

### WORKFLOW

例如：

```text
Phase Execution
TDD
Verification
Review
Self Repair
```

---

### DOMAIN SKILL

例如：

```text
Class Refactoring
DDD
Repository
JNPF
Architecture
```

---

### CAPABILITY

例如：

```text
Serena
Git
Browser
Database
Build
Test
```

---

### MEMORY

例如：

```text
ecc-memory
```

---

### ADVISORY

例如：

```text

ECC
第三方方法论
```

---

### LEGACY

```text
没人知道为什么存在
没人维护
已经过时
功能重复
```

# 六、这里会产生一个非常重要的结果

你会发现：

> **Superpowers 和 ECC 不需要马上删除。**

它们完全可以暂时变成：

```text
External / Advisory
```

而不是：

```text
Authoritative Governance
```

这样就已经解决了大部分“冲突”。

---

# 七、第三步：Quarantine —— 这是我最推荐你的方法

对于不确定的旧 Rules / Skills：

不要删。

建立：

```text
.ai/quarantine/
```

或者：

```text
.ai/archive/
```

把：

```text
Legacy Rule
Legacy Skill
Experimental Skill
Duplicate Workflow
```

先移进去。

并且明确：

```text
NOT LOADED
NOT AUTHORITATIVE
```

这样：

> **清理成本很低，风险也很低。**

这比逐条判断：

> “这个 Rule 到底还要不要？”

省大量时间。

---

# 八、我们真正需要清理的不是“文件”，而是“权威性”

这句话非常重要。

例如：

```text
Superpowers
```

可以继续存在。

但：

```text
Governance Authority = NO
```

ECC：

```text
Capability / Methodology = MAY
Governance Authority = NO
```

Serena：

```text
Capability Provider = YES
Governance Authority = NO
```

ecc-memory：

```text
Memory Provider = YES
Governance Authority = NO
```

最终：

```text
AI Engineering Control Plane
       ↓
Governance Authority = ONLY
```

这样就算系统里有 100 个插件，也不怕。

---

# 九、第四步：Migrate —— 把真正好的东西吸收进来

例如你发现 Superpowers 中：

```text
verification-before-completion
```

非常优秀。

不要继续依赖：

```text
Superpowers Skill
```

而是：

```text
Superpowers principle
        ↓
Our Verification Policy
        ↓
Our Skill
        ↓
Our Hook
        ↓
Our Gate
```

这样以后即使卸载 Superpowers：

> **我们的工程能力完全不受影响。**

---

# 十、ECC 也采用同样策略

不要：

```text
ECC Skill
→ 永久装着
```

而是：

```text
ECC
 ↓
Identify valuable technique
 ↓
Evaluate
 ↓
Adopt / Reject
 ↓
Our Skill / Policy
```

这样你就不会被 ECC 的复杂结构拖着走。

---

# 十一、MCP 则不用清理成“一锅粥”

例如：

以后统一进入：

```text
Capability Registry
```

例如：

于是 MCP 只是：

不用参与我们的治理。

# 十二、Memory 更要谨慎

`ecc-memory` 不应该被当成：

```text
Memory Provider
```

以后 AgentOS 自己拥有：

```text
Memory Contract
```

那么：

```text
ecc-memory
```

能用就用。

以后换 Provider 也不影响 Agent。

# 十三、我甚至建议现在不要追求“零旧配置”

真正的目标应该是：

```text

不能绕过 Control Plane
不能影响 Gate
不能改变 AgentOS Policy
```

这才是干净。

也就是说：

> **Clean Architecture ≠ Empty Directory**

真正的：

> **Clean Harness**

是：

> **Authority Clear + Loading Clear + Boundary Clear。**
