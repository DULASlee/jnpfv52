## 0. 阶段定位

**核心原则：PM Skill 是专家，不是管线零件。三轮是 AI 迭代精化，不是重型工程管线。**

本阶段交付三轮循环编排器（轻量）+ 三轮 PM/Analyst Skill system prompt 设计。前两轮零工程步骤（SA C# 编译 + 内存传递 + 轻量校验），第 3 轮调用 26 号接线的一次性工程保障。

**交付：** 轻量三轮编排器 + Round 1 PM prompt + Round 2 联合 prompt + Round 3 确认 prompt + PSpec/DecisionTable LLM 增强（Round 2 内）。

## 2. 三轮循环编排器（轻量）

**文件**：`Skills/RequirementAnalysisOrchestrator.cs`

**不是重型状态机，是一个轻量 for 循环：**

```csharp
// 伪代码
async Task RunThreeRoundsAsync(SkillContext context, CancellationToken ct)
{
    var warnings = new List<string>();      // 轻量校验 WARNING
    var assumptions = new List<Assumption>(); // 内存传递
    var compileResult = (SaNineViewCompileResult?)null;

    // ── Round 1：PM Skill 独立完善 ──
    var round1 = await pmSkill.EnhanceAsync(context, ct);  // 1 次 LLM
    // PM 补全行业惯例 → IR-0 → 自主出 3 题
    compileResult = compiler.Compile(round1.Model);         // C# 毫秒级
    warnings = lightValidator.Validate(context, compileResult); // < 10ms
    var answers1 = await AskUser(round1.Questions, ct);     // 用户回答

    // ── Round 2：PM + Analyst 联合精化 ──
    var round2 = await jointSkill.RefineAsync(              // 1 次 LLM
        context, round1, answers1, warnings, compileResult.Assumptions, ct);
    // PM 增量完善 + Analyst SA 分析(7C#+2LLM) + 联合出 3 题
    compileResult = compiler.Compile(round2.Model);         // C# 全量重编译
    var answers2 = await AskUser(round2.Questions, ct);

    // ── Round 3：最终确认 + 工程一次性保障 ──
    var round3 = await confirmSkill.ConfirmAsync(           // 1 次 LLM
        context, compileResult, round2, answers2, ct);
    // 遗漏检查 + 假设项确认
    var answers3 = await AskUser(round3.Questions, ct);

    // ★ 工程一次性保障（调用 26 号接线）
    await analystSkill.FinalizeAsync(context, ct);
    // SA 最终编译 → 投影 → 门禁 → Materializer → sa_assumptions → (28号: 一致性+评分+渲染)
}
```

## 3. Round 1：PM Skill 独立完善（1 次 LLM）

### 3.1 PM Skill system prompt 核心设计

```
你是有 10 年经验的行业产品经理。用户不是专家，你是。

任务：
  1. 读取领域种子知识（行业惯例、业务模式库、标准 ER 子模型）
  2. 基于你的行业知识，完善用户的原始需求：
     - 补全用户不懂的行业惯例（如请假类型、审批层级、状态流转）
     - 这些你能定的，不要问用户
  3. 产出专业版 IR-0 骨架（businessEvents + entityDrafts + roleMatrix）
  4. 然后判断：这份需求里最需要用户确认的 3 个模糊点是什么？
     - 只问真正模糊的、需要业务方决策的点
     - 行业惯例能定的不要问
     - 每个问题含：问题文本 + 选项 + context_hint（为什么问）+ 默认值

输出 JSON：
  {
    "skeleton": { ... IR-0 骨架 ... },
    "questions": [
      {
        "text": "...",
        "format": "MATRIX_SINGLE | MATRIX_MULTI | SINGLE | MULTI",
        "matrix_rows": [...],      // 矩阵行（事件/实体）
        "options": [...],
        "context_hint": "...",
        "default_option": "..."
      }
    ]
  }
```

### 3.2 Round 1 执行流程

```
PM LLM（~1 分钟）→ IR-0 + 3 个问题
SA C# 编译（~1 秒）→ compileResult（内存）
轻量校验（< 10ms）→ warnings（内存）
用户回答（~2 分钟）→ answers1
```

## 4. Round 2：PM + Analyst 联合精化（1 次 LLM）

### 4.1 联合 Skill system prompt 核心设计

```
你是产品经理 + 系统需求分析师联合体。

输入：
  - Round 1 产出的 IR-0 骨架
  - 用户对 3 个问题的回答
  - 轻量校验 WARNING（如有）
  - SA 编译 Assumptions（编译器推导的假设项）

任务：
  1. PM 部分：基于用户回答，增量完善需求（只针对新增信息）
  2. Analyst 部分：
     a. SA 九步分析（7 步 C# 编译器已有结果）
     b. 你深度分析 2 步：
        - PSpec：异常路径、边界条件、业务规则
        - DecisionTable：条件分支、决策逻辑
     c. 标记所有非用户明确的推导为 assumption（含 confidence）
  3. 联合判断：分析中发现的遗漏/冲突/假设中，最重要的 3 个需要用户裁决的点是什么？

约束（宪法二）：
  - PSpec/DecisionTable 的 LLM 只精化属性，不增删实体/字段
  - 实体/字段清单是不可变输入

输出 JSON：
  {
    "refined_skeleton": { ... 增量完善后的骨架 ... },
    "pspec_enhancement": { "boundaries": [...], "exceptions": [...] },
    "decision_table_enhancement": { "preconditions": [...], "edge_cases": [...] },
    "assumptions": [...],
    "questions": [ ... 3 个问题 ... ]
  }
```

### 4.2 PSpec/DecisionTable LLM 增强（Round 2 内）

**不是独立模块，是联合 LLM 调用的一部分。**

```
PSpec 合并：
  C# 编译器产出（主体，不可变）：main_logic/input_spec/output_spec
  LLM 精化（追加）：boundaries/exceptions
  校验：LLM 不得修改主体 → 忽略 + WARNING

DecisionTable 合并：
  C# 编译器产出（主体）：decision_table 主体矩阵
  LLM 精化（追加）：preconditions/edge_cases
  校验：LLM 不得增删行列 → 拒绝

LLM 调用规格：
  MaxConcurrent = 3（Provider 限流）
  输入 ≤ 15K tokens（全局索引 + 当前事件 SA 产出）
  输出 ≤ 2K tokens
```

### 4.3 Round 2 执行流程

```
联合 LLM（~2 分钟，含 PSpec/DT 增强）→ 增量骨架 + SA 分析 + 3 个问题
SA C# 全量重编译（~1 秒）→ compileResult（内存）
用户回答（~2 分钟）→ answers2
```

## 6. LLM 响应 Redis 缓存（可选优化层）

### 6.1 问题与收益校准

```
优雅架构下的 LLM 缓存 hit 率分析：
  正常流程：每次 prompt 含上轮上下文 → cache hit 率 ≈ 0%（不缓存也无所谓）
  LLM 失败重试：相同 prompt → cache hit 率 100%（有价值）
  断点续跑：已完成事件 → cache hit 率 100%（有价值）
  开发调试：同一测试用例反复跑 → cache hit 率高（开发者体验好）
  Round 3 门禁失败修复重跑：如果 DFD/Dict/BPM 未变 → 省 ~30 秒（最有价值）
```

### 6.2 方案

```csharp
// LlmGatewayService.ChatAsync 入口加缓存层

public async Task<ChatCompletionResponse> ChatAsync(ChatCompletionRequest request, CancellationToken ct)
{
    // 条件 3：只缓存 Temperature=0 的确定性调用
    var canCache = request.Temperature == 0 && _options.LlmCacheEnabled;
    string? cacheKey = null;

    if (canCache)
    {
        // 条件 2：key 必须包含模型版本
        cacheKey = $"llm:{request.ProviderCode}:{request.ModelUsed}:" +
                   $"{ComputePromptHash(request.SystemPrompt, request.Messages, request.MaxTokens)}";
        var cached = await _cacheManager.GetAsync<string>(cacheKey);
        if (cached != null)
            return JsonSerializer.Deserialize<ChatCompletionResponse>(cached)!;
    }

    // 原有逻辑：构造 HTTP → 打 Provider → 落审计日志
    var response = await CallProviderAsync(request, ct);

    // 条件 1：只缓存成功响应
    if (canCache && response.IsSuccess)
        await _cacheManager.SetAsync(cacheKey!, JsonSerializer.Serialize(response),
            TimeSpan.FromHours(_options.LlmCacheTtlHours));

    return response;
}

static string ComputePromptHash(string systemPrompt, List<ChatMessage> messages, int maxTokens)
{
    var raw = systemPrompt + "|" + maxTokens + "|" +
              string.Join("|", messages.Select(m => $"{m.Role}:{m.Content}"));
    return Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(raw))).ToLowerInvariant();
}
```

### 6.3 三个必须满足的条件

```
条件 1：只缓存成功响应
  HTTP 200 + 解析成功 + 格式校验通过 → 缓存
  失败/超时/格式错误 → 不缓存（避免缓存脏数据）

条件 2：缓存 key 必须包含模型版本
  key = SHA256(provider + model + systemPrompt + messages + temperature + maxTokens)
  模型升级（如 gpt-4o → gpt-4o-2025）→ key 不同 → 旧缓存自动失效
  避免"模型升级但缓存命中旧版本响应"

条件 3：只缓存 Temperature=0 的调用
  Temperature > 0 的 ToT 创意分支不缓存（需要多样性）
  SaPipelineOptions.LlmCacheEnabled 控制总开关
```

### 6.4 Round 3 重跑场景（机会 D 延伸）

```
Round 3 的 PSpec/DecisionTable LLM 精化是最耗时的步骤（~30 秒/事件）。
如果 Round 3 门禁失败需要修复重跑：

  PSpec/DecisionTable 的 LLM key = SHA256(eventId + DFD + Dict + BPM)
  Round 3 首次成功 → 缓存
  门禁失败修复后重跑 → 如果 DFD/Dict/BPM 未变 → 缓存命中 → 省全部 LLM 时间

  这不需要单独实现——是条件 B 的自然延伸。
  Round 3 的 PSpec/DT 调用如果 Temperature=0（确定性精化），自动走缓存。
```

### 6.5 不缓存的场景

```
× Temperature > 0 的调用（ToT 创意分支需要多样性）
× TreeSearchAsync 的多路并行分支（每路需要不同温度扰动）
× 失败的响应（条件 1）
× 正常流程中的首次调用（cache miss 是正常的，不阻断）
  → 缓存主要用于：失败重试 + 断点续跑 + 开发调试 + Round 3 门禁失败重跑
```

## 7. LLM 并发限流与超时分级

> **26 号交付了 LLM 基础设施层稳定性（3 Provider 降级链 + 真熔断 + JSON 修复 + Token 预估）。**
> **本阶段交付应用层：并发限流 + 超时分级 + 按任务路由 Provider。**

### 7.1 并发限流（SemaphoreSlim）

**问题**：Round 2 的 PSpec/DecisionTable LLM 如果 5 事件并行 → 同时 5 个 HTTP 请求 → Provider 限流 429 → 全部重试 → 雪崩。

**方案**（26 号配置项已定义 `MaxConcurrentLlmCalls=3`，本阶段在 LlmGatewayService 实现）：

```csharp
// LlmGatewayService 新增
private readonly SemaphoreSlim _concurrencyLimiter;

// 构造函数
_concurrencyLimiter = new SemaphoreSlim(
    _configuration.GetValue("AI:MaxConcurrentLlmCalls", 3));

// ChatAsync 入口
await _concurrencyLimiter.WaitAsync(ct);
try { /* 原有请求逻辑 */ }
finally { _concurrencyLimiter.Release(); }
```

**效果**：5 事件并行时最多 3 个并发，其余排队等待，不打爆 Provider。

### 7.2 超时分级（按调用类型设不同超时）

**问题**：当前默认 TimeoutMs=120000（2 分钟），最坏 120s × 3 重试 × 3 Provider = 18 分钟卡死。

**方案**：按调用场景设不同超时，调用方在 ChatCompletionRequest.TimeoutMs 中指定：

```
需求门控评估：     30 秒（快速判断，不能让用户等太久）
PM Skill 骨架：   90 秒（ToT 多候选，需要足够时间）
PSpec/DT 增强：   60 秒（单事件深度分析）
Round 3 确认：    45 秒（全局审查）

默认从 120 秒降到 60 秒
最坏情况：60s × 3 重试 × 3 Provider = 9 分钟（可接受）
```

### 7.3 按任务路由 Provider（不同模型擅长不同任务）

**方案**：不只用于容灾，还能按能力路由——分摊负载降低单一 Provider 被限流的概率。

```json
// appsettings.json
"AI": {
  "ProviderRouting": {
    "pm-skill": "deepseek",       // PM 骨架用推理强的
    "analyst-gate": "mimo",       // 门控评估用速度快的
    "pspec-enhance": "deepseek",  // PSpec 深度分析用推理强的
    "confirm": "mimo"             // 确认审查用速度快的
  }
}
```

```csharp
// LlmGatewayService 新增
public string ResolveProvider(string skillId)
    => _providerRouting.TryGetValue(skillId, out var p) ? p : _defaultProvider;

// 三轮编排器调用时
request.ProviderCode = _llm.ResolveProvider("pm-skill");       // Round 1
request.ProviderCode = _llm.ResolveProvider("pspec-enhance");  // Round 2
request.ProviderCode = _llm.ResolveProvider("confirm");        // Round 3
```

**效果**：门控/确认等轻量任务路由到快但便宜的模型，PM/PSpec 等重度任务路由到强但贵的模型。**分摊负载 = 降低单一 Provider 被限流的概率。**

### 7.4 验收标准

```
□ 并发限流：5 事件并行时最多 3 个并发 LLM 请求（SemaphoreSlim 验证）
□ 超时分级：门控 30s / PM 90s / PSpec 60s / 确认 45s（调用方设 TimeoutMs 验证）
□ 按任务路由：PM Skill 走 deepseek / 门控走 mimo（ResolveProvider 验证）
□ 审计日志记录实际使用的 Provider（区分路由选择 vs 降级切换）
```
