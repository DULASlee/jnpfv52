## 一、这篇文章到底在说什么？

一句话：**别让Agent开车，让Agent当导航。Harness（运行时）才是司机。**

> Agent 负责局部智能，Harness 负责全局控制。

这句话值千金。展开来讲，就是一个生产级Agent系统必须把五样东西从Agent手里夺回来：

1. **任务生命周期**：任务必须有一个清晰的状态机，不能“好像还在跑”。
2. **执行计划裁决**：Agent可以出主意（声明式计划），但Harness拍板能不能跑、并行还是串行、超没超预算。
3. **Agent路由**：不是每个Agent都能接每个活，路由要结合能力、权限、历史质量。
4. **失败处理**：重试、降级、跳过还是终止，不能让出错的Agent自己说了算。
5. **硬终止条件**：max_steps、max_tokens、max_duration、max_tool_calls四道硬闸。

此外，文章还深入拆解了五个核心模块：**工具治理**（Tool Registry）、**状态与记忆**（分层存储+遗忘机制）、**评估体系**（四层Eval，特别是轨迹评估）、**成本控制**（Token Budget+分级熔断）、**MCP工具接入**（标准化但不裸奔）。

具体对接点：

### 1. 你把“声明式计划”已经做到了极致

文章强调Planner应该输出声明式计划，而不是命令式调用。你的SA九步法产出物——业务事件清单、数据流图、ER子模型、规则表——本质上就是最完整的声明式计划。开发Agent不直接和用户对话，只读取这份结构化文档，这正是文章推崇的“Agent间靠协议通信”的最佳实践。

### 2. 你的“确认点”就是最精准的Human-in-the-Loop

文章说高风险操作要人审批。你在需求分析完成后设置“用户确认”节点，就是最关键的Human-in-the-Loop。这个确认点设在“业务理解完成之后、代码生成之前”，比任何在工具调用层加审批都更精准。

### 3. 工具治理，你必须现在就想

这一点文章敲了很好的警钟。你的开发Agent将来要调JNPF的哪些接口？创建模型、创建菜单、发布应用——这些就是工具。你必须在Tool Registry里给它们定好风险等级、权限、审计策略。不能直接给Agent一个超级管理员Token就随便调。

文章把状态分三层、记忆分两类。你之前设计的“SA九步法存数据库表”，天然就解决了这个问题——这些表就是Session State和Semantic Memory。你不需要向量数据库，你的ER图、规则表本身就是结构化记忆，直接检索即可。

### 5. 成本控制，多租户场景必须做

## 三、它漏了什么？——Agent间冲突解决

文章讲得很全，但有一个缺口：**多个Agent同时操作同一个项目时，怎么解决冲突？**

你的场景里，一个用户可能同时让“需求Agent”和“开发Agent”并行工作（边改需求边生成代码）。如果没有锁机制，会出现数据不一致。

这个你得补上：对每个项目的“元数据草稿”加乐观锁或悲观锁，同一时刻只允许一个Agent写入。
