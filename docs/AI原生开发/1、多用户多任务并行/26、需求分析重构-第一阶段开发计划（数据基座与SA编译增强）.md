## 8. 领域种子数据共享（内存，非 Redis）

### 8.1 现状确认

PM Skill 运行时，领域种子**已经在 SkillContext 中**：

```
SkillHarness.cs:147 → _contextBuilder.FindSeedMatchesAsync(requirement) → SQL 查种子
SkillHarness.cs:160 → SeedMatches = seeds → 放入 SkillContext
SkillModels.cs:95   → SkillContext.SeedMatches 属性

结论：种子在 pipeline 启动时一次性加载到 SkillContext 内存
      三轮共享同一份 SkillContext 实例 → 三轮共享同一份种子
      不需要 Redis 缓存（连缓存查询都省了）
```

### 8.2 不需要 Redis 缓存的理由

```
优雅架构下：
  整个三轮只查 2-3 次种子（Round 1 PM Skill + Round 2 联合 Skill 复用 SkillContext）
  种子已在 SkillContext.SeedMatches 内存中
  → 零次额外 SQL 查询（pipeline 启动时 1 次加载）

平台级优化（非本阶段范围）：
  ContextBuilderService.MatchAsync 内部的 SQL 查询可用 ICacheManager 缓存
  让多个 pipeline 并行启动时不重复查种子表
  但这是平台基础设施优化，不是需求分析子链的重点
```

### 8.3 本阶段无需改动

领域种子数据共享已由现有 SkillContext 机制天然实现。本阶段不涉及种子缓存改动。

### 12.2 改进 1：3 Provider 降级链（主+备+兜底）

**当前**：只有 `_fallbackProvider`（单字符串），主挂了切备用，备用也挂了=全部失败。

**改为**：有序降级链（3 个 Provider），逐级降级。

```csharp
// 配置（Configurations/AI.json，根级 LlmGateway 节）
"LlmGateway": {
  "Providers": [
    {"Name":"mimo","Model":"mimo-v2.5-pro","Level":0,"MaxRetries":3,"TimeoutSeconds":60},
    {"Name":"deepseek","Model":"deepseek-v4-pro","Level":1,"MaxRetries":3,"TimeoutSeconds":80},
    {"Name":"openai","Model":"gpt-4o","Level":2,"MaxRetries":2,"TimeoutSeconds":100}
  ]
}

// LlmGatewayService 实现（已落地）
// - LoadLevelChain() 从 "LlmGateway:Providers" 读取分级数组，按 Level 排序，最多 3 级
// - BuildProviderChain() 每次调用现建链（非字段），chainIdx 从 0 递增逐级降级
// - 无配置时回退 DefaultLevelChain()（2 级：mimo→deepseek）
// - ChatAsync + TryCreateStreamAsync 双路径共用同一条链
// 现有重试/退避/审计日志/熔断全部复用
```

**效果**：deepseek 限流 → 自动切 mimo → mimo 也限流 → 切 openai。三个同时挂的概率极低。

### 12.3 改进 2：真熔断（失败阈值阻断）

**当前**：`_failureCounts` 只计数不阻断。`GetFailureCount()` 方法定义了但无人调用。Provider 宕机时每条请求还是打满 maxRetries。

**改为**：失败次数超阈值 → 直接跳过该 Provider，不走重试。

```csharp
// 配置（Configurations/AI.json）
"AI": {
  "CircuitBreaker": {
    "FailureThreshold": 5,     // 连续失败 5 次熔断
    "WindowSeconds": 60,       // 60 秒时间窗口
    "CooldownMs": 300000       // 5 分钟后半开探测
  }
}

// 实现（已落地）：Llm/LlmCircuitBreaker.cs（ILlmCircuitBreaker, ITransient）
// 三态机：Closed → Open → HalfOpen → Closed（或 Open）
// - CheckAndTransition(provider)：发送前检查，熔断开启返回 true（Open→HalfOpen 冷却期满自动转换）
// - RecordSuccess / RecordFailure：调用后记录，驱动状态转换
// ChatAsync 入口（发送前）：
//   if (_circuitBreaker.CheckAndTransition(providerName)) { continue; }  // 跳过，不重试
// Stream 路径（TryCreateStreamAsync）同样接入
// 旧的 _failureCounts 计数器保留并行（冗余但无害），熔断以 LlmCircuitBreaker 为准
```

**效果**：Provider 宕机时不浪费 3 次重试 × N 秒等待，直接降级。

### 12.4 改进 3：JSON 响应修复器

**问题**：LLM 经常不稳定地返回 markdown 包裹的 JSON（````json ... ````）或尾部多余文本或尾逗号。当前直接反序列化 → JsonException → 被吞掉当失败重试 → 重试 3 次还是同样乱码 → 浪费请求。

**方案**：ParseResponse 调用前先修复（前置，非 catch 后兜底）。

```csharp
// 实现：Llm/LlmJsonFixer.cs
// 两个入口：
//   TryFix(raw)           → (string? Fixed, bool WasFixed)，异常路径修复（catch 内用）
//   FixJsonResponse(raw)  → string?，ParseResponse 前置修复入口（26 号 §12.4 契约）
//
// FixJsonResponse 语义：对合法 JSON 原样返回（不改动），对需修复的文本修复后返回，
//                       修复失败返回 null（调用方保留原文走原解析）。
// 修复步骤（TryFixInternal，每步后预校验 JsonDocument.Parse，合法立即返回）：
//   1.   剥 markdown 代码块包裹（```json ... ```）
//   1.5  取首个 {/[ 到匹配闭合符（字符串感知深度计数，避免误截嵌套结构）
//   2.   平衡未闭合的括号/大括号
//   3.   移除尾逗号（} 或 ] 前的 ,，正则多次迭代）
//   4.   截断字符串修复（未闭合引号补全）
//   综合：依次应用 2+3 后预校验

// LlmGatewayService.ParseResponse 前置调用（parse 前）
var proactivelyFixed = LlmJsonFixer.FixJsonResponse(body);
var effectiveBody = proactivelyFixed ?? body;
using var doc = JsonDocument.Parse(effectiveBody);  // 用修复后的 body
// catch 块仍保留 TryFix 作为二级兜底（前置修复未生效时才重试）
```

**效果**：LLM 返回 `json\n{"passed":true}\n``` 时自动修复，不再无意义重试。

### 12.5 改进 4：Token 预估前置校验

**问题**：prompt 累积超长 → LLM 返回 "context length exceeded" → 重试 3 次还是同样错误 → 浪费 3 次请求。

**方案**：发送前预估，超限截断消息历史（保留 systemPrompt + 最近 N 条消息），而非直接拒绝。

```csharp
// 实现（已落地）：Llm/LlmTokenEstimator.cs
// - EstimateTokens(text)：CJK 感知启发式（CJK ~2 字符/token，英文 ~4 字符/token，+20% 余量）
// - EstimateRequestTokens(request)：SystemPrompt + Messages + MaxTokens 总和
// - TruncateForTokenLimit(request, tokenBudget)：从末尾向前保留消息，返回新 request（record with）

// ChatAsync 发送前（仅首级首次，chainIdx==0）
var estimated = LlmTokenEstimator.EstimateRequestTokens(request);
if (estimated > 100_000)
    _logger.LogWarning("请求Token预估值过大({Estimated})，可能超出模型上下文窗口", estimated);
if (_configuration.GetValue("AI:EnforceTokenLimit", false) && estimated > 200_000)
{
    var tokenLimit = _configuration.GetValue("AI:TokenLimit", 200_000);
    var inputBudget = Math.Max(1, tokenLimit - request.MaxTokens);
    request = LlmTokenEstimator.TruncateForTokenLimit(request, inputBudget);
    // 截断策略：保留 systemPrompt + 从末尾向前累加，直到加入下一条会超预算为止
    // 至少保留 1 条最新消息
}
```

**效果**：prompt 超长时不发无效请求，截断后发送（不报 context exceeded）。

### 12.7 验收标准

```
□ 3 Provider 降级链：主 Provider 模拟失败 → 自动切备用 → 备用也失败 → 切兜底
□ 真熔断：连续失败 5 次 → 跳过该 Provider（不重试）→ 60 秒后半开探测
□ JSON 修复器：markdown 包裹 JSON + 尾逗号 → 自动修复成功解析
□ Token 预估：超长 prompt → 截断后发送（不报 context exceeded）
□ 审计日志记录降级链路（哪个 Provider 降级到哪个）
```
