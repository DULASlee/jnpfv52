# 设计规格编写模板（AI 生成版）

> 本模板只有一个目的：让 AI 大模型基于它写出**可直接落地、前后一致、无自相矛盾**的设计规格。
> 用法：把本模板交给 AI，AI 按「第 0 部分 生成协议」执行，按「第 1 部分 模板正文」逐节填充，按「第 2 部分 校验清单」收尾。
> 与主模板《1、设计规格文档编写模板10.5.md》同步（v10.5：P0 执行前提 + T2 降级协议 + 十查）。

---

# 第 0 部分 生成协议（AI 必须先读并严格执行这一段）

## 0.0 执行前提（P0，未声明不得开始）

- **运行模式（二选一，在产出文档头部声明）：**
  - **T1 工具完备**——具备文件写入与 hash 计算（带工具的 Agent），契约库机制全量生效；
  - **T2 纯文本**——无工具环境，契约以文档内**结构化契约块**承载（见 5.7 降级协议），块锚点引用替代 hash，**禁止虚构 hash**。
- **人工闸门 G1~G5：** G1 §2 决策定稿（含 5.1 / 5.5 / 5.6 / 5.7 / 5.8 及 5.2 / 5.3 基线层的范式选型）→ G2 §3 分解定稿 → G3 §5 基线定稿 → G4 逐模块节拍（可批量授权豁免）→ G5 终审通过。**闸门处 AI 只输出"备选方案 + 推荐 + 风险"，选定由人完成；未确认保持「待决策」占位，不得自行定稿。**
- **事实边界：** AI 只能引用输入上下文中真实存在的证据（用户提供的需求文档 / 代码片段 / 表结构 / 接口清单 / 工单摘录）；**禁止编造文件路径、commit hash、工单号**。上下文缺失的证据一律 `[待确认]` 并附"需要什么证据、向谁索取"；关键决策被阻断时，按 5.4 登记假设后继续，依赖假设的推导显式标注。

## 0.1 生成顺序（禁止按文档章节号顺序写）

按以下顺序推进，在 0.0 闸门处取得确认后再进入下一步：

1. 读需求，产出 §1 概述（含硬约束、NFR 业务量估算、致命问题）；
2. 产出 §2 架构决策（闸门 G1：输出备选+推荐+风险，人选定后定稿）；
3. 产出 §3 系统分解（模块清单；闸门 G2）；
4. 产出 §5 全局基线：5.1 安全基线、**5.2 迁移基线、5.3 灰度基线（基线层）**、5.5、5.6、5.7、5.8（如适用）——§4 之前必须完成（闸门 G3）；
5. 产出 §0 全局锚定卡初版（回填基线速览，完成上游契约预登记：ID + 一句话；§0 初版依赖 §3 与 §5 基线，此前只可建带占位标记的骨架）；
6. **逐个**产出 §4 模块设计。模块内节拍固定、不可倒置：**先写 4.N.1~4.N.8 正文 → 4.N.9 五问自检 → 把 4.N.2/4.N.7 字段级决策物化为契约定义（T1：写入契约库获得 ID@版本+hash；T2：输出结构化契约块并锚定版本）→ 输出 4.N.10（引用该凭证）→ 回填 §0 与 3.2**（闸门 G4，可批量授权）；
7. 回填 5.1 威胁建模、**5.2 / 5.3 执行层**、§6；
8. 执行第 2 部分校验（闸门 G5）。

## 0.2 上下文组装（每写一个模块只允许携带以下内容，禁止携带其他模块全文）

- §0 全局锚定卡；
- 当前模块命中 [适用条件] 的维度指令（只取命中项，不携带全量模板）；
- 直接上游模块的 4.N.10 摘要；
- 当前模块消费的契约定义（T1：契约库条目，hash 校验通过后；T2：按块锚点取结构化契约块，版本一致即可；上游并行未物化时按「待回填」占位处理，终审强制清零）；
- 当前模块的需求描述。

写第 N 个模块时，**不得**携带前 N-1 个模块的设计全文；需要细节时按需回查，不全程携带。

## 0.3 硬规则（违反任何一条即返工）

1. **事实必须有来源。** 引用的存量事实标注精确来源：文件路径、表名.字段名、commit hash、需求/事故工单号。"记忆""惯例""经验""经核实""据评估"不构成有效来源。来源必须真实存在于输入上下文（0.0 事实边界）。
2. **[待确认] 必须受控。** 定稿时仍无法举证的事项，必须登记入 5.4 并取得编号（A-1、A-2…），正文只引用编号；不留匿名 `[待确认]` 标记。
3. **摘要不承载字段级约束。** §0 与 4.N.10 只做认知摘要；字段级约束（类型、长度、必填、枚举、校验）唯一源是契约定义，禁止凭摘要补全约束。层级界定：方法签名级（方法名+参数+顶层类型）属认知层可写；字段级明细属编译层。
4. **禁止总结性断言。** 不写"无未决项""无遗留问题""已全部确认"；未决事项只有两种合法形态：5.4 编号条目，或已补齐证据的事实。
5. **状态机与决策表未列入默认非法。** 含 2 个及以上状态的实体必须给状态转移矩阵；资金、安全、核心状态流转的组合规则必须决策表化。
6. **前置条件必须回答"从哪来"。** 接口前置条件的三类来源：上游数据 / 上游契约 / 运行时上下文；答不上来源的接口设计不成立。
7. **禁止自行发明全局基线。** 并发、日志、契约、租户、迁移、灰度策略必须落在对应 §5 基线内；确需偏离走 2.1 架构回溯。
8. **生成与校验分离。** 生成阶段按结构填写，不同时自检；全部生成完后单独执行校验。
9. **契约物化先于 4.N.10。** 对外契约从 4.N.2/4.N.7 的字段级决策物化而来（T1 入契约库 / T2 结构化契约块），拿到引用凭证（hash / 锚点）后才能输出 4.N.10，顺序不可倒置；禁止虚构 hash。
10. **数字必须有来源类型。** 性能与量级数字标注 实测 / 估算（附依据）/ 目标（验收线）；无来源的数字不得写成已确认指标。

## 0.4 节拍

- 一次只生成一个模块；每模块按 0.1 第 6 步节拍（正文 → 五问自检 → 物化 → 4.N.10 → 回填 §0/3.2）推进，确认后再进入下一个模块。
- 用户显式批量授权时可豁免交互节拍，但「契约物化先于 4.N.10」「§0 / 3.2 回填」「终审十查」三项不豁免。
- 多轨并行时遵守 3.3 契约先行：跨轨共享接口由提供方在并行开工前先物化契约（v0 草稿版即可）。

# 第 1 部分 模板正文

## 0. 全局锚定卡（≤1500 字）

本卡是全文速览投影，AI 写每个模块时唯一携带的全局参照。**正文是唯一源，本卡与正文冲突时以正文为准并立即回填。**初版在 §3 与 §5 基线定稿后建立。

- 系统一句话定义：做什么，不做什么。
- 模块清单与职责边界：每行一句话（投影自 3.1）。
- 全局硬约束：通常 ≤5 条，只列**系统架构不变量**（如"路由快照零差异""租户数据隔离"）；文档编写纪律不得入此列。局部约束（只适用部分模块/轨道/时期，如"纯移动""本期零 schema 变更"）不得进入此列，按路由规则落位：横切技术策略 → §5 对应节；一次性取舍 → §2；类内纪律 → 模块类型分流。
- 局部约束索引：已降级约束及其落位（正文为源，本行为指针）。
- 全局基线速览：交互一致性范式、可观测性基线、契约引用规则、多租户隔离（如适用）各一行（投影自 5.5 / 5.6 / 5.7 / 5.8）。
- 共享数据实体清单：仅名称 + 关键字段（提炼自 4.N.2；初版可标注「待 §4 提炼，占位」）。
- 跨模块接口契约：方法签名 + 契约 ID@版本。条目三态：**已知** / **已知上游**（仅 ID + 一句话）/ **占位**。§4 启动前完成上游契约预登记；凭证回填在 4.N.10 完成后执行；并行未物化条目按「待回填」占位，终审第八查清零。
- 本次设计明确排除的内容（提取自 1.1）。
- 待确认项编号列表：A-1、A-2……（投影自 5.4）。

维护规则：每完成一个模块，检查是否产生新共享实体/契约，有则回填；若本卡修改频率超过模块总数 1/3，回到 §3 重新分解，不继续打补丁。字数超限先压投影粒度（契约段只留 ID 清单、实体清单只留名称），不删条目类别；模块 >20 可放宽至 ≤2500 字并注明；**不拆多卡**（破坏唯一全局参照），超上限回 §3 拆设计文档本身。

## 1. 概述

### 1.1 目的与范围

- 本设计要解决什么问题？不解决会怎样？
- 本期明确排除什么？（排除项须来自已提出的需求，不可自造。）
- 硬约束是什么？指出成本、合规、团队结构、技术栈中与本设计存在张力的点（第 2 章决策的直接输入）。
- 致命问题：≤3 个当前无法自答、且答案会改变架构走向的问题，抛给决策者。确实没有时允许写"无"，但须给出判断依据。
- 非功能需求（NFR）清单：可用性、可扩展性、容量、成本、合规、可维护性——逐条给目标值 + 测量口径 + 承接维度（§4 / §5 / §6）+ 验收方式；NFR 之间或与硬约束的冲突记入张力点。**容量维度须包含业务量估算**（日交易量 / 消息频率 / 峰值并发 / 数据增长速率），作为 5.5 幂等窗口、重试预算的取值依据。**NFR 目标值同时是 4.N.6 告警阈值与 §6 SLO 的共同来源（三处同源，不新造目标）。**

### 1.2 术语与缩写

列出领域术语与缩写，避免歧义。

### 1.3 参考资料

需求文档、上游设计、RFC/规范、事故报告等，每条注明来源。AI 生成时本节同时登记**输入上下文材料清单**（用户提供了哪些需求文档 / 代码片段 / 表结构 / 接口清单——事实边界以此为限）。

## 2. 架构决策记录

只记录困难、影响全局的取舍。5.5 / 5.6 / 5.7 / 5.8 及 5.2 / 5.3 基线层属全局取舍，必须在本章立项——§5 各节承载本章决策产出的规范正文。**本章定稿是闸门 G1：闸门前每条决策只输出"备选 + 推荐 + 风险"，人选定后定稿。**

对每个关键决策：

- **背景：** 什么约束或需求触发了这个决策？（指向 1.1 的硬约束或业务规则，不写"技术考虑"。）
- **备选方案：** 至少两个方案及其核心代价。
- **决定：** 选了什么？给出完整推理链——事实 → 判断 → 结论，禁止从事实直接跳到结论。
- **失效条件：** 什么情况下需要重新评估？给出检查时机。
- **元数据：** 决策日期、决策者。

### 2.1 架构回溯

模块设计中发现与本章决策不可调和（代价超上限、物理约束冲突、性能不可达）时，停下回本章重评，记录：冲突点 / 新事实 / 重评结论 / **已否决方案重评**（新事实使哪些原否决方案重新可行）。

## 3. 系统分解

### 3.1 模块清单

| 模块 | 职责（一句话） | 对外接口概要 | 依赖方向 |
|---|---|---|---|
| … | … | … | → / ← |

模块名称表达单一职责；名称含"和/以及/与/及"通常应拆分，高内聚成对术语注明理由后可保留。**依赖方向列不得成环（A→B→C→A）**——有环须注明打破方式（接口抽取 / 事件解耦 / 合并）或回 §3 重分解；终审第九查核验。

### 3.2 模块间交互

- 核心交互模式（同步 / 异步 / 共享存储），标注数据流向与所有权边界。
- 依赖模块对逐一核对上下游类型与字段级约束一致（§3 阶段做方向性核对，字段级核对在契约物化后回填本段；回填列入逐模块节拍，遗漏由终审第八查拦截）。
- 发布单元与集成策略：模块是否独立发布？集成顺序（先契约后实现）？接口 mock 与契约测试策略？多轨并行时共享接口的合并顺序与仲裁？

### 3.3 多轨隔离 [可选]

多轨道（含多 AI Agent 并行）时按层级约定隔离：文件级（禁触清单）、接口级（合并权与仲裁）、数据级（schema 变更顺序与回滚、topic schema 变更）、依赖级（共享库版本与变更通知）、**契约先行**（跨轨共享接口由提供方在并行开工前先物化契约，v0 草稿版即可；无法先行时下游登记「待回填」占位，上游物化后回填并重新校验，终审强制清零）。本节只约定轨道间隔离与协调；单系统内集成顺序与仲裁统一在 3.2。

## 4. 模块详细设计

对 3.1 每个模块按 4.N.1~4.N.10 展开。

**模块类型分流：** 业务功能型 / 结构重构型（纯移动、架构调整）。重构型模块的 4.N.1 成功标准改写为**重构证据标准**（行为不变性的证明方式：路由快照零 diff、契约测试、特征捕获单测），其余维度照常。

**因果链：** 4.N.2~4.N.7 每个设计决策注明回应 4.N.1 的哪条规则/场景；无法关联的决策删除或说明服务于哪个 NFR。

**决策输出格式：** 有实质取舍的维度按"选定 X / 否决 Y 及理由 / 失效条件"三要素输出；不涉及的维度一句话说明原因。

**维度裁剪：** 标注 [适用条件] 的维度，不命中时一句话说明"本模块不涉及，因为……"；未标注的维度默认全部适用。

### 4.N [模块名称]

#### 4.N.1 业务上下文

- 为谁解决什么问题？业务成功标准？
- 主流程 + 关键分支 + 异常路径 + 终态。
- 负责什么 / 不负责什么。
- 业务规则清单：每条含判断条件、执行动作、**业务来源**（需求条目 / 法规 / 客户裁决）、**规则作用域**（平台级 / 租户级 / 项目级）。资金、安全、核心状态流转的组合规则必须决策表化并默认非法，指明守卫方式（枚举组合单测 / 规则引擎 / 契约测试）与变更审计责任；其余规则说明主要组合 + 未覆盖组合的处理策略。规则冲突时明确优先级或指向仲裁记录。
- 是否涉及敏感数据或权限边界？

#### 4.N.2 数据模型与状态

- 核心数据结构概览（实体清单、关键关系、生命周期意图）与关键类型选型决策及理由（回应 4.N.1 规则，如"金额字段 decimal(18,2)"）；全量字段级明细唯一源为契约定义（T1 契约库 / T2 结构化契约块，见 5.7），本段不复制全表（层级界定见 5.7）。
- **状态转移矩阵（硬性）：** 含 2 个及以上状态的实体必须给矩阵（2 状态可极简但须列非法转移）：当前状态 × 触发动作（含触发角色/权限）→ 目标状态 + 守卫条件 + 附加动作。未列入的转移默认非法，实现必须显式拦截。自检：每个状态从初始态可达、非终态有出边、终态无出边。
- 一致性边界与跨边界最终一致策略（符合 5.5）。
- 有状态模块的恢复：RPO（可接受丢失窗口）、RTO（恢复时间上限）、备份/快照策略与恢复演练验证方式。

#### 4.N.3 并发与竞态 [适用条件：存在共享可变状态或并发调用方]

在 5.5 内裁剪：锁策略、幂等键、重试参数沿用全局基线，偏离走 2.1。回答：是否存在并发？冲突时谁赢？隔离边界？至少一个具体竞态场景及其裁决。

#### 4.N.4 错误处理与降级

- 依赖挂掉 / 超时 / 脏数据时的行为；每个异常路径有明确的降级或回退动作。
- **业务级补偿：** 部分成功或后续失败时的业务对冲（如扣款成功→发单失败→退款/挂起+对账），须与 4.N.2 终态一致；仅技术重试不构成补偿。
- 重试参数自洽：为每个跨模块调用定义业务级等待上限（≤ 5.5 系统级总超时上限），校验重试次数 × 单次超时 ≤ 业务级上限；退避参数不超出 5.5 基线。

#### 4.N.5 性能特征 [适用条件：存在性能敏感路径（高吞吐、低延迟、大数据量、高并发）或显式资源持有]

- 核心路径复杂度；瓶颈在哪？10× 规模下是否成立？不成立的扩容/降级触发条件？
- 运行时资源（连接、线程、缓存、句柄）生命周期；峰值下的占用上限。
