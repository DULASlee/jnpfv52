# 软件设计规格模板 v10.4

基于 IEEE 1016 Software Design Description 核心结构，适配现代系统架构实践。
适用于新建系统与存量系统改造。

---

## 使用说明

- 每个章节标题后的引导问题是思考提示，不是必填表格。用你能说清楚的方式回答即可。
- 标注 `[可选]` 的章节在简单项目中可跳过，但需一句话说明跳过原因。
- 本文档是设计决策的记录，不是实现代码或测试用例的载体；API 与数据的字段级精确定义物化在契约库中（见 5.7），本文档记录其决策与理由。
- **摘要管认知，契约管编译：** §0 与 4.N.10 的摘要服务于快速理解与一致性终审；生成集成代码时，字段级约束（类型、长度、必填、枚举、校验）以契约库的机器可读定义为唯一依据，禁止凭摘要补全约束（见 5.7）。
- **事实必须有有效来源。** 修改/维护项目中引用的存量事实，须标注精确来源：文件路径、表名.字段名、commit hash、需求/事故工单号。"记忆""惯例""经验""经核实""据评估"不构成有效来源。暂无法举证的事实标注 `[待确认: 缺什么证据]`，在获得证据前不得作为已确认事实参与任何推导；要么补齐证据，要么将此前提显式登记为架构假设并给出验证方式（见 5.4）。
- **[待确认] 受控引用：** 正文中的 `[待确认: 缺什么证据]` 仅用于"证据暂缺、待补齐"的瞬时状态；定稿时仍无法举证的事项，必须升级登记入 5.4 架构假设登记并取得条目编号（A-1、A-2…，按登记顺序递增），正文改为引用编号（如"见假设 A-2"），不得保留匿名标记。编号仅作交叉引用键，分配与核对落点为 hooks / 设计评审（回应附录 B"编号体系不入模板"决策：本文档编号非流程控制体系）。
- **事实必须与决策相关。** 每条引用的事实注明它支撑了哪个设计决策；与任何决策无关的事实不罗列。
- 新建项目无存量参考时，将前提条件作为架构假设显式声明，并注明验证方式（见 5.4）。
- **先业务后技术：** 每个模块先回答"为谁解决什么问题、怎么流转、边界在哪"，再谈技术实现。禁止跳过业务上下文直接给技术方案。
- **砍刀先行：** 范围裁剪只针对已提出的需求做减法。禁止凭空构造新需求再砍除，以制造"深思熟虑"的假象。
- **AI 辅助生成时：** 生成中发现前文有错，立即标注并回改，不要"先写完再说"。多模块长文档的上下文组装、生成/校验分离与跨模块终审机制，见附录 C。
- **全局基线先行与生成顺序（强制）：** 生成与阅读顺序一致——**§1 → §2 → §3 → §5 基线（5.1 安全基线 / 5.5 / 5.6 / 5.7 / 5.8，如适用）→ §0 初版（回填基线速览、完成上游契约预登记、消除可消除的占位）→ §4 逐模块（模块内节拍见附录 C 逐模块推进，不可倒置）→ §5 其余（5.2 / 5.3 / 5.1 威胁建模回填）→ §6 → 附录 C 终审**。AI 按此顺序推进，不得按章节号顺序；前序章节经确认后再展开后续。§0 骨架（带占位标记）可在 §1 定稿后先行建立。产物就绪条件：**§0 初版依赖 §3 模块清单与 §5 基线定稿；4.N.10 依赖契约物化产出的 hash——先物化、后输出摘要**。禁止在基线缺位时自行假设并发 / 日志 / 契约 / 租户策略。

## 0. 全局锚定卡（≤1500 字）

本卡是全文的速览投影：读者据此一分钟把握全局，AI 分模块编写时以此为唯一全局参照——写第 N 个模块时只需携带本卡，而非前 N-1 个模块的全文。

**正文是唯一源。** 本卡与正文冲突时，以正文为准并立即回填修正；要修改任何被投影的信息，先改正文，再改本卡。在 §3 与 §5 基线定稿后、首个模块设计开始前建立初版，包含且仅包含：

- 系统一句话定义：做什么，不做什么。
- 模块清单与职责边界：每行一句话（投影自 3.1）。
- 全局硬约束：通常 ≤5 条（提取自 1.1；超出时合并同类项但不得删除，合并理由记入局部约束索引）。**只允许列适用于所有模块的系统架构不变量**（如"路由快照零差异""租户数据隔离"；"事实有来源"等文档编写纪律、非系统行为不变量，不得入此列）。任何只适用于部分模块、某个轨道或某一时期的约束（如"纯移动""本期零 schema 变更"），不得进入此列，按下列路由规则落位：① 属横切技术策略（安全 / 数据迁移 / 发布灰度 / 一致性范式 / 可观测性 / 契约）→ §5 对应节；② 属一次性取舍 → 第 2 章架构决策；③ 属某类模块的局部纪律 → 模块类型分流对应类型段。无法判断是否全局时，默认视为局部。
- 局部约束索引：列出已降级为局部的约束及其落位（正文为源，本行为投影），供终审第七查核对，防止"降级 = 静默消失"。
- 全局基线速览：交互一致性范式、可观测性基线、契约引用规则、多租户隔离（如适用）各一行（投影自 5.5 / 5.6 / 5.7 / 5.8）。§5 基线定稿前本条可标注「待 §5 定稿，占位」。
- 共享数据实体清单：仅名称 + 关键字段，不展开（提炼自各模块 4.N.2；初版可标注「待 §4 提炼，占位」，首个模块完成后开始回填）。
- 跨模块接口契约：方法签名 + 契约 ID@版本（汇编自各模块 4.N.10；字段级约束以契约库为准，见 5.7）。本段条目三态：**已知**（本模块输出）/ **已知上游**（上游模块 4.N.10 已输出：仅 ID + 一句话，不做 hash 验证）/ **占位**（尚未输出）。§4 启动前完成上游接口契约预登记，让首个模块编写时即有可用清单；hash 回填在 4.N.10 完成后执行。并行轨道下未物化条目的处理见 3.3 契约先行与 5.7 并行条款。
- 本次设计明确排除的内容（提取自 1.1）。
- 待确认项编号列表：A-1、A-2……（投影自 5.4；随模块推进更新）。

维护规则：每完成一个模块，检查是否产生新的共享实体或接口契约，如有则回填本卡并显式记录；契约库条目变更引起 hash 变化时，同步回填本卡与对应模块的 4.N.10。若本卡的修改频率超过模块总数的 1/3，通常不是本卡的问题，而是 §3 系统分解本身不稳——回到 §3 重新划分，而不是继续打补丁。

## 1. 概述

### 1.1 目的与范围

- 本设计要解决什么问题？不解决会怎样？
- 本期明确排除什么？（排除项须来自已提出的需求，不可自造。）
- 硬约束是什么？指出成本、合规、团队结构、技术栈中与本设计存在张力的点——它们是第 2 章决策的直接输入。
- 致命问题：列出 ≤3 个当前无法自答、且答案会改变架构走向的问题，明确抛给决策者。确实没有时允许写"无"，但须给出判断依据（为何不存在会改变架构走向的问题）。
- 非功能需求（NFR）清单：可用性、可扩展性、容量、成本、合规、可维护性——逐条给出目标值与测量口径，并注明承接维度（§4 对应模块维度 / §5 对应节 / §6 SLO）与验收方式；NFR 之间或与硬约束的冲突，记入上方硬约束张力点。**容量维度须包含业务量估算**（日交易量 / 消息频率 / 峰值并发 / 数据增长速率），作为幂等窗口、重试预算等全局参数（5.5）的取值依据，§2 决策引用。

### 1.2 术语与缩写

列出本文档中使用的领域术语和技术缩写，避免歧义。

### 1.3 参考资料

需求文档、上游设计、相关 RFC/规范、事故报告等。每条注明来源。

## 2. 架构决策记录

只记录真正困难的、影响全局的取舍。日常技术选型不需要出现在这里。全局交互与一致性范式（5.5）、可观测性基线（5.6）、契约载体与演进策略（5.7）、多租户与数据隔离（5.8）属影响全局的取舍，必须在本章立项记录——§5 各节承载的是本章决策产出的规范正文。

对每个关键决策：

- **背景：** 什么约束或需求触发了这个决策？（优先指向 1.1 的硬约束或业务规则，不要泛泛写"技术考虑"。）
- **备选方案：** 至少列出两个方案及其核心代价。
- **决定：** 选了什么？给出完整推理链——事实 → 判断 → 结论，不允许从事实直接跳到结论。
- **失效条件：** 什么情况下这个决定需要重新评估？
- **决策元数据与复审：** 记录决策日期与决策者；失效条件须给出检查时机（何时或什么事件触发重评）。2.1 回溯触发时，按"冲突点 / 新事实 / 重评结论"三件事执行，并回填本条目；另须重评已否决方案——因新事实，哪些原否决方案需重新进入评估，回溯条目附其状态变化。

附一张架构图（组件图 / 时序图 / 数据流图，选最能表达当前决策的类型）。

### 2.1 架构回溯触发条件

如果在第 4 章模块详细设计中发现某个模块的设计与本章架构决策存在不可调和的矛盾（代价超出预设上限、物理约束冲突、性能不可达），必须停下来回到本章重新评估，而不是在模块设计中硬凑。

触发时记录三件事：

- **冲突点：** 哪个模块的哪个设计与哪条架构决策矛盾？
- **新事实：** 是什么信息导致了矛盾暴露？
- **重评结论：** 修改架构决策，还是调整模块设计？

## 3. 系统分解

### 3.1 模块清单

| 模块 | 职责（一句话） | 对外接口概要 | 依赖方向 |
|---|---|---|---|
| … | … | … | → / ← |

模块名称须表达单一职责：名称中出现"和 / 以及 / 与 / 及"，通常意味着应该拆分。领域成对术语（如"用户与权限"）若高内聚不可拆，须注明理由后保留。

### 3.2 模块间交互

描述模块之间的核心交互模式（同步调用 / 异步消息 / 共享存储等）。标注数据流向和所有权边界。

有依赖关系的模块对，逐一核对上游输出与下游输入在类型与字段级约束上均一致（以契约库为准，见 5.7；§3 阶段契约库尚未物化，初稿基于接口概要做方向性核对，字段级核对结果在 §4 各模块契约物化后回填本段，作为终审输入；回填列入逐模块节拍（附录 C），遗漏由终审第八查拦截）。

- 发布单元与集成策略：模块是否独立发布/部署（发布单元）？集成顺序（先契约后实现？）、接口 mock 与契约测试策略；多轨并行时共享接口的集成节奏与冲突仲裁（合并顺序、接口变更通知）。模块设计须能回答"谁在什么顺序把 N 个模块捏合成可运行系统"。

### 3.3 多轨隔离 [可选]

若存在并行开发轨道或团队边界（含多个 AI Agent 并行工作的场景），说明各轨道的文件/目录/服务归属，为每条轨道列出明确禁触的文件/目录，并显式约定共享资源的访问方式。共享文件无归属声明即视为冲突隐患。本节只约定轨道之间的隔离与协调规则；单系统内的集成顺序与仲裁统一在 3.2。隔离按层级展开：

- 文件级：禁触文件/目录清单（已有）。
- 接口级：共享接口的合并权、合并顺序与争议仲裁（见 3.2 集成策略）。
- 数据级：共享 schema 的变更顺序与回滚、共享消息 topic 的 schema/分区变更。
- 依赖级：共享依赖库的版本与变更通知。
- 契约先行：跨轨共享接口由提供方轨道在并行开工前先物化契约（v0 草稿版即可），下游轨道基于已物化契约开发；确实无法先行时，下游按 5.7 登记「hash 待回填」占位，上游物化后回填并重新校验，终审第八查强制占位清零。

## 4. 模块详细设计

对第 3 章列出的每个模块，按以下结构展开。简单模块可精简，但推理链不可断。

**模块类型分流：** 模块分业务功能型与结构重构型（纯移动/架构调整，其产出是代码结构而非新业务能力）。结构重构型模块的 4.N.1 业务成功标准改写为「重构证据标准」——行为不变性的证明方式（如路由快照零 diff、契约测试、特征捕获单测），其余维度照常。这不视为跳过业务分析：重构模块的「业务」就是证据生产，其成功标准同样必须可验证。

**因果链要求：** 4.N.2 ~ 4.N.7 中的每个设计决策，应注明它回应的是 4.N.1 中的哪条业务规则或哪个业务场景。用自然语言引用即可（如"为满足'订单金额保留两位小数'的规则，选用 decimal(18,2)"）。无法关联到任何业务规则的设计决策，要么删除，要么说明它服务于哪个非功能性需求。

**决策输出格式：** 每个有实质取舍的维度，按"选定 X / 否决 Y 及理由 / 失效条件"三要素输出。确认某个维度不涉及本模块时，一句话说明原因即可，禁止展开空转段落。

**维度裁剪：** 标注了 [适用条件] 的维度，不满足条件的模块一句话说明"本模块不涉及，因为……"即可跳过；未标注的维度默认全部适用，核心业务逻辑模块通常全部展开。裁剪是为了省去无意义展开，不是逃避分析——跳过理由必须具体到本模块的实际情形。

---

### 4.N [模块名称]

#### 4.N.1 业务上下文

- 为谁解决什么问题？业务成功标准是什么？
- 主流程 + 关键分支 + 异常路径 + 终态。
- 负责什么 / 不负责什么（写清容易混淆的职责归谁）。
- 业务规则清单：每条含判断条件、执行动作、**业务来源**（需求条目 / 法规 / 客户裁决）与**规则作用域**（平台级 / 租户级 / 项目级可定制；租户差异如何表达与校验）。涉及资金、安全、核心状态流转的组合规则必须决策表化并默认非法（未列入组合由实现显式拦截），并指明组合空间的守卫方式（枚举组合的单测 / 规则引擎 / 契约测试）与变更审计责任（需求新增组合时由谁复核）；其余业务规则可说明主要组合，但须注明未覆盖组合的处理策略。规则间存在矛盾时，明确优先级或指向仲裁记录，禁止实现时自行裁决。
- 本模块是否涉及敏感数据处理或权限边界？如有，在后续维度中一并说明。

#### 4.N.2 数据模型与状态

- 核心数据结构概览（实体清单、关键关系、生命周期意图）与关键类型选型决策及理由（回应 4.N.1 业务规则，如"金额字段 decimal(18,2)"）；全量字段级明细（逐字段类型、长度、必填、枚举、校验）唯一源为契约库 5.7，本段不复制全表，只记决策、理由与契约引用（认知层 / 编译层界定见 5.7 首段）。
- **状态转移矩阵（硬性）：** 含 2 个及以上状态的核心实体（2 状态实体矩阵可极简，但须显式列出非法转移），禁止用自然语言段落描述生命周期，必须给出状态转移矩阵——当前状态 × 触发动作（含触发角色/权限）→ 目标状态 + 守卫条件 + 附加动作。默认语义：未列入矩阵的转移一律非法，实现必须显式拦截。矩阵自检：每个状态从初始态可达，每个非终态至少一条出边，终态无出边。
- 一致性边界在哪里？跨边界如何保证最终一致？（跨边界策略须符合 5.5 全局范式。）
- 有状态模块：故障后如何重建状态？持久化策略是什么？给出恢复目标：RPO（可接受丢失窗口）与 RTO（恢复时间上限）、备份/快照策略与恢复演练验证方式。

**深度锚点：** 一个不了解上下文的工程师，能否仅凭此段 + 契约库对应条目正确建表/建模并写出恢复逻辑？

#### 4.N.3 并发与竞态 [适用条件：存在共享可变状态或并发调用方]

### 5.5 全局交互与一致性范式 [适用条件：多模块或模块内共享可变状态，或存在跨进程/跨服务交互]

并发控制、事务与幂等是全局决策，不下放模块：各模块 4.N.3 只能在本节范式内裁剪；确需偏离的模块走 2.1 架构回溯，不得自行发明。范式选型的推理链（备选与代价）记录在 §2 对应决策条目。

- 跨模块事务模型：显式选定一种**主范式**（如：禁止跨模块强事务 + Outbox 最终一致 / TCC / 两阶段提交），全系统唯一，模块不得混用。**范式分层**：主范式（默认）+ **强一致白名单**（允许升级为强一致的业务域/操作，每条升级须给出"主范式不适用"的具体原因，审批记录于 §2）；模块在 4.N.3 标明自身位于哪一层。
- 幂等基线：幂等键构成（如：主体/租户标识 + 业务键）、传递载体（请求头 / 消息属性）、幂等窗口与去重存储。默认要求：所有跨模块写操作可安全重试。
- 并发控制档位：默认档位（如：数据库乐观锁版本列）、允许升级为分布式锁的场景白名单、冲突裁决默认规则（谁赢）。
- 重试与超时基线：本节给出**系统级总超时上限**（全系统统一）与默认超时、指数退避参数上限；各调用方在 4.N.4 定义**业务级等待上限**（≤ 系统级上限），重试预算校验式为：**重试次数 × 单次超时 ≤ 调用方业务级等待上限**。**嵌套调用重试预算按调用栈深度递减**（顶层 N 次，深度每 +1 减 1，深度 ≥ N 不重试），避免乘性放大。幂等窗口长度的取值依据（业务量估算）放 1.1 NFR 容量维度，§2 决策引用。

单进程且无共享可变状态的极简系统，一句话声明跳过原因即可；模块内并发（内存缓存、后台线程竞争）同样在本节基线内由 4.N.3 裁剪，不得在模块内自行发明。

### 5.6 全局可观测性基线

各模块 4.N.6 在本基线内扩展，不得自立日志/指标格式。

- 标准日志结构：统一 JSON 字段集（时间戳、级别、traceId/spanId、租户/用户标识、模块、事件码、业务载荷）；业务日志必须落在该结构内。
- 链路透传：traceId 的生成/恢复位置、跨进程传播载体（HTTP 头 / 消息属性）、异步与定时任务的续传规则。
- 指标与健康检查：指标命名规范（模块_指标_单位）、统一健康检查端点；4.N.6 只登记本模块特有指标与阈值。

### 5.7 契约库与版本化

摘要管认知，契约管编译：§0 与 4.N.10 的摘要服务于边界理解与终审，不承载字段级精确约束；约束（类型、长度、必填、枚举取值、校验规则）的唯一源是契约库中的机器可读定义，摘要只引用，不复制明细。

**层级界定：** 方法签名级信息（方法名、参数名、顶层类型）属**认知层**，§0 / 4.N.10 / 4.N.7 决策记录可承载；字段级约束明细（逐字段全量类型、长度、必填、枚举值、校验规则）属**编译层**，唯一源为契约库。文档正文记录类型与接口的**选型决策及理由**（这是设计内容，不因唯一源在契约库而删除），但不复制明细全表。

- 载体：按技术栈选定一种主载体（OpenAPI / JSON Schema / Protobuf / 领域 DSL），契约与设计文档同库存放、同评审、同版本演进。
- 唯一源方向：设计期字段与约束的决策及理由记录在 4.N.2 / 4.N.7；模块 4.N.9 自检通过后、4.N.10 输出前，把 4.N.2 / 4.N.7 的字段级决策**物化**进契约库——由设计决策转换生成机器可读定义（人工或工具辅助均可）；**4.N.10 是摘要、不含字段级明细，不能作为物化来源**。物化产出契约 ID@版本与内容 hash 后，4.N.10 方可引用。此后字段级唯一源为契约库——下游模块编写与代码生成以契约库为准。存量系统可由现状代码 / 表结构反向提取契约库初版，提取结果的确认附契约可信度评估（强类型代码高 / 弱类型代码低 / 表结构反推低），低可信度条目须补强证据后方可生效。契约库变更后：更新 hash → 回填 §0 与相关模块 4.N.10（见 §0 维护规则）；正文 4.N.2 / 4.N.7 不复制明细，仅保持契约引用与理由的最新性。
- 引用格式：契约 ID @ 版本 + 内容 hash + 存放路径。下游编写或生成前必须校验 hash，不一致即阻断；禁止凭摘要生成集成代码。
- 兼容性：契约演进默认只允许增量变更（新增可选字段、新增枚举值须说明消费方默认行为）；破坏性变更升主版本并给出双轨过渡期（与 5.2 / 5.3 衔接）。
- 所有权：契约由提供方模块拥有并维护，消费方只引用，禁止双头编写。
- 并行轨道：跨轨契约由提供方轨道先行物化（v0 草稿版即可）供下游引用；确实无法先行时，下游登记「hash 待回填」占位（§0 三态=占位），上游物化后回填并重新校验；终审第八查强制占位清零（见 3.3 契约先行）。

### 5.8 多租户与数据隔离 [适用条件：多租户或需数据隔离的系统]

租户与数据隔离是全局决策，不下放模块（立项记录于 §2），模块不得自行切换隔离策略。须统一回答：

- 租户标识：生成、传播（请求头 / 令牌 / 消息属性）、解析与透传规则；匿名 / 无租户上下文的处理（配合 4.N.7 调用前置条件）。
- 隔离级别：独立数据库 / 独立 schema / 行级租户字段——按数据敏感度分级选定，全系统一致。
- 跨租户访问防护：越权查询 / 写入的拦截点、检测与告警（配合 5.1 威胁建模）。
- 租户级配置与规则：租户级业务规则、配置、特性的存储与加载（见 4.N.1 规则作用域），层级覆盖优先级（平台级 > 租户级 > 项目级，冲突时上层优先并记录仲裁）。
- 租户数据生命周期：备份 / 恢复 / 导出须落在租户边界内；租户删除 / 归档的数据保留与清理策略。

## 附录 A：写作原则备忘

- **决策三要素：** 选定 / 否决理由 / 失效条件。缺任何一个，决策不完整。
- **推理链完整：** 事实 → 判断 → 结论，不允许跳步，更不允许结论先于事实。
- **事实与假设分清：** 存量事实标来源，新研假设标验证计划。不要把假设当事实推导，[待确认] 的事实不作为决策前提。
- **先业务后技术：** 每个模块先讲清业务再谈实现，禁止跳过。
- **砍刀只砍已有的：** 范围裁剪针对已提出的需求，不自造需求再砍。
- **不为凑结构写空话：** 某维度确实不涉及，一句话说明，禁止展开空转。
- **消灭模糊词：** 定稿前全文搜索"适当、合理、酌情、相关、根据需要、尽量"，命中即改为可执行的精确表述。
- **矩阵化优先：** 含 2 个及以上状态的生命周期、多条件组合的业务规则，禁止纯自然语言描述——用状态转移矩阵（4.N.2）与决策表表达；未列入的转移 / 取值组合默认非法（资金、安全、核心状态流转类规则必守；其余规则可说明主要组合并注明未覆盖组合的处理策略）。
- **细节下沉：** 本文档记录设计决策，不记录实现。代码、完整 API 定义、测试用例另行产出。
- **发现前置决策有误时停下来：** 按 2.1 架构回溯触发条件处理，不在模块设计中硬凑。
- **禁止"无未决项"式断言：** 定稿不写"无未决项""无遗留问题""已全部确认"等总结性声明。未决事项只有两种合法形态——已登记 5.4 的编号条目，或已补齐证据的事实；"无未决"这一结论以 5.4 台账 + 终审第七查为准，不由文档自证。

## 附录 C：AI 辅助编写的永续机制

多模块长文档的核心风险是上下文膨胀：写到第 N 个模块时，注意力被前 N-1 个模块的全文稀释，质量随进度衰减。以下机制将单模块编写所需的上下文从随模块数线性增长（O(n)）压缩为常量（O(1)）——第 8 个模块与第 1 个模块的编写条件等价。这些规则约束的是信息的流动方式，人与 AI 均可参照。

**上下文组装。** 编写任一模块时，工作上下文只需包含：

- §0 全局锚定卡（≤1500 字，随回填更新，含全局基线速览与契约 ID 清单）；
- 当前模块适用的维度指令（仅 [适用条件] 命中的维度，非全量模板）；
- 直接上游模块的 4.N.10 接口摘要（≤300 字/个）；
- 当前模块消费的契约的机器可读定义（按直接上游模块的 4.N.10 契约引用从契约库取用，hash 校验通过后携带；只取本模块消费的条目，不携带全库）；
- 当前模块的需求描述。

不应携带：其他模块的设计全文、无关的历史过程。需要细节时按需回查正文对应章节或按 5.7 取用契约库，而非全程携带。

**生成与校验分离。** 生成阶段按模板结构填写，不同时执行自检；模块生成完毕后，单独执行 4.N.9 五问与模糊词扫描。生成与评估是两类认知任务，交替混行会互相干扰。

**逐模块推进。** 每个模块按固定节拍推进，顺序不可倒置：完成 4.N.1 ~ 4.N.8 → 单独执行 4.N.9 五问自检并当场修正 → 把 4.N.2 / 4.N.7 的字段级决策物化进契约库、获得 ID@版本 + 内容 hash（见 5.7）→ 输出 4.N.10（引用该 hash）→ 回填 §0 与 3.2（如有新契约或字段级核对结果）→ 确认无误后开始下一个模块。避免同一次生成中连续产出多个模块。逐模块确认节拍经用户显式批量授权可豁免；豁免时「契约物化先于 4.N.10」「§0 / 3.2 回填」「跨模块终审八查」三项内核纪律不豁免——豁免的是交互节拍，不是质量内核。

**跨模块终审。** 全部模块完成后，基于所有 4.N.10 摘要、§0 与全部被引用契约的契约库定义执行八项一致性检查（字段级检查以契约库为准，不依赖摘要）：

1. 接口连续：每个模块的输入类型与上游模块的输出类型一致？
2. 实体一致：同一实体在不同模块中的字段名与类型一致（以契约库定义为准，摘要不含字段级明细）？
3. 枚举一致：同一枚举跨模块取值相同（以契约库枚举定义为准）？
4. 约束传递：§0 中的全局硬约束在每个相关模块均有体现？
5. 无孤儿模块：是否存在既无上游输入、也无下游消费的模块？
6. 契约一致：所有 4.N.10 引用的契约 ID@版本与内容 hash 和契约库当前条目一致？摘要与契约库冲突时以契约库为准并回填修正。
7. 局部约束落位：§0"局部约束索引"中每条已降级约束，均能在其落位章节（§2 对应决策 / §5 对应节 / 模块类型分流对应段）找到规则？正文是否残留未登记的 `[待确认]`（应为 0）？
8. 回填完整与占位清零：3.2 字段级核对结果已回填且与契约库一致？全文占位标记（§0「待 §5 定稿」/ 共享实体「待 §4 提炼」/ 契约「hash 待回填」/ 预登记未物化条目）已全部消除或转为合法终态？
