# 软件设计规格模板 v10.0

基于 IEEE 1016 Software Design Description 核心结构，适配现代系统架构实践。
适用于新建系统与存量系统改造。

---

## 使用说明

- 每个章节标题后的引导问题是思考提示，不是必填表格。用你能说清楚的方式回答即可。
- 标注 `[可选]` 的章节在简单项目中可跳过，但需一句话说明跳过原因。
- 本文档是设计决策的记录，不是实现代码、API 完整定义或测试用例的载体。这些产物在设计确认后另行生成。
- **事实必须有有效来源。** 修改/维护项目中引用的存量事实，须标注精确来源：文件路径、表名.字段名、commit hash、需求/事故工单号。"记忆""惯例""经验""经核实""据评估"不构成有效来源。暂无法举证的事实标注 `[待确认: 缺什么证据]`，在获得证据前不得作为已确认事实参与任何推导；要么补齐证据，要么将此前提显式登记为架构假设并给出验证方式（见 5.4）。
- **事实必须与决策相关。** 每条引用的事实注明它支撑了哪个设计决策；与任何决策无关的事实不罗列。
- 新建项目无存量参考时，将前提条件作为架构假设显式声明，并注明验证方式（见 5.4）。
- **先业务后技术：** 每个模块先回答"为谁解决什么问题、怎么流转、边界在哪"，再谈技术实现。禁止跳过业务上下文直接给技术方案。
- **砍刀先行：** 范围裁剪只针对已提出的需求做减法。禁止凭空构造新需求再砍除，以制造"深思熟虑"的假象。
- **AI 辅助生成时：** 建议 §1、§2 完成并经确认后再展开 §4，避免方向跑偏后大面积返工；生成中发现前文有错，立即标注并回改，不要"先写完再说"。多模块长文档的上下文组装、生成/校验分离与跨模块终审机制，见附录 C。

## 0. 全局锚定卡（≤1500 字）

本卡是全文的速览投影：读者据此一分钟把握全局，AI 分模块编写时以此为唯一全局参照——写第 N 个模块时只需携带本卡，而非前 N-1 个模块的全文。

**正文是唯一源。** 本卡与正文冲突时，以正文为准并立即回填修正；要修改任何被投影的信息，先改正文，再改本卡。在 §3 定稿、首个模块设计开始前建立初版，包含且仅包含：

- 系统一句话定义：做什么，不做什么。
- 模块清单与职责边界：每行一句话（投影自 3.1）。
- 全局硬约束：≤5 条（提取自 1.1）。
- 共享数据实体清单：仅名称 + 关键字段，不展开（提炼自各模块 4.N.2）。
- 跨模块接口契约：仅方法签名与类型（汇编自各模块 4.N.10）。初版允许本段标注「待 §4 汇编，占位」——契约是 §4 的产出物，§4 未开始时本段无法完整；首个模块完成后开始回填。
- 本次设计明确排除的内容（提取自 1.1）。

维护规则：每完成一个模块，检查是否产生新的共享实体或接口契约，如有则回填本卡并显式记录。若本卡的修改频率超过模块总数的 1/3，通常不是本卡的问题，而是 §3 系统分解本身不稳——回到 §3 重新划分，而不是继续打补丁。

## 1. 概述

### 1.1 目的与范围

- 本设计要解决什么问题？不解决会怎样？
- 本期明确排除什么？（排除项须来自已提出的需求，不可自造。）
- 硬约束是什么？指出成本、合规、团队结构、技术栈中与本设计存在张力的点——它们是第 2 章决策的直接输入。
- 致命问题：列出 ≤3 个当前无法自答、且答案会改变架构走向的问题，明确抛给决策者。

### 1.2 术语与缩写

列出本文档中使用的领域术语和技术缩写，避免歧义。

### 1.3 参考资料

需求文档、上游设计、相关 RFC/规范、事故报告等。每条注明来源。

---

## 2. 架构决策记录

只记录真正困难的、影响全局的取舍。日常技术选型不需要出现在这里。

对每个关键决策：

- **背景：** 什么约束或需求触发了这个决策？（优先指向 1.1 的硬约束或业务规则，不要泛泛写"技术考虑"。）
- **备选方案：** 至少列出两个方案及其核心代价。
- **决定：** 选了什么？给出完整推理链——事实 → 判断 → 结论，不允许从事实直接跳到结论。
- **失效条件：** 什么情况下这个决定需要重新评估？

附一张架构图（组件图 / 时序图 / 数据流图，选最能表达当前决策的类型）。

### 2.1 架构回溯触发条件

如果在第 4 章模块详细设计中发现某个模块的设计与本章架构决策存在不可调和的矛盾（代价超出预设上限、物理约束冲突、性能不可达），必须停下来回到本章重新评估，而不是在模块设计中硬凑。

触发时记录三件事：

- **冲突点：** 哪个模块的哪个设计与哪条架构决策矛盾？
- **新事实：** 是什么信息导致了矛盾暴露？
- **重评结论：** 修改架构决策，还是调整模块设计？

## 3. 系统分解

### 3.1 模块清单

| 模块 | 职责（一句话） | 对外接口概要 | 依赖方向 |
|---|---|---|---|
| … | … | … | → / ← |

模块名称须表达单一职责：名称中出现"和 / 以及 / 与 / 及"，通常意味着应该拆分。

### 3.2 模块间交互

描述模块之间的核心交互模式（同步调用 / 异步消息 / 共享存储等）。标注数据流向和所有权边界。

有依赖关系的模块对，逐一核对上游输出类型与下游输入类型一致。

### 3.3 多轨隔离 [可选]

若存在并行开发轨道或团队边界（含多个 AI Agent 并行工作的场景），说明各轨道的文件/目录/服务归属，为每条轨道列出明确禁触的文件/目录，并显式约定共享资源的访问方式。共享文件无归属声明即视为冲突隐患。

## 4. 模块详细设计

对第 3 章列出的每个模块，按以下结构展开。简单模块可精简，但推理链不可断。

**模块类型分流：** 模块分业务功能型与结构重构型（纯移动/架构调整，其产出是代码结构而非新业务能力）。结构重构型模块的 4.N.1 业务成功标准改写为「重构证据标准」——行为不变性的证明方式（如路由快照零 diff、契约测试、特征捕获单测），其余维度照常。这不视为跳过业务分析：重构模块的「业务」就是证据生产，其成功标准同样必须可验证。

**因果链要求：** 4.N.2 ~ 4.N.7 中的每个设计决策，应注明它回应的是 4.N.1 中的哪条业务规则或哪个业务场景。用自然语言引用即可（如"为满足'订单金额保留两位小数'的规则，选用 decimal(18,2)"）。无法关联到任何业务规则的设计决策，要么删除，要么说明它服务于哪个非功能性需求。

**决策输出格式：** 每个有实质取舍的维度，按"选定 X / 否决 Y 及理由 / 失效条件"三要素输出。确认某个维度不涉及本模块时，一句话说明原因即可，禁止展开空转段落。

**维度裁剪：** 标注了 [适用条件] 的维度，不满足条件的模块一句话说明"本模块不涉及，因为……"即可跳过；未标注的维度默认全部适用，核心业务逻辑模块通常全部展开。裁剪是为了省去无意义展开，不是逃避分析——跳过理由必须具体到本模块的实际情形。

### 4.N [模块名称]

#### 4.N.1 业务上下文

- 为谁解决什么问题？业务成功标准是什么？
- 主流程 + 关键分支 + 异常路径 + 终态。
- 负责什么 / 不负责什么（写清容易混淆的职责归谁）。
- 业务规则清单：每条含判断条件和执行动作。
- 本模块是否涉及敏感数据处理或权限边界？如有，在后续维度中一并说明。

#### 4.N.2 数据模型与状态

- 核心数据结构、字段类型、生命周期。
- 一致性边界在哪里？跨边界如何保证最终一致？
- 有状态模块：故障后如何重建状态？持久化策略是什么？

**深度锚点：** 一个不了解上下文的工程师，能否仅凭此段正确建表/建模并写出恢复逻辑？

#### 4.N.3 并发与竞态 [适用条件：存在共享可变状态或并发调用方]

- 是否存在并发访问？冲突时谁赢？隔离边界在哪？
- 锁 / 无锁 / 乐观并发的选择及理由。
- 列出至少一个具体竞态场景及其裁决方式。

**深度锚点：** 最坏并发场景下（峰值请求同时到达），数据是否仍正确？

#### 4.N.4 错误处理与降级

- 依赖挂掉 / 超时 / 脏数据时的行为是什么？
- 每个异常路径有明确的降级或回退动作。
- 重试策略的参数自洽性（重试次数 × 单次超时 ≤ 总超时上限）。

**深度锚点：** 每个异常路径是否都有明确的"然后怎么办"，而非仅"记录日志"？

#### 4.N.5 性能特征 [适用条件：存在非平凡计算路径或显式资源持有]

- 核心路径的时间/空间复杂度。
- 瓶颈在哪？10× 当前规模下是否仍成立？
- 若不成立，扩容或降级的触发条件是什么？
- 本模块持有的运行时资源（连接、线程、缓存、文件句柄等）的生命周期是什么？峰值并发 / 最大数据量下，资源占用是否有明确上限？

**深度锚点：** 能否给出一个具体的量级数字（如"单表 500 万行时查询 < 200ms"、"并发 1000 连接时内存 < 512MB"），而非"性能良好"？

#### 4.N.6 可观测性契约

- 暴露哪些 Metrics / Tracing / 健康检查端点？
- 告警阈值和处置动作（回滚 / 限流 / 人工介入）。无直接用户界面的后台模块不得以"N/A"跳过——至少登记观察项与异常时的替代处置。

**深度锚点：** 运维人员能否仅凭此段配置监控面板和告警规则？

#### 4.N.7 组件接口与依赖

- 对外暴露的接口签名（入参、出参、校验规则）。
- 依赖方向是否单向？是否需要防腐层？
- DI 注册方式和生命周期。
- 有无借鉴的成熟方案？为什么选/不选？（自研理由必须具体到本项目的约束，不可泛泛。）

**深度锚点：** 调用方能否仅凭此段完成集成，无需阅读本模块内部实现？

#### 4.N.8 落地影响

- 修改项目：受影响的文件/目录及变更内容。
- 新建项目：新增的包/目录/组件清单。
- 验收标准：每条可验证断言 + 失败时的回滚动作。

#### 4.N.9 设计自检（3 问）

写完本模块设计后、进入下一个模块之前，回答以下三问。每问一句话结论。发现问题当场修正。

1. **参数自洽：** 本模块所有数值参数，在最坏正常场景下是否成立？
2. **引用完整：** 本模块是否有删除或替换操作？被删除的实体是否在其他地方仍被引用？
3. **规则覆盖：** 4.N.1 中列出的每条业务规则，是否都能在 4.N.2 ~ 4.N.7 中找到对应的设计承接？找不到承接的规则，补上设计或说明排除原因。

#### 4.N.10 模块接口摘要（≤300 字）

完成 4.N.9 自检后输出。此摘要是模块间信息传递的压缩格式：下游模块的编写者（人或 AI）据此理解本模块的边界与供给，无需通读本模块全文；§0 的跨模块接口契约段由全部模块的本摘要汇编而成。

- 对外暴露接口：[方法签名列表]
- 依赖的上游数据：[实体.字段列表]
- 本模块产生的事件/消息：[列表]
- 关键约束：[一句话]
- 本模块明确不处理的场景：[一句话]

## 附录 A：写作原则备忘

- **决策三要素：** 选定 / 否决理由 / 失效条件。缺任何一个，决策不完整。
- **推理链完整：** 事实 → 判断 → 结论，不允许跳步，更不允许结论先于事实。
- **事实与假设分清：** 存量事实标来源，新研假设标验证计划。不要把假设当事实推导，[待确认] 的事实不作为决策前提。
- **先业务后技术：** 每个模块先讲清业务再谈实现，禁止跳过。
- **砍刀只砍已有的：** 范围裁剪针对已提出的需求，不自造需求再砍。
- **不为凑结构写空话：** 某维度确实不涉及，一句话说明，禁止展开空转。
- **消灭模糊词：** 定稿前全文搜索"适当、合理、酌情、相关、根据需要、尽量"，命中即改为可执行的精确表述。
- **细节下沉：** 本文档记录设计决策，不记录实现。代码、完整 API 定义、测试用例另行产出。
- **发现前置决策有误时停下来：** 按 2.1 架构回溯触发条件处理，不在模块设计中硬凑。

## 附录 C：AI 辅助编写的永续机制

多模块长文档的核心风险是上下文膨胀：写到第 N 个模块时，注意力被前 N-1 个模块的全文稀释，质量随进度衰减。以下机制将单模块编写所需的上下文从随模块数线性增长（O(n)）压缩为常量（O(1)）——第 8 个模块与第 1 个模块的编写条件等价。这些规则约束的是信息的流动方式，人与 AI 均可参照。

**上下文组装。** 编写任一模块时，工作上下文只需包含：

- §0 全局锚定卡（≤1500 字，随回填更新）；
- 当前模块适用的维度指令（仅 [适用条件] 命中的维度，非全量模板）；
- 直接上游模块的 4.N.10 接口摘要（≤300 字/个）；
- 当前模块的需求描述。

不应携带：其他模块的设计全文、无关的历史过程。需要细节时按需回查正文对应章节，而非全程携带。

**生成与校验分离。** 生成阶段按模板结构填写，不同时执行自检；模块生成完毕后，单独执行 4.N.9 三问与模糊词扫描。生成与评估是两类认知任务，交替混行会互相干扰。

**逐模块推进。** 每完成一个模块：先输出 4.N.10，回填 §0（如有新契约），确认无误后再开始下一个模块。避免同一次生成中连续产出多个模块。逐模块确认节拍经用户显式批量授权可豁免；豁免时「4.N.10 先行」「§0 回填」「跨模块终审五查」三项内核纪律不豁免——豁免的是交互节拍，不是质量内核。

**跨模块终审。** 全部模块完成后，基于所有 4.N.10 摘要与 §0（而非全文）执行五项一致性检查：

1. 接口连续：每个模块的输入类型与上游模块的输出类型一致？
2. 实体一致：同一实体在不同模块中的字段名与类型一致？
3. 枚举一致：同一枚举跨模块取值相同？
4. 约束传递：§0 中的全局硬约束在每个相关模块均有体现？
5. 无孤儿模块：是否存在既无上游输入、也无下游消费的模块？
