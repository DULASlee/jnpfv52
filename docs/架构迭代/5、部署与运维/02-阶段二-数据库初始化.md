## 2.1 了解要建哪些库、执行哪个 SQL [必选]

> **库名以 `ConnectionStrings.json` 为准**（阶段一 1.1.2 已读取 `$MAIN_DB`、`$JOB_DB`）。  
> **不要自己编库名**——必须与 JSON 中 `DBName` 及下表 SQL 脚本一致。

JNPF 后端通过 `application/JNPF.API.Entry/Configurations/ConnectionStrings.json` 连接 **两个库**：

| 顺序 | ConfigId | 库名（默认） | **必须执行的脚本** | 用途 |
|------|----------|-------------|-------------------|------|
| 1 | `default` | **ZXAF_V1_DevTest1** | `web/主库脚本.sql` | 用户、权限、低代码、工作流、大屏等 **全部业务表** |
| 2 | `JNPF-Job` | **jnpf_sundial** | `web/jnpf_sundial_init_sqlserver.sql` | Sundial 定时任务（Job 表） |

### 两个「init」文件的关系（易混淆）

| 文件 | 语法 | 建哪个库 | SQL Server 部署是否执行 |
|------|------|----------|------------------------|
| `web/主库脚本.sql` | SQL Server | **ZXAF_V1_DevTest1**（主库） | ✅ **必须** |
| `web/jnpf_sundial_init_sqlserver.sql` | SQL Server | **jnpf_sundial**（调度库） | ✅ **必须** |
| `web/jnpf_sundial_init.sql` | **Oracle** | jnpf_sundial（Oracle 版） | ❌ **不要**在 SQL Server 上执行 |

> **与架构文档 05/10 的说明：**  
> 05/10 文档写「`jnpf_sundial_init.sql` 不含 BLADE_VISUAL / FLOW 表」——**这是对的**，因为那是 **调度库 Oracle 脚本**，本来就没有业务表。  
> 业务表（含 `flow_*`、`blade_visual_*`）在 **`web/主库脚本.sql`** 里。05/10 中的 `【待 DDL 验证】` 针对的是 **init 脚本**；主库脚本已含完整 DDL，**部署手册以本仓库实测为准**。

## 2.5 准备 admin 登录数据 [必选]

> **这一步做什么：** 确保数据库里有 **能成功登录** 的最小业务数据。  
> ⚠️ **本仓库不含 seed SQL 文件**——`web/主库脚本.sql` 只有建表语句，没有 `INSERT`。

### 最小可登录数据集（缺一不可）

仅导入 `base_user` 一行 **通常不够**。登录 + 菜单 + 系统配置至少需要：

| 表 | 最少需要的数据 | 说明 |
|----|----------------|------|
| **base_user** | `admin` 账号 1 条 | 登录必需；含 `f_password`、`f_secretkey`（MD5+密钥哈希，非明文） |
| **base_sys_config** | 系统配置项（迁移环境约 70+ 条） | 验证码开关、默认密码策略、Token 相关等；**缺失可能导致登录接口报错** |
| **base_role** | 至少 1 个管理员角色 | admin 的角色载体 |
| **base_user_relation** | admin ↔ 角色/组织 关联 | 权限必需 |
| **base_module** | 菜单模块数据 | 登录后左侧菜单；无数据则菜单空白 |
| **base_authorize** | 角色-模块权限 | 与 `base_module` 配合 |

> v5.2 迁移方案实测：CodeFirst 仅 seed 最小 admin 时，`BASE_SYS_CONFIG` 约 7 条；从 v3.6 回填后约 74 条。**生产/完整体验建议还原含数据的 `.bak` 或整库迁移包。**

### 推荐获取方式（按优先级）

| 方式 | 适用场景 | 操作 |
|------|----------|------|
| **A. 还原完整 .bak** | JNPF 交付含数据备份 | SSMS → 还原数据库覆盖 `ZXAF_V1_DevTest1` |
| **B. 已有迁移完成库** | v3.6 → v5.2 迁移后 | 跳过导入 DDL，直接连已有库 |
| **C. 从参考环境导出** | 内网有跑通的测试库 | 导出上表相关数据（勿只导 `base_user`） |
| **D. 仅 DDL 空库** | 只有 `主库脚本.sql` | **无法在本仓库内自助 seed** → 联系 JNPF 获取 seed 包或 `.bak` |

> **本仓库现状：** 未提供可复制的 seed SQL 片段。架构师若需审 seed 内容，请向 JNPF 索取交付用 `.bak` 或迁移后测试库导出。

### 2.5.1 最小可登录验证 SQL

导入 seed / 还原备份 **之后立刻执行**：

```sql
-- 1) admin 账号存在且启用（f_enabled_mark=1 表示启用；f_lock_mark 为空或 0）
SELECT f_id, f_account, f_real_name, f_enabled_mark, f_lock_mark, f_is_administrator
FROM base_user
WHERE f_account = 'admin';
-- 期望：1 行；f_enabled_mark = 1

-- 2) 系统配置非空（完全空库为 0 行 → 登录可能失败）
SELECT COUNT(*) AS sys_config_count FROM base_sys_config WHERE f_delete_mark IS NULL;

-- 3) admin 角色关联
SELECT COUNT(*) AS relation_count
FROM base_user_relation ur
INNER JOIN base_user u ON ur.f_user_id = u.f_id
WHERE u.f_account = 'admin';
-- 期望：relation_count >= 1

-- 4) 菜单模块非空（可选但强烈建议）
SELECT COUNT(*) AS module_count FROM base_module WHERE f_delete_mark IS NULL AND f_enabled_mark = 1;
```

🪟 **Windows 11** 一行执行示例：

```powershell
sqlcmd -S $DB_HOST -U $DB_USER -P "$DB_PASS" -d $MAIN_DB -Q "SELECT f_id, f_account, f_real_name, f_enabled_mark FROM base_user WHERE f_account='admin'"
```

| # | 验证什么 | 通过标准 | 失败怎么办 |
|---|----------|----------|-----------|
| 1 | admin 行 | 1 行，`f_enabled_mark=1` | 方式 A/C/D |
| 2 | sys_config | `sys_config_count` > 0（完整环境 >> 10） | 勿只 seed user，补全 config |
| 3 | 角色关联 | `relation_count` ≥ 1 | 补 `base_user_relation` + `base_role` |
| 4 | 菜单 | `module_count` > 0（完整登录体验） | 还原完整 .bak 或迁移包 |

**默认密码（以 seed 来源文档为准，非明文存库）：**

| 环境文档 | 账号 | 明文密码 |
|----------|------|----------|
| 培训/操作手册 | `admin` | `123456` |
| v5.2 迁移方案 | `admin` | `000000` |

> ⚠️ **生产必须修改默认密码。** 前端传输：MD5(明文) → AES-ECB-Hex；库中 `f_password` 为 MD5(MD5(明文)+`f_secretkey`)。
