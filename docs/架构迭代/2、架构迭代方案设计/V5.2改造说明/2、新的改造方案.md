### 5. Phase 2 — 转换脚本编写（Day 2-4）

#### 5.1 总体策略

```
不直接在 v5.2 库上操作 v3.6 数据。

正确流程：
  v3.6 源库 → SELECT 提取 → 转换/映射 → INSERT 到 v5.2 目标库

每张表的迁移脚本结构：
  -- [注释] 源表：v3.6.xxx  →  目标表：v5.2.YYY
  -- [注释] 映射方式：直接映射 / 重命名 / 重构
  -- [注释] 行数预期：N 行
  
  BEGIN TRANSACTION;
    -- 先清空目标表（保留 admin 账号等骨架数据的特殊处理）
    DELETE FROM [v5.2_target_table] WHERE ...;
    
    -- 插入转换后数据
    INSERT INTO [v5.2_target_table] (col1, col2, ...)
    SELECT 
      src.col1,                    -- 直接映射
      src.col2 AS col_renamed,     -- 重命名映射
      'default_value' AS new_col,  -- 新字段默认值
      -- src.old_col,              -- 已删除字段，注释掉
    FROM [ZXAF_V1_DevTest1].[dbo].[v36_source_table] src;
    
  COMMIT;
  -- [验证] SELECT COUNT(*) FROM [v5.2_target_table];
```

#### 5.3 关键映射难点处理规则

**难点 1：表名变更（如 flow_task → WORKFLOW_TASK）**

```
处理方式：
1. 读 v5.2 WORKFLOW_TASK 的 Entity 定义（C# 代码），获取字段列表
2. 读 v3.6 flow_task 的字段列表
3. 按业务语义匹配字段（不依赖字段名一致性）
4. 无法匹配的字段：v3.6 独有→忽略，v5.2 独有→默认值
5. 生成 INSERT INTO ... SELECT ... 转换脚本
```

**难点 2：字段重命名（如 F_NICKNAME → F_NICK_NAME）**

```
处理方式：
1. 在差异分析阶段标注所有重命名项
2. 转换脚本中用 SELECT src.F_NICKNAME AS F_NICK_NAME 实现
3. 如果重命名项过多（>10），生成一张映射表供脚本引用
```

**难点 3：新增 NOT NULL 字段（v5.2 有，v3.6 没有）**

```
处理方式：
1. 分析字段语义，确定合理默认值
2. 如果是枚举/状态字段，查看 v5.2 源码中的常量定义
3. 如果无法确定默认值，标记为"需架构师确认"
4. 绝不使用 NULL（除非字段允许）
```

**难点 4：BASE_MODULE 菜单路由映射**

```
这是迁移中最复杂的部分。

v3.6 的菜单 F_URL_ADDRESS 可能是：
  /system/user          （旧路由格式）
  /systemManage/user    （v3.6 特定路径）

v5.2 的前端路由可能是：
  /system/user          （相同格式）
  /system/user/index    （更深层级）

处理方式：
1. 导出 v5.2 前端路由表（Phase 1 已做）
2. 对 v3.6 的每条菜单 urlAddress，在 v5.2 路由中查找最佳匹配
3. 匹配策略：
   a. 精确匹配 → 直接使用
   b. 前缀匹配 → 使用 v5.2 路由
   c. 无匹配 → 标记为"v5.2 已废弃"或"需手动确认"
4. 输出映射清单，架构师审核后执行
```
