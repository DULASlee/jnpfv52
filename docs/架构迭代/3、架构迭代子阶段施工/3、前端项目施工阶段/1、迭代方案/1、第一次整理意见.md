# 重新定义合并策略：dist 为真理之源

## 一、你的判断完全正确，这改变了整个合并逻辑

你点出了一个工程师思维中最常见的盲区：

```
工程师的默认思维：
  "源码是干净的 → dist是构建产物 → 以源码为准 → dist中的定制是'脏的'"

实际情况：
  "dist是在生产环境跑了很久、验证过的东西 → 它才是活的标准 →
   从GitHub临时拉来的源码是'参考' → 源码必须向dist对齐，不是反过来"

打个比方：
  工程师的思路 = 拿着设计图纸说"房子应该长这样"
  你的思路 = 房子已经住了一年没塌，图纸才刚找到，以房子为准
```

这个原则一旦确立，**合并方向就反转了**：

```
旧方向（错误）：源码为标准 → dist中多出的是"垃圾" → 清理dist
新方向（正确）：dist为标准 → 源码中多出的是"候选清理项" → 源码向dist对齐

旧方向：water在dist中 → "删掉，源码里没有"
新方向：water在dist中 → "生产环境在用，说明是必要的 → 源码缺这个，要补回来（后补）"

旧方向：extend/79个vue在源码中 → "是官方Demo，保留"
新方向：extend/79个vue在源码中 → "dist里有没有用到？没用到的就是多余的 → 可以清"
```

## 二、以 dist 为标准的审计方法

核心方法论：**从 dist 反推出完整的功能清单，然后拿这个清单去校验源码。**

### 2.1 从 dist 提取功能清单

```
dist_v1.1/ 的结构就是答案：

1. 提取页面路由清单
   ├── 从 dist/assets/js/ 中搜索路由定义
   ├── 或从 dist 的 _app.config.js / 白名单配置中提取
   ├── 或从 dist 运行时的 Network 请求中看菜单API返回
   └── 产出：完整的页面路由清单（哪些页面是真实在用的）

2. 提取依赖清单
   ├── 从 dist/assets/js/vendor-*.js 中搜索库名
   ├── 或从 dist 的 HTML 中看加载了哪些CDN资源
   └── 产出：dist实际使用的第三方库清单

3. 提取chunk清单
   ├── 从 dist/assets/js/ 中列出所有chunk文件名
   ├── chunk文件名中包含的目录路径 → 对应源码中的页面
   └── 产出：dist实际打包了哪些页面/组件

4. 提取API调用清单
   ├── 从 dist/assets/js/ 中搜索所有 API 路径字符串
   │   （如 /api/system/user, /api/workflow/task 等）
   └── 产出：前端实际调用了哪些后端接口
```

### 2.2 拿 dist 清单校验源码

```
对每个 dist 中存在的功能，检查源码：

┌──────────────────────────────────────────────────────────┐
│  dist有 → 源码有     → 正常，保留                         │
│  dist有 → 源码没有   → 标记为"待补"，后续加回来           │
│  dist没有 → 源码有   → 标记为"候选清理项"                 │
│  dist没有 → 源码也没有 → 不相关                           │
└──────────────────────────────────────────────────────────┘

举例：
├── echarts: dist有 + 源码有 → 保留 ✓
├── xlsx: dist有 + 源码有 → 保留 ✓
├── water页面: dist有 + 源码没有 → 标记"待补"（不急，后补）
├── printDevH5: dist有 + 源码没有 → 标记"待补"
├── extend/graphDemo: dist有没有？ → 如果dist没有，就是候选清理项
├── logicflow: dist有没有？ → 确认后决定保留还是清理
└── tinymce: dist有没有？ → 确认后决定保留还是清理
```

## 三、修正后的执行方案

### 步骤1：dist 审计（0.5天）

```
这是最优先做的事情，因为dist是真理之源。
在碰源码之前，先彻底搞清楚dist里有什么。

任务：
├── 1.1 列出 dist_v1.1 中所有 JS chunk 文件名
│       → 每个chunk对应源码中的什么模块
│
├── 1.2 从 dist 的路由配置/白名单中提取所有页面路径
│       → 产出：页面路由清单表
│
├── 1.3 从 dist 的 vendor/chunk 中搜索第三方库引用
│       → 产出：dist实际依赖清单表
│
├── 1.4 从 dist 的 JS 中搜索所有 API 路径
│       → 产出：后端接口调用清单表
│
└── 1.5 运行 dist_v1.1，逐页截图记录所有可访问的页面
        → 产出：功能页面清单表（带截图）

产出文档（只此一份，其余文档后置）：

| # | 功能/页面 | dist中有 | 源码中有 | 处置 |
|---|-----------|---------|---------|------|
| 1 | 登录页 | ✓ | ✓ | 保留 |
| 2 | 用户管理 | ✓ | ✓ | 保留 |
| 3 | 工作流 | ✓ | ✓ | 保留 |
| 4 | water/水务9页 | ✓ | ✗ | 待补 |
| 5 | printDevH5 | ✓ | ✗ | 待补 |
| 6 | extend/graphDemo | ? | ✓ | 待确认 |
| 7 | ... | ... | ... | ... |
```

### 步骤2：源码对齐清理（1天）

```
基于步骤1的清单，对源码进行"向dist看齐"的清理。

原则：
├── dist有的 → 不动
├── dist没有的 + 源码有的 → 清理（但先确认再删）
└── 不确定的 → 先不动，等跑起来再验证

具体操作：

2.1 依赖对齐
    ├── dist有 + 源码有 → 保留（echarts, xlsx等）
    ├── dist没有 + 源码有 → 标记，暂不删
    │   （先跑起来看功能，确认不影响后再清理）
    └── dist有 + 源码没有 → 标记"待补"

2.2 页面/组件对齐
    ├── dist有 + 源码有 → 保留
    ├── dist没有 + 源码有 → 在后端菜单中隐藏（不删文件）
    │   └── 为什么隐藏而不删：
    │       a. 可能有些功能虽不在当前dist版本中，但未来会用
    │       b. 删文件有风险，隐藏菜单无风险
    │       c. 与你"先简略后边不够再加"的原则一致
    └── dist有 + 源码没有 → 记录到"待补清单"

2.3 环境配置对齐
    ├── 从 dist_v1.1/_app.config.js 中提取实际的API地址等
    ├── 用这些值配置源码的 .env.production
    └── 确保与现有后端地址一致
```

### 步骤3：构建并验证功能对等（1天）

```
目标：新构建产物的功能必须覆盖 dist_v1.1 的所有功能。

3.1 pnpm install → pnpm build
    ├── 零ERROR目标
    └── WARNING先记录，不阻塞

3.2 部署新 dist，逐项对照旧 dist 的功能
    ├── 登录 ✓
    ├── 所有基础菜单（用户/角色/组织/菜单/字典）✓
    ├── 在线开发（表单设计+列表设计）✓
    ├── 工作流（设计+审批）✓
    ├── Excel导入导出 ✓
    ├── 图表/报表 ✓
    ├── 打印模板 ✓
    ├── 门户页面 ✓
    └── 其他dist中有的页面逐个验证

3.3 记录差异
    ├── "旧dist有但新dist没有的功能" → 优先级P0，必须补
    ├── "新dist有但旧dist没有的功能" → 候选清理，先隐藏菜单
    └── "功能表现不一致" → 分析原因，修复

产出：功能对等验证表（通过/不通过/待补）
```

### 步骤4：修补缺失（按需，1-2天）

```
只有步骤3中发现的"旧dist有但新dist没有"的功能才需要补。

已知可能缺失的：
├── printDevH5（H5打印）→ 补路由白名单
├── water相关页面 → 后补（如果不影响当前使用，可以推迟）
└── 其他步骤3中发现的缺失 → 逐个评估

原则：
├── 影响登录/核心流程的 → 立刻补
├── 只影响某个边缘功能的 → 记录，排期补
└── 不确定是否需要的 → 先问使用人员
```

## 五、"待补清单"的管理方式

```
对于dist有但源码暂时没有的功能（如water、printDevH5），处理方式：

不要：立刻试图从dist反编译恢复源码
     → 反编译minified JS产出的代码质量极差
     → 维护成本远高于重写

要：
├── 记录到一个简单的清单表：
│   | 功能 | dist中的路径/入口 | 优先级 | 状态 |
│
├── 确认每个功能的当前使用状态：
│   ├── 还在用 → P0，优先补
│   ├── 偶尔用 → P1，排期补
│   └── 已废弃 → 不补
│
└── 补的方式（按优先级）：
    ├── P0：用低代码平台的在线开发能力重新创建（推荐）
    │   → 这才是低代码平台的正确用法
    │   → 比写Vue代码快得多
    │   → 且自动适配平台升级
    │
    ├── P1：如果在线开发搞不定 → 手写Vue组件
    │   → 放在 views/extend/ 下
    │   → 不破坏平台约定
    │
    └── P2：从dist中提取关键逻辑作为参考（不是直接复制）
        → 只看数据结构和API调用方式
        → 代码重写
```
