## 二、架构设计说明书（9 项）

### A-9：§3.2 新增"双入口架构"说明

在 §3.2 分层架构核心决策中新增一节：

**双入口架构说明：**

JNPF-AI 提供两个完全独立的开发入口，底层共享 IR 类型系统和编译网关，上层操作完全分开：

| 入口                   | 路由前缀     | 页面形态                                         | 依赖模块                                    | 角色              |
| ---------------------- | ------------ | ------------------------------------------------ | ------------------------------------------- | ----------------- |
| 手工入口（已有，冻结） | /visualdev/* | 原 JNPF 可视化设计器（拖控件、设字段、配工作流） | visualdev + codegen（不依赖 inteAssistant） | 开发者 + 业务专家 |
| AI 入口（新增）        | /studio/ai/* | 项目工作台（AI 对话 + 实时预览）                 | inteAssistant + visualdev（编译）+ codegen  | 业务专家为主      |

**隔离约束：**
- 手工入口不调用 inteAssistant 模块的任何服务。AI 入口不依赖 visualdev 的拖拽设计器组件
- 两者通过 IR 类型系统（types.ts 唯一真源）实现产物同构
- 两者通过统一编译网关实现编译路径统一
- AI 入口完全不可用时（所有 LLM Provider 故障），手工入口 100% 正常运行

### A-14：§3.2 新增 ARC-3-005 变更影响传播

**ARC-3-005 变更影响传播算法**

**决策：** 变更影响评估基于 IR 依赖图的反向 BFS，不依赖 LLM 判断或硬编码规则表。

**算法三步：**
1. `buildDependencyGraph(ir)`: 遍历 IR 所有节点，解析节点间的引用关系（正向边 + 反向边），构建 `IRDependencyGraph`。复杂度 O(N)
2. `propagateImpact(graph, changedNodeIds)`: 从变更节点出发，沿反向边 BFS，收集所有受影响节点。复杂度 O(V+E)
3. `determineReentryStage(impactedNodes, graph)`: 将受影响节点的类型映射到产出该类型的流水线阶段，取最早阶段。映射关系从 IR 类型系统自然推导

**性能：** 500 节点 IR 的完整评估 < 100ms

**支撑：** 审判令一（精准重入）

### A-15：§6 新增 ARC-6-002 SSE 语义事件协议

**ARC-6-002 SSE 语义事件协议**

**决策：** AI 流水线运行期间，通过 SSE 向前端推送结构化语义事件（非纯进度百分比），实现 AI 思考过程的白盒化。

**事件类型 PipelineSSEEvent：**
- `stage`: 当前阶段名
- `phase`: 当前子阶段（如 "analyzing_requirements"）
- `progress`: 0-100 进度
- `thought`: 人类可读的思考描述（如 "正在分析请假模块与审批流的耦合关系"）
- `agent`: 当前执行的智能体名称
- `warning`: 可选，风险提示（如 "检测到 3 处接口需要调整"）
- `timeout_alert`: 可选，超时警报
- `elapsed_ms`: 已耗时
- `estimated_remaining_ms`: 预计剩余时间

**Agent Checkpoint 机制：** 每个 Agent 基类内置 `checkpoint(phase, thought, detail?)` 方法，在关键推理节点调用。checkpoint 同时写入 SSE 流和 `BASE_AI_PIPELINE_MESSAGE` 表（持久化）。

**超时监控 AgentTimeoutMonitor：**
- 软超时（超过预期时间）：推送 warning 事件，前端显示黄色提示
- 硬超时（超过最大时间）：推送 timeout 事件 + 触发 §4.0 熔断计数
- 每个 Agent 独立计时，互不影响

**支撑：** 审判令三（实况解说）

### A-16：§3.2 新增 ARC-3-006 分治编辑架构

**ARC-3-006 分治编辑架构（Surgical Edit）**

**决策：** 用户发起变更时，Agent 输出 JSON Patch 编辑指令而非完整 IR。Agent 只处理相关子树，不接触无关节点。

**六步流程：**
1. **节点定位**：`buildNodeSummaryList(ir)` 生成节点摘要列表（200-500 行）→ LLM 列表选择（< 2s）→ 返回 relevantNodeIds + confidence
2. **Agent 路由**：根据节点类型 → Agent 映射表确定执行 Agent（如 RuleNode → 规则引擎 Agent）
3. **切片提取**：`agentScope.extractSlice(ir)` 从 IR 中提取相关子树（Agent 只看到自己的工作范围）
4. **编辑指令生成**：Agent 输入切片 + 变更请求 → 输出 `IREditPatch`（JSON Patch 格式的 replace/add/remove 操作列表）
5. **确定性应用**：`applyPatch(ir, patch)` 逐条应用操作，每条记录 oldValue（可回滚）
6. **验证 + 展示**：`validator.ts` + `vue-tsc` 校验 → IR Diff Viewer 展示变更 → 用户确认

**与三路合并的关系：** V1 实现分治编辑。V2 评估是否需要补充三路合并作为 Agent 输出完整 IR 时的兜底方案。

**V2 路标：** 当 IR 节点数超过 1000 或 LLM 列表选择准确率不足时，升级节点定位为向量索引方案。

**支撑：** 审判令二（差分修补）

### A-17：§3.2 新增 ARC-3-007 Agent 视图机制

**ARC-3-007 Agent 视图机制（Agent Scope）**

**决策：** 每个 Agent 注册一个固定的 `AgentScope`，定义其可读、可写的 IR 节点类型。Agent 只能操作自己视图范围内的节点，跨视图修改必须通过编排智能体（OrchestratorAgent）协调。

**AgentScope 接口：**
- `ownedNodeTypes`: 该 Agent 负责产出的节点类型
- `readableNodeTypes`: 该 Agent 可读的节点类型（输入原材料）
- `writableNodeTypes`: 该 Agent 可写的节点类型（输出产物）
- `extractSlice(ir)`: 从 IR 中按类型过滤，提取该 Agent 的工作切片

**6 个 Agent 的视图注册表（见详细设计 §3）：**

| Agent        | 可读                                       | 可写                               |
| ------------ | ------------------------------------------ | ---------------------------------- |
| 需求分析师   | 全部（概览级别，不展开内部字段）           | Requirement                        |
| 架构师       | Requirement + ModuleDefinition             | ModuleDefinition + TableDefinition |
| UI 设计师    | Component + DataSource + Requirement       | Component                          |
| 数据库设计师 | TableDefinition + DataSource + Requirement | TableDefinition + DataSource       |
| 工作流设计师 | WorkflowStep + Component                   | WorkflowStep                       |
| 规则引擎     | RuleNode + Component + Requirement         | RuleNode                           |

**隔离保证：** 分治编辑的 Step 2（Agent 路由）自动将操作限制在目标 Agent 的 writableNodeTypes 范围内。如果 LLM 生成的编辑指令试图修改 Agent 视图外的节点，`applyPatch` 拒绝执行并报错。

**支撑：** 审判令一 + KIMI 模块划分审核

### D-8：§4.7a 新增 变更影响传播

新增小节 §4.7a"变更影响传播算法"：

**三个核心函数的接口契约：**

```typescript
// 1. 构建依赖图
function buildDependencyGraph(ir: FormPageIR): IRDependencyGraph

interface IRDependencyGraph {
  nodes: Map<string, IRNode>;
  forwardEdges: Map<string, Set<string>>;   // node.id → 引用的节点 ID 集合
  reverseEdges: Map<string, Set<string>>;   // node.id → 被哪些节点引用
}

// 2. 影响传播（反向 BFS）
function propagateImpact(
  graph: IRDependencyGraph,
  changedNodeIds: Set<string>
): Set<string>   // 返回所有受影响节点 ID

// 3. 确定重入阶段
function determineReentryStage(
  impactedNodeIds: Set<string>,
  graph: IRDependencyGraph
): PipelineStage  // 返回最早需要重入的阶段
```

**节点类型→阶段映射表：**
- Requirement → stage1
- ModuleDefinition, TableDefinition → stage2
- Component, DataSource, WorkflowStep, RuleNode → stage3
- CompileConfig → stage4

**复杂度：** buildDependencyGraph O(N), propagateImpact O(V+E), determineReentryStage O(K)。总延迟 < 100ms（500 节点）

### D-9：§4.7b 新增 分治编辑详细设计

新增小节 §4.7b"分治编辑（Surgical Edit）"：

**完整六步流程接口契约：**

```typescript
// Step 1: 节点定位
function buildNodeSummaryList(ir: FormPageIR): string
// 输出：每行一个节点摘要 "[id] type: label — description"

interface NodeLocateResult {
  nodeIds: string[];
  confidence: number;    // 0.0-1.0
  reason: string;
}

// Step 2: Agent 路由
function routeToAgent(nodeIds: string[], graph: IRDependencyGraph): AgentName
// 基于节点类型 → Agent 映射表，无需 LLM

// Step 3: 切片提取
interface AgentScope {
  agentName: string;
  ownedNodeTypes: NodeType[];
  readableNodeTypes: NodeType[];
  writableNodeTypes: NodeType[];
  extractSlice(ir: FormPageIR): AgentSlice;
}

interface AgentSlice {
  nodes: IRNode[];            // 切片内的节点
  context: string;            // 这些节点在整体 IR 中的角色描述
  writableNodeIds: string[];  // Agent 可修改的节点 ID 列表
}

// Step 4: 编辑指令
interface ScopedEditInput {
  slice: AgentSlice;
  changeRequest: string;      // 用户的自然语言变更请求
  currentIRVersion: string;   // IR 版本标识（一致性校验用）
}

interface ScopedEditOutput {
  patch: IREditPatch;
  impactAnalysis: string;
}

interface IREditPatch {
  targetNodeIds: string[];
  operations: IREditOperation[];
  explanation: string;
}

interface IREditOperation {
  op: 'replace' | 'add' | 'remove';
  path: string;          // JSONPath 指向目标字段
  value?: any;           // 新值
  oldValue?: any;        // 旧值（applyPatch 时自动填充）
  reason: string;        // 人类可读的修改原因
}

// Step 5: 应用
function applyPatch(ir: FormPageIR, patch: IREditPatch, scope: AgentScope): {
  result: FormPageIR;
  applied: IREditOperation[];
  failed: IREditOperation[];  // 含失败原因
}
// 关键约束：只允许修改 scope.writableNodeIds 范围内的节点
// 超出范围的操作直接 reject

// Step 6: 验证
function validateAfterPatch(ir: FormPageIR): {
  valid: boolean;
  errors: ValidationError[];
}
```
