# JNPF V5.2 真气运行诊断 — 非颠覆性迭代完善方案

> **诊断日期：** 2026-06-06
> **核心原则：** 只做加法和增强，不做减法和替换。每一个改进点必须满足"改完之后现有业务功能零影响"。
> **代码依据：** 所有结论基于 `docs/architecture/V53/export/` 中的真实代码

---

## 红线定义：什么算"颠覆性改造"

| 行为 | 是否颠覆性 | 说明 |
|------|-----------|------|
| 新增 NuGet 包 + 新增代码 | ❌ 非颠覆 | 纯加法，不影响现有逻辑 |
| 在已有方法中追加可选逻辑 | ❌ 非颠覆 | 默认关闭，配置开启 |
| 替换现有 DI 容器（如换 Autofac） | ✅ 颠覆 | 影响所有服务解析 |
| 替换 ORM（如换 EF Core） | ✅ 颠覆 | 影响所有数据访问 |
| 修改现有 Service 方法签名 | ✅ 颠覆 | 影响所有调用方 |
| 修改 API 路由规则 | ✅ 颠覆 | 前端全部 404 |
| 修改事件总线底层实现 | ✅ 颠覆 | 影响所有事件订阅者 |
| 新增中间件（注册在管道末尾） | ❌ 非颠覆 | 不影响现有请求流程 |
| 新增全局过滤器（追加到现有过滤器后） | ⚠️ 需验证 | 需确认不影响现有查询 |

### 2. SqlSugar DiffLog（数据变更审计）

**现状：** `SetDbAop()` 中配置了 OnLogExecuting / OnLogExecuted / OnError，但 DiffLog 未配置。

**改进方案：**

```csharp
// SqlSugarConfigureExtensions.cs — 在 SetDbAop() 方法末尾追加
// DiffLog 仅在显式调用 .EnableDiffLogEvent() 的操作上触发，普通查询/更新不受影响
db.Aop.OnDiffLog = (diff) =>
{
    // diff.BeforeData → 变更前数据
    // diff.AfterData → 变更后数据
    // diff.DiffType → insert/update/delete
    // diff.TableName → 表名
    // diff.BusinessData → 业务数据（可附加 UserId/TenantId）

    // 写入审计日志表（异步，不阻塞主流程）
    _ = Task.Run(async () =>
    {
        try
        {
            var db = _sqlSugarClient.CopyNew();
            await db.Insertable(new SysDiffLogEntity
            {
                Id = IdGenerator.NextId(),
                TableName = diff.TableName,
                DiffType = diff.DiffType.ToString(),
                BeforeData = diff.BeforeData.ToJson(),
                AfterData = diff.AfterData.ToJson(),
                CreateTime = DateTime.Now
            }).ExecuteCommandAsync();
        }
        catch { /* 审计日志写入失败不应影响业务 */ }
    });
};
```

**使用方式（逐个业务点按需开启）：**
```csharp
// 仅对需要审计的操作开启 DiffLog，其他操作完全不受影响
await db.Updateable(entity)
    .EnableDiffLogEvent(new { UserId = userId, TenantId = tenantId })
    .ExecuteCommandAsync();
```

**影响面：** 仅注册回调函数，不触发任何行为。只有在业务代码中显式调用 `.EnableDiffLogEvent()` 时才会产生审计数据。现有代码零影响。
**工作量：** 1 天（含审计表设计）
**收益：** 数据变更可追溯，满足合规要求。

### 4. API 限流（Rate Limiting）

**现状：** 无任何限流机制。恶意请求可无限调用。

**改进方案：**

```csharp
// Startup.cs ConfigureServices 追加
services.AddRateLimiter(options =>
{
    // 全局固定窗口限流
    options.AddFixedWindowLimiter("fixed", opt =>
    {
        opt.PermitLimit = 100; // 每秒 100 请求
        opt.Window = TimeSpan.FromSeconds(1);
        opt.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
        opt.QueueLimit = 10;
    });

    // 登录接口滑动窗口限流
    options.AddSlidingWindowLimiter("login", opt =>
    {
        opt.PermitLimit = 10; // 每分钟 10 次登录尝试
        opt.Window = TimeSpan.FromMinutes(1);
        opt.SegmentsPerWindow = 6;
    });

    // 限流触发时返回 429
    options.OnRejected = (context, cancellationToken) =>
    {
        context.HttpContext.Response.StatusCode = StatusCodes.Status429TooManyRequests;
        return ValueTask.CompletedTask;
    };
});

// Startup.cs Configure 追加（在 UseRouting 之后，UseAuthentication 之前）
app.UseRateLimiter();

// 对特定端点应用限流 — 在 DynamicApiController 上添加特性
[Authorize]
[EnableRateLimiting("fixed")]
public class UserService : IDynamicApiController { ... }
```

**影响面：** 新增中间件 + 特性，不修改现有方法。默认不限流，仅对标记了 `[EnableRateLimiting]` 的端点生效。
**工作量：** 1 天
**收益：** 防止 API 滥用，保护后端资源。

### 6. 租户写操作安全加固

**现状：** Trap 8 已记录：`db.Updateable(entity).ExecuteCommand()` 不自动附加 TenantId，可能更新所有租户数据。

**改进方案：** 创建租户感知的仓储扩展方法，不修改现有仓储基类。

```csharp
// 新增文件：SqlSugarRepositoryTenantExtensions.cs
public static class SqlSugarRepositoryTenantExtensions
{
    /// <summary>
    /// 租户安全更新 — 自动附加 TenantId 条件
    /// </summary>
    public static async Task<int> TenantSafeUpdateAsync<TEntity>(
        this ISqlSugarRepository<TEntity> repo,
        TEntity entity,
        string tenantId,
        Expression<Func<TEntity, bool>>? additionalWhere = null)
        where TEntity : class, new()
    {
        var updateable = repo.Context.Updateable(entity)
            .Where(x => ((ITenantFilter)x).TenantId == tenantId);

        if (additionalWhere != null)
            updateable = updateable.Where(additionalWhere);

        return await updateable.ExecuteCommandAsync();
    }

    /// <summary>
    /// 租户安全删除 — 自动附加 TenantId 条件
    /// </summary>
    public static async Task<int> TenantSafeDeleteAsync<TEntity>(
        this ISqlSugarRepository<TEntity> repo,
        Expression<Func<TEntity, bool>> where,
        string tenantId)
        where TEntity : class, new()
    {
        return await repo.Context.Deleteable<TEntity>()
            .Where(where)
            .Where(x => ((ITenantFilter)x).TenantId == tenantId)
            .ExecuteCommandAsync();
    }
}
```

**影响面：** 新增扩展方法，现有代码不受影响。新代码应使用 `TenantSafeUpdateAsync`，旧代码逐步迁移。
**工作量：** 2 天（含测试）
**收益：** 消除跨租户数据泄露风险。

### 7. QueryFilter.Clear() 安全化

**现状：** `SqlSugarRepository.cs:57` 调用 `base.Context.QueryFilter.Clear()` 会清除所有全局过滤器（包括软删除），仅重新添加租户过滤器。当前因无其他全局过滤器，暂无实际问题，但为未来扩展埋下隐患。

**改进方案：** 在添加软删除过滤器（第 12 项）时同步修改。方案如下：

```csharp
// 改前（当前代码）

base.Context.QueryFilter.Clear();

// 未来追加软删除过滤器时，在此处同步添加：
// base.Context.QueryFilter.AddTableFilter<ISoftDelete>(it => it.DeleteMark == 0);
```

**影响面：** 当前无需修改代码。在第 12 项（软删除过滤器）实施时，需在此处追加一行过滤器注册。
**工作量：** 0.5 天（与第 12 项合并实施）

### 15. 事件 Outbox 模式

**现状：** 数据库操作和事件发布不是原子的，可能"事务提交成功但事件丢失"。

**改进方案：**

```sql
-- 新增 Outbox 表
CREATE TABLE SYS_EVENT_OUTBOX (
    F_ID VARCHAR(50) PRIMARY KEY,
    F_EVENT_TYPE VARCHAR(200) NOT NULL,
    F_PAYLOAD NVARCHAR(MAX) NOT NULL,
    F_CREATED_AT DATETIME NOT NULL,
    F_PROCESSED_AT DATETIME NULL,
    F_RETRY_COUNT INT DEFAULT 0,
    F_STATUS INT DEFAULT 0, -- 0=待处理, 1=已处理, 2=失败
    F_ERROR NVARCHAR(MAX) NULL
);
```

```csharp
// 事件发布改为写入 Outbox 表（与业务操作同一事务）
public async Task PublishWithOutboxAsync<T>(T eventSource) where T : class
{
    // 写入 Outbox 表
    await _db.Insertable(new SysEventOutboxEntity
    {
        Id = IdGenerator.NextId(),
        EventType = typeof(T).Name,
        Payload = eventSource.ToJson(),
        CreatedAt = DateTime.Now,
        Status = 0
    }).ExecuteCommandAsync();
}

// 后台服务：OutboxProcessor（HostedService）
// 每 5 秒扫描 Outbox 表，投递待处理事件到消息队列
// 成功后更新状态为 1，失败累加重试次数
```

**影响面：** 新增 1 张表 + 1 个后台服务。现有事件发布逻辑逐步迁移到 Outbox 模式。
**工作量：** 5 天
**收益：** 事件不丢失，保证最终一致性。

## 改进效果量化

| 维度 | 改进前 | 改进后 | 提升幅度 |

## 不做的事情（明确排除）

| 改进项 | 排除原因 |
|--------|----------|
| 替换 SqlSugar → EF Core | 颠覆性改造，影响全部数据访问层 |
| 替换 DI 容器 → Autofac | 影响所有服务解析，需全面回归 |
| 引入模块化 DI 基类（ABP Module） | 需要重构所有模块入口，影响面过大 |
| 引入 CQRS 模式 | 架构范式变更，需重新设计数据流 |
| 引入 gRPC 内部通信 | 需要新增 Proto 文件和代码生成 |
| 引入分布式事务（Saga） | 复杂度高，当前场景不需要 |
| 修改 DynamicApiController 路由规则 | 前端全部 404 |
| 修改事件总线底层实现 | 影响所有事件订阅者 |
| 修改 RESTfulResult 包装逻辑 | 前端解析逻辑需同步修改 |
