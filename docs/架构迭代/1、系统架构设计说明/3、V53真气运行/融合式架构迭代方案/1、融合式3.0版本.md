## 一、清言方案的价值点提取与融合决策

### 1.1 必须融合的清言独有贡献

| 清言贡献                           | 融合到哪里         | 决策理由                                                     |
| ---------------------------------- | ------------------ | ------------------------------------------------------------ |
| **业务冻结期机制**                 | 阶段1-4执行期间    | 核心文件重构期间如果业务需求持续涌入，PR冲突会导致重构质量下降。冻结非紧急需求是手术成功的前提 |
| **测试门禁制度**                   | 每个基础文件修改后 | 清言强调"每一步独立可验证"，这一点比小米方案更严格。必须先有测试绿灯再合并 |
| **API路由/返回格式不动**           | 贯穿全程           | 368个代码生成模板 + 前端项目是产品护城河，任何路由或格式变更都是灾难级风险 |
| **TenantSafeUpdateAsync 扩展方法** | 阶段5的P0验证      | 在 Repository 重构完成后，为旧业务代码提供安全的过渡路径——新代码用新 Repository，旧代码用扩展方法 |
| **JWT Secret 环境变量优先**        | 阶段1同步执行      | 清言方案只改1行代码（环境变量优先读取），零风险高收益，应在阶段1就完成 |
| **[BypassOutbox] 旁路机制**        | 阶段5的事件管道    | 低价值日志（如审计日志写表）不应污染 Outbox 表，旁路机制防止表膨胀 |
| **Scrutor 替代自研扫描**           | 阶段3的模块系统    | 清言建议用成熟库替代自研扫描，减少维护负担。可在 JnpfModule 系统中集成 Scrutor |
| **CancellationToken 覆盖率提升**   | 阶段6-7渐进推进    | 清言指出这是提升系统韧性的低成本手段，每个 Sprint 覆盖一个模块 |
| **绞杀者无花果模式**               | 阶段5起            | 核心层重构完成后，新模块基于新体系开发，老模块逐步绞杀迁移，而非一次性切换 |
| **Swagger 分组配置**               | 阶段6作为独立任务  | 清言指出 Swagger 当前只有一个分组，按模块分组能提升开发者体验 |

### 1.2 清言方案中需要修正的条目

| 清言建议                                             | 修正决策                                   | 理由                                                         |
| ---------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| **"不修改 SqlSugarRepository 结构，仅新增扩展方法"** | **不采纳**                                 | Repository 构造函数的 16 项职责无法通过扩展方法解决，并发状态污染必须通过重构根治 |
| **"保持现有 AppStartup，逐步增强"**                  | **部分采纳**                               | 保留旧 AppStartup 并行运行（兼容性），但必须新建 JnpfModule 体系作为标准路径 |
| **"Outbox 作为可选策略"**                            | **修正为"默认策略 + [BypassOutbox] 豁免"** | 纯可选会导致业务人员继续使用不靠谱的内存事件。应默认走 Outbox，仅低价值事件豁免 |
| **"8周完成全部迭代"**                                | **不现实**                                 | 仅核心层重构（5个文件）+ 充分测试就需要 5-6 周。8周无法覆盖 OpenTelemetry、API版本控制等P2项 |

### 1.3 小米方案中需要吸收清言思想的修正

| 小米原方案                                         | 修正为                                                       | 理由                                                         |
| -------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **阶段5中 Refresh Token 和事件管道同一周并行开发** | **分开：事件管道先（第7周），Refresh Token 后（第8周）**     | 事件管道依赖 Outbox 表，与 Repository 重构后的 TenantContext 联动更紧密，应优先完成 |
| **阶段7一次性推进6个P2任务**                       | **分两个Sprint：先可观测性（7.1+7.6），后API治理（7.2+7.3+7.4+7.5）** | 清言的"每一步独立可验证"原则应贯彻到P2阶段，避免同时推进太多变更 |
| **App 静态类标记 [Obsolete]**                      | **暂不标记，仅通过 Analyzer 禁止新增调用**                   | 清言指出 86 处调用一次性迁移不现实，应先封堵增量，再逐步消化存量 |

### 任务 4.1 重构 SqlSugarRepository.cs（第5周）

**文件：** `JNPF.Extras.DatabaseAccessor.SqlSugar/SqlSugarRepository.cs`

**重构后的构造函数结构（~30行）：**

```
参数：
  ISqlSugarClient context
  ITenantContext tenantContext
  ITenantIsolationStrategy strategy

函数体：
  1. base.Context = context.CopyNew()  或直接赋值（取决于阶段1的评估结论）
  2. tenantContext.ResolveAsync()
  3. if (tenantContext.IsMultiTenant):
       切换到租户连接 scope
       strategy.ApplyQueryFilter(base.Context, tenantContext)
       strategy.ApplyWriteProtection(base.Context, tenantContext)
  4. if (tenantContext.IsMultiSystem && tenantContext.SystemId 非空):
       注册系统过滤器
       AppendDataExecutingHandler 追加系统写入回调
  5. 结束
```

**删除的代码：**
- `using var serviceScope = serviceProvider.CreateScope()`
- `App.GetConfig<ConnectionStringsOptions>(...)`
- `App.GetConfig<TenantOptions>(...)`
- `App.HttpContext` 直接引用
- `base.Context.Ado.CommandTimeOut = 30`
- `base.Context.Aop.OnLogExecuting = ...`
- `base.Context.Aop.OnError = ...`
- Oracle OnExecutingChangeSql
- `if (systemId == "orgSystem") return;`

### 任务 5.2 一体化事件可靠性管道（第7周）

**新建文件清单：**

```
JNPF.Extras.EventBus.RabbitMQ/
├── Outbox/
│   ├── EventOutboxMessage.cs
│   ├── IEventOutboxStore.cs
│   ├── SqlSugarEventOutboxStore.cs
│   └── EventOutboxDispatcher.cs
├── Retry/
│   ├── PollyRetryHandlerExecutor.cs
│   └── CircuitBreakerState.cs
└── Idempotency/
    ├── ProcessedEvent.cs
    ├── IdempotentEventHandler.cs
    └── BypassOutboxAttribute.cs    ← 清言方案融合：标记低价值事件跳过 Outbox
```

**管道设计：**
```
业务代码发布事件
       ↓
[是否标记 BypassOutbox?]
    是 → 直接投递到 EventBus（适用于低价值日志等）
    否 ↓
EventOutboxStore.WriteAsync()    ← 与业务操作同一事务
       ↓
EventOutboxDispatcher 轮询（每5秒）
       ↓
PollyRetryHandlerExecutor 投递   ← 指数退避 + 熔断
       ↓ 失败时
回到 Outbox，标记失败
       ↓ 超过最大重试
标记 DeadLetter                  ← 死信
       ↓ 成功时
IdempotentEventHandler 幂等检查
       ↓ 未处理过
执行事件处理器 → 写入 ProcessedEvent
```

**已有文件的最小改动：**
- `RetryEventHandlerExecutor.cs`：标记 `[Obsolete]`（保留向后兼容，不删除）
- `LogEventSubscriber.cs`：标记 `[BypassOutbox]`（低价值日志旁路）

**验收标准：**
- 模拟 EventBus 暂时不可用：事件持久化到 Outbox
- 恢复后自动投递
- 同一事件投递两次：第二次被幂等跳过
- 持续失败：退避递增 + 熔断
- 超过重试上限：标记死信
- [BypassOutbox] 标记的事件绕过 Outbox 直接投递

**预估工时：** 5 天
