## 千问评审 4 项微调的采纳决策

在集成之前，对每项微调进行逐条技术分析和裁决：

### 微调 1：AppendDataExecutingHandler 线程安全

**千问意见：** 禁止运行时动态修改委托链，改为启动时一次性组装，运行时通过读取 Scoped 的 ITenantContext 实现多租户逻辑。

**我的技术分析：**

千问的分析完全正确。原方案中 `AppendDataExecutingHandler` 的设计存在一个根本性的假设错误——它假设 Repository 构造函数中的 `AppendDataExecutingHandler` 调用是"线程安全"的，因为每个 Repository 实例有自己的 `CopyNew()` 上下文。但实际情况是：

- 如果 ISqlSugarClient 保持 Singleton（连接池共享），`CopyNew()` 返回的上下文实例的 Aop 属性是独立的，此时 Repository 构造函数中的赋值是安全的——但仅限于该上下文实例本身。
- 如果 ISqlSugarClient 改为 Scoped，每个请求的上下文是独立的，赋值也安全。
- **但真正的问题是：** `AppendDataExecutingHandler` 的设计意图是"追加"回调，但如果两个并发请求同时操作同一个上下文实例（Singleton 场景下极有可能），保存旧回调和赋值新回调之间存在竞态窗口。

千问提出的"启动时一次性组装完整委托链，运行时通过读取 Scoped 的 ITenantContext 来分支"是更优雅、更安全的设计。具体来说：

```
启动阶段（ConfigureServices）：
  组装一个完整的 DataExecuting 委托，内部逻辑为：
  1. 检查实体是否实现 ITenantFilter → 如果是，从 ITenantContext（Scoped）读取 TenantId 并自动写入
  2. 检查实体是否实现 IZxSystemFilter → 如果是，从 ITenantContext（Scoped）读取 SystemId 并自动写入
  3. 检查实体是否实现 ISoftDelete → 如果是，自动设置 IsDeleted = false（未来扩展）

运行阶段（每次数据库操作）：
  委托自动执行，通过 ITenantContext 读取当前请求的租户/系统信息
  无需在 Repository 构造函数中动态修改委托链
```

**裁决：完全采纳。** 这是比原方案更根本的解决方案。它将 `AppendDataExecutingHandler` 从"运行时链式追加"改为"启动时一次性组装 + 运行时上下文分支"，彻底消除了竞态条件。

**对开发计划的影响：**
- `AppendDataExecutingHandler` 方法的语义改变：不再是运行时追加的工具方法，而是启动时组装完整委托的工厂方法
- SqlSugarConfigureExtensions.cs 的修改内容需要调整
- SqlSugarRepository.cs 构造函数中不再需要调用 `AppendDataExecutingHandler`
- 这实际上让 Repository 构造函数**更简洁**了

### 微调 2：TenantContext 的 AsyncLocal 机制

**千问意见：** 引入 `AsyncLocal<TenantInfo>` 机制，解决后台任务/MQ 消费者等无 HttpContext 场景的租户上下文传播问题。

**我的技术分析：**

千问指出的问题是真实的。当前代码中 `LogEventSubscriber` 的处理方式是事件数据中携带 `TenantId`，然后通过 `_tenantManager.ChangTenant(db, log.TenantId)` 手动切换——这是一种 ad-hoc 方式，缺乏统一的上下文传播机制。

ABP vNext 的 `ICurrentTenant` 正是使用 `AsyncLocal` 来实现跨异步调用链的租户上下文传播。在 .NET 中，`AsyncLocal<T>` 保证在 `async/await` 调用链中值的正确流动（ExecutionContext 携带），这正是我们需要的。

但需要注意一个细节：`AsyncLocal` 的值在 `Task.Run` 或 `new Thread` 启动的新执行上下文中会被**拷贝**（而非共享），这意味着：

- HTTP 请求中的 `AsyncLocal` 值在请求管道内正确流动
- 后台任务如果通过 `Task.Run` 启动，需要在启动前显式设置 `AsyncLocal` 值
- EventBus 消费者需要在消费时从事件数据中提取 TenantId 并设置到 `AsyncLocal`

**裁决：完全采纳。** 这是 .NET 中处理跨执行上下文状态传播的标准模式。

**具体设计补充：**

```
TenantContext 内部结构：

public class TenantContext : ITenantContext
{
    private static readonly AsyncLocal<TenantInfo> _current = new();
    
    public string TenantId => _current.Value?.TenantId;
    public string SystemId => _current.Value?.SystemId;
    // ... 其他属性
    
    // HTTP 请求入口：中间件调用
    public void SetFromHttpContext(HttpContext httpContext) { ... }
    
    // 后台任务入口：任务启动前调用
    public void SetExplicit(string tenantId, string systemId) { ... }
    
    // EventBus 消费者入口：事件处理前调用
    public void SetFromEvent(LogEventSource logEvent) { ... }
    
    // 退出时清理（using 模式）
    public IDisposable BeginScope(TenantInfo info) { ... }
}
```

### 微调 3：CopyNew() 的连接池压测基准

**千问意见：** 在阶段 0 增加连接池压测基准，阶段 4 验证时必须包含高并发压测。

**我的技术分析：**

这个建议是务实的风险控制措施。`CopyNew()` 的实际行为取决于 SqlSugar 的内部实现——它可能创建新的连接实例（从连接池获取），也可能共享底层连接。在没有实际压测数据之前，无法判断其在高并发下的表现。

但需要指出：连接池耗尽的风险不仅来自 `CopyNew()`，更根本的原因是 Repository 构造函数中 `CreateScope()` 的滥用（已在阶段 4 重构中消除）。`CopyNew()` 只是创建了 SqlSugar 内部的上下文副本，不一定会创建新的 ADO.NET 连接——连接的实际获取是在执行 SQL 时才发生的。

**裁决：采纳。** 将压测作为阶段 0 和阶段 4 的正式交付物，但调整压测目标和阈值：

- 阶段 0：获取基线数据（当前架构下的连接池使用情况、响应时间 P50/P95/P99）
- 阶段 4：对比测试（重构后同一压测场景下的数据，差异不超过 10% 为通过）
- 压测工具：优先使用 wrk（轻量级），复杂场景用 JMeter
- 压测并发数：500 并发，持续 60 秒

### 微调 4：Outbox 轮询升级为"信号量唤醒 + 兜底轮询"

**千问意见：** 用 Channel<T> 替代纯定时轮询，引入分布式锁防止多实例重复消费。

**我的技术分析：**

千问的建议在多实例部署场景下是正确的。但需要根据 JNPF 的实际部署模式做差异化处理：

**当前现实：** 根据 sln 结构（单体架构，51 个项目编译为一个进程），JNPF V5.2 目前是**单实例部署**。多实例（K8s 多 Pod）是未来可能的部署模式，但不是当前的首要场景。

**差异化方案：**

| 部署模式       | Outbox 投递策略                      | 适用阶段 |
| -------------- | ------------------------------------ | -------- |
| 单实例（当前） | Channel<T> 信号量唤醒 + 30秒兜底轮询 | 阶段 5   |
| 多实例（未来） | 上述 + Redis SETNX 分布式锁          | 未来按需 |

对于单实例场景，`Channel<T>` 方案已经足够：

```
EventOutboxStore.WriteAsync():
  1. 写入数据库
  2. _channel.Writer.TryWrite(wakeupSignal)

EventOutboxDispatcher.ExecuteAsync():
  while (!stoppingToken.IsCancellationRequested)
  {
      // 优先等待信号
      var received = await _channel.Reader.WaitToReadAsync(
          stoppingToken).AsTask()
          .WaitAsync(TimeSpan.FromSeconds(30));  // 30秒兜底
      
      // 处理 Pending 消息
      await ProcessPendingMessages();
  }
```

对于多实例场景，增加 Redis 分布式锁：
```
// 获取锁
var lockKey = "jnpf:outbox:dispatch:lock";
var acquired = await _redis.StringSetAsync(lockKey, instanceId, 
    TimeSpan.FromSeconds(30), When.NotExists);
if (!acquired) return;  // 其他实例正在处理
```

**裁决：采纳，但分两步实施。** 阶段 5 实现 Channel<T> + 兜底轮询（单实例版），多实例分布式锁作为未来扩展点预留接口。

### 阶段 1 变更：AppendDataExecutingHandler 设计重写

#### 任务 1.1 修正：SqlSugarConfigureExtensions.cs 增强

**文件：** `SqlSugarConfigureExtensions.cs`

**关键设计变更（千问微调 1）：**

原方案中的 `AppendDataExecutingHandler` 是一个**运行时**链式追加方法。新方案将其改为**启动时一次性组装**的工厂方法。

**新设计的 `ConfigureGlobalDataExecuting` 方法：**

```
方法签名：
  public static void ConfigureGlobalDataExecuting(
      SqlSugarScopeProvider db, 
      IServiceProvider serviceProvider)

实现逻辑：
  db.Aop.DataExecuting = (oldValue, entityInfo) =>
  {
      // 从 Scoped 的 ITenantContext 获取当前请求的上下文
      var httpContext = serviceProvider.GetService<IHttpContextAccessor>()?.HttpContext;
      ITenantContext tenantContext = null;
      
      // 优先从请求的 Scoped 服务获取
      if (httpContext?.RequestServices != null)
          tenantContext = httpContext.RequestServices.GetService<ITenantContext>();
      
      // 维度1：租户字段自动写入
      if (tenantContext?.IsMultiTenant == true 
          && typeof(ITenantFilter).IsAssignableFrom(entityInfo.EntityValue.GetType()))
      {
          if (entityInfo.PropertyName == "TenantId" 
              && entityInfo.OperationType is DataFilterType.InsertByObject 
                                          or DataFilterType.UpdateByObject 
                                          or DataFilterType.DeleteByObject)
          {
              entityInfo.SetValue(tenantContext.IsolationFieldValue);
          }
      }
      
      // 维度2：系统字段自动写入
      if (tenantContext?.IsMultiSystem == true 
          && !string.IsNullOrEmpty(tenantContext.SystemId)
          && typeof(IZxSystemFilter).IsAssignableFrom(entityInfo.EntityValue.GetType()))
      {
          if (entityInfo.PropertyName == "ZxSystemId" 
              && entityInfo.OperationType is DataFilterType.InsertByObject 
                                          or DataFilterType.UpdateByObject 
                                          or DataFilterType.DeleteByObject)
          {
              entityInfo.SetValue(tenantContext.SystemId);
          }
      }
      
      // 维度3：软删除自动写入（未来扩展点）
      // if (typeof(ISoftDelete).IsAssignableFrom(...)) { ... }
  };
```

**核心变化点：**

| 原方案（v3.0）                          | 新方案（v4.0）                                       |
| --------------------------------------- | ---------------------------------------------------- |
| `AppendDataExecutingHandler` 运行时追加 | `ConfigureGlobalDataExecuting` 启动时一次组装        |
| 委托链在 Repository 构造函数中动态构建  | 完整委托在 Startup/Module 阶段一次性赋值             |
| 多维度过滤器各自注册回调，链式串联      | 统一委托内部通过类型检查分支处理多维度               |
| 依赖运行时调用顺序                      | 无顺序依赖，所有维度在同一委托中并列处理             |
| 有竞态条件风险                          | 无竞态条件（委托不可变，上下文通过 Scoped 服务读取） |

**调用时机：** 在 `SetDbAop` 方法末尾调用 `ConfigureGlobalDataExecuting(db, serviceProvider)`。

**移除：** 原 `AppendDataExecutingHandler` 方法不再需要。

**本次修改后，此文件封存。**

**预估工时：** 2 天（含 `ConfigureGlobalDataExecuting` 的单元测试）

### 阶段 2 变更：TenantContext 引入 AsyncLocal

#### 任务 2.3 修正：TenantContext 服务族

**关键设计变更（千问微调 2）：**

`TenantContext` 内部引入 `AsyncLocal<TenantInfo>` 作为跨执行上下文的租户信息传播机制。

**修正后的 `TenantContext.cs` 核心结构：**

```
public class TenantContext : ITenantContext
{
    // AsyncLocal：跨 async/await 调用链传播租户信息
    private static readonly AsyncLocal<TenantInfo> _asyncLocal = new();
    
    private readonly IHttpContextAccessor _httpContextAccessor;
    private readonly ICacheManager _cacheManager;
    private readonly IOptions<TenantOptions> _tenantOptions;
    private readonly IOptions<ConnectionStringsOptions> _connectionOptions;
    
    // 优先级：AsyncLocal > HttpContext > 默认值
    public string TenantId => _asyncLocal.Value?.TenantId 
        ?? ResolveFromHttpContext()?.TenantId 
        ?? _connectionOptions.Value.DefaultConnectionConfig.ConfigId.ToString();
    
    public string SystemId => _asyncLocal.Value?.SystemId 
        ?? ResolveSystemFromHttpContext();
    
    public bool IsMultiTenant => _tenantOptions.Value.MultiTenancy;
    public bool IsMultiSystem => _tenantOptions.Value.MultiSystem;
    // ... 其他属性类似
    
    // === 入口点1：HTTP 请求（中间件调用） ===
    public void SetFromHttpContext(HttpContext httpContext)
    {
        var tenantId = httpContext?.User.FindFirst("TenantId")?.Value;
        var systemId = httpContext?.User.FindFirst("ZxSystemId")?.Value;
        var userId = httpContext?.User.FindFirst("UserId")?.Value;
        
        // 从缓存解析连接配置
        var tenantConnection = ResolveTenantConnection(tenantId);
        
        _asyncLocal.Value = new TenantInfo
        {
            TenantId = tenantId,
            SystemId = systemId ?? ResolveSystemFromCache(userId),
            ConnectionConfigId = tenantConnection?.ConfigId,
            IsolationType = tenantConnection?.IsolationType ?? 0,
            IsolationFieldValue = tenantConnection?.IsolationField
        };
    }
    
    // === 入口点2：后台任务 / 定时器（任务启动前调用） ===
    public void SetExplicit(string tenantId, string systemId = null)
    {
        var tenantConnection = ResolveTenantConnection(tenantId);
        _asyncLocal.Value = new TenantInfo
        {
            TenantId = tenantId,
            SystemId = systemId,
            ConnectionConfigId = tenantConnection?.ConfigId,
            IsolationType = tenantConnection?.IsolationType ?? 0,
            IsolationFieldValue = tenantConnection?.IsolationField
        };
    }
    
    // === 入口点3：EventBus 消费者（事件处理前调用） ===
    public void SetFromEvent(LogEventSource logEvent)
    {
        SetExplicit(logEvent.TenantId, logEvent.SystemId);
    }
    
    // === 作用域管理（using 模式，退出时自动恢复） ===
    public IDisposable BeginScope(TenantInfo info)
    {
        var previous = _asyncLocal.Value;
        _asyncLocal.Value = info;
        return new DisposableAction(() => _asyncLocal.Value = previous);
    }
    
    // === AsyncLocal 值对象 ===
    private class TenantInfo
    {
        public string TenantId { get; set; }
        public string SystemId { get; set; }
        public string ConnectionConfigId { get; set; }
        public int IsolationType { get; set; }
        public string IsolationFieldValue { get; set; }
    }
}
```

**新增入口点的使用场景：**

| 场景          | 调用方式                                | 示例                                    |
| ------------- | --------------------------------------- | --------------------------------------- |
| HTTP 请求     | 中间件中调用 `SetFromHttpContext`       | `app.UseMiddleware<TenantMiddleware>()` |
| 定时任务      | 任务开始时调用 `SetExplicit`            | `tenantContext.SetExplicit("tenant_a")` |
| EventBus 消费 | 消费前调用 `SetFromEvent`               | `tenantContext.SetFromEvent(logEvent)`  |
| 临时切换租户  | `using (tenantContext.BeginScope(...))` | 管理员查看其他租户数据                  |

**新增文件：**

```
TenantContext/
├── ITenantContext.cs                    — 新增 SetExplicit、SetFromEvent、BeginScope 方法
├── TenantContext.cs                     — AsyncLocal 实现
├── TenantInfo.cs                        — AsyncLocal 值对象
├── TenantMiddleware.cs                  — HTTP 请求入口中间件
├── DisposableAction.cs                  — using 模式辅助类
├── ITenantResolver.cs                   — （不变）
├── ClaimTenantResolver.cs               — （不变）
├── CacheTenantResolver.cs               — （不变）
├── ITenantIsolationStrategy.cs          — （不变）
├── ColumnIsolationStrategy.cs           — （不变）
└── SchemaIsolationStrategy.cs           — （不变）
```

**与阶段 1 的 `ConfigureGlobalDataExecuting` 的联动：**

阶段 1 组装的全局 `DataExecuting` 委托内部通过 `ITenantContext`（从 `httpContext.RequestServices.GetService<ITenantContext>()` 获取）读取当前租户信息。由于 `ITenantContext` 是 Scoped 的，且内部使用 `AsyncLocal`，无论在 HTTP 请求还是后台任务中，都能正确获取当前租户的上下文。

### 阶段 4 变更：Repository 重构 + 压测验证

#### 任务 4.1 修正：SqlSugarRepository.cs 重构

**关键设计变更（千问微调 1 的下游影响）：**

由于阶段 1 将 `DataExecuting` 的组装从"运行时"改为"启动时"，Repository 构造函数中**不再需要调用 `AppendDataExecutingHandler`**。

**修正后的构造函数结构（~25行，比原方案更简洁）：**

```
构造函数参数：
  ISqlSugarClient context
  ITenantContext tenantContext
  ITenantIsolationStrategy strategy

构造函数体：
  第1步：获取隔离上下文
    base.Context = context.CopyNew()  // 或直接赋值（取决于阶段1评估）
  
  第2步：应用租户隔离
    if (tenantContext.IsMultiTenant && !tenantContext.IsDefaultTenant())
    {
        // 切换到租户连接 scope
        base.Context = base.Context.AsTenant()
            .GetConnectionScope(tenantContext.ConnectionConfigId);
        
        // 通过策略应用查询过滤器
        strategy.ApplyQueryFilter(base.Context, tenantContext);
    }
  
  第3步：应用系统过滤
    if (tenantContext.IsMultiSystem && !string.IsNullOrEmpty(tenantContext.SystemId))
    {
        base.Context.QueryFilter.AddTableFilter<IZxSystemFilter>(
            it => it.ZxSystemId == tenantContext.SystemId);
    }
  
  第4步：结束
    // DataExecuting（租户/系统字段自动写入）已在启动时通过
    // ConfigureGlobalDataExecuting 全局配置，此处不需要任何 AOP 操作
    // SQL日志、超时、Oracle适配、DiffLog 也已在 SqlSugarConfigureExtensions 中全局配置
```

**对比 v3.0 方案的进一步简化：**

| v3.0 构造函数                          | v4.0 构造函数                                                |
| -------------------------------------- | ------------------------------------------------------------ |
| ~30 行                                 | ~25 行                                                       |
| 包含 `AppendDataExecutingHandler` 调用 | 不包含任何 AOP 操作                                          |
| 租户写保护通过运行时追加回调           | 租户写保护通过启动时全局委托 + Scoped 上下文                 |
| 系统写保护通过运行时追加回调           | 系统查询过滤器仍通过 QueryFilter 注册（仅读保护），写保护由全局委托处理 |

### 阶段 5 变更：Outbox 投递策略升级

#### 任务 5.2 修正：一体化事件管道

**关键设计变更（千问微调 4）：**

将 `EventOutboxDispatcher` 的纯定时轮询改为"信号量唤醒 + 兜底轮询"。

**修正后的 `EventOutboxDispatcher` 核心逻辑：**

```
public class EventOutboxDispatcher : BackgroundService
{
    private readonly Channel<bool> _wakeupChannel = Channel.CreateBounded<bool>(1);
    private readonly IEventOutboxStore _outboxStore;
    private readonly IEventBus _eventBus;
    private readonly TimeSpan _fallbackInterval = TimeSpan.FromSeconds(30);
    private readonly int _batchSize = 50;
    
    // 业务代码写入 Outbox 后调用此方法唤醒 Dispatcher
    public void NotifyNewMessage()
    {
        _wakeupChannel.Writer.TryWrite(true);
    }
    
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                // 优先等待唤醒信号，30秒兜底
                using var cts = CancellationTokenSource
                    .CreateLinkedTokenSource(stoppingToken);
                cts.CancelAfter(_fallbackInterval);
                
                try
                {
                    await _wakeupChannel.Reader.WaitToReadAsync(cts.Token);
                }
                catch (OperationCanceledException) when (!stoppingToken.IsCancellationRequested)
                {
                    // 超时，执行兜底轮询
                }
                
                // 处理 Pending 消息
                await ProcessPendingMessages(stoppingToken);
            }
            catch (Exception ex)
            {
                Log.Error(ex, "Outbox dispatcher error");
                await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
            }
        }
    }
    
    private async Task ProcessPendingMessages(CancellationToken ct)
    {
        var messages = await _outboxStore.GetPendingAsync(_batchSize);
        foreach (var message in messages)
        {
            // 使用 PollyRetryHandlerExecutor 投递
            // 投递成功 → MarkCompleted
            // 投递失败 → MarkFailed（重试计数+1）
            // 超过最大重试 → MarkDeadLetter
        }
    }
}
```

**`SqlSugarEventOutboxStore.WriteAsync` 修改：**

```
public async Task WriteAsync(string eventName, object payload)
{
    // 1. 写入 Outbox 表（与业务操作在同一事务中）
    await _db.Insertable(new EventOutboxMessage { ... }).ExecuteCommandAsync();
    
    // 2. 唤醒 Dispatcher
    _dispatcher.NotifyNewMessage();
}
```
