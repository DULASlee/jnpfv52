# 第三阶段审查意见

## 这是切面二最有价值的发现

**CurrentUser 接口执行 35-45 次串行 SQL，占登录总耗时 45%。** 这就是"一分钟登录"的后端主因。

三个问题叠加在一起：

```
问题1：N+1 查询 × 3处
  → 把本该 1 次 SQL 完成的事拆成了 N 次

问题2：缓存写了不读
  → GetUserInfo() 写了缓存，GetCurrentUser() 直接绕过查库

问题3：全部串行 await
  → 35-45 次 SQL 按序排队，每条 10-100ms，累计 500ms-4.5s
```

**慢数据库场景下的真实计算：**
- 45 条 SQL × 100ms/条 = 4.5 秒（仅 CurrentUser）
- 加上 Login 接口 500ms
- 加上 vendor chunk 下载解析 2-3 秒
- 加上网络延迟
- 总计 8-12 秒是正常的，数据库再差一点确实能到十几秒

用户说"一分钟"有感知放大成分，但 10+ 秒的等待对登录页来说已经完全不可接受。

## 第四阶段：优化方案编制

**工程师开工指令：**

基于前三阶段的发现，编制具体的优化方案。**按以下优先级排列，每个优化项必须包含：改动文件、改动方式、预估工作量、预期收益、风险。**

### P0 项（本周必须完成）

**P0-1：CurrentUser N+1 查询消除**

当前：3 个 N+1 问题导致 35-45 次 SQL。
目标：减少到 5-8 次 SQL。

具体要求：
1. `UserManager.cs:453-458` 的 `GetSubsidiary()` foreach 循环 → 改为批量查询（一次 SQL 取所有子级）
2. `OAuthService.cs:434-458` 的 `GetUserModuleListByIds()` for 循环 → 改为一次 IN 查询
3. `UserManager.cs:2121` 的 `GetRoleNameByIds()` 全表加载 → 改为按 ID 列表查询

**P0-2：CurrentUser 缓存修复**

当前：`GetUserInfo()` 写缓存，`GetCurrentUser()` 不读。
目标：CurrentUser 走缓存，命中时直接返回。

具体要求：
1. 分析缓存 Key 的组成（UserId + TenantId？）
2. 确认缓存失效策略（权限变更时如何清除？）
3. 给出修复方案

**P0-3：前端 vendor 分包**

当前：60+ 全局组件打入单一 4.5MB chunk。
目标：登录页只加载需要的 ~200KB。

具体要求：
1. `registerGlobComp.ts` 中的重型组件（Tinymce、ECharts、Monaco）改为动态 `import()` 懒加载
2. 配置 `manualChunks` 将 `ant-design-vue`、`vue`、`echarts`、`monaco-editor` 拆成独立 chunk
3. 全局注册改为按需引入

### P1 项（两周内完成）

**P1-1：CurrentUser 子查询并行化**

当前：5 个子查询串行 await。
目标：改为 `Task.WhenAll` 并行。

具体要求：
1. 确认 5 个子查询之间是否有数据依赖
2. 确认 SqlSugarScope 并发查询的线程安全性（切面一已确认 SqlSugarScope 是线程安全的单例）
3. 给出并行化代码方案

**P1-2：getLoginConfig 缓存**

当前：每次打开登录页都查库。
目标：加缓存，TTL 建议 1 小时。
