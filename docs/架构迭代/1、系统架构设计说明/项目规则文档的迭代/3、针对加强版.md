# 文件二：`.claude/rules/jnpf-expert-traps.md`

```markdown
# JNPF 专家陷阱与保命指南

这些是 JNPF 框架中违反 .NET 通用直觉的真实陷阱。每一个都是"不告诉你，你死也想不通为什么报错"的血泪教训。

---

## 陷阱 1：DynamicApiController 路由绑定 — 改名 = 生产事故

- **你会做什么**：重命名 Service 方法（如 GetUser → GetUserDetail），认为这是无害的重构
- **实际后果**：JNPF API 路由由 `{类名}/{方法名}` 自动生成。改名 = URL 变了 = 前端所有 API 调用 404 = 工作流节点绑定断裂 = 生产事故
- **保命规则**：NEVER 重命名已发布的 Service 类或公共方法。MUST 重命名时，先 Grep 前端 api 文件和工作流定义中的 URL 引用，全部同步修改

---

## 陷阱 2：Mapster Adapt() 审计字段覆盖 — 一行代码篡改所有审计信息

- **你会做什么**：`input.Adapt<Entity>()` 优雅映射，直接存库
- **实际后果**：Adapt() 会把 InputDto 中同名字段（包括 CreateTime、CreateUserId、TenantId）全部覆盖到 Entity 上。Update 操作如果不处理，原记录的创建时间和创建人被篡改
- **保命规则**：Update 操作 ALWAYS 先 `var entity = await db.Queryable<T>().InSingleAsync(id)` 查出原实体，再 `input.Adapt(entity)` 或用 `.Ignore(dest => dest.CreateTime)` 排除审计字段。NEVER 直接 `db.Updateable(input.Adapt<T>())` 全量覆盖

---

## 陷阱 3：SqlSugar 导航属性序列化 — 没写循环也炸 N+1

- **你会做什么**：查出列表后直接 return，认为没有循环就不会有 N+1
- **实际后果**：SqlSugar 导航属性默认懒加载。列表返回后 JSON 序列化器访问每个实体的导航属性时，每个属性触发一次数据库查询。100 条记录 × 3 个导航属性 = 300 次查询
- **保命规则**：列表查询 ALWAYS 使用 `.Includes(o => o.User, o => o.Department)` 预加载，或用 `.Select(x => new ListOutput { ... })` 投影到 DTO（DTO 无导航属性）。NEVER 返回含导航属性的裸实体列表

---

## 陷阱 4：Oops.Bah vs Oops.Oh — 用错 = 用户看到"服务器内部错误"

- **你会做什么**：业务校验失败时随便 throw 一个异常
- **实际后果**：Oops.Bah("用户名已存在") → HTTP 200 + 业务错误码 + 前端显示 msg。Oops.Oh("用户名已存在") → HTTP 500 + 错误日志 + 前端显示"服务器内部错误"。用错了用户永远看不到真正的错误原因
- **保命规则**：用户操作导致的业务错误（校验失败、规则冲突、权限不足、数据不存在）→ Oops.Bah。系统内部故障（数据库连接失败、外部服务超时）→ Oops.Oh。NEVER 混用

---

## 陷阱 5：RESTfulResult 双重包装 — 数据嵌套两层，前端解析崩溃

- **你会做什么**：手动返回 `new RESTfulResult<T> { code = 200, data = result }`，觉得更可靠
- **实际后果**：JNPF 框架自动将所有返回值包装为 RESTfulResult<T>。你手动包装后，框架再包一层。前端拿到 `{ code: 200, data: { code: 200, data: 真正的数据 } }`，解析时取到的是内层对象
- **保命规则**：直接 `return result` 或 `return PageResult<T>`。NEVER 手动 new RESTfulResult。框架已自动处理

---

## 陷阱 6：Async 后缀破坏路由 — GetListAsync ≠ GetList

- **你会做什么**：遵循 C# 异步命名规范，命名为 GetPageListAsync
- **实际后果**：DynamicApiController 用全名生成路由。`GetPageListAsync` → `/api/xxx/GetPageListAsync`。前端已绑定 `/api/xxx/GetPageList`，直接 404
- **保命规则**：IDynamicApiController 接口方法 NEVER 加 Async 后缀。即使实现内部 async/await，接口方法名保持 `GetPageList`、`GetInfo`、`Add`、`Update`、`Delete`

---

## 陷阱 7：ITenantFilter 在子查询中失效 — 数据泄露无声无息

- **你会做什么**：写子查询或 Join 时假设 ITenantFilter 自动生效
- **实际后果**：ITenantFilter 只在主 Queryable 上自动应用。子查询、Join、Union、Ado.SqlQuery 不自动带租户过滤。数据泄露不会报错，只会静默返回其他租户的数据
- **保命规则**：涉及子查询或原生 SQL 时，ALWAYS 手动加 `.Where(x => x.TenantId == tenantId)`。写完后验证生成的 SQL 是否包含 TenantId 条件

---

## 陷阱 8：Updateable/Deleteable 不自动过滤租户 — 一个 Update 改了全租户的数据

- **你会做什么**：`db.Updateable(entity).ExecuteCommand()`，假设和 Queryable 一样自动带租户条件
- **实际后果**：SqlSugar 的 ITenantFilter 只对 Queryable 自动生效。Updateable/Deleteable 的 WHERE 条件中不自动包含 TenantId。如果不显式指定，可能更新到所有租户的数据
- **保命规则**：写操作 ALWAYS 显式指定租户条件：`db.Updateable(entity).Where(x => x.TenantId == tenantId).ExecuteCommand()`

---

## 陷阱 9：Service 类的 public 方法 = API 端点 — 辅助方法也会暴露

- **你会做什么**：在 Service 类中写一个 public 辅助方法供其他方法调用
- **实际后果**：DynamicApiController 将实现类的所有 public 方法都映射为 API 端点。你的"内部辅助方法"变成了一个公开可访问的 API
- **保命规则**：内部辅助方法 MUST 声明为 private 或 protected。NEVER 在 IDynamicApiController 实现类中暴露不需要对外的 public 方法

---

## 陷阱 10：EventBus 至少一次投递 — 同一个订单触发了两次工作流

- **你会做什么**：发布事件后假设处理器只执行一次
- **实际后果**：RabbitMQ 保证至少一次投递（at-least-once），Channel 进程内模式在异常重试时也可能重复执行。用户下了单，触发了两次工作流实例
- **保命规则**：事件处理器 MUST 实现幂等 — 先查询目标状态或检查已处理的 EventId 再执行业务逻辑。NEVER 假设事件只执行一次

---

## 陷阱 11：Mapster 循环引用栈溢出 — 带导航属性的实体直接 Adapt 爆炸

- **你会做什么**：`entity.Adapt<Dto>()` 用于所有映射场景
- **实际后果**：JNPF 实体常见循环引用（User → Department → Users → Department...）。Mapster 默认配置下无限递归直到栈溢出
- **保命规则**：映射含导航属性的复杂实体时，ALWAYS 使用 `.Select()` 投影到 DTO，或配置 Mapster 的 `MaxDepth` 限制递归深度。NEVER 直接 Adapt 含循环引用的实体图

---

## 陷阱 12：.vm 模板是 Velocity 语法 — 在模板里写 C# 会生成无效代码

- **你会做什么**：在 .vm 模板中使用 C# 语法 `if (x == null)` 或 `foreach (var item in list)`
- **实际后果**：Apache Velocity 使用完全不同的语法。C# 语法在模板中被当作纯文本输出，生成的代码是无效的 C#，编译报错
- **保命规则**：修改 .vm 模板前 ALWAYS 先 Read 一个现有工作的模板学习结构。Velocity 语法：`#if($entity.Name)` / `#foreach($field in $fields)` / `#set($x = "value")` / `$entity.Name`
```
