# 架构深潜之总纲

现在我希望请一位低代码行业的资深专家对我们现有的JNPF低代码框架针对低代码行业2025年主流行业水平，以及跟宜搭，葡萄城活字格，简道云和钉钉低代码等竞品做一个架构和框架功能的深入分析，提出最必须改进的几个功能我应该如何做？我记得你前面对3.6版本升级到5.2版本做过一次深入分析，我们是否也可以提示这位资深专家运用你上次的方法来进行这一次的分析？下面的专家建议我觉得技术上是有参考价值，但是缺乏系统级产品的深度和格局。我们应该深挖现有技术架构的缺陷和现有功能的残缺和不完整。我们应该从框架现有应用功能的完整性、稳定性、可靠性、可用性等用户实际使用体验上提升。在技术架构上，要对现有框架的现有技术架构进一步的优化和提升，从基础设施层、服务层、应用层、代码生成的可靠性完整性，代码生成的性能上进行提升，譬如说日志记录的清晰完整，项目现有的日志记录似乎还有点混乱，很不好排查故障，系统启动后登录页面渲染很慢，需要一分多钟还看不到登录界面完全显示。从现有框架的现有的功能上来说，还要对现有应用功能进一步的完善，譬如数字大屏的组件完整性，数据的渲染能力，是否支持监控视频回放，对uniapp来说，是否能更好的支持代码的生成和部署，能否更好的排除跨端部署的兼容性。全部都是要针对现有的进行向下钻探，从底层架构上进行优化提升，从现有功能的好用程度进行提升。现有专家的建议，简直就是一种徒有其表的分析，完全缺乏saas级系统级软件项目开发经验。甚至对底层优化，提都没提到，让我非常失望。



我完全理解你的失望。那位专家的分析本质上是"功能清单对比+战略建议PPT"，而不是真正的**技术尽职调查**。它在做的事情是"你有什么、别人有什么、你还缺什么"，而不是"你的东西为什么不好用、哪里有结构性缺陷、怎么从根上改"。

下面我帮你写一份**专家分析工作指引（SOW）**，你可以直接交给下一位专家，明确告诉他分析方法论、钻探深度、交付标准。这份指引会融入你提到的所有痛点，也会参照我之前对3.6→5.2版本升级分析时的框架。

## JNPF V5.2 深度架构审计与改进分析 — 专家工作指引

### 一、分析定位：这不是竞品对标，而是架构审计

**核心要求：** 本次分析不是做一份"行业报告"或"战略建议书"，而是对 JNPF V5.2 进行一次**产品级技术架构审计**，目标是：

- 找出框架中**真实存在的技术缺陷**，而非罗列"还缺什么功能"
- 评估每个缺陷对**最终用户实际使用体验**的影响程度
- 给出**可落地、有优先级、有工程量评估**的改进方案
- 与竞品的对比必须深入到**架构机制层面**，而非功能表面对勾

**分析哲学：向下钻探，不要横向铺开。** 与其说"缺AI能力"，不如先搞清楚"登录页为什么要一分钟才能渲染出来"。前者是战略畅想，后者才是工程师要解决的问题。

### 二、分层审计框架（必做）

请专家按照以下六层架构逐层审计，每一层都必须回答三个问题：**现状是什么、问题是什么、怎么改。**

#### 第一层：基础设施层

| 审计项                 | 具体要求                                                     |
| ---------------------- | ------------------------------------------------------------ |
| **启动性能**           | 系统冷启动到登录页完全可交互的全链路耗时分析。逐阶段拆解：应用初始化 → DI容器注册 → 数据库连接池 → 中间件管道 → 首次HTTP响应 → 前端资源加载 → 页面渲染完成。定位瓶颈在后端启动、前端构建产物、还是网络加载 |
| **日志体系**           | 审计现有日志实现：日志框架选型（Serilog/NLog/内置ILogger）、日志级别划分是否合理、结构化日志是否完整（含TraceId/RequestId/UserId/TenantId）、日志输出目标（文件/控制台/ELK）、日志采样与轮转策略。**重点**：当前日志是否"混乱"？能否根据TraceId串联一次完整请求的全链路？故障排查时能否快速定位问题模块？ |
| **异常处理**           | 全局异常处理中间件是否完整？是否所有未捕获异常都能被拦截并记录？异常信息是否包含足够的上下文（请求路径、参数、用户信息）？是否有异常分类（业务异常/系统异常/第三方异常）和分级响应策略？ |
| **配置管理**           | 配置项是否集中管理？环境隔离（dev/staging/prod）是否清晰？敏感配置（数据库密码、密钥）是否有加密或外部化管理？热更新能力？ |
| **数据库连接与连接池** | SqlSugar连接池配置是否合理？多数据库切换时连接管理是否正确？连接泄露检测？慢SQL监控是否具备？ |
| **缓存策略**           | Redis/内存缓存的使用场景、缓存穿透/击穿/雪崩的防护、缓存与数据库的一致性策略 |
| **依赖健康**           | NuGet依赖版本是否合理？是否有已知漏洞的依赖？.NET版本升级路径（当前.NET 6，2024年11月已EOL） |

### 四、必须回答的"硬问题清单"

以下问题源自团队实际使用中的痛点，**每个问题都必须给出定位分析和改进建议**：

1. **登录页渲染问题**：系统启动后登录页面渲染需要一分钟以上才能完全显示，请从后端启动流程、前端构建产物大小、首屏请求链路、资源加载策略四个维度定位根因并给出优化方案
2. **日志排查困难**：当前日志记录"混乱"，请评估日志体系的完整性，给出从混乱到可观测的具体改造方案（含结构化日志规范、TraceId串联方案、日志分级策略）
3. **代码生成后的可运行性**：生成的代码是否能真正"开箱即用"？还是需要大量手动修改？请测试至少5种复杂场景的代码生成并记录所有需要手动修改的地方
4. **UniApp跨端部署**：代码生成的UniApp代码在HBuilderX中的编译成功率、各端（H5/iOS/Android/微信小程序）的兼容性问题清单
5. **数据大屏视频能力**：DataV组件是否支持监控视频接入？支持哪些流协议？是否有视频回放能力？与海康/大华等主流监控设备的兼容性？
6. **大数据量场景**：表单/列表在万级、十万级数据量下的性能表现（查询速度、渲染速度、导出速度）
7. **并发场景**：多用户同时编辑同一表单/流程时的数据一致性保障机制
8. **升级与迁移**：从低版本升级到V5.2时，存量数据和配置的兼容性情况；未来升级的平滑度

## 一、基础设施层五个切面的推进顺序

顺序设计的核心原则：**先造尺子，再量东西。**

```
切面1：日志与可观测性基础设施
  ↓  ← 建立度量能力，让后续所有优化都有数据支撑
切面2：应用启动与冷启动性能
  ↓  ← 用切面1建立的TraceId/指标体系来定位启动慢的根因
切面3：请求管道与热路径性能（含CurrentUser聚合、RequestActionFilter）
  ↓  ← 启动优化完成后，优化每次请求的执行效率
切面4：数据库层与数据访问（SqlSugar配置、连接池、慢SQL、迁移安全）
  ↓  ← 数据库通常是最终瓶颈，放在这里是因为前面三层的优化会改变DB调用模式
切面5：安全基础设施（JWT管理、限流、注入防护、XSS）
  ← 安全加固独立于性能优化，但需要前面四层稳定后再做
```

**为什么日志排第一？** 你去优化登录慢，优化完了怎么证明快了？快了多少？瓶颈到底在后端启动还是前端打包还是接口串行？如果靠"感觉好像快了一点"来判断，那就是在做玄学工程。日志和可观测性就是那把尺子——先把尺子造好，后面的每次优化才能被度量、被验证、被持续监控。

## 切面1初步源码结论

### 1. JNPF 当前不是“没日志”，而是“多套日志互不贯通”

当前至少有这些日志通道：

- 文件日志：`Startup.cs` 中 `AddFileLogging` 按 `Information/Warning/Error` 拆 3 个文件。
- 控制台日志：`AddConsoleFormatter`，并且 SQL 日志大量 `Console.WriteLine`。
- 请求日志：`RequestActionFilter` → `EventBus` → `LogEventSubscriber` → `BASE_SYS_LOG`。
- 异常日志：`FriendlyExceptionFilter` → `LogExceptionHandler` → `BASE_SYS_LOG`，同时可写 `ILogger<FriendlyException>`。
- 登录日志：`OAuthService.AddLoginLog()` → `Log:CreateVisLog` → `BASE_SYS_LOG`。
- 数据接口日志：`DataInterfaceService` 直接写 `BASE_API_LOG`。
- 调度/事件总线日志：`ScheduleHostedService`、`EventBusHostedService` 走 `ILogger`。
- 业务散落日志：Workflow、微信、SqlSugar 等仍有多处 `Console.WriteLine`。

问题核心：这些通道没有统一 `TraceId/UserId/TenantId/RequestId` 语义，无法稳定串联一次完整故障。

### 2. `[IgnoreLog]` 使用过宽，登录链路确实被排除

全仓库共搜索到 **54 处 `[IgnoreLog]`**，分布在 14 个文件，集中在：

- `OAuthService.cs`：14 处，登录、验证码、租户配置、SSO、扫码登录都被忽略。
- `FileService.cs`：5 处，文件上传、分片、合并被忽略。
- `TenantService.cs`：7 处。
- `VisualdevShortLinkService.cs`：7 处。
- `DataInterfaceService.cs`：4 处。
- `WebHookService.cs`：3 处。

分类判断：

- 合理忽略：验证码图片内容、部分静态文件/大文件上传的完整 body。
- 应降级记录：登录、扫码、SSO、租户配置、文件上传、短链访问。应记录耗时、状态、账号脱敏、IP、tenantId，不记密码、验证码、文件内容。
- 不应完全忽略：数据接口外部调用、WebHook、短链触发、租户切换相关接口。这些出了问题正是最需要审计的链路。

### 3. `RequestActionFilter` 是可观测性入口，也是潜在性能风险点

关键代码在 `backend/modularity/common/JNPF.Common.Core/Filter/RequestActionFilter.cs`：

- 每个非 IgnoreLog 请求都会执行 `NetHelper.GetLocation(ipAddress)`。
- 会序列化 `context.ActionArguments.ToJsonString()`。
- 会把 `JsonResult.Value` 再序列化写入 `SysLogEntity.Json`。
- 通过 `EventBus.PublishAsync` 写日志，最终 `LogEventSubscriber` 执行数据库插入。

补充核查：`NetHelper.GetLocation()` 使用的是本地 `IPTools.Core.IpTool.Search(ip)`，不是远程 API，所以不是秒级网络风险，但仍是每请求一次的同步计算成本。

真正高风险点是：

- 大列表返回会把返回值写入日志，日志体积不可控。
- 文件上传参数如果未被 `[IgnoreLog]` 拦截，存在序列化风险。
- 每个请求都可能额外触发数据库日志写入。
- 日志写入失败被 try-catch 保护，不会直接打断业务，但会吞掉日志失败细节，只写 `_logger.LogError(ex, ex.Message)`。

### 4. 多租户日志链路不完整

`SysLogEntity` 对应表 `BASE_SYS_LOG`，字段里有 `UserId/UserName/IP/RequestURL/RequestDuration/Json`，但**没有 TenantId 字段**。

当前租户信息在事件层传递：

`LogEventSubscriber.CreateLog()` 收到 `LogEventSource.TenantId` 后执行：

```csharp
await _tenantManager.ChangTenant(_sqlSugarClient, log.TenantId);
await _sqlSugarClient.CopyNew().Insertable(log.Entity).IgnoreColumns(ignoreNullColumn: true).ExecuteCommandAsync();
```

这意味着：

- 业务库日志可能按租户切库写入。
- 文件日志没有 TenantId 字段。
- 中央运维要跨租户查日志很困难。
- 如果是独立库模式，租户 A 的日志进入 A 库，平台级全局检索需要额外聚合方案。

### 5. 异常处理存在，但上下文不够工程化

当前异常链路是：

`FriendlyExceptionFilter` → `IGlobalExceptionHandler` → `LogExceptionHandler` → `Log:CreateExLog` → `BASE_SYS_LOG`

问题：

- 异常日志记录 `Message + StackTrace + TargetSite.GetParameters().ToString()`，没有标准化异常类型、InnerException、TraceId、请求头摘要、请求体摘要。
- 若接口有 `[IgnoreLog]`，异常日志也会被跳过。
- `async void` 存在于 `DbJobPersistence`、`MessageManager.WeChatMpSend`、`ImReplyService.ForcedOffline` 等位置，这类异常传播和日志捕获天然不可靠。

## 八、一个需要你决策的架构问题

在专家给出改造方案之前，有一个**你需要提前决定**的架构方向问题：

**`BASE_SYS_LOG`业务库日志的未来走向。**

当前的架构是：请求日志通过EventBus写入`BASE_SYS_LOG`，每个租户的库各存各的。这是JNPF自研的业务日志体系。

引入Serilog后，有两种路线：

**路线A：保留`BASE_SYS_LOG`，Serilog只管文件日志**
- 优点：改动最小，不影响现有数据库日志查询功能（如系统管理界面中的操作日志列表）
- 缺点：两套日志体系长期并行，维护成本高，字段不一致风险

**路线B：`BASE_SYS_LOG`改为Serilog的自定义Sink**
- 优点：统一入口，统一格式，文件和数据库日志完全一致
- 缺点：改动较大，现有的日志查询界面可能需要适配

**路线C：`BASE_SYS_LOG`保留用于业务审计，Serilog用于技术日志**
- 优点：职责分离——业务审计（谁在什么时候做了什么操作）和技术日志（请求链路、SQL、异常）是两种不同的观测需求
- 缺点：需要明确界定哪些信息进哪个系统

**我的建议是路线C。** 因为"操作审计"和"技术故障排查"本质上是两种不同的观测需求：

```
操作审计日志（BASE_SYS_LOG）          技术可观测日志（Serilog）
├── 谁做的？（UserId/UserName）         ├── TraceId / RequestId
├── 做了什么？（操作类型/接口）          ├── 完整请求链路
├── 什么时候？（时间戳）                ├── SQL耗时 / 慢查询标记
├── 对谁的数据？（TenantId/业务数据ID）  ├── 异常类型/堆栈/InnerException
├── 结果如何？（成功/失败）              ├── 中间件耗时分解
└── 用于安全审计和合规                  └── 用于性能优化和故障排查
```

这个决策会影响后续所有阶段的技术方案，请在专家开始正式改造方案设计前确定。

## 一、架构决策确认：路线C正确，但边界要更清晰

路线C的"业务审计日志 vs 技术可观测日志"分离是正确的。但专家的描述中有一个模糊地带需要钉死：

**`traceId`在两套系统中的角色不同。**

```
┌─────────────────────────────────┬──────────────────────────────────┐
│  业务审计日志 (BASE_SYS_LOG)     │  技术可观测日志 (Serilog)          │
├─────────────────────────────────┼──────────────────────────────────┤
│  主键：操作ID（自增/雪花）         │  主键：TraceId                    │
│  核心关注：谁对什么做了什么操作      │  核心关注：一次请求的完整技术链路    │
│  traceId：关联字段，用于跨系统检索   │  traceId：主键，用于串联所有节点    │
│  生命周期：长期保留（合规要求）      │  生命周期：短期（7-30天轮转）       │
│  查询方式：按用户/时间/操作类型      │  查询方式：按TraceId/耗时/错误码    │
│  权限模型：租户管理员看本租户        │  权限模型：运维/SRE看全局           │
│  存储：各租户库                   │  存储：中央存储（文件/ELK/Seq）     │
│  法律属性：可能作为电子证据          │  法律属性：运维工具，无法律效力      │
└─────────────────────────────────┴──────────────────────────────────┘
```

**关键约束：** `BASE_SYS_LOG`加`TraceId`字段后，业务日志可以按TraceId反查技术日志，技术日志也可以按TraceId反查业务操作。但两者的读写权限、保留策略、查询入口必须独立。不能因为两者共享一个TraceId就把查询逻辑混在一起。

## 二、EventBus反压问题比专家描述的更严重

专家发现EventBus用`Channel.CreateBounded(capacity: 3000, FullMode: Wait)`，但对影响的判断偏保守。专家说"请求路径中等待日志入队的风险"——这不是"风险"，是**确定性问题**。

**根因分析：**

```
请求进入 → Action执行 → OnActionExecuted触发
  → RequestActionFilter.BuildLogEvent()
  → EventBus.PublishAsync(logEvent)
    → Channel.Writer.WriteAsync()
      → 如果队列已满（3000条），WriteAsync会AWAIT
      → 此时请求线程被阻塞，等待队列有空位
      → 前端用户看到的就是请求卡住
```

**雪崩场景推演：**

```
某个时段请求量突增（如批量导入、报表生成、首页多人同时登录）
  → 每个请求产生一条日志事件
  → 日志消费者（LogEventSubscriber）执行数据库INSERT
  → INSERT变慢（数据库负载高、锁竞争、慢SQL）
  → 消费速度下降，队列堆积到3000
  → 新请求的PublishAsync开始等待
  → 请求响应时间飙升
  → 前端超时重试，产生更多请求
  → 队列继续堆积
  → 系统雪崩
```

**这不仅仅是"日志问题"，而是日志系统可以拖垮整个业务系统。**

请要求专家在改造方案中必须回答：

> 1. `FullMode = Wait`改为`FullMode = DropOldest`或`FullMode = DropWrite`是否可行？丢几条日志是否可接受？
> 2. 如果改为`FullMode = DropWrite`，是否需要一个监控指标来告警"日志队列满，有日志丢失"？
> 3. `LogEventSubscriber`的消费速度是否有上限控制？如果数据库INSERT持续慢，消费者是否会被拖死？
> 4. 长期方案是否应该把EventBus日志队列改为异步非阻塞，让`RequestActionFilter`中的日志投递变成fire-and-forget（带丢弃策略）？
> 5. 切到RabbitMQ后（如果客户配置了RabbitMQ），`durable: false`和无确认机制意味着RabbitMQ重启会丢日志。这对业务审计日志是否可接受？

**我给出的明确建议是：**

```
RequestActionFilter中的日志投递必须是异步非阻塞的：

方案：改为带容量限制的异步Channel + DropWrite策略
- 队列容量：10000
- FullMode：DropWrite（丢弃新日志，不阻塞请求）
- 监控：暴露队列深度指标，超过80%触发告警
- 降级：队列满时至少写一条"日志丢失告警"到stderr
- 对于业务审计日志（关键操作）：绕过队列，直接同步写库
  （用LogPolicy区分：MetadataOnly的操作可以丢，Full的审计操作不能丢）
```

这就需要LogPolicy和日志投递策略联动——不是所有日志都走同一个队列。**审计级日志（如权限变更、数据删除）必须同步写入，不能丢。诊断级日志（如普通查询的请求参数和返回值）可以异步且可丢弃。**

## 三、租户切换并发问题：不只是"需要验证"，从代码模式就能判断存在风险

专家说"我不会直接断言已经存在租户串写"，态度谨慎。但从代码模式来看，**这个风险是结构性存在的**，不需要跑并发测试来验证，从代码语义就能分析出来。

**关键代码路径：**

```csharp
// LogEventSubscriber 是单例
public class LogEventSubscriber : IEventSubscriber<LogEvent>
{
    private readonly SqlSugarScope _sqlSugarClient;  // 单例注入
    private readonly TenantManager _tenantManager;    // 单例注入

    public async Task OnEvent(LogEvent log)
    {
        // 步骤1：修改共享SqlSugarScope的租户上下文
        await _tenantManager.ChangTenant(_sqlSugarClient, log.TenantId);
        
        // 步骤2：CopyNew创建副本并写入
        await _sqlSugarClient.CopyNew()
            .Insertable(log.Entity)
            .ExecuteCommandAsync();
    }
}
```

**并发竞态分析：**

```
时间线    请求A（租户1）                    请求B（租户2）
─────────────────────────────────────────────────────────
T1      ChangTenant(client, tenant1)        
T2        → client.CurrentTenant = 1       
T3                                        ChangTenant(client, tenant2)
T4                                          → client.CurrentTenant = 2
T5        → client.CopyNew()              
T6        → copy.CurrentTenant = ???       // 读到的是2，不是1！
T7        → INSERT到租户2的库               // 数据写错库了
```

`CopyNew()`是在`ChangTenant`之后执行的，但`ChangTenant`修改的是**同一个单例对象的状态**。如果两个并发请求交叉执行，后一个`ChangTenant`会覆盖前一个的租户上下文。

**但有一个关键细节需要专家确认：** `CopyNew()`的实现是什么？

- 如果`CopyNew()`是深拷贝，捕获的是当前时刻的完整状态——那问题发生在步骤T5/T6，CopyNew读到了被B覆盖后的租户上下文
- 如果`CopyNew()`是创建一个新的SqlSugarClient实例但共享连接字符串配置——那可能安全，但需要确认新实例是否会继承原始实例的QueryFilter和AOP配置
- 如果`CopyNew()`是调用`SqlSugarScope`的工厂方法创建全新实例——那需要确认新实例的租户上下文是独立的

**请要求专家做以下确认（不需要跑并发测试，纯代码分析）：**

> 1. 找到`SqlSugarScope.CopyNew()`的源码实现（NuGet包中的方法），分析它创建的新实例是否携带调用时刻的租户上下文
> 2. 如果携带，是否存在上面分析的并发覆盖问题
> 3. 如果不携带，新实例的租户上下文默认是什么？是否需要在`CopyNew()`之后再显式设置租户？
> 4. 搜索`TenantManager.ChangTenant()`的实现，确认它是否修改了传入的`_sqlSugarClient`的全局状态，还是只修改了某个局部作用域的状态

**如果确认存在并发风险，修复方案有三个层次：**

```
方案1（最小改动）：在LogEventSubscriber中，先CopyNew再ChangTenant
  → var client = _sqlSugarClient.CopyNew();
  → await _tenantManager.ChangTenant(client, log.TenantId);
  → await client.Insertable(log.Entity).ExecuteCommandAsync();
  → 风险：CopyNew后的实例是否支持ChangTenant？需要验证

方案2（中等改动）：用SqlSugarScope的租户工厂模式
  → 不在Subscriber中切换租户，而是用log.TenantId直接获取对应的租户专用Client
  → 需要SqlSugar支持按TenantId创建独立Client的API

方案3（架构改动）：日志写入不走共享SqlSugarScope
  → 为日志写入创建独立的、无租户过滤的SqlSugarClient
  → 通过connectionString直接连接目标库
  → 完全隔离，不影响业务层的SqlSugar状态
```

**方案3是最干净的**，因为它从根本上消除了日志写入和业务操作共享SqlSugar状态的风险。日志写入应该是"旁路"操作，不应该修改或依赖业务层的任何状态。

```csharp
public class TraceIdMiddleware : IMiddleware
{
    public const string TraceIdHeaderName = "X-Trace-Id";
    public const string TraceIdItemKey = "TraceId";

    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        var traceId = context.Request.Headers.TryGetValue(TraceIdHeaderName, out var existingId)
            && !string.IsNullOrWhiteSpace(existingId)
            ? existingId.ToString()
            : GenerateTraceId();

        context.Items[TraceIdItemKey] = traceId;
        context.Response.Headers[TraceIdHeaderName] = traceId;

        // 注入到 Serilog LogContext（阶段2用）
        // using (LogContext.PushProperty("TraceId", traceId)) { await next(context); }
        await next(context);
    }

    private static string GenerateTraceId()
        => Activity.Current?.TraceId.ToString() ?? Guid.NewGuid().ToString("N");
}
```

**注册位置：** `Startup.cs`，置于 `app.UseAuthentication()` **之前**

**验收：** 所有响应头都有 `X-Trace-Id`，值在同一请求内不变。

        key = kv.Key,
        type = kv.Value?.GetType().Name ?? "null",
        size = kv.Value?.ToJsonString()?.Length ?? 0,
        isFile = kv.Value is IFormFile
    });
    return summary.ToJsonString();
}

private static string SummarizeResult(object? result)
{
    if (result == null) return "{}";
    var json = result.ToJsonString();
    return json.Length > 2000
        ? $"{{\"_truncated\":true,\"_length\":{json.Length},\"_preview\":{json[..200].ToJsonString()}}}"
        : json;
}

            .Insertable(log.Entity)
            .IgnoreColumns(ignoreNullColumn: true)
            .ExecuteCommandAsync();
    }
}

### 需要修正的部分

**阶段2的租户串库修复方案有设计缺陷。**

专家提出的方案是：

```csharp
using var scope = _scopeFactory.CreateScope();
var db = scope.ServiceProvider.GetRequiredService<ISqlSugarClient>();
```

这个方案的问题是：**`IServiceScopeFactory.CreateScope()`创建的scope会在`using`结束时Dispose，但SqlSugarScope的内部连接池管理与DI scope的生命周期不是简单对齐的。**

具体来说：

1. 如果`ISqlSugarClient`在DI中注册为Scoped，每次`CreateScope`都会创建一个新的SqlSugarScope实例——每个实例可能有自己的连接池，54个日志事件/秒意味着每秒创建和销毁54个scope和对应的SqlSugar实例，GC压力和连接池碎片会成为新问题

2. 如果`ISqlSugarClient`在DI中注册为Singleton（JNPF当前的注册方式），`scope.ServiceProvider.GetRequiredService<ISqlSugarClient>()`拿到的仍然是同一个单例实例，`CreateScope`没有起到隔离作用

**正确的修复思路应该是：**

```
方案A（最小改动，推荐）：
  不改变LogEventSubscriber的注入方式
  移除static字段，改为构造函数注入ISqlSugarClient（单例）
  写日志时使用sqlSugarClient.AsTenant().ChangeDatabase(tenantId)
  然后用一个局部的、独立的DB连接执行INSERT
  关键：不修改全局SqlSugarScope的租户状态，只在本次INSERT时临时切换

方案B（最干净）：
  为日志写入创建独立的SqlSugarClient，不走业务层的SqlSugarScope
  通过connectionString直接连接目标租户库
  完全隔离，零共享状态
  需要维护一个TenantId→ConnectionString的映射
```

请要求专家在修复方案中**明确SqlSugarScope的DI注册方式**（Singleton/Scoped/Transient），然后选择与之匹配的隔离方案。不能假设CreateScope就能解决问题。

### 2.3 业务审计日志（BASE_SYS_LOG）存储与查询架构

#### 当前问题

`BASE_SYS_LOG`存储在各租户的业务数据库中，这意味着：

1. **跨租户查询不可能**——平台管理员无法在一处查看所有租户的操作日志
2. **日志表膨胀**——随着使用时间增长，`BASE_SYS_LOG`可能成为每个租户库中最大的表
3. **查询性能退化**——没有分区策略，全表扫描风险

#### 存储架构改造

```
方案A：各租户库保留 + 中央日志库聚合（推荐）
═══════════════════════════════════════════

  租户A库 ──┐
  租户B库 ──┤──→ EventBus ──→ 中央日志库 (JNPF_LOG_CENTER)
  租户C库 ──┘                  ├─ 全量操作日志（所有租户）
                               ├─ 按TenantId分区
                               ├─ 按时间分区（月分区）
                               └─ 系统管理页面统一查询入口

  优势：
  ├── 租户管理员仍然在本库查日志（兼容现有逻辑）
  ├── 平台管理员可在中央库查所有租户日志
  ├── 中央库可独立优化（分区、索引、归档策略）
  └── 租户库的BASE_SYS_LOG可以定期归档/清理

  劣势：
  ├── 需要额外的数据库资源
  └── 双写（租户库+中央库）增加写入延迟

方案B：统一中央库，取消租库存储（激进）
═══════════════════════════════════════

  所有日志 → 中央日志库 (JNPF_LOG_CENTER)
  ├─ 租户管理员通过API查询，后端按TenantId过滤
  └─ 平台管理员看全局

  优势：简单，无双写
  劣势：改变了现有查询逻辑，租户数据不在租户库内（合规风险？）
```

**我推荐方案A。** 因为JNPF的私有化客户对数据归属有强烈敏感性——"我的操作日志应该在我的数据库里"这个诉求在政务和金融客户中非常普遍。方案A在兼容这个诉求的同时，为平台管理员提供了跨租户查询能力。

```csharp
// 新增：TechnicalLogController
[ApiController]
[Route("api/sysLog")]
public class TechnicalLogController : ControllerBase
{
    private readonly string _logBasePath;

    /// <summary>
    /// 查询错误日志列表
    /// </summary>
    [HttpGet("errors")]
    public async Task<IActionResult> GetErrorLogs(
        [FromQuery] DateTime startTime,
        [FromQuery] DateTime endTime,
        [FromQuery] string traceId = null,
        [FromQuery] string keyword = null,
        [FromQuery] int pageIndex = 1,
        [FromQuery] int pageSize = 20)
    {
        // 1. 确定需要读取的日志文件列表
        var logFiles = GetLogFilesInRange("logs/error-", startTime, endTime);
        
        // 2. 逐文件流式读取，过滤匹配条件
        var results = new List<LogEntry>();
        foreach (var file in logFiles)
        {
            using var stream = new FileStream(file, FileMode.Open, FileAccess.Read, FileShare.ReadWrite);
            using var reader = new StreamReader(stream);
            string line;
            while ((line = await reader.ReadLineAsync()) != null)
            {
                var entry = JsonSerializer.Deserialize<LogEntry>(line);
                if (entry != null 
                    && entry.Timestamp >= startTime 
                    && entry.Timestamp <= endTime
                    && (traceId == null || entry.TraceId == traceId)
                    && (keyword == null || entry.Message?.Contains(keyword) == true))
                {
                    results.Add(entry);
                }
            }
        }
        
        // 3. 分页返回
        var total = results.Count;
        var page = results
            .OrderByDescending(x => x.Timestamp)
            .Skip((pageIndex - 1) * pageSize)
            .Take(pageSize)
            .ToList();
        
        return Ok(new { total, page });
    }

    /// <summary>
    /// 按TraceId查询全链路日志
    /// </summary>
    [HttpGet("trace/{traceId}")]
    public async Task<IActionResult> GetTraceLogs(string traceId)
    {
        // 1. 查BASE_SYS_LOG（业务审计日志）
        var businessLogs = await _sysLogService.QueryByTraceId(traceId);
        
        // 2. 查技术日志文件（所有级别）
        var techLogs = await SearchAllLogFiles(traceId);
        
        // 3. 合并并按时间排序
        var merged = businessLogs.Select(x => new TraceLogEntry {
            Source = "Audit",
            Timestamp = x.F_CREATION_TIME,
            TraceId = x.F_TRACE_ID,
            Message = $"{x.F_TYPE}: {x.F_REQUEST_URL}",
            UserId = x.F_USER_ID,
            TenantId = x.F_TENANT_ID
        })
        .Concat(techLogs.Select(x => new TraceLogEntry {
            Source = "Technical",
            Timestamp = x.Timestamp,
            TraceId = x.TraceId,
            Message = x.Message,
            Level = x.Level,
            Exception = x.Exception
        }))
        .OrderBy(x => x.Timestamp)
        .ToList();
        
        return Ok(merged);
    }
}
```

#### 策略2：请求日志采样

高并发场景下，不是每个请求都需要完整的技术日志：

```csharp
// 在RequestActionFilter中实现采样
public class RequestActionFilter : IAsyncActionFilter
{
    private static readonly Sampler _sampler = new AdaptiveSampler(
        targetRate: 1000,  // 目标：每秒最多1000条完整日志
        windowSeconds: 10  // 10秒滑动窗口
    );

    public async Task OnActionExecutionAsync(ActionExecutingContext context, ActionExecutionDelegate next)
    {
        var shouldSample = _sampler.ShouldSample();
        
        // 完整日志 vs 摘要日志
        if (shouldSample)
        {
            // 完整记录：请求参数摘要、返回值摘要、SQL耗时、全链路
            WriteDetailedLog(context, result);
        }
        else
        {
            // 摘要记录：仅TraceId、路径、耗时、状态码（约200字节 vs 完整的800字节）
            WriteSummaryLog(context, result);
        }
    }
}
```

#### 策略3：慢查询独立通道

```
普通SQL日志：不记录（生产环境关闭SqlSugar的SQL日志）
慢SQL日志（>500ms）：始终记录，独立文件
超慢SQL日志（>2s）：记录+告警
```

这样，正常情况下SQL日志流量为零，只有慢查询才产生日志。

**两类操作的线程安全性完全不同：**

| 操作                           | 作用域                   | 线程安全性                 |
| ------------------------------ | ------------------------ | -------------------------- |
| `ChangeDatabase(tenantId)`     | 线程本地（Thread-Local） | ✅ 多线程可以各自切换不同DB |
| `QueryFilter.Clear()`          | **全局（Global）**       | ❌ 清空所有线程的过滤器     |
| `QueryFilter.AddTableFilter()` | **全局（Global）**       | ❌ 竞态导致多租户过滤器叠加 |
| `Aop.DataExecuting = ...`      | **全局（Global）**       | ❌ 后一个线程的赋值覆盖前者 |

**真实竞态场景（不需要跑测试，从语义分析即可确认）：**

────────────────────────────────────────────────────────────

                                    QueryFilter.Clear()

QueryFilter.AddTableFilter(tenant1)
─────────────────────────────────────────────────────────────────

但租户2的过滤器也在（没被清掉）。

### 正确的修复方案：方案B——日志写入使用独立 SqlSugarClient

**核心原则：日志写入是旁路操作，必须与业务层的 SqlSugarScope 零共享。**

**修改文件：** `backend/modularity/common/JNPF.Common.Core/EventBus/LogEventSubscriber.cs`

```csharp
[SuppressSniffer]
public class LogEventSubscriber : IEventSubscriber, ISingleton
{
    private readonly ConnectionStringsOptions _connectionStrings;
    private readonly ICacheManager _cacheManager;

    // 移除：private static SqlSugarScope? _sqlSugarClient;
    // 移除：private readonly ITenantManager _tenantManager;
    // 移除：private readonly IUserManager _userManager;
    // 以上三者都与业务层共享状态，全部不需要

    public LogEventSubscriber(
        IOptions<ConnectionStringsOptions> connectionOptions,
        ICacheManager cacheManager)
    {
        _connectionStrings = connectionOptions.Value;
        _cacheManager = cacheManager;
    }

    [EventSubscribe("Log:CreateReLog")]
    [EventSubscribe("Log:CreateExLog")]
    [EventSubscribe("Log:CreateVisLog")]
    [EventSubscribe("Log:CreateOpLog")]
    public async Task CreateLog(EventHandlerExecutingContext context)
    {
        var log = (LogEventSource)context.Source;

        // 独立连接配置，完全不依赖业务层 SqlSugarScope
        var connConfig = await ResolveConnectionConfig(log.TenantId);

        // 每次写入创建独立 SqlSugarClient，IsAutoCloseConnection = true 确保连接自动归还
        using var db = new SqlSugarClient(connConfig);

        await db.Insertable(log.Entity)
            .IgnoreColumns(ignoreNullColumn: true)
            .ExecuteCommandAsync();
    }

    private async Task<ConnectionConfig> ResolveConnectionConfig(string tenantId)
    {
        var defaultConfig = _connectionStrings.DefaultConnectionConfig;

        // 无租户 ID 或默认租户：使用主库
        if (tenantId.IsNullOrEmpty() || tenantId == "default")
        {
            return new ConnectionConfig
            {
                ConfigId = defaultConfig.ConfigId,
                DbType = defaultConfig.DbType,
                ConnectionString = JNPFTenantExtensions.ToConnectionString(defaultConfig),
                IsAutoCloseConnection = true,
                InitKeyType = InitKeyType.Attribute,
            };
        }

        // 有租户 ID：从缓存获取连接串，不触碰业务层 SqlSugarScope
        var tenantCache = _cacheManager.Get<List<GlobalTenantCacheModel>>(CommonConst.GLOBALTENANT)
            ?.Find(it => it.TenantId == tenantId);

        if (tenantCache?.connectionConfig?.ConfigList?.Any() == true)
        {
            var dbConn = tenantCache.connectionConfig.ConfigList.First();
            return new ConnectionConfig
            {
                ConfigId = tenantId,
                DbType = dbConn.dbType,
                ConnectionString = dbConn.connectionStr,
                IsAutoCloseConnection = true,
                InitKeyType = InitKeyType.Attribute,
            };
        }

        // 缓存未命中：降级写入主库，并记录告警（不抛出异常，不阻塞日志消费）
        // 这条日志会以主库租户身份写入，F_TENANT_ID 字段仍保留原始租户标识
        return new ConnectionConfig
        {
            ConfigId = defaultConfig.ConfigId,
            DbType = defaultConfig.DbType,
            ConnectionString = JNPFTenantExtensions.ToConnectionString(defaultConfig),
            IsAutoCloseConnection = true,
            InitKeyType = InitKeyType.Attribute,
        };
    }
}
```

| 问题                                 | 方案B的处理方式                               |
| ------------------------------------ | --------------------------------------------- |
| `CreateScope` 无法隔离 Singleton     | 完全不用 DI 获取 SqlSugarScope                |
| `QueryFilter.Clear()` 污染全局过滤器 | 独立 SqlSugarClient 有独立的 QueryFilter      |
| `Aop.DataExecuting` 被并发覆盖       | 独立实例，AOP 互不影响                        |

public static class SerilogBootstrap
{
    public static IHostBuilder UseSerilogLogging(this IHostBuilder builder)
    {
        return builder.UseSerilog((context, services, config) =>
        {
            var env = context.HostingEnvironment;
            var cfg = context.Configuration;

            config
                // 生产环境默认 Warning，特定命名空间单独控制
                .MinimumLevel.Is(env.IsProduction()
                    ? LogEventLevel.Warning
                    : LogEventLevel.Debug)
                .MinimumLevel.Override("Microsoft.AspNetCore", LogEventLevel.Error)
                .MinimumLevel.Override("System.Net.Http", LogEventLevel.Error)
                .MinimumLevel.Override("JNPF.RequestAction", LogEventLevel.Information) // 请求日志保持
                .MinimumLevel.Override("JNPF.SqlSugar.SlowQuery", LogEventLevel.Warning) // 慢SQL独立

                // 从 LogContext 读取 TraceId/UserId/TenantId（由 TraceIdMiddleware 注入）
                .Enrich.FromLogContext()
                .Enrich.WithEnvironmentName()
                .Enrich.WithMachineName()

                // Sink 1：错误日志（Error+，所有客户必须）
                .WriteTo.File(
                    formatter: new CompactJsonFormatter(),
                    path: "logs/error-.json",
                    restrictedToMinimumLevel: LogEventLevel.Error,
                    rollingInterval: RollingInterval.Day,
                    fileSizeLimitBytes: 50L * 1024 * 1024,  // 50MB 切割
                    retainedFileCountLimit: 90,              // 90天
                    rollOnFileSizeLimit: true,
                    buffered: false)                         // 错误日志不缓冲，立即落盘

                // Sink 2：全量技术日志（Warning+，所有客户）
                .WriteTo.File(
                    formatter: new CompactJsonFormatter(),
                    path: "logs/jnpf-.json",
                    restrictedToMinimumLevel: LogEventLevel.Warning,
                    rollingInterval: RollingInterval.Day,
                    fileSizeLimitBytes: 100L * 1024 * 1024, // 100MB 切割
                    retainedFileCountLimit: 30,              // 30天
                    rollOnFileSizeLimit: true,
                    buffered: true,                          // 普通日志缓冲写入
                    flushToDiskInterval: TimeSpan.FromSeconds(5))

                // Sink 3：慢SQL专用日志（通过 ByIncludingOnly 过滤）
                .WriteTo.Logger(lc => lc
                    .Filter.ByIncludingOnly(e =>
                        e.Properties.ContainsKey("SlowSql") ||
                        e.Properties.ContainsKey("SlowSqlMs"))
                    .WriteTo.File(
                        formatter: new CompactJsonFormatter(),
                        path: "logs/slow-sql-.json",

                    sink => sink.Seq(

    context.Items[TraceIdItemKey] = traceId;
    context.Response.Headers[TraceIdHeaderName] = traceId;

    }

### 2.4 SQL 慢查询日志替换 Console.WriteLine

**修改文件：** `backend/application/JNPF.API.Entry/Extensions/SqlSugarConfigureExtensions.cs`，`SetDbAop` 方法：

```csharp
public static void SetDbAop(SqlSugarScopeProvider db)
{
    var config = db.CurrentConnectionConfig;
    db.Ado.CommandTimeOut = 30;

    // 替换 Console.WriteLine(SQL) 为结构化 Serilog
    db.Aop.OnLogExecuted = (sql, pars) =>
    {
        var elapsed = db.Ado.SqlExecutionTime.TotalMilliseconds;
        if (elapsed >= 2000)
        {
            // 超慢 SQL：Error 级别 + 告警
            Log.ForContext("SlowSql", true)
               .ForContext("SlowSqlMs", (long)elapsed)
               .Error("SuperSlow SQL ({ElapsedMs}ms): {Sql}", (long)elapsed,
                   UtilMethods.GetSqlString(config.DbType, sql, pars));
        }
        else if (elapsed >= 500)
        {
            // 慢 SQL：Warning 级别
            Log.ForContext("SlowSql", true)
               .ForContext("SlowSqlMs", (long)elapsed)
               .Warning("Slow SQL ({ElapsedMs}ms): {Sql}", (long)elapsed,
                   UtilMethods.GetSqlString(config.DbType, sql, pars));
        }
        // 正常 SQL：不记录（生产环境完全无 SQL 流量日志）
    };

    db.Aop.OnError = ex =>
    {
        var pars = db.Utilities.SerializeObject(
            ((SugarParameter[])ex.Parametres).ToDictionary(it => it.ParameterName, it => it.Value));
        Log.Error(ex, "SQL Error: {Sql} Params: {Params}", ex.Sql, pars);
    };
}
```

这一改动的效果：**生产环境正常 SQL 零日志输出**，只有 ≥500ms 的慢查询才写日志，且写入专用的 `slow-sql-.json` 而非 stdout。

### 2.6 磁盘空间保护机制

**新增文件：** `backend/common/JNPF.Common.Core/HostedServices/LogDiskGuardService.cs`

```csharp
public class LogDiskGuardService : BackgroundService
{
    private readonly ILogger<LogDiskGuardService> _logger;
    private readonly string _logPath;
    private readonly long _warningThresholdBytes = 5L * 1024 * 1024 * 1024; // 5GB 剩余告警
    private readonly long _criticalThresholdBytes = 1L * 1024 * 1024 * 1024; // 1GB 剩余降级

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await Task.Delay(TimeSpan.FromMinutes(15), stoppingToken);

            try
            {
                var drive = new DriveInfo(Path.GetPathRoot(_logPath)!);
                var freeSpace = drive.AvailableFreeSpace;

                if (freeSpace < _criticalThresholdBytes)
                {
                    // 紧急：删除最老的日志文件
                    PurgeOldestLogFiles(keepDays: 3);
                    _logger.LogError(
                        "LOG_DISK_CRITICAL: Only {FreeGB:F1}GB free. Auto-purged old logs.",
                        freeSpace / 1e9);
                }
                else if (freeSpace < _warningThresholdBytes)
                {
                    _logger.LogWarning(
                        "LOG_DISK_WARNING: Only {FreeGB:F1}GB free. Consider cleanup.",
                        freeSpace / 1e9);
                }
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "LogDiskGuard check failed");
            }
        }
    }

    private void PurgeOldestLogFiles(int keepDays)
    {
        var cutoff = DateTime.UtcNow.AddDays(-keepDays);
        foreach (var file in Directory.GetFiles(_logPath, "*.json"))
        {
            if (File.GetLastWriteTimeUtc(file) < cutoff)
                File.Delete(file);
        }
    }
}

    private async IAsyncEnumerable<TechLogEntry> ReadLogFileAsync(
        string filePath,
        DateTime startTime, DateTime endTime,
        string? traceId, string? keyword)
    {
        using var stream = new FileStream(filePath, FileMode.Open, FileAccess.Read, FileShare.ReadWrite);
        using var reader = new StreamReader(stream);

        while ((line = await reader.ReadLineAsync()) != null)

            try { entry = JsonSerializer.Deserialize<TechLogEntry>(line); }

            if (traceId != null && entry.TraceId != traceId) continue;

            yield return entry;
        }

### 4.1 是否需要分区

- 所有类型日志合计约 5000 条/天（仅记录有业务意义的操作，非每个请求都写）

### 坑1：`new SqlSugarClient(connConfig)` 不是万能的

专家方案中LogEventSubscriber的修复代码：

**需要工程师验证的问题：**

> 2. 检查`tenantCache.connectionConfig.ConfigList`中的`dbType`值是什么类型（是枚举还是字符串？是`DbType.SqlServer`还是`"SqlServer"`？）

### 坑2：Serilog替换AddFileLogging后，原有的3个文件日志Provider要移除

当前`Startup.cs`中有：

```csharp
Array.ForEach(new[] { LogLevel.Information, LogLevel.Warning, LogLevel.Error }, logLevel =>
{
    services.AddFileLogging(options => { ... });
});
```

**这3个AddFileLogging调用必须移除**，否则会和Serilog同时写文件，造成日志重复和IO浪费。但移除前要确认：

> 1. 是否有其他代码依赖`AddFileLogging`的输出路径或格式？（搜索是否有代码在读取这些文件）
> 2. `AddFileLogging`注册的是`ILoggerProvider`，移除后原有的`_logger.LogInformation()`调用是否会报错？（不会，因为Serilog也注册了`ILoggerProvider`，只是底层实现换了）

### 坑3：`CompactJsonFormatter`输出的是Serilog Compact JSON格式，不是标准JSON

```csharp
.WriteTo.File(formatter: new CompactJsonFormatter(), ...)
```

`CompactJsonFormatter`输出的格式是：

```json
{"@t":"2025-01-01T00:00:00.0000000Z","@m":"Slow SQL...","@l":"Warning","TraceId":"abc","UserId":"123"}
```

注意字段名是`@t`、`@m`、`@l`、`@x`（异常），不是`Timestamp`、`Message`、`Level`。

**前端解析和TechnicalLogService的`TechLogEntry`模型必须用这些字段名：**

```csharp
public class TechLogEntry
{
    [JsonPropertyName("@t")]   // 不是 "Timestamp"
    public DateTime Timestamp { get; set; }
    
    [JsonPropertyName("@m")]   // 不是 "Message"
    public string Message { get; set; }
    
    [JsonPropertyName("@l")]   // 不是 "Level"
    public string Level { get; set; }
    
    [JsonPropertyName("@x")]   // 不是 "Exception"
    public string Exception { get; set; }
    
    [JsonPropertyName("TraceId")]
    public string TraceId { get; set; }
    
    [JsonPropertyName("UserId")]
    public string UserId { get; set; }
    
    [JsonPropertyName("TenantId")]
    public string TenantId { get; set; }
}
```

或者换用`RenderedCompactJsonFormatter`，或者直接用普通`JsonFormatter`（字段名更直观但体积更大）。**建议用普通`JsonFormatter`降低前端解析复杂度：**

```csharp
// 替代方案：输出人类可读的标准JSON
.WriteTo.File(
    formatter: new Serilog.Formatting.Json.JsonFormatter(renderMessage: true),
    ...)
```

输出：

```json
{"Timestamp":"2025-01-01T00:00:00.0000000+08:00","Level":"Warning","Message":"Slow SQL (1234ms): SELECT ...","TraceId":"abc","UserId":"123","Exception":null}
```

### 坑4：`FileShare.ReadWrite`读取正在写入的日志文件可能遇到JSON截断

TechnicalLogService中：

```csharp
using var stream = new FileStream(filePath, FileMode.Open, FileAccess.Read, FileShare.ReadWrite);
using var reader = new StreamReader(stream);
string? line;
while ((line = await reader.ReadLineAsync()) != null)
{
    var entry = JsonSerializer.Deserialize<TechLogEntry>(line);
}
```

**风险：** Serilog写文件时，某一行JSON可能写了一半还没Flush，此时读取会得到不完整的JSON行，`JsonSerializer.Deserialize`会抛异常。

专家代码中有`try { ... } catch { continue; }`保护，但工程师需要注意：

> 1. 确保catch块不会吞掉真正的解析错误（比如格式确实不对的日志行）
> 2. 考虑加一个日志：`_logger.LogDebug("Skipped malformed log line in {File}", filePath)`
> 3. 最后一行（正在写入的行）大概率会被跳过，这是可接受的行为

### 坑5：`LogEventSubscriber`修复后，`ResolveConnectionConfig`中的缓存结构

## 四、一个需要你做的决策

专家方案中有一个技术选型需要你最终拍板：

**Serilog输出格式用哪种？**

| 格式                                | 优点                                                         | 缺点                                     | 推荐场景                    |
| ----------------------------------- | ------------------------------------------------------------ | ---------------------------------------- | --------------------------- |
| `CompactJsonFormatter`              | 体积最小（约减30%），Serilog原生支持，Seq可直接解析          | 字段名是`@t`/`@m`/`@l`，前端解析需要适配 | 有Seq的B/C类客户            |
| `JsonFormatter(renderMessage:true)` | 标准JSON，字段名直观（`Timestamp`/`Message`/`Level`），前端直接解析 | 体积稍大                                 | A/D类客户（前端直接查文件） |
| 两者都支持                          | 配置化切换，不同Sink用不同格式                               | 增加配置复杂度                           | 兼顾所有客户类型            |

**我的建议：默认用`JsonFormatter`，Seq Sink单独用`CompactJsonFormatter`。** 因为A类/D类客户的前端日志查看器是直接解析文件的，用标准JSON字段名可以减少前端适配工作。Seq有自己的解析能力，可以用Compact格式节省存储。

```csharp
// 文件Sink用标准JSON（前端可直接解析）
.WriteTo.File(
    formatter: new JsonFormatter(renderMessage: true),
    path: "logs/error-.json", ...)

// Seq Sink用Compact格式（Seq原生支持，存储更省）
.WriteTo.Conditional(
    _ => cfg["Logging:Seq:Enabled"] == "true",
    sink => sink.Seq(
        cfg["Logging:Seq:ServerUrl"]!,
        compact: true))
```

这个决策确认后，工程师就可以按批次1开始写代码了。

### 阶段D：登录后CurrentUser接口优化（第8-10天）

**这是整个切面2中技术含量最高的优化，因为涉及接口拆分和缓存设计。**

#### 任务D1：CurrentUser接口分析（工程师先做测量）

```

方法：在OAuthService.GetCurrentUser()内部各步骤加Stopwatch日志

currentUserModel.columnList = ... → 测量耗时
currentUserModel.resourceList = ... → 测量耗时

```

#### 任务D2：串行改并行（前置优化，工程师可先做）

```
当前：五个查询是串行await
改为：用Task.WhenAll并行执行

// 原代码（串行）：
currentUserModel.moduleList = await _moduleService.GetUserModuleListByIds(...);
currentUserModel.buttonList = await _moduleButtonService.GetUserModuleButtonList(...);
currentUserModel.columnList = await _columnService.GetUserModuleColumnList(...);
currentUserModel.resourceList = await _moduleDataAuthorizeSchemeService.GetResourceList(...);
currentUserModel.formList = await _formService.GetUserModuleFormList(...);

// 改后（并行）：
var moduleTask = _moduleService.GetUserModuleListByIds(...);
var buttonTask = _moduleButtonService.GetUserModuleButtonList(...);
var columnTask = _columnService.GetUserModuleColumnList(...);
var resourceTask = _moduleDataAuthorizeSchemeService.GetResourceList(...);
var formTask = _formService.GetUserModuleFormList(...);

await Task.WhenAll(moduleTask, buttonTask, columnTask, resourceTask, formTask);

currentUserModel.moduleList = moduleTask.Result;
currentUserModel.buttonList = buttonTask.Result;
// ... 以此类推
```

**注意：** 这里需要验证五个查询之间是否有数据依赖（后面的查询是否依赖前面查询的结果）。从之前专家的分析看，`buttonList`/`columnList`等查询需要`dataScopeModuleIds`（来自moduleList查询结果），所以**不能完全并行**。需要进一步分析依赖关系。

#### 任务D3：CurrentUser接口拆分（需要专家评审架构方案）

```
目标：将CurrentUser拆分为"首屏必需"和"后台懒加载"两层

首屏必需（登录后立即获取）：
├── userInfo（用户基本信息：姓名、头像、角色）
├── sysConfig（系统配置：主题、语言、布局）
└── basicMenu（最小菜单集：首页和默认路由）

后台懒加载（首页渲染后异步获取）：
├── fullMenu（完整菜单列表）
├── buttonList（按钮权限）
├── columnList（列权限）
├── resourceList（数据权限资源）
└── formList（表单权限）

前端改造：
├── login() → 只调用GetCurrentUserLite()（首屏必需）
├── 首页渲染完成后 → 异步调用GetFullPermissions()
├── 路由守卫中 → 用懒加载后的权限数据做路由判断
└── 关键：不能因为懒加载导致页面闪跳（已有路由不受影响）
```
