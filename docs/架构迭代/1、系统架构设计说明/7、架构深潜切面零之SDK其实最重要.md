# 切面0执行指导：JNPF V5.2 .NET 6 → .NET 10 升级施工包

---

## 零、升级前必须理解的核心原则

```
原则1：一次到位，不走.NET 8过渡
原因：.NET 8 LTS 2026年11月终止支持，只剩6个月，不值得做一次迁移。

原则2：先让编译通过，再修行为变更
原因：编译错误是确定性的（编译器告诉你哪里错了），行为变更是隐蔽的
（代码能编译但运行结果不同）。两个阶段必须分开，不能混在一起。

原则3：保持功能不变，不趁机重构
原因：升级和重构混在一起，出了问题你不知道是升级导致的还是重构导致的。
所有"顺便优化"的冲动必须压制。升级期间只做"让代码在.NET 10上等价运行"。

原则4：保留.NET 6分支作为回退基线
原因：升级过程中如果发现某个核心依赖不可用，需要能快速回退。
```


### 1.3 全局配置文件检查

```bash
# 检查是否有global.json锁定SDK版本
cat global.json 2>/dev/null || echo "无global.json"

# 检查是否有Directory.Build.props（统一管理所有项目的属性）
cat Directory.Build.props 2>/dev/null || echo "无Directory.Build.props"

# 检查是否有Directory.Packages.props（中央包管理）
cat Directory.Packages.props 2>/dev/null || echo "无Directory.Packages.props"
```

**如果有`global.json`：**
```json
// 如果当前是：
{ "sdk": { "version": "6.0.xxx" } }
// 改为：
{ "sdk": { "version": "10.0.xxx", "rollForward": "latestMinor" } }
```

**如果没有`Directory.Build.props`，建议创建一个：**
```xml
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
```
这样可以一次性统一所有项目的TargetFramework，而不需要逐个修改.csproj。

## 二、第二阶段：执行升级（第2-4天）

### 2.1 创建升级分支

```bash
git checkout -b feature/dotnet10-upgrade
git push -u origin feature/dotnet10-upgrade
```

### 2.2 修改TargetFramework

**方案A：使用Directory.Build.props统一管理（推荐）**

如果已创建`Directory.Build.props`，只需修改一处：

```xml
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
  </PropertyGroup>
</Project>
```

**方案B：逐个修改.csproj（如果没有Directory.Build.props）**

```bash
# 批量替换所有.csproj中的TargetFramework
# Linux/macOS:
find . -name "*.csproj" -exec sed -i 's/<TargetFramework>net6.0</<TargetFramework>net10.0</g' {} \;

# Windows PowerShell:
Get-ChildItem -Recurse -Filter "*.csproj" | ForEach-Object {
    (Get-Content $_.FullName) -replace '<TargetFramework>net6.0</TargetFramework>',
        '<TargetFramework>net10.0</TargetFramework>' |
    Set-Content $_.FullName
}
```

### 2.3 升级NuGet包

```bash
# 步骤1：升级框架级包（Microsoft.AspNetCore.*）
# 这些包在.NET 10中可能已经不需要显式引用了（内置到框架中）
# 具体哪些需要移除取决于当前.csproj中的引用

# 步骤2：升级核心依赖包
# 按照NuGet兼容性报告中的目标版本逐一升级

# 对整个解决方案统一升级（如果有Directory.Packages.props）
dotnet outdated JNPF.sln --upgrade

# 或者对单个项目逐一升级（更可控）
# 在每个项目目录下执行：
dotnet add package SqlSugar --version [目标版本]
dotnet add package Serilog.AspNetCore --version [目标版本]
# ... 其他包
```

**升级顺序建议：**

```
先升级不影响编译的包（底层基础设施）
├── 1. Serilog.AspNetCore
├── 2. Serilog.Sinks.File
├── 3. CSRedisCore
├── 4. Newtonsoft.Json（通常不需要改版本）
│
再升级可能有API变化的包
├── 5. SqlSugar（最核心，优先验证）
├── 6. Quartz.NET
├── 7. RabbitMQ.Client
├── 8. Mapster
│
最后升级UI/API相关包
├── 9. Swashbuckle.AspNetCore
├── 10. MiniProfiler
└── 11. 其他
```

### 2.6 .NET 6 → .NET 10 常见破坏性变更清单

以下是JNPF技术栈最可能遇到的破坏性变更，**按可能性从高到低排列**：

```
═══════════════════════════════════════════════════════════════
 高概率遇到的变更（几乎一定会影响JNPF）
═══════════════════════════════════════════════════════════════

1. System.Text.Json 行为变化
   影响范围：所有使用JSON序列化/反序列化的地方
   具体变化：
   ├── .NET 8+: JsonPropertyName大小写不敏感匹配为默认
   ├── .NET 8+: JsonSerializable源生成器行为变化
   ├── .NET 8+: System.Text.Json和Newtonsoft.Json混用时的默认选择
   └── JNPF中大量使用Newtonsoft.Json(JsonConvert)，
       需确认.NET 10下是否仍有正确的Newtonsoft.Json注册
   
   检查方法：
   grep -r "JsonConvert\|Newtonsoft" --include="*.cs" | wc -l
   # 如果数量很大（>100处），说明JNPF重度依赖Newtonsoft，
   # 需要在.NET 10中确保Newtonsoft仍然是默认JSON处理器

   修复示例：
   // 确保Startup.cs中有：
   services.AddControllers()
       .AddNewtonsoftJson(options => {
           options.SerializerSettings.DateFormatString = "yyyy-MM-dd HH:mm:ss";
           // 保持与.NET 6一致的序列化行为
       });

2. ASP.NET Core 认证/授权中间件管道
   影响范围：所有使用[Authorize]的地方
   具体变化：
   ├── .NET 8+: 授权中间件(app.UseAuthorization)行为微调
   ├── .NET 8+: [Authorize]的默认策略处理变化
   ├── .NET 8+: 认证方案的注册方式有推荐变化
   └── JNPF使用JWT认证，需要确认JWT Bearer的配置在.NET 10上等价

   检查方法：
   找到JNPF的JWT配置代码，对比.NET 10文档的推荐方式

3. 全局Using隐式引入
   影响范围：可能有命名冲突
   具体变化：
   ├── .NET 6+默认隐式引入System、System.Threading.Tasks等
   ├── .NET 10可能扩展隐式引入范围
   ├── 如果JNPF中有自定义的同名类，可能冲突
   └── 例如：JNPF如果有自己的System.IO.File扩展方法，可能与内置冲突

   检查方法：
   编译时搜索CS0104（歧义引用）错误

4. IHostBuilder vs WebApplicationBuilder
   影响范围：Program.cs / Startup.cs
   具体变化：
   ├── .NET 8+: 推荐使用WebApplicationBuilder（最小托管模型）
   ├── 但IHostBuilder仍然支持（向后兼容）
   └── JNPF如果用的是IHostBuilder模式，.NET 10下仍然可用
       不需要改为WebApplicationBuilder（升级期间不要重构）

   检查方法：
   查看Program.cs用的是哪种模式

═══════════════════════════════════════════════════════════════
 中概率遇到的变更（取决于JNPF的具体实现方式）
═══════════════════════════════════════════════════════════════

5. SignalR行为变化
   影响范围：如果JNPF的IM模块使用SignalR
   具体变化：
   ├── .NET 8+: SignalR的Hub连接管理有API变化
   ├── LongPolling传输在.NET 8+中有优化
   └── 如果JNPF用SignalR做在线用户/消息推送，需要验证

6. 日志Provider注册顺序
   影响范围：Startup.cs中的日志配置
   具体变化：
   ├── .NET 8+: ILoggerFactory的行为可能有细微变化
   └── 多个Provider同时注册时的输出行为可能不完全一致

7. HttpClient默认行为
   影响范围：所有使用HttpClient的地方
   具体变化：
   ├── .NET 8+: HttpClient的默认超时、重试策略有变化
   ├── .NET 8+: SocketsHttpHandler的默认连接池行为变化
   └── 如果JNPF用HttpClient调外部API，可能受影响

8. 文件提供程序(FileProvider)行为
   影响范围：静态文件服务
   具体变化：
   ├── .NET 8+: PhysicalFileProvider的行为有细微调整
   └── 如果JNPF有自定义的文件服务逻辑，需要验证

═══════════════════════════════════════════════════════════════
 低概率遇到但后果严重的变更
═══════════════════════════════════════════════════════════════

9. Blazor相关（如果使用）
   影响范围：如果JNPF的某些前端功能用了Blazor
   注意：JNPF是Vue3前端，大概率不用Blazor，但如果数据大屏或其他
   模块有Blazor Server渲染，需要检查

10. 数据保护API(DataProtection)行为变化
    影响范围：加密、Token生成
    具体变化：
    ├── .NET 8+: DataProtection的默认加密算法可能有变化
    ├── 如果JNPF的JWT密钥用了DataProtection，需要验证兼容性
    └── 已生成的token在升级后是否仍然可验证？
```

### 3.3 特别关注：JSON序列化兼容性测试

**这是.NET 6→10最容易出隐蔽Bug的地方。**

```
测试步骤：

1. 在.NET 6环境下（升级前分支）：
   ├── 创建一个复杂表单（包含20+控件类型）
   ├── 保存表单配置（VisualDev保存）
   ├── 导出该表单的JSON配置
   └── 记录一个工作流的JSON定义

2. 切换到.NET 10环境（升级后分支）：
   ├── 打开同一个表单 → 是否正确渲染？
   ├── 编辑并保存 → 是否正确持久化？
   ├── 导出JSON → 与.NET 6的导出是否一致（结构和值）？
   └── 工作流是否正确加载和执行？

3. 反向测试：
   ├── 在.NET 10环境中新建表单
   ├── 导出JSON
   ├── 切到.NET 6环境导入 → 是否正常？
   └── 目的：确认序列化格式双向兼容

重点关注：
├── 日期格式是否一致（"2025-01-01T00:00:00" vs "2025-01-01 00:00:00"）
├── 枚举序列化是否一致（数字 vs 字符串）
├── null值处理是否一致
├── 数字精度是否一致（decimal/float/double）
└── 特殊字符（中文、emoji）处理是否一致
```
