### 二、缺漏2：eval 内部的语义深度扫描（表达式引擎的靶向目标）
架构师只让你数 `eval` 出现了多少次。这毫无意义。1 次 `eval(复杂的异步闭包)` 和 99 次 `eval('formData.age > 18')`，对架构重构的挑战完全不同。
**必须补充的侦察指令：**
```bash
# 1. 提取所有 eval / new Function 的实际入参字符串
# 这是表达式引擎必须 100% 兼容的语法子集
grep -rnPo "(eval|new Function)\s*\(\s*['\"](.*?)['\"]" $WEB/src/ --include="*.js" --include="*.ts" --include="*.vue" > ~/jnpf-survey/web/eval-params-exact.txt
# 2. 扫描表达式是否引用了全局变量或复杂上下文（这是安全引擎的死穴）
# 如果 eval 里出现了 window, document, $store, uni 等，说明表达式不是纯函数，IR 无法无损表达
grep -rnPo "(eval|new Function)\s*.*?(window|document|\$store|\$parent|uni|this)" $WEB/src/ --include="*.js" --include="*.ts" --include="*.vue" > ~/jnpf-survey/web/eval-impure.txt
```
**为什么重要？** 如果 `eval` 里大量使用了 `this.$store` 或 `window`，说明你的安全表达式引擎必须设计“上下文注入机制”；如果都是纯数据比较，直接上 AST 解析即可。

### 三、缺漏3：组件元数据与接口契约扫描（代码生成器的物料清单）
架构师让你扫“组件文件列表”，但代码生成器不需要文件列表，它需要的是**组件的 Props/Events/Slots 契约**。生成器必须知道给 `<BasicTable>` 传什么参数才是合法的。
**必须补充的侦察指令：**
```bash
# 1. 扫描核心业务组件（Parser, BasicTable, BasicForm）的 Props 定义
# 这是编译器生成模板代码的依据
for f in $(find $WEB/src/components -iname "*parser*" -o -iname "*basic*table*" -o -iname "*basic*form*" | grep ".vue$"); do
  echo "===== $f Props =====" >> ~/jnpf-survey/web/component-contracts.txt
  # 提取 defineProps 或 props: {} 内容
  grep -A 50 "defineProps\|props:" "$f" | head -80 >> ~/jnpf-survey/web/component-contracts.txt
  echo -e "\n\n" >> ~/jnpf-survey/web/component-contracts.txt
done
# 2. 扫描组件的 Emits 定义
for f in $(find $WEB/src/components -iname "*parser*" -o -iname "*basic*table*" -o -iname "*basic*form*" | grep ".vue$"); do
  echo "===== $f Emits =====" >> ~/jnpf-survey/web/component-emits.txt
  grep -A 20 "defineEmits\|emits:" "$f" | head -40 >> ~/jnpf-survey/web/component-emits.txt
done
```
**为什么重要？** OutSystems 的编译器之所以能生成源码，是因为它拥有所有底层组件精确的 TS 类型定义。没有契约，生成的代码就是一堆红波浪线。

架构师让你找“代码生成器的前端页面”，这又偏了。前端页面只是个壳，真正的毒瘤是**现在生成的代码到底有多烂**。你必须解剖现有的生成产物，才能定义新编译器的质量下限。

**为什么重要？** 如果 App 端有大量 DOM 操作和上千行条件编译，你的 UniApp 编译器就必须设计强大的“平台适配 IR 层”和“DOM 抹平层”。
