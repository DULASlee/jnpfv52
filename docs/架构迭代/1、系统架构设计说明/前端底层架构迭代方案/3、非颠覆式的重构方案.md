## 一、现状精确图谱——JNPF 前端到底怎么跑的

### 1.1 核心问题：前端代码在哪里？

```
通过代码探索发现——

web-vue3/src/views/ 下的页面代码：
  system/user/index.vue          — 用户列表（手写页面）
  system/role/index.vue          — 角色列表（手写页面）
  workflow/flowTask/TodoList.vue — 待办任务（手写页面）
  ...

这些是"硬编码页面"——直接用 Vue 组件写的，
不走低代码引擎，不走渲染器。

那"低代码引擎"在哪里？
```

### 1.2 低代码引擎的真正位置

JNPF 的低代码引擎不在运行时——它在**代码生成器**中。

```
JNPF 的低代码不是"运行时渲染 JSON"，
而是"配置 → 生成代码 → 部署生成的代码"。

流程：

  设计器（前端）               代码生成器（后端）          生成的项目
  ┌──────────┐               ┌──────────────┐          ┌──────────────┐
  │ 配置界面  │  → JSON配置  │ Velocity模板  │ → 源码   │ 独立Vue项目  │
  │（表单/列表│  ──────────→ │ Java后端     │ ──────→ │ （可运行）    │
  │/详情配置）│               │              │          │              │
  └──────────┘               └──────────────┘          └──────────────┘

  设计器输出的是 JSON 配置
  后端用 Velocity 模板把 JSON 配置编译成 Vue 代码
  生成的代码是独立的 Vue 项目
```

### 1.3 现有的"运行时渲染"

但 web-vue3 中确实也有运行时渲染——

```
web-vue3 中有两种页面：

类型 A：硬编码页面
  system/user/index.vue — 开发者手写的 Vue 组件
  这些页面不走任何引擎，直接是 Vue 代码

类型 B：动态渲染页面
  通过代码生成器生成的页面，部署在 web-vue3 中
  这些页面虽然看起来像硬编码，但实际上是生成出来的
  生成的代码质量差（85%重复），但确实是可运行的 Vue 代码

类型 C：实时渲染（如果有的话）
  某些设计器预览可能用了 JSON → Vue 的实时渲染
  这部分使用 eval + Parser 组件
```

### 1.4 现有代码生成的实现方式

```
代码生成器的核心在后端：

  后端 Java 代码（JNPF-CodeGenerator 模块）：
    template/web/vue/ — Velocity 模板文件
    src/main/java/.../generator/ — 生成器逻辑

  Velocity 模板的工作方式：
    读取配置 → 替换模板中的占位符 → 输出 .vue 文件

  模板示例（简化版）：
    <template>
      <div>
        #foreach($field in $fields)
        <el-form-item label="$field.label">
          <el-input v-model="formData.$field.name" />
        </el-form-item>
        #end
      </div>
    </template>

    <script setup>
    import { reactive } from 'vue';
    
    const formData = reactive({
      #foreach($field in $fields)
      $field.name: $field.defaultValue,
      #end
    });
    </script>

  这就是为什么生成的代码"85%重复"——
  因为模板只是简单地遍历配置，没有抽象和复用。
```

### 1.5 现有的渲染引擎组件

```
在 web-vue3 中找到的渲染相关组件：

  basic/         — 基础组件库（二次封装 UI 库组件）
    BasicForm.vue    — 表单渲染器
    BasicTable.vue   — 表格渲染器
    BasicDetail.vue  — 详情渲染器
    
  components/    — 通用组件
    jnpfParser/      — 动态组件解析器
    jnpfForm/        — 表单相关组件
    jnpfTable/       — 表格相关组件

  jnpfParser 的工作方式：
    输入：JSON Schema（字段配置数组）
    处理：遍历数组，根据字段类型选择组件，用 eval 计算可见性/校验
    输出：Vue 组件树

  BasicForm 的工作方式：
    输入：fields（字段配置数组）、formData（数据）
    处理：遍历 fields，为每个字段渲染对应的表单控件
    特殊：可见性用 eval 判断，联动用 watch + eval 实现
```

### 1.6 现有状态管理

```
web-vue3/src/store/ — Pinia stores

  modules/
    user.js     — 用户信息、Token、权限
    dict.js     — 字典数据缓存
    theme.js    — 主题配置
    
  设计：
    用户信息通过 Token → API 获取 → 存入 Pinia
    字典数据按需加载 → 缓存在 Pinia 中
    主题通过 CSS 变量控制
```

### 1.7 现有的数据获取方式

```
web-vue3/src/api/ — API 定义目录

  system/
    user.js    — 用户相关 API
    role.js    — 角色相关 API
    menu.js    — 菜单相关 API
    ...
  workflow/
    ...
    
  每个 API 文件的典型写法：

      return request({
        url: '/api/system/user/list',

      });
    }
    
    export function createUser(data) {
      return request({
        url: '/api/system/user/create',
        method: 'post',

      });
    }

  页面组件中的典型使用：

    const list = ref([]);
    const total = ref(0);

      loading.value = true;
      try {
        const res = await getUserList({ pageIndex, pageSize, ...searchParams });
        list.value = res.data.list;
        total.value = res.data.total;
      } finally {
        loading.value = false;
      }
    }
    
    onMounted(() => fetchData());

  问题：
    每个列表页面都重复这套 loading/data/total/fetchData 逻辑
    没有缓存（同一数据在不同页面重复请求）
    没有去重（同一请求可能被发送多次）
```

## 二、现有架构的精确分层

```
基于以上代码探索，JNPF 现有前端架构的真实分层是：

Layer 0：工程化
  Vite + Vue 3 + TypeScript（假严格）
  pnpm（未统一）
  ESLint（CI 断裂）

Layer 1：共享基础
  src/utils/request.js    — Axios 封装（拦截器 + Token 注入）
  src/utils/auth.js       — Token 存取
  src/utils/encryption.js — RSA + AES 加密
  src/utils/permission.js — 权限判断函数
  src/utils/common.js     — 通用工具

Layer 2：状态管理
  src/store/              — Pinia stores（user/dict/theme）

Layer 3：组件库
  src/components/jnpfParser/  — 动态组件解析器
  src/components/jnpfForm/    — 表单相关
  src/components/jnpfTable/   — 表格相关
  src/components/basic/       — UI 库二次封装
  src/components/common/      — 通用组件

Layer 4：业务页面
  src/views/              — 手写页面 + 生成器生成的页面

Layer 5：路由
  src/router/             — 动态路由（后端菜单 → 前端路由）

Layer 6：代码生成器
  后端 Java Velocity 模板
  前端只做配置采集（设计器）
```

**关键发现：现有架构没有"Layer 3：渲染引擎"和"Layer 2：数据引擎"这两个独立层。**

- 渲染逻辑散落在 `jnpfParser`、`BasicForm`、`BasicTable` 等组件中
- 数据获取逻辑散落在每个页面组件中（`loading`/`fetchData`/`list` 模式）

## 三、精确增强方案——在现有地基上加固

### 原则

```
不动：
  业务页面（src/views/）—— 这些页面在跑，不能动
  设计器（Designer）—— 用户在用，不能动
  后端代码生成器 —— 单独演进，不在前端重构范围内
  路由系统 —— 已经在用，不能动

加固：
  Layer 0 工程化 —— 补齐 Monorepo + TypeScript
  Layer 1 共享基础 —— 整合三项目共享

新建（但不替换现有组件，而是"包裹"或"增强"）：
  数据引擎 —— 在现有 API 层之上加一层，不替换现有 api/ 文件
  渲染引擎 —— 在现有 jnpfParser 之上加一层，不替换现有组件
  表达式引擎 —— 替换 eval，但输出兼容现有接口
  组件注册表 —— 管理现有组件，不替换组件本身
```

### 3.1 Layer 0 加固：工程化基座

```
现状：
  web-vue3：Vite + Vue 3 + TS（假严格）+ ESLint（CI 断裂）
  datascreen：零 TS、零 Lint、零 CI
  app：零 TS、零 Lint、HBuilder X 绑定

增强方案（不重造）：
  ① web-vue3 的 tsconfig.json 开启 strict 逐步收紧
    第一步：noImplicitAny: true（最痛但最重要）
    第二步：strictNullChecks: true
    第三步：strict: true
    每一步都是一轮修复 + 验证 + 封存

  ② ESLint 门禁修复
    移除 continue-on-error
    将现有 warnings 逐步转化为 errors
    新代码必须通过，旧代码宽限期

  ③ Monorepo 迁移
    pnpm-workspace.yaml 管理三个项目
    packages/shared/ — 共享代码
    apps/web-vue3/   — 主项目（原位不动，只改 package.json）
    apps/datascreen/ — 大屏
    apps/app/        — UniApp
    
    时机：F-1 阶段执行

  ④ app 脱离 HBuilder X
    将 app 迁移到 Vite + @dcloudio/vite-plugin-uni
    保留现有功能不变，只换构建工具
    时机：F-1 后期

影响范围：
  零业务代码改动
  只改工程配置文件
  CI 流程优化
```

### 3.2 Layer 1 增强：共享基础

```
现状：
  三项目各自有 request.js / auth.js / encryption.js

增强方案（不替换）：
  在 packages/shared/ 中创建 @jnpf/shared 包
  将三项目共有的逻辑迁移到共享包中
  三项目通过 import from '@jnpf/shared' 引用
  
  迁移顺序（从风险最低的开始）：
    ① utils（日期、数字、字符串工具）—— 零风险
    ② types（TypeScript 类型定义）—— 零风险
    ③ encryption（加密函数）—— 低风险
    ④ permission（权限判断）—— 低风险
    ⑤ auth（Token 管理）—— 中风险
    ⑥ request（HTTP 封装）—— 高风险（最后做）

  request.js 的迁移策略：
    不是"把三个项目合并成一个 request.js"
    而是"在共享包中定义标准接口，各项目实现适配器"
    
    @jnpf/shared/http 定义接口：
      interface HttpClient {
        get<T>(url: string, params?: unknown): Promise<T>;
        post<T>(url: string, data?: unknown): Promise<T>;
        put<T>(url: string, data?: unknown): Promise<T>;
        delete<T>(url: string): Promise<T>;
      }
    
    各项目提供自己的 HttpClient 实现（基于各自的 Axios 配置）
    统一错误处理、Token 注入、重试策略在共享层

影响范围：
  每个业务页面的 import 路径会变化
  但 API 签名不变，行为不变
```

### 3.3 数据层增强：在现有 API 层上加缓存 + 统一获取模式

```
现状：
  src/api/system/user.js     — getUserList(params)
  src/api/system/role.js     — getRoleList(params)
  每个页面自己管理 loading/data/total/fetchData

  典型的列表页面代码（重复了几十次）：
    
    const loading = ref(false);
    const list = ref([]);
    const total = ref(0);
    const pagination = reactive({ pageIndex: 1, pageSize: 20 });
    
    async function fetchData() {
      loading.value = true;
      try {
        const res = await getUserList({
          ...searchParams,
          pageIndex: pagination.pageIndex,
          pageSize: pagination.pageSize,
        });
        list.value = res.data.list;
        total.value = res.data.total;
      } catch (err) {
        console.error(err);
      } finally {
        loading.value = false;
      }
    }
    
    function handleSearch() {
      pagination.pageIndex = 1;
      fetchData();
    }
    
    function handlePageChange(page) {
      pagination.pageIndex = page;
      fetchData();
    }
    
    onMounted(() => fetchData());

增强方案（不替换 api/ 文件）：
  在现有 API 函数之上封装 composables
  
  新增文件：src/composables/useTableData.ts（不修改任何现有文件）

  function useTableData<T>(
    fetcher: (params: Record<string, unknown>) => Promise<{ list: T[]; total: number }>,
    options?: {
      defaultPageSize?: number;
      immediate?: boolean;
      cacheTime?: number;
    }
  ) {
    const loading = ref(false);
    const list = ref<T[]>([]) as Ref<T[]>;
    const total = ref(0);
    const pagination = reactive({
      pageIndex: 1,
      pageSize: options?.defaultPageSize ?? 20,
    });
    
    const searchParams = reactive<Record<string, unknown>>({});
    
    // 缓存
    let cache: { key: string; data: { list: T[]; total: number }; timestamp: number } | null = null;
    
    async function fetchData(params?: Record<string, unknown>) {
      const mergedParams = {
        ...searchParams,
        ...params,
        pageIndex: pagination.pageIndex,
        pageSize: pagination.pageSize,
      };
      
      // 缓存检查
      const cacheKey = JSON.stringify(mergedParams);
      if (cache?.key === cacheKey && Date.now() - cache.timestamp < (options?.cacheTime ?? 30_000)) {
        list.value = cache.data.list;
        total.value = cache.data.total;
        return;
      }
      
      loading.value = true;
      try {
        const res = await fetcher(mergedParams);
        list.value = res.data.list;
        total.value = res.data.total;
        
        cache = { key: cacheKey, data: { list: res.data.list, total: res.data.total }, timestamp: Date.now() };
      } catch (err) {
        throw err;
      } finally {
        loading.value = false;
      }
    }
    
    function handleSearch() {
      pagination.pageIndex = 1;
      fetchData();
    }
    
    function handlePageChange(page: number) {
      pagination.pageIndex = page;
      fetchData();
    }
    
    function handleSizeChange(size: number) {
      pagination.pageSize = size;
      pagination.pageIndex = 1;
      fetchData();
    }
    
    function refresh() {
      cache = null;
      fetchData();
    }
    
    // 立即加载
    if (options?.immediate !== false) {
      onMounted(() => fetchData());
    }
    
    return {
      loading,
      list,
      total,
      pagination,
      searchParams,
      fetchData,
      handleSearch,
      handlePageChange,
      handleSizeChange,
      refresh,
    };
  }

使用方式（对比）：

  之前（每个页面重复写）：
    const loading = ref(false);
    const list = ref([]);
    const total = ref(0);
    const pagination = reactive({ pageIndex: 1, pageSize: 20 });
    async function fetchData() { ... }  // 30 行
    function handleSearch() { ... }
    function handlePageChange() { ... }
    onMounted(() => fetchData());

  之后（一行搞定）：

      = useTableData(getUserList);

影响范围：
  现有页面可以逐步迁移（不是强制替换）
  新页面直接用 useTableData
  现有 api/ 文件不需要改
```

```
同样的思路扩展到其他场景：

  useFormData — 表单数据管理（loading、submit、reset、validate）
  useDetailData — 详情数据加载
```

### 3.4 表达式引擎：替换 eval，但保持兼容

```
现状：
  BasicForm 中：
    if (item.visible) {
      const visible = new Function('data', 'return ' + item.visible)(formData);
    }
    
  jnpfParser 中：
    eval('return ' + expression)
    
  大屏 datascreen 中：
    funEval(formatter)  // eval 包装

增强方案：
  创建 src/utils/expression.ts
  提供一个 safeEval 函数，签名与 eval 完全兼容
  
  不替换现有组件，而是替换组件内部的 eval 调用

  核心设计：

  class ExpressionEngine {
    // 编译缓存
    private cache = new Map<string, CompiledFn>();
    
    // 安全求值（签名兼容 new Function）
    evaluate(expression: string, context: Record<string, unknown>): unknown {
      if (!expression) return undefined;
      
      let compiled = this.cache.get(expression);
      if (!compiled) {
        compiled = this.compile(expression);
        this.cache.set(expression, compiled);
      }
      
      return compiled(context);
    }
    
    private compile(expression: string): CompiledFn {
      // Tokenize
      const tokens = this.tokenize(expression);
      
      // Parse → AST
      const ast = this.parse(tokens);
      
      // Security check
      this.securityCheck(ast);
      
      // Compile → executable function
      return this.generate(ast);
    }
  }

  // 全局实例
  export const exprEngine = new ExpressionEngine();
  
  // 兼容函数——替换 eval 时只需改一行
  export function safeEval(expression: string, data: Record<string, unknown>): unknown {
    return exprEngine.evaluate(expression, { formData: data, ...data });
  }

替换方式（最小侵入）：

  之前：
    const visible = new Function('data', 'return ' + item.visible)(formData);
    
  之后（只改这一行）：
    const visible = safeEval(item.visible, formData);

  之前：
    eval('return ' + expression);
    
  之后：
    safeEval(expression, context);

  不改组件结构，不改业务逻辑，只替换表达式求值方式。

分批替换策略：

  第一批：BasicForm.vue 中的 eval（表单可见性 + 校验）
    影响范围：所有使用 BasicForm 的页面
    验证方式：配置相同的表单，对比 eval 和 safeEval 的输出
    
  第二批：jnpfParser 中的 eval
    影响范围：所有使用 Parser 的动态渲染页面
    
  第三批：datascreen 中的 eval
    影响范围：大屏组件注册和数据格式化

  每一批都是独立的 PR，独立验证，独立合并。
```

### 3.5 渲染引擎：在现有 jnpfParser 基础上增强

```
现状：
  jnpfParser 的工作方式：
    输入：JSON Schema（字段配置数组）
    处理：
      for (const field of schema) {
        switch (field.type) {
          case 'input': return <el-input v-model={formData[field.name]} />;
          case 'select': return <el-select v-model={formData[field.name]}> ... </el-select>;
          case 'table': return <el-table ... />;
          case 'detail': return <DetailRenderer ... />;
          default: return null;
        }
      }

  问题：
    switch-case 无法扩展（加新组件需要改源码）
    渲染逻辑和数据逻辑混在一起
    没有统一的组件注册机制

增强方案（不重写 Parser，在它之上建一层）：

  第一步：抽象组件注册表（不改 Parser，新增）

    src/core/componentRegistry.ts

    const registry = new Map<string, ComponentEntry>();
    
    // 注册现有组件
    registry.set('input', { component: Input, props: [...] });
    registry.set('select', { component: Select, props: [...] });
    registry.set('table', { component: BasicTable, props: [...] });
    // ...
    
    // 第三方/自定义组件也可以注册
    registry.set('echarts:bar', { component: EChartsBar, props: [...] });
    registry.set('custom:map', { component: MapComponent, props: [...] });

  第二步：增强 Parser 使用注册表（逐步替换 switch-case）

    之前：
      switch (field.type) {
        case 'input': return <el-input />;
        case 'select': return <el-select />;
        // 50 个 case...
      }
    
    之后：
      const entry = registry.get(field.type);
      if (entry) {
        return h(entry.component, resolveProps(field, entry.props, formData));
      }
      
    好处：
      新组件不需要改 Parser 源码，只需要注册
      大屏组件、自定义组件自动支持

  第三步：封装 SchemaRenderer（可选，不影响现有代码）

    新增一个 Vue 组件：
    
    <template>
      <SchemaRenderer :schema="pageSchema" :data="formData" />
    </template>
    
    内部使用增强后的 Parser + 注册表
    
    现有代码不需要改，新代码可以选择用 SchemaRenderer

影响范围：
  Parser 的外部接口不变（输入还是 JSON Schema，输出还是 Vue 组件）
  内部实现从 switch-case 变为注册表查找
  新增 SchemaRenderer 组件供新代码使用
```

### 3.6 表单引擎：增强 BasicForm，不替换

```
现状：
  BasicForm.vue 的工作方式：
    props: fields（字段配置）、modelValue（数据）
    遍历 fields，为每个字段渲染 el-form-item + 对应控件
    可见性：new Function('data', 'return ' + visible)(formData)
    校验：ElForm 的 rules 对象
    联动：在组件内部 watch formData 的某些字段

增强方案（直接修改 BasicForm.vue 内部实现）：

  改动 1：替换 eval → safeEval（上一节已描述）

  改动 2：抽取 useForm composable（不改 BasicForm 的 props 接口）

    创建 src/composables/useForm.ts
    
    function useForm(options) {
      return {
        formData,        // reactive
        errors,          // 校验错误
        isDirty,         // 是否修改过
        validate,        // 手动校验
        reset,           // 重置
        submit,          // 提交（防重复）
      };
    }
    
    BasicForm 内部使用 useForm：
    
    // 之前（散落在 BasicForm 的 setup 中）
    const formData = reactive({});
    const errors = ref({});
    function validate() { ... }
    
    // 之后（抽取到 useForm，BasicForm 的 setup 更简洁）
    const form = useForm({ fields: props.fields, modelValue: props.modelValue });
    
    // BasicForm 的 props 接口不变——
    // 外部使用 BasicForm 的方式不需要任何改动

  改动 3：联动逻辑集中化

    现在：联动逻辑分散在 BasicForm 的 watch 中
    之后：集中到 useForm 的 LinkageEngine 中
    
    linkages: [
      { trigger: 'province', effect: { target: 'city', action: 'refresh' } },
      { trigger: 'status', effect: { target: 'reason', action: 'visible', when: 'status == 0' } },
    ]
    
    useForm 内部自动处理联动
    不需要每个表单都手写 watch

影响范围：
  BasicForm 的外部接口（props）不变
  内部实现增强
  使用 BasicForm 的页面不需要改动
```

### 3.7 组件注册表：管理现有组件，不替换

```
现状：
  组件分散在：
    src/components/basic/       — UI 库二次封装
    src/components/jnpfParser/  — 动态组件
    src/components/jnpfForm/    — 表单组件
    src/components/jnpfTable/   — 表格组件
    src/components/common/      — 通用组件

增强方案：
  创建 src/core/componentRegistry.ts
  不移动任何现有组件，只是"登记"它们
  
  // 注册 BasicForm
  registry.register('form:basic', {
    component: () => import('@/components/basic/BasicForm.vue'),
    category: 'form',
    defaultProps: { ... },
  });
  
  // 注册 BasicTable
  registry.register('table:basic', {
    component: () => import('@/components/basic/BasicTable.vue'),
    category: 'data',
    defaultProps: { ... },
  });
  
  // 大屏组件也可以注册
  registry.register('chart:bar', {
    component: () => import('@/components/chart/BarChart.vue'),
    category: 'chart',
    defaultProps: { ... },
  });

价值：
  增强后的 Parser 通过注册表查找组件
  新组件注册即可用，不需要改 Parser 源码
  设计器可以动态展示"有哪些组件可以用"
  代码生成器可以知道"这个组件的代码怎么生成"

实现方式：
  现有组件完全不动
  注册表只是一个 Map<string, ComponentEntry>
  组件通过动态 import 懒加载
  注册表在应用启动时初始化
```

### 3.8 模块宿主：增强现有路由系统

```
现状：
  src/router/index.js — 路由配置
  后端返回菜单配置 → 前端动态 addRoute

  现有的"模块"概念：
    就是目录（src/views/system/、src/views/workflow/）
    没有模块生命周期
    没有模块间接口
    没有模块隔离

增强方案（在现有路由系统上加一层）：

  创建 src/core/moduleHost.ts
  不替换现有路由，而是在路由之上加模块生命周期

  // 模块定义（比完整的 ModuleDefinition 简化很多）
  const systemModule = {
    id: 'system',
    name: '系统管理',
    
    // 组件注册（增强现有注册表）
    register(registry) {
      registry.register('system:user-select', { ... });
      registry.register('system:dept-tree', { ... });
    },
    
    // 权限定义（从后端菜单配置自动提取）
    permissions: [
      'sys:user:list', 'sys:user:add', 'sys:user:update', 'sys:user:delete',
      'sys:role:list', 'sys:role:add', ...
    ],
  };
  
  const workflowModule = {
    id: 'workflow',
    name: '工作流',
    dependencies: ['system'],  // 依赖系统管理模块
    
    register(registry) {
      registry.register('workflow:flow-designer', { ... });
      registry.register('workflow:task-list', { ... });
    },
    
    permissions: ['wf:task:todo', 'wf:task:done', ...],
  };

  // 模块宿主
  const host = new ModuleHost();
  host.register(systemModule);
  host.register(workflowModule);
  host.loadAll(); // 拓扑排序 → 依次初始化
  
  现有路由不需要改。
  模块宿主在路由之上提供：
    ① 模块初始化顺序（拓扑排序）
    ② 组件注册（在路由加载之前就注册好）
    ③ 权限收集（从所有模块收集权限码）
    ④ 模块间接口（expose/invoke）
```

## 六、核心区别

```
之前的方案（重造）：
  设计 JADF → 定义 9 块骨骼 → 从零构建 → 替换现有系统
  风险：推倒重来，工期不可控，业务中断

现在的方案（增强）：
  理解现状 → 识别可加固/可替换的点 → 逐点增强 → 兼容现有
  风险：逐点验证，可随时回退，业务不受影响

类比：
  之前：拆掉现有大楼，盖新大楼
  现在：在现有大楼里加固承重墙、升级水电线路、
       更换老旧电梯、重新粉刷——大楼一直在住人，一直在服务
```
