## 四、最有价值的改进建议（按优先级排序）

### 🔴 P0：AI 原生能力建设（战略级紧迫）

这是 2026 年低代码平台的生死线。JNPF 宣传已有 AI 快速建表等能力，但源码中 `inteAssistant` 模块实际是集成助手（WebHook + 定时任务），不是 AI 助手。需要立即启动真正的 AI 模块。

建议实施路径：

阶段一（1-2 月）：AI 快速建表

├── 接入大模型 API（DeepSeek/通义千问/文心一言）

├── 自然语言 → 解析表单结构 → 生成 FormGenerator JSON

├── 复用现有 VisualDevService 的 Create/Update 接口

└── 前端增加 AI 输入入口（对话框 → 生成 → 预览 → 确认）

阶段二（2-3 月）：AI 推荐字段 + AI 创建流程

├── 基于表单上下文推荐关联字段和校验规则

├── 自然语言 → 解析流程节点 → 生成 FlowProcess JSON

└── 与现有 FlowTaskNodeTypeEnum（start/approver/condition/timer/subFlow/end）对齐

阶段三（3-6 月）：AI Agent

├── 多轮对话式应用构建

├── 智能数据分析 + 报表自动生成

└── AI 驱动的流程自动化决策

关键技术要点：

- 不是"外挂"大模型 API，而是让 AI 生成的 JSON 直接进入现有 `VisualDevService.Create()` 管道
- 控件映射：自然语言中的"姓名"→ `jnpfKey: 'input'`，"部门"→ `jnpfKey: 'depSelect'`，"日期"→ `jnpfKey: 'datePicker'`，利用已有的 55+ 控件定义
- 现有 `componentMap.ts` 就是最好的 AI 输出 Schema——让大模型输出 `GenItem[]` 格式

### 🟡 P1：流程引擎增强

| 缺失能力     | 行业标准                 | 建议方案                                                     |
| :----------- | :----------------------- | :----------------------------------------------------------- |
| 并行网关     | BPMN 2.0 ParallelGateway | 在 `FlowTaskNodeTypeEnum` 增加 `parallel`/`join` 节点类型    |
| 会签/或签    | 多人审批模式             | 扩展 `ApproverNode` 的属性面板，增加 `approvalType: 'countersign' |
| 定时边界事件 | 审批超时自动转审         | 复用现有 `timer` 节点，增加与 `approver` 的关联              |
| 流程版本管理 | 历史版本对比/回滚        | 扩展 `FlowTemplateUtil`，增加版本快照机制                    |

### 🟡 P2：连接器生态 + 应用市场

现状：`IntegrateService` + `WebHookService` 提供基础集成能力，但缺乏标准化连接器。

建议：

1. 连接器框架：抽象 `IConnector` 接口，标准化第三方系统集成（ERP/CRM/OA/钉钉/企微/飞书）
2. 应用模板市场：利用现有的 `VisualDevService.ActionsCopy()` + `ExportJson.json.vm` 导入导出能力，构建在线模板库
3. 预置行业模板：制造业（MES/WMS）、政务（审批/公文）、教育（学生管理）等

### 🟢 P3：开发者体验优化

| 改进点           | 当前痛点                                | 建议                                                    |
| :--------------- | :-------------------------------------- | :------------------------------------------------------ |
| 代码生成模板升级 | Velocity 模板维护成本高，93 个文件      | 考虑迁移到 Razor/Scriban 模板引擎，或增加模板可视化编辑 |
| 表单设计器 UX    | 控件属性面板偏简陋                      | 增加实时预览、控件搜索、最近使用                        |
| 前端代码质量     | 生成代码用 `@@/` 路径别名(实际是 `/@/`) | 修正 .vm 模板中的路径错误                               |
| TypeScript 支持  | 生成的前端代码类型注解不完整            | 增强 `api.ts.vm` 和 `columnList.ts.vm` 的类型定义       |

### 🟢 P4：数据分析深化

简道云在数据看板方面领先。JNPF 已有 `VisualData`（数据可视化）模块，建议：

- 增加交互式数据分析能力（下钻/联动/筛选）
- 支持 SQL 自定义查询 + 可视化图表绑定
- AI 辅助的智能数据洞察

## 六、给您的行动建议

1. 立即启动 AI 模块——这不是锦上添花，是 2026 年的生存能力。JNPF 的最大优势是已有完整的元数据体系（`componentMap.ts` 的 55+ 控件定义 + `VisualDevService` 的 CRUD 管道），AI 只需生成正确的 JSON Schema 即可接入现有流水线，技术上完全可行且成本可控。
2. 不要追赶简道云的"零代码易用性"——那是简道云的护城河。JNPF 的护城河是源码交付 + 私有化 + 深度定制 + 信创，应该在这条路上深挖，做"给专业 IT 团队用的 AI 低代码平台"。
3. 先做 AI 建表 Demo，再做流程和 Agent——控制节奏，先用最小代价证明价值。`VisualDevService.Create()` 已经是现成的入口，AI 只需要学会输出 `GenItem[]` JSON。
4. 考虑发起一个独立的 AI 模块工程——在 `backend/modularity/` 下新建 `ai` 模块（`JNPF.AI.Application`、`JNPF.AI.Domain`），不要在 `inteAssistant` 上改造，那是集成助手，职责不同。

如果您认可这个分析方向，我可以立即进入下一步——为 P0 AI 快速建表 制定具体的技术施工包，包括大模型接入架构、Prompt Engineering 设计、`GenItem[]` Schema 规范和 VisualDevService 对接方案。

JNPF 低代码引擎采用「VisualDev 设计 → RunService 在线运行 / CodeGenService Velocity 模板出码」双轨架构，支持 4 种表关系模式、5 类节点工作流、50+ 表单控件，PC/App/DataV 三端共享后端 API。

已完成 JNPF 低代码平台八大能力边界调研：权限为 RBAC+组织数据权限+列/字段权限；多租户支持 SCHEMA/COLUMN 与独立库；API 由 Service 经 DynamicApiController 自动生成；集成含 OAuth/WebHook/WebSocket/EventBus/RabbitMQ；报表以 PrintDev 打印模板为主、缺独立聚合报表；门户 VisualPortal 拖拽设计器完整；无应用/模板市场（仅有 JSON 导入导出）；SqlSugar 支持 SQL Server/MySQL/Oracle/PostgreSQL/达梦/人大金仓。

两个深度探索子代理均已完成。基于它们的发现，我需要对上面的分析做一个重要修正：

修正：工作流引擎能力比我初始判断更强。 子代理在 `ApproversProperties` 中发现 `counterSign` 字段已支持三种模式（0=或签、1=会签、2=依次审批），并支持会签比例配置 `counterSignConfig`。因此 P1 中关于"缺会签/或签"的建议应调整为——缺的是并行网关（ParallelGateway）和定时边界事件，会签/或签已具备。

此外，子代理还发现了一个比 AI 之外同样严重的短板：聚合报表/BI 引擎完全缺失（架构文档自身也标注为"严重缺失"），以及应用模板市场未实现（仅有 JSON 导入导出）。这两项在竞品对比中（简道云的数据看板、宜搭的行业模板库）都是明显差距。

综合两个子代理的调研结果，上面分析报告中的 P0（AI 原生能力）依然是第一优先级，但 P2 应上调报表/BI 引擎的优先级，与连接器生态并列。
