这个洞察非常精准。任务分解确实是多Agent协作中最关键的"隐形杠杆"——Fugu的7B Conductor之所以能超越单体大模型，核心能力之一就是**将复杂任务分解为模型可可靠执行的子任务**。

让我深入分析这个环节，并设计一个可落地的"任务分解层"。

---

## 一、为什么任务分解是"质量杠杆"

### 1.1 当前JNPF流水线的隐含假设

```
当前Phase 3 Plan → Phase 4 Build 的假设：
"架构师输出的方案足够详细，开发者可以直接执行"

实际情况：
- 架构师输出《数据模型蓝图》+《API定义》
- 开发者面对：Entity→Service→Controller→前端→测试，5个并行维度
- 每个维度又含：字段定义→验证规则→权限配置→异常处理→日志
```

**问题**：Phase 3 的"Plan"粒度太粗，Phase 4 的"Build"被迫同时处理**架构决策+实现细节+交叉验证**，认知负荷爆炸。

### 1.2 任务分解的量化收益

| 分解维度       | 未分解             | 分解后               | 收益来源                   |
| :------------- | :----------------- | :------------------- | :------------------------- |
| **上下文窗口** | 单任务占用80%      | 子任务各占用30%      | 每个子任务有更多"思考预算" |
| **错误定位**   | 失败需排查5个维度  | 失败定位到具体子任务 | 调试时间↓70%               |
| **回滚成本**   | 全量回滚           | 单个子任务回滚       | 修复成本↓60%               |
| **并行度**     | 伪并行（文件冲突） | 真并行（子任务隔离） | 执行效率↑40%               |
| **验证精度**   | 端到端模糊验证     | 子任务精确验证       | 漏检率↓50%                 |

## 二、任务分解角色的定位：Planner（规划师）

### 2.1 与现有角色的关系

```
┌─────────────────────────────────────────────────────────────┐
│  Phase 2 Brainstorm → 架构师（Architect）                    │
│  ├── 输出：2-3个可选方案 + 失效边界 + 风险点                  │
│  └── 不承诺具体实现路径                                       │
├─────────────────────────────────────────────────────────────┤
│  ⭐ NEW: Phase 2.8 Decompose → 规划师（Planner）              │
│  ├── 输入：架构师选定的方案                                   │
│  ├── 职责：将方案分解为可独立执行、可验证的原子任务           │
│  └── 输出：《任务分解清单》+《依赖图》+《验收标准》           │
├─────────────────────────────────────────────────────────────┤
│  Phase 3 Plan → 原Plan被Planner替代，或合并为"详细设计"       │
│  ├── 输入：Planner的任务分解清单                              │
│  ├── 职责：为每个原子任务指定具体实现策略                     │
│  └── 输出：每个子任务的《实现方案》                           │
├─────────────────────────────────────────────────────────────┤
│  Phase 4 Build → 开发者（Coder）                             │
│  ├── 输入：单个子任务的《实现方案》                           │
│  ├── 职责：原子任务实现                                       │
│  └── 输出：代码 + 单元验证                                    │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 Planner的核心能力

| 能力         | 说明                                         | 与Architect的区别                                |
| :----------- | :------------------------------------------- | :----------------------------------------------- |
| **边界识别** | 识别任务间的天然边界（数据层/逻辑层/表现层） | Architect关注模块间边界，Planner关注实现步骤边界 |
| **依赖排序** | 确定任务执行顺序（数据库→API→前端）          | Architect不承诺顺序，Planner必须确定             |
| **验收标准** | 为每个子任务定义"完成"的精确标准             | Architect定义功能标准，Planner定义实现标准       |
| **资源估算** | 估算每个子任务的Token/时间成本               | Architect不做估算，Planner需控制预算             |
| **回滚策略** | 定义每个子任务失败时的回退路径               | Architect不处理失败，Planner必须预设             |

## 三、Planner的实现：不是新角色，是"模式增强"

### 3.1 最小实现：在现有架构师模式中增加"分解阶段"

**不新增独立角色**，而是在 `architect.md` 中增加分解能力：

```markdown
<!-- .claude/subagents/architect.md 增加分解章节 -->

## 阶段 2.8: 任务分解（Decompose）

在输出《架构设计说明书》后，Architect 必须继续执行分解：

### 分解原则

1. **原子性**：每个子任务只修改一个文件或一个紧密耦合的文件组
2. **可验证性**：每个子任务有明确的"完成"判断标准（编译通过/测试通过/截图匹配）
3. **无环依赖**：子任务依赖图必须是有向无环图（DAG）
4. **Token预算**：每个子任务的预估Token消耗 < 4000（占128K context的3%）

### 分解输出格式

```markdown
## 任务分解清单

### 子任务 1: [名称]
- **目标**：[一句话]
- **输入**：[前置子任务的输出]
- **输出**：[具体文件/函数/配置]
- **验收标准**：[可验证的条件]
- **预估Token**：[N]
- **依赖**：[前置子任务编号，无则填"-"]
- **回滚策略**：[失败时如何恢复]

### 子任务 2: [名称]
...
```

### 分解检查清单

- [ ] 所有子任务的输出合并 = 完整实现架构师方案
- [ ] 无遗漏的交叉依赖（如Entity变更→DTO→前端）
- [ ] 每个子任务可在 < 10 分钟内完成
- [ ] 子任务数 ≤ 7（认知负荷上限）
```

### 3.2 进阶实现：独立Planner模式（推荐）

当团队熟悉分解后，可升级为独立模式：

```markdown
<!-- .claude/subagents/planner.md -->
---
name: planner
description: JNPF 任务规划师。将架构方案分解为可执行的原子任务。
tools: Read, Grep, Glob
---

你是 JNPF v5.2 项目的任务规划师。你的唯一职责是**分解**，不实现、不审查。

## 输入
- 《架构设计说明书》（来自Architect）
- 项目目录结构（通过Glob获取）
- 相关规则文件（low-code-principles.md, jnpf-expert-traps.md）

## 输出
《任务分解清单》+《依赖图》+《子任务验收标准》

## 分解策略

### 策略1: 按数据流分解（推荐用于CRUD功能）
```
数据库迁移 → Entity定义 → Repository实现 → Service实现 → API暴露 → 前端页面 → 集成测试
```

### 策略2: 按风险分解（推荐用于架构变更）
```
高风险核心逻辑 → 低风险适配层 → 前端兼容 → 回归测试
```

### 策略3: 按并行度分解（推荐用于独立模块）
```
模块A独立实现 || 模块B独立实现 || 模块C独立实现 → 集成联调
```

## 禁止
- 不分解直接输出"按架构师方案实现"
- 子任务粒度超过一个文件组
- 遗漏跨模块依赖（如Entity变更→前端DTO）
- 不定义验收标准
```

## 六、与Fugu本质的对比

| Fugu能力             | 你的Planner实现                             | 差距                       |
| :------------------- | :------------------------------------------ | :------------------------- |
| 7B Conductor动态分解 | **规则模板分解**（策略1/2/3）               | 无RL优化，但可人工迭代规则 |
| 专家模型池动态选择   | **固定角色映射**（Architect→Planner→Coder） | 无动态选择，但阶段明确     |
| 递归自我纠错         | **子任务失败→回滚策略→重新调度**            | 需人工触发，非自动         |
| 真实任务反馈优化     | **mistake-log.md积累→人工复盘**             | 无自动优化，但可手动改进   |

**结论**：Planner实现了Fugu **"任务分解"核心能力**的70%，剩余30%（动态优化、自动纠错）需要外部条件成熟。

## 八、最终判断

**Planner不是"新增角色"，是"Architect的延伸能力"**。

在单体Claude Code环境中：
- **Phase 2.8 Decompose** = Architect输出后的强制步骤
- **Planner模式** = Architect模式的"分解子模式"
- **不新增Hook**，利用现有状态机检查

**核心价值**：将"模糊的Plan"转化为"精确的子任务清单"，使Phase 4 Build的每个Coder只面对**单一维度、明确边界、可验证标准**的原子任务。

这是**在不增加系统复杂度的情况下，显著提升编程质量**的关键杠杆。
