### 二、 核心攻坚：jnpf与AI原生低代码的“架构级免疫”设计

在 jnpf 这类企业级低代码平台，以及 AI 原生低代码场景中，**最大的痛点是：AI 擅长生成“业务逻辑”，但极度缺乏对“平台级隐形规则”（如租户、数据权限、审计）的敬畏和记忆。**

如果靠 Prompt 每次提醒 AI “记得加租户过滤”、“记得写审计日志”，不仅浪费 Token，而且必定会漏。因此，**必须将这些“隐形规则”下沉到框架底层，通过全局拦截器、AOP（面向切面编程）、ORM 拦截器来实现“架构级免疫”**。

以下是针对 jnpf 及 AI 低代码场景，**必须设计为全局拦截/自动注入的 8 大核心功能**：

#### 1. 多租户数据隔离（Tenant Isolation）—— 绝对的红线

- **痛点**：AI 写 LINQ 或 SQL 时，极易写出 `WHERE id = @id`，漏掉 `AND tenant_id = @tenantId`，导致跨租户数据泄露（水平越权）。

- 架构级免疫设计

  ：

  - **.NET (EF Core)**：在 `DbContext.OnModelCreating` 中配置**全局查询过滤器（Global Query Filters）**。`modelBuilder.Entity<Order>().HasQueryFilter(e => e.TenantId == _currentTenant.Id)`。同时重写 `SaveChangesAsync`，在实体状态为 `Added` 时，自动注入 `TenantId`。
  - **Java (MyBatis-Plus)**：使用 `TenantLineInnerInterceptor`，在 SQL 解析阶段自动拼接 `tenant_id` 条件。

- **AI 视角**：AI 完全不需要知道租户字段的存在，它只管写业务逻辑，框架底层自动拦截并拼装。

#### 2. 数据权限控制（Data Permission）—— 低代码的核心灵魂

- **痛点**：jnpf 的核心卖点之一是“数据权限”（如：只能看本部门数据、只能看自己创建的数据）。如果让 AI 在每个 Service 里手写 `if (role == 'manager')`，代码会迅速腐化且极易出错。

- 架构级免疫设计

  ：

  - **声明式注解/AOP**：在 Controller 或 Service 方法上打注解，如 `[DataPermission(FilterType = DataScope.DeptAndChild)]`。
  - **SQL 拦截器**：框架通过 AOP 拦截该注解，解析当前用户的数据权限规则，**在 SQL 执行前，动态改写 SQL**（例如自动追加 `WHERE create_dept_id IN (1, 2, 3)`）。

- **AI 视角**：AI 只需要在生成 Controller 时加上对应的注解（这可以通过代码生成器模板或简单的 Linter 检查），具体的过滤逻辑由框架 SQL 拦截器 100% 兜底。

#### 3. 实体审计与自动填充（Audit & Auto-Fill）

- **痛点**：所有业务表都需要 `Creator`, `CreateTime`, `Updater`, `UpdateTime`, `IsDeleted`。AI 经常忘记赋值，或者在 Update 时错误地覆盖了 `Creator`。

- 架构级免疫设计

  ：

  - **ORM 拦截器**：实现 `SaveChangesInterceptor`（.NET）或 `MetaObjectHandler`（Java）。

  - 在 

    ```
    SavingChanges
    ```

     事件中，统一拦截实体状态：

    - `EntityState.Added`：自动填充 Creator, CreateTime, TenantId, OrgId。
    - `EntityState.Modified`：自动填充 Updater, UpdateTime，**并强制保护 Creator 和 CreateTime 不被篡改**。

- **AI 视角**：AI 生成的实体类只需继承 `BaseEntity`（或实现 `IAuditEntity` 接口），无需写任何赋值代码。

#### 4. 软删除与级联隐藏（Soft Delete）

- **痛点**：AI 可能会生成 `context.Orders.Remove(entity)` 或 `DELETE FROM` 语句，导致物理删除，破坏低代码平台的数据关联性。

- 架构级免疫设计

  ：

  - **全局过滤器+重写删除**：在 ORM 层配置 `HasQueryFilter(e => !e.IsDeleted)`（自动隐藏已删除数据）。
  - 重写 `Remove` 方法或拦截 `Delete` 操作，将其**自动转换为 `UPDATE ... SET IsDeleted = 1`**。

- **AI 视角**：AI 即使写出了物理删除的代码，框架底层也会将其“扭转”为软删除，且查询时自动过滤。

#### 5. 敏感数据脱敏（Data Masking）

- **痛点**：AI 在生成 DTO 或返回 JSON 时，直接把手机号、身份证、银行卡号明文返回给前端，造成合规风险。

- 架构级免疫设计

  ：

  - **JSON 序列化拦截**：自定义 JSON 转换器（如 .NET 的 `JsonConverter` 或 Java 的 Jackson `Serializer`）。
  - 在实体属性上打标 `[SensitiveData(SensitiveType.Phone)]`。在序列化输出时，拦截器自动将 `13812345678` 替换为 `138****5678`。

- **AI 视角**：AI 只需在生成实体类时加上注解（或者由代码生成器自动加），无需在业务代码里写正则替换逻辑。

#### 6. 字典值与关联数据翻译（Dictionary Translation）

- **痛点**：低代码平台有大量字典码（如 `status = 1`），前端需要显示“已审批”。AI 经常在 Service 里写大量的 `switch-case` 或额外的 `foreach` 去查字典表，导致 N+1 查询性能问题。

- 架构级免疫设计

  ：

  - **AOP/序列化拦截**：在返回的 DTO 属性上打标 `[DictTranslate(DictType = "OrderStatus")]`。
  - 在 API 响应序列化阶段，拦截器批量收集所有需要翻译的字典码，**一次性从 Redis 缓存中查询并注入到返回的 JSON 中**（如自动生成 `status_Text = "已审批"`）。

- **AI 视角**：彻底消灭 AI 生成的冗余翻译代码，提升系统性能。

#### 7. 乐观锁与防并发控制（Concurrency Control）

- **痛点**：两个用户同时修改同一条低代码表单数据，后提交的覆盖先提交的。AI 极少会主动去写乐观锁逻辑。

- 架构级免疫设计

  ：

  - **ORM 并发令牌**：在 `BaseEntity` 中定义 `[ConcurrencyCheck]` 或 `[Version]` 字段（如 `RowVersion`）。
  - ORM 在执行 Update 时，自动在 WHERE 条件中带上版本号，并在更新后递增。如果受影响行数为 0，框架自动抛出 `DbUpdateConcurrencyException`。

- **AI 视角**：AI 无需处理并发逻辑，框架自动拦截并抛出标准异常，前端捕获后提示“数据已被他人修改”。

#### 8. 接口防重放与幂等性（Idempotency）

- **痛点**：AI 生成的前端代码在网络卡顿时可能会重复提交表单，导致创建多条重复数据。

- 架构级免疫设计

  ：

  - **中间件/Filter**：设计 `[Idempotent(ExpireSeconds = 10)]` 注解。
  - 拦截器提取请求的 Header 中的 `Request-Id`（或基于参数 Hash），在 Redis 中做分布式锁。如果 10 秒内重复请求，直接返回上次的缓存结果或拒绝。

- **AI 视角**：AI 只需在 Controller 的 `POST/PUT` 方法上加上注解，底层的防重放逻辑由框架统一处理。

### 三、 审查员（Reviewer）职责的彻底转变

当上述 8 大功能全部实现“架构级免疫”后，**审查员（Reviewer Agent）的职责将发生质的飞跃**：

- **过去的 Reviewer（低效且易错）**：
  去阅读 AI 写的几百行 Service 代码，检查里面有没有写 `where tenant_id = xxx`，有没有写 `if (IsDeleted)`，有没有给 `CreateTime` 赋值。（极其消耗 Token，且容易漏看）。

- 现在的 Reviewer（降维打击）

  ：

  不查业务逻辑，只查“契约与注解”

  。

  Reviewer 只需要通过简单的 Roslyn 分析器或 AST 脚本检查：

  1. 新增的 Entity 是否继承了 `BaseEntity`？（如果没有，打回）
  2. 包含手机号的字段是否加了 `[SensitiveData]` 注解？（如果没有，打回）
  3. 需要数据权限的 Controller 是否加了 `[DataPermission]` 注解？（如果没有，打回）

**这种检查是 100% 确定性的，可以通过静态脚本自动完成，甚至不需要消耗 LLM 的 Token！**

### 四、 总结：低代码平台的 AI 协作第一定律

在 jnpf 或任何 AI 原生低代码平台的架构设计中，必须确立一条铁律：

> **“凡是涉及全局一致性、安全合规、平台级约束的逻辑，绝对不允许出现在业务代码（Service/Controller）中，必须全部下沉到框架的拦截器、中间件和 ORM 扩展中。”**

**AI 的职责边界被严格限制在：实现纯粹的业务逻辑流转。** 这样不仅彻底解决了 AI 遗忘安全规则的问题，也让生成的代码极其干净、易维护，真正实现了低代码平台“又快又稳”的初衷。
