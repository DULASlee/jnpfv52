------

### 第一部分：架构升维——从“被动查询湖”到“主动感知与预测湖”（解决盲区1）

要让第三期的“岗位总管家”能够主动报告问题、进行预测性分析，第一期的数据底座绝对不能只是一个“静态的分析库（OLAP）”，它必须是一个 **“动静结合、流批一体”** 的感知网络。

我们需要在原有的五层架构中，强力插入 **“实时事件与特征层”**，并对语义层进行升维。

#### 1. 架构增补：引入 L2.5 实时事件流与特征存储 (Event & Feature Store)

- **之前的缺陷**：L2分析库是定时同步（CDC/增量）的静态数据，AI只能查到“过去发生了什么”，无法感知“现在正在发生什么”，更无法做实时预警。

- 升维方案

  ：

  - **实时变更捕获 (Change Stream)**：利用 SQL Server CDC 或引入轻量级消息组件（如 Redis Streams / RabbitMQ，不引入重型Kafka），将核心业务表（如设备状态、工单状态、质检结果）的**每一次变更**转化为实时事件流（Event Stream）。
  - **特征存储 (Feature Store)**：为AI预测模型准备“特征”。例如，不仅存“设备当前温度”，还要实时计算并存储“设备过去1小时温度滑动平均值”、“温度上升斜率”。这些特征是AI进行“预测性维护”的燃料。

#### 2. 语义层升维：从“查询字典”到“感知与预测规则库”

- **之前的缺陷**：指标字典（Metrics Store）只定义了“怎么查（MQL）”，没有定义“什么时候该报警”、“什么趋势意味着危险”。

- 升维方案

  ：在 

  ```
  BASE_METRIC_DEFINITION
  ```

   中扩展

  主动感知模型（Proactive Semantic Rules）

  ：

  - **静态阈值规则 (Threshold)**：如“OEE < 85% 触发警告”。
  - **动态 anomaly 规则 (Anomaly)**：如“当前产量偏离历史同时段均值 2 个标准差”。
  - **时序预测配置 (Forecast)**：标记该指标是否支持时序预测（如基于 Prophet/ARIMA 算法预测未来 3 天的物料消耗）。

#### 3. 新增核心组件：主动感知路由引擎 (Event & Alert Router)

- **职责**：它是“岗位总管家”的“神经末梢”。它实时订阅 L2.5 的事件流，结合 L4 语义层的规则，一旦发现异常，**主动触发** L5 层的 Agent。
- **工作流**：`设备温度变更事件` -> `特征计算(升温过快)` -> `匹配语义层预警规则` -> `生成“设备异常预警事件”` -> `主动推送给“设备管家Agent”` -> `Agent生成分析报告并推送到工作台`。

### 第二部分：低代码平台 (Design-time) 能力增强核查（解决盲区2）

这是我们最容易忽视的地方：**运行时的系统再智能，如果低代码平台（Baobab-Studio）只能通过写代码来实现，那就不是“AI原生低代码”，而是“披着低代码外衣的传统开发”。**

为了支撑第一期的数据中台以及后续的引擎AI化和岗位专家，**我们的低代码平台自身必须具备以下 4 大核心“AI原生设计器”**。我对照了现有的 V5.2 重构计划（F-0~F-10），发现这些能力目前是**完全缺失**的，必须作为**新增工作线（Studio AI-Tooling）** 纳入重构计划。

#### 1. 数据资产与语义建模设计器 (Semantic Modeler) —— 支撑第一期

- **现状缺失**：现有的数据库设计器只能建物理表（DDL），无法定义“业务指标”和“语义关系”。

- 平台增强

  ：在 Studio 中新增“数据资产管理”模块。

  - **可视化指标定义**：业务人员通过拖拽字段、配置公式（如 `及格数/总数`）、设置同义词，可视化生成 `BASE_METRIC_DEFINITION`，而不是让后端写 JSON。
  - **语义关系图谱画布**：可视化连线配置表与表之间的 Join 关系，生成 Semantic Graph。
  - **AI 试算沙箱**：在配置指标时，提供一个“AI对话测试框”，当场测试“帮我查一下上个月的XX指标”，验证口径是否正确。

#### 2. 主动预警与规则编排设计器 (Alert & Rule Flow Designer) —— 预埋第二/三期

- **现状缺失**：现有的 `FlowIR`（流程引擎）是 **“人驱动”** 的（人点击发起 -> 审批）。缺乏 **“数据/事件驱动”** 的自动化规则流。

- 平台增强

  ：新增“数据预警编排画布”（类似 Node-RED 或 Zapier）。

  - **触发器 (Trigger)**：可视化选择“当 指标[OEE] 满足 条件[<85%] 持续 [10分钟]” 或 “当 收到 [设备停机] 事件”。
  - **AI 动作 (AI Action)**：拖拽接入“调用 LLM 分析原因”、“生成预警简报”、“调用 钉钉/邮件 MCP 发送通知”。
  - **编译产物**：生成 `AlertRuleIR`，运行时由后端的 `Event & Alert Router` 加载执行。

#### 3. MCP 工具与技能注册中心 (MCP & Skill Registry) —— 预埋第二/三期

- **现状缺失**：现有的 API 管理只是简单的 Swagger 导入，没有面向 AI Agent 的“工具（Tool/Skill）”概念，缺乏 AI 需要的“参数 Schema 描述”和“业务意图描述”。

- 平台增强

  ：在 Studio 的“接口管理”中升维出“AI 技能库”。

  - **一键封装 MCP**：将现有的 JNPF 业务 API（如启动流程、查询工单）一键包装为标准的 MCP Server 工具。
  - **AI 提示词配置**：为每个工具配置“AI 调用指南”（Description for LLM），告诉大模型“什么时候该调用这个工具，参数怎么传”。

#### 4. 智能体 (Agent) 原型配置器 —— 预埋第三期

- **现状缺失**：无。

- 平台增强

  ：在第一期先做一个“极简版”的 Agent 配置面板（为第三期全面可视化做准备）。

  - 允许管理员创建一个“虚拟角色”（如：数据分析师）。
  - 为其挂载第一期做好的 `data-mcp`（查数据工具）和 `Alert-mcp`（查预警工具）。
  - 配置其 System Prompt（人设与边界）。

### 第三部分：融合后的全局架构与演进流程图 (ADR 辅助说明)

为了彻底消除理解歧义，我采用 ADR（架构决策记录）和 Mermaid 流程图，将“被动查询”、“主动感知”以及“低代码平台设计态”完美融合。

#### ADR-021: 确立“事件驱动+语义规则”的主动感知架构 (Proactive AI Architecture)

- **上下文**：单纯的数据湖和指标字典只能支持“人问AI答”的被动模式。企业管理系统的核心价值在于“防患于未然”，需要AI主动发现业务异常并预警。

- 决策

  ：

  1. 在数据中台 L2 层之上引入 **L2.5 实时事件流 (Event Stream)**，捕获核心业务实体的状态变更。
  2. 在语义层 L4 扩展 **主动感知规则 (Proactive Rules)**，定义指标的异常阈值和时序特征。
  3. 新增 **事件路由引擎 (Event Router)**，实时匹配事件与规则，主动触发 Agent 或预警流程。

- **后果**：数据中台从“静态仓库”升级为“动态神经网络”，为第二期的引擎AI化和第三期的“岗位总管家主动汇报”提供底层弹药。

#### ADR-022: 低代码平台 (Studio) 必须新增“语义与规则设计器”

- **上下文**：如果指标字典、预警规则、MCP工具都需要开发人员通过写代码或改数据库来配置，JNPF 就沦为传统的开发框架，失去了“低代码”的业务赋能价值。
- **决策**：在 Baobab-Studio 现有重构计划（F-0~F-10）之外，**强制新增“AI 原生工具链 (AI-Tooling)”工作线**。包含：语义建模设计器、预警规则编排画布、MCP技能注册中心。
- **后果**：实施成本增加约 3-4 周的前端设计器开发工作量，但换来的是客户业务人员能够“自助式”定义企业数据资产和 AI 预警规则，形成极高的平台粘性。
