#### 1. 关于 4角色×核心场景权限矩阵（§9.2.1）完整性验证

- **现状核查**：
  文档定义了 4 角色（业务专家、开发者、管理员、创始人）在 14 个核心场景下的权限。

- 缺失项排查

  ：

  - **发现缺口**：在 §9.2.1 的表格中，**“模型工坊（IR手工设计器）”** 的权限仅标注了“开发者”，但根据 §4.7 增量修改流程，**业务专家**在“增量修改”场景下也可能触发 IR 的微调（分治编辑）。
  - **理由**：业务专家在验收沙箱时，可能会提出“把按钮变绿”这种具体的 UI/IR 调整需求，系统需要允许业务专家在特定上下文（增量修改模式）下拥有有限的 IR 编辑权限。

- 修正建议（P0）

  ：

  - **细化权限粒度**：不要简单标注“开发者 ✅”，而是在 `IRDesigner.vue` 组件内部做逻辑分流。

  - 规则

    ：

    - **开发者**：全量权限（进入/编辑/保存）。
    - **业务专家**：仅在 `context.mode === 'incremental-edit'`（增量编辑模式）下可见并可操作，且操作范围受限于 `IR_EDIT_SCOPE`（例如只能修改样式、文本，不能修改逻辑、数据绑定）。

  - **文档更新**：在 §9.2.1 表格中增加一行说明：“模型工坊（增量编辑模式）：业务专家（受限）”。

#### 2. 多租户6层隔离机制（§9.3.1）漏洞扫描

- **设计回顾**：
  L1 应用层(JWT) -> L2 中间件 -> L3 ORM -> L4 数据库(per-tenant DB) -> L5 沙箱 -> L6 创始人。

- 风险点分析

  ：

  - **漏洞 A (L4 层)**：文档提到“共享 SQL Server + per-tenant DB”。在 SQL Server 中，**跨数据库查询（Cross-DB Query）** 默认是允许的。如果 ORM 层配置失误（例如拼接 SQL 字符串），开发者可能绕过 ITenantFilter 直接访问其他租户的 DB。
  - **漏洞 B (L5 沙箱层)**：沙箱内的应用连接的是共享 SQL Server 实例。如果沙箱内的代码（由 AI 生成）硬编码了其他租户的 DB 名称（例如 `JNPF_Sandbox_tenant_002`），存在数据泄露风险。

- 修正建议（P0）

  ：

  - **L4 层加固**：在 SQL Server 服务器层面，为每个租户的 DB 创建独立的 Login，并限制该 Login **只能访问自己的 Database**。不要使用 `sa` 或高权限账号连接。
  - **L5 层加固**：沙箱部署时，后端必须对生成的代码进行**AST（抽象语法树）扫描**，禁止代码中出现硬编码的租户 ID 或 DB 名称。如果发现可疑硬编码，强制阻断部署并标记为 `blocked`。

#### 3. 创始人二次认证流程（第九章重点）审查

- **设计回顾**：
  §9.4 定义了 TOTP 二次认证 + FounderGuard 中间件 + 不可删审计。

- 风险点

  ：

  - **CSRF 风险**：TOTP 验证接口 (`POST /api/founder/auth/verify`) 仅依赖 Header 中的 `X-Founder-Token`。如果攻击者窃取了 Token，可以直接绕过 TOTP。
  - **会话固定**：TOTP 验证通过后生成的 `sessionToken`，文档未明确其有效期和绑定机制。

- 修正建议（P0）

  ：

  - **增加绑定**：TOTP 验证通过后生成的 `sessionToken` 必须绑定 **IP 地址** 和 **User-Agent**。如果 IP 变更，强制重新验证。
  - **敏感操作重验**：对于极高风险操作（如“签发知识补丁”、“修改熔炉配置”），不要依赖 5 分钟的缓存，必须**每次操作都重新弹窗验证 TOTP**。
  - **审计日志**：`BASE_FOUNDER_AUTH_LOG` 必须记录 `Client IP` 和 `User-Agent`，且该表必须设置数据库级别的 **DELETE/UPDATE TRIGGER**，一旦检测到删除/修改操作，立即触发熔炉侧告警。
