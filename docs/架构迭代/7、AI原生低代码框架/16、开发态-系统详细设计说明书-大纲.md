## 1.2 系统定义

### 1.2.1 一句话定义

JNPF-AI 是一个 **AI 原生的低代码企业应用开发平台**。它的根基是 JNPF V5.2 手工低代码开发体系——可视化表单设计、流程引擎、大屏编译器、代码生成器、多租户权限——这一体系**独立完整、可脱离 AI 正常运行**，是整个平台的兜底保障。在此根基之上，平台增量集成了 AI 大模型辅助开发能力：用户用自然语言描述需求，AI 自动完成需求分析、架构设计、详细设计、代码生成、沙箱部署、迭代修复的全流程。AI 生成的产物与手工开发的产物**同构 IR**，双向可互转——AI 可用时提效 10 倍，AI 不可用时 100% 回退到手工模式，系统零瘫痪。

## 4.0 全局熔断规则（所有阶段共享）

### 4.0.1 熔断定义

任何阶段的任一异步操作（LLM 调用、编译、沙箱部署）连续失败 3 次，该流水线实例进入 `blocked` 状态。`blocked` 状态**仅能由人工退出**（创始人或管理员手动重置为 `pending`），不设自动恢复。

### 4.0.2 失败分类与独立计数

| 失败类型 | 定义 | 超时值 | 重试策略 |
|----------|------|--------|----------|
| `llm_timeout` | LLM 调用超时（P95 > 60s） | 60s | 切换供应商重试（MiMo→DeepSeek），2 次均失败计为 1 次 llm_timeout |
| `compile_failure` | IR 编译失败（vue-tsc 类型错误） | — | 自动重试 3 轮（重试间隔 2s/4s/8s 指数退避） |
| `sandbox_failure` | 沙箱创建/部署/健康检查失败 | 30s | 销毁当前沙箱 → 重新创建 → 重试最多 3 次 |
| `validation_failure` | IR 校验失败（cleanSchema/validateIR 不通过） | — | 自动重试 3 轮 |

### 4.0.3 计数器生命周期与重置策略

- 每个流水线实例独立计数（`PipelineState.FailureCounts` 字典）
- **成功即重置**：同类型失败连续计数。中间出现一次成功，则该类型计数器**归零**。例如：LLM 调用失败 → 失败 → 成功 → 计数器从 2 重置为 0
- 阶段切换时不清零（失败计数跨阶段累积）
- 全局计数器不跨流水线实例共享

### 4.0.4 blocked 通知机制

| 维度 | 设计 |
|------|------|
| **通知对象** | 租户管理员（该流水线所属租户）+ 平台管理员（平台级通知） |
| **通知渠道** | SignalR 实时推送到 `/messageHub`（§3.2.8）+ BASE_AI_PIPELINE_MESSAGE 写入一条 `F_ROLE = 'system'`、`F_CONTENT = '{"type":"alert","status":"blocked","reason":"...","stage":"...","failureCount":3}'` 的告警消息 |
| **通知时机** | 状态变更为 `blocked` 的瞬间（同步触发，不延迟） |
| **通知内容** | 流水线 ID、失败类型、失败阶段、最近 3 次失败的错误摘要 |

## 4.7 增量修改流程（§4.7 独立设计）

> **设计依据**：架构师三问 §4.7。本小节定义从交付阶段回退到前序阶段的完整流程。

### 4.7a 变更影响传播算法（D-8 · 审判令一）
三个核心函数: buildDependencyGraph O(N) + propagateImpact O(V+E) + determineReentryStage O(K)。总延迟 < 100ms（500节点）。
节点类型到阶段的映射: Requirement→stage1, ModuleDefinition/TableDefinition→stage2, Component/DataSource/WorkflowStep/RuleNode→stage3, CompileConfig→stage4。

### 4.7.1 回退粒度

用户可以从阶段 5（交付）回退到任意已完成阶段。回退目标与代价：

| 回退目标 | 保留的产物 | 需要重新生成的产物 | 适用场景 |
|----------|-----------|-------------------|----------|
| 阶段 1（需求分析） | 无 | 全部（需求→架构→设计→IR→编译→部署） | 需求理解完全错误，需要重新分析 |
| 阶段 2（架构设计） | 需求分析文档 | 架构→设计→IR→编译→部署 | 架构方案需要调整 |
| 阶段 3（总体设计） | 需求文档 + 架构设计 | IR→编译→部署 | **最常见**——架构正确但 IR 需要调整 |
| 阶段 4（自动开发） | 需求+架构+IR | 编译→部署 | IR 正确但编译失败 |

**被跳过阶段的产物处理**：标记为 `superseded`（已取代），保留但不删除。开发者可在版本历史中对比新旧产物差异。

### 4.7b 分治编辑详细设计（D-9 · 审判令二）
六步流程: buildNodeSummaryList → routeToAgent → extractSlice → Agent输出IREditPatch → applyPatch(只允许修改scope.writableNodeIds范围内节点) → validateAfterPatch。
IREditOperation: op(replace/add/remove) + path(JSONPath) + value + oldValue(自动填充用于回滚) + reason。

### 4.7.2 增量 vs 全量

**决定：全量替换 IR，不部分更新。**

理由：IR 的组件注册表引用是全局的（例如表单引用了组件注册表中的 `BasicTable`，如果仅部分替换，新 IR 中的组件引用可能与旧注册表版本不兼容）。全量替换避免了引用断裂风险。

**配套机制：IR 版本历史**

全量替换前，系统自动将当前 IR JSON 快照存入 `BASE_AI_PIPELINE_MESSAGE` 表（`F_ROLE = 'system'`, `F_CONTENT = IR_JSON_SNAPSHOT`, `F_STAGE = 'delivery'`），以便回退到历史 IR。版本快照格式：

```json
{
  "pipelineId": 123,
  "stage": "delivery",
  "snapshotAt": "2026-06-16T10:00:00Z",
  "irVersion": 3,
  "irContent": { ... }
}
```

### 4.7.3 上游产物版本自动升级

回退到阶段 N 时，系统自动检查阶段 1 至 N-1 中是否存在标记为 `superseded` 的产物。如有，替换为该阶段**最新 `approved` 状态的版本**作为输入。

**示例**：用户从阶段 5 回退到阶段 3。系统检查发现阶段 2 的架构设计文档有 v1（`superseded`）和 v2（`approved`），则自动以 v2 作为阶段 3 的输入。用户无需手动选择版本。

**版本链条**：

```
阶段 2 第一次产出 → approved (v1)
       ↓ 用户修改需求 → 回退到阶段 2
阶段 2 重新产出 → approved (v2), v1 → superseded
       ↓ 流水线继续到阶段 5
       ↓ 用户再次修改 → 回退到阶段 3
阶段 3 自动获取阶段 2 的 v2 (approved) 作为输入 ✅
```

### 4.7.4 沙箱销毁时序

**销毁时机**：用户选择回退目标并确认弹窗后，**在重新执行目标阶段之前**销毁。不在"点击增量修改按钮"瞬间销毁——因为用户可能在看到确认弹窗后取消操作。

**销毁→重建时序**：

```
1. 用户点击"增量修改" → 弹出回退目标选择器（此时沙箱仍在运行）
2. 用户选择目标阶段（阶段 1/2/3/4） → 弹出确认提示
3. 用户点击"确认" → 保存 IR 版本快照（BASE_IR_VERSION）→ 销毁沙箱
4. 销毁完成后 → 重新执行目标阶段及后续阶段
5. 阶段 4 完成后 → 创建新沙箱 → admin/admin123 自动创建 → 返回新 URL
```

### 4.7.5 IR 版本快照存储方案

**新建 BASE_IR_VERSION 表**（同步补入 §6 DDL）：

```sql
CREATE TABLE BASE_IR_VERSION (
  F_ID          BIGINT PRIMARY KEY,
  F_TENANT_ID   NVARCHAR(50) NOT NULL,
  F_PIPELINE_ID BIGINT NOT NULL,           -- 流水线 ID
  F_STAGE       NVARCHAR(20) NOT NULL,     -- 快照所属阶段
  F_VERSION     INT NOT NULL DEFAULT 1,    -- 版本号（同一流水线内递增）
  F_IR_CONTENT  NVARCHAR(MAX) NOT NULL,    -- IR JSON 完整快照
  F_STATUS      NVARCHAR(20) DEFAULT 'active',  -- active / superseded
  F_DIFF        NVARCHAR(MAX),  -- RFC 6902 JSON Patch 格式的差异
  F_TRIGGERED_BY NVARCHAR(50),  -- 触发者: "pipeline" | "user_rollback" | "founder_patch"
  F_CHANGE_SUMMARY NVARCHAR(500),  -- 变更摘要
  F_PARENT_VERSION INT,  -- 父版本号（链式追溯）
  F_CREATED_AT  DATETIME NOT NULL,
  INDEX IDX_PIPELINE (F_PIPELINE_ID, F_STAGE, F_VERSION),
  INDEX IDX_TENANT (F_TENANT_ID)
);
```

**快照触发时机**：
- 阶段 5 交付完成后，自动保存一份 `active` 快照
- 增量修改确认后，旧版本标记为 `superseded`，新快照标记为 `active`
- 每个阶段每个流水线最多保留 10 个版本（超量自动清理最早的非 active 版本）

## 6.1 命名规范（升标）

**强制规则**：
- 表名：`{MODULE_PREFIX}_{ENTITY}` 大写下划线
- 列名：`F_` 前缀（如 `F_TENANT_ID`），禁止裸 PascalCase
- 用户 ID：`string`（不用 `long`）
- 租户基类：所有业务表继承租户基类（含 `F_TENANT_ID`）
- 审计字段：自动注入
- 逻辑删除：`F_IS_DELETED BIT DEFAULT 0`
- 主键：`F_ID BIGINT`（雪花算法）

### 6.6.2 SandboxManager 双层模式设计

```
  服务启动
     │
     ▼
  ┌──────────────────────┐
  │ 从 DB 加载 running     │  ← 恢复重启前的沙箱状态
  │ 状态的沙箱列表         │
  └──────┬───────────────┘
         │
         ▼
  ┌──────────────────────┐
  │ docker inspect 验证    │  ← 确认容器仍存在
  │ 容器存活              │
  └──────┬───────────────┘
         │
    ┌────┴────┐
    │         │
    ▼         ▼
  存活      已死
    │         │
    ▼         ▼
  恢复      标记为
  内存      destroyed
  缓存
```

**操作规则**：
- `CreateAsync`：docker run → INSERT → 加入内存 ConcurrentDictionary
- `DestroyAsync`：docker stop → UPDATE status='destroyed' → 从内存移除
- `GetStatusAsync`：先从内存查 → 内存无则从 DB 查 → DB 有且 status=running 则 docker inspect 验证
- 服务重启恢复：`SELECT * FROM BASE_SANDBOX WHERE F_STATUS IN ('pending','running') AND F_IS_DELETED=0` → docker inspect 逐一验证

### 6.6.3 知识图谱并发控制（D-03 补充约束）

知识补丁注入（KnowledgePatchService）涉及 BASE_KNOWLEDGE_NODE 和 BASE_KNOWLEDGE_EDGE 的 UPSERT 操作。同时业务专家的 RAG 查询可能读取这些表。

**并发控制方案：乐观锁 + 版本字段**

```sql
-- 在 BASE_KNOWLEDGE_NODE 和 BASE_KNOWLEDGE_EDGE 中增加版本控制字段
ALTER TABLE BASE_KNOWLEDGE_NODE ADD F_VERSION INT DEFAULT 1;
ALTER TABLE BASE_KNOWLEDGE_EDGE ADD F_VERSION INT DEFAULT 1;

-- 备份表（存储被覆盖的旧版本，用于回滚）
CREATE TABLE BASE_KNOWLEDGE_NODE_BACKUP (
  F_ID BIGINT PRIMARY KEY,
  F_ORIGINAL_ID BIGINT,       -- 指向 BASE_KNOWLEDGE_NODE.F_ID
  F_TENANT_ID NVARCHAR(50),
  F_NODE_ID NVARCHAR(50),
  F_CONTENT NVARCHAR(MAX),
  F_VERSION INT,               -- 被覆盖时的版本号
  F_BACKUP_AT DATETIME,        -- 备份时间
  F_BACKUP_REASON NVARCHAR(50) -- 'upsert' | 'delete'
);
```

**UPSERT 流程（乐观锁）**：
```
1. SELECT F_ID, F_VERSION FROM BASE_KNOWLEDGE_NODE WHERE F_NODE_ID = @nodeId
2. 如果存在：
   a. 将当前行 INSERT INTO BASE_KNOWLEDGE_NODE_BACKUP
   b. UPDATE BASE_KNOWLEDGE_NODE SET ... F_VERSION = F_VERSION + 1
      WHERE F_ID = @id AND F_VERSION = @version  -- 乐观锁
   c. 如果 affected rows = 0 → 版本冲突 → 返回当前版本号让调用方决定
3. 如果不存在：INSERT ... F_VERSION = 1
```

**"仅 verified 可合并"的判定条件**：
- `F_STATUS = 'verified'` 的节点/边才被 KnowledgePatch 合并
- `F_STATUS = 'candidate'` 的仅存在于熔炉侧，不注入工作室
- `F_STATUS = 'deprecated'` 的保留但查询时默认过滤

### 6.6.5 知识图谱 UPSERT 设计约束（DB-18/19）

- **事务包裹**：所有知识图谱 UPSERT 操作必须用 `BEGIN TRAN → 备份旧值到 *_BACKUP → UPSERT → COMMIT` 包裹
- **乐观锁冲突处理**：`F_VERSION` 冲突时指数退避重试，最多 3 次。第 3 次仍冲突则返回错误让调用方决定
- **清理机制**（DB-20）：StaleMonitorService 顺带清理 `BASE_KNOWLEDGE_NODE_BACKUP` 中超过 30 天的记录

#### 知识图谱备份清理详细设计（DB-20 扩展 · v2.1 玛维思 #7）

**保留策略**：
| 参数 | 值 | 说明 |
|------|-----|------|
| 备份保留天数 | **30 天** | 超过 30 天的 `BASE_KNOWLEDGE_NODE_BACKUP` / `BASE_KNOWLEDGE_EDGE_BACKUP` 自动清理 |
| 清理周期 | 每小时 | StaleMonitorService 定时扫描（与 pipeline stale 检测共用 Quartz Job） |
| 单次清理上限 | 1000 条/批 | 防止长事务锁表 |
| 清理 SQL | `DELETE TOP(1000) FROM BASE_KNOWLEDGE_NODE_BACKUP WHERE F_BACKUP_AT < DATEADD(DAY, -30, GETDATE())` | 分批循环执行直到 affected=0 |

**乐观锁冲突指数退避重试**：
```
第 1 次冲突 → 等待 100ms → 重读 F_VERSION → 重试 UPSERT
第 2 次冲突 → 等待 200ms → 重读 F_VERSION → 重试 UPSERT
第 3 次冲突 → 等待 400ms → 重读 F_VERSION → 重试 UPSERT
第 4 次冲突 → 返回错误 (HTTP 409 Conflict)，含当前 F_VERSION 供调用方决定
```

**"仅 verified 可合并"的判定条件**：
- `F_STATUS = 'verified'` 的节点/边才被 KnowledgePatch 合并
- `F_STATUS = 'candidate'` 的仅存在于熔炉侧，不注入工作室
- `F_STATUS = 'deprecated'` 的保留但查询时默认过滤

**备份表清理日志**：每次清理操作写入 `BASE_AI_PIPELINE_MESSAGE`（`F_ROLE='system'`, `F_CONTENT='{"type":"backup_cleanup","deleted":N,"before":"<datetime>"}'`），供管理员审计。

    OR->>V1: validateBatch1Output({modules, flows, wireframes})
    alt modules为空或flows为空
        V1-->>OR: ❌ batch1_invalid
        OR->>OR: status=blocked, 通知管理员
    else 校验通过
        V1-->>OR: ✅ batch1_valid (modules={N}, flows={M}, wireframes={P})

        Note over OR,DBs: 批次2 (3 Agent并行): 消费批次1产物
        OR->>DB: design(domainModel, modules)
        OR->>API: design(apiSpecs, flows)
        OR->>PM: design(permissions, modules, flows)
        par 批次2并行
            DB-->>OR: erDiagrams[] + ddls[]
            API-->>OR: apiSequences[] + endpointSpecs[]
            PM-->>OR: permissionMatrix + roleConfigs[]
        end
    end

    OR->>DBs: INSERT BASE_IR_VERSION (6 Agent output)
    OR->>OR: merge → 完整 IR 集合
    OR->>OR: F_STAGE_STATUS=Review, 等待双视图门禁确认
```

**两批次设计说明**：批次1产出(modules/flows/wireframes)供批次2消费。`validateBatch1Output()` 检查批次1的modules/tables非空——若为空则直接blocked，避免批次2基于空数据生成垃圾。校验链与议题1 `PipelineValidationJob` 共用 cleanSchema→validateIR→vue-tsc 三步。

#### SSE 连接状态灯（3 色）

| 状态 | 颜色 | 指示灯 | 触发条件 |
|------|------|--------|----------|
| 已连接 | 绿色 #52c41a | 常亮圆点 (8px) + "实时" | EventSource 正常接收 |
| 重连中 | 黄色 #faad14 | 脉冲圆点 + "重连中({n}/5)" | EventSource error 事件触发，指数退避重连 |
| 已断开 | 红色 #ff4d4f | 常亮圆点 + "已断开" + 手动重连按钮 | 重试 5 次失败或服务端返回 502/503 |

**重连策略**：首次延迟 1s → 2s → 4s → 8s → 16s（指数退避，最多 5 次）。5 次失败后停止自动重连，显示手动重连按钮。重连成功后从 `Last-Event-ID` header 续接。

#### 超时分级提示（4 级，与 AgentTimeoutMonitor 对齐）

| 级别 | 名称 | 触发条件 | UI 表现 | 用户操作 |
|------|------|----------|---------|----------|
| L1 | 思考中 | `elapsed < expected_ms` | 灰色打字机效果，正常 | 等待 |
| L2 | 长时任务 | `elapsed ≥ expected_ms` | 黄色脉冲 "处理中…已耗时 Xs" | 可继续等待 |
| L3 | 超时预警 | `elapsed ≥ expected_ms × 1.5` | 橙色边框 "预计还需 Xs，是否继续？" | [继续等待] / [跳过此步骤] |
| L4 | 硬超时 | `elapsed ≥ max_ms` | 红色边框 + "已超时" + 原因 | [跳过此智能体] / [降级到手工模式] |

**配置来源**：`expected_ms` 和 `max_ms` 从 AgentTimeoutMonitor 的 prompt template 配置中读取，每 Agent 独立配置。

ALTER TABLE BASE_USER ADD F_TENANT_ID NVARCHAR(50) NOT NULL DEFAULT 'default';
ALTER TABLE BASE_ROLE ADD F_TENANT_ID NVARCHAR(50) NOT NULL DEFAULT 'default';

ALTER TABLE BASE_IR_VERSION ADD F_TENANT_ID NVARCHAR(50) NOT NULL DEFAULT 'default';
-- ... 逐表执行
```

**回滚方案（迁移前快照备份）：**

```sql
-- 每张表迁移前执行快照备份
SELECT * INTO BASE_USER_PRE_MIGRATION FROM BASE_USER;
SELECT * INTO BASE_ROLE_PRE_MIGRATION FROM BASE_ROLE;
SELECT * INTO BASE_PERMISSION_PRE_MIGRATION FROM BASE_PERMISSION;
-- ... 逐表执行

-- 回滚时从快照恢复
-- DROP TABLE BASE_USER; EXEC sp_rename 'BASE_USER_PRE_MIGRATION', 'BASE_USER';
```

**迁移SOP：**
1. 停止写入服务（或开启只读模式）
2. 执行快照备份（每张表 `SELECT INTO *_PRE_MIGRATION`）
3. 执行 ALTER TABLE 添加 F_TENANT_ID
4. 更新 ITenantFilter 配置为 `MultiTenancy=true`
5. 启动服务 + 越权测试 10 条全绿
6. 确认无问题后清理快照表

## 9.4 创始人二次认证设计

### 9.4.1 三重认证

| 层级 | 认证机制 | 实现 |
|------|----------|------|
| **L1 用户认证** | JWT（普通登录） | JwtHandler |
| **L2 角色认证** | BASE_ROLE.code='founder' | BASE_ROLE |
| **L3 TOTP 二次认证** | HMAC-SHA1 时间令牌 | FounderAuthService |

### 9.4.2 TOTP 流程

```
1. 创始人登录 → JWT 中 role='founder'
2. 访问 /api/founder/* → FounderGuard 中间件
3. 检查 X-Founder-Token header
4. 检查 TOTP session 是否有效（5 分钟内）
5. 验证通过 → 允许访问 + 写入 BASE_FOUNDER_AUTH_LOG
```

### 9.4.3 审计与锁定

| 机制 | 实现 |
|------|------|
| **所有创始人操作** | 写入 BASE_FOUNDER_AUTH_LOG（不可删审计） |
| **TOTP 错误 3 次** | 锁定 5 分钟 |
| **不可删审计** | DB 触发器禁止 DELETE / TRUNCATE |

## 9.5 创始人越权边界模型（v2.1 新增）

> **设计依据**：首席架构师裁定千问 SEC-11。创始人作为平台最高权限角色，并非"无所不能"——必须明确哪些操作是合法越权（跨租户管理）、哪些是受限越权（需二次认证）、哪些是不可越权（数据完整性底线）。

### 9.5.1 三级边界

| 级别 | 名称 | 定义 | 示例 | 技术实现 |
|------|------|------|------|----------|
| **L1** | 合法越权 | 创始人为平台管理需要，可访问任意租户数据/操作 | 查看任意租户的 AI 调用日志、审核任意知识图谱候选模式、管理任意沙箱实例 | FounderGuard 放行 + 写入审计日志 |
| **L2** | 受限越权 | 创始人在特定条件下可操作，但需 TOTP 二次认证 + 不可删审计 | 签发 KnowledgePatch、修改模型与 Prompt 配置、查看系统级审计日志 | FounderGuard + TOTP + BASE_FOUNDER_AUTH_LOG |
| **L3** | 不可越权 | 创始人也不允许的操作——数据完整性底线 | 删除/修改 BASE_FOUNDER_AUTH_LOG 记录、禁用租户隔离机制、删除已 verified 的领域知识 | DB 触发器禁止 DELETE + 代码层硬编码检查 + 中间件断言 |

### 9.5.2 L3 不可越权清单（完整）

| 操作 | 防护机制 | 违反后果 |
|------|----------|----------|
| DELETE/TRUNCATE BASE_FOUNDER_AUTH_LOG | DB 触发器 INSTEAD OF DELETE → RAISERROR + ROLLBACK | 审计链断裂 |
| 修改已 verified 的知识图谱节点 | UPSERT 乐观锁校验 F_STATUS='verified' → 拒绝覆盖 | 知识污染 |
| 禁用 ITenantFilter | Startup.cs 中间件顺序自检断言 → 启动失败 | 跨租户数据泄露 |
| 修改平台级配置（MultiTenancy=false 等） | ConfigController 硬编码检查 → 403 | 安全机制关闭 |
| 删除其他创始人的审计记录 | OAuth 表触发器 + FounderGuard 身份校验 | 掩盖操作痕迹 |

### 9.5.3 设计原则

- **最小惊讶原则**：创始人权限边界对创始人本人透明——操作前明确提示"此操作将被记录且不可撤销"
- **审计完整性**：即使是创始人，所有操作（含仅查看）均写入 BASE_FOUNDER_AUTH_LOG
- **物理不可删**：DB 触发器是最后防线——应用层即使被绕过，数据库层仍拒绝 DELETE
- **代码层硬编码**：L3 不可越权清单不通过配置文件控制，直接硬编码在中间件/触发器/服务代码中
