## 核心洞察：Agent 不需要搜索整个 IR，只需要看自己的切片

你提到"agent 角色分类、agent 技能集、agent 能调用的 MCP、agent 需要的原材料"——这四件事其实可以用一个统一的机制解决：**每个 Agent 在 IR 上有一个固定的视图（View）**。

就像数据库视图——DBA 不需要给每个用户建搜索引擎，只需要定义"你能看到哪些表、哪些列"。

```typescript
// 每个 Agent 注册自己关心的 IR 节点类型
interface AgentScope {
  agentName: string;
  
  // 这个 Agent 负责的 IR 节点类型
  ownedNodeTypes: NodeType[];
  
  // 这个 Agent 可读的节点类型（输入原材料）
  readableNodeTypes: NodeType[];
  
  // 这个 Agent 可写的节点类型（输出产物）
  writableNodeTypes: NodeType[];
  
  // 从 IR 中提取这个 Agent 的"工作切片"
  extractSlice(ir: FormPageIR): AgentSlice;
}
```

**每个 Agent 的视图定义：**

| Agent        | 可读（原材料）                 | 可写（产物）                       | 从 IR 中提取的切片      |
| ------------ | ------------------------------ | ---------------------------------- | ----------------------- |
| 需求分析师   | 全部（概览）                   | Requirement 节点                   | 需求摘要 + 业务上下文   |
| 架构师       | Requirement + ModuleDefinition | ModuleDefinition + TableDefinition | 模块划分 + 表结构       |
| UI 设计师    | Component + DataSource         | Component                          | 页面组件树 + 数据源引用 |
| 数据库设计师 | TableDefinition + DataSource   | TableDefinition + DataSource       | 表结构 + 字段 + 外键    |
| 工作流设计师 | WorkflowStep + Component       | WorkflowStep                       | 流程步骤 + 触发条件     |
| 规则引擎     | RuleNode + Component           | RuleNode                           | 业务规则 + 条件 + 动作  |

**关键点：Agent 的视图是确定性的——根据 Agent 角色从 IR 类型系统自动推导，不需要维护。**

## 自然语言 → 节点定位：不需要向量数据库

200-500 个节点的规模，用 LLM 做**列表选择题**就够了。方法如下：

```typescript
// 从 IR 提取所有节点的"摘要行"
function buildNodeSummaryList(ir: FormPageIR): string {
  return ir.allNodes.map(node => 
    `[${node.id}] ${node.type}: ${node.label} — ${node.description || ''}`
  ).join('\n');
}

// 给 LLM 的 Prompt
const LOCATE_PROMPT = `
你是 IR 节点定位器。用户需求："{userRequest}"

当前应用的 IR 节点列表：
{buildNodeSummaryList(ir)}

请选出与用户需求直接相关的节点 ID（最多 5 个）。
输出 JSON：{ "nodeIds": ["xxx"], "confidence": 0.0-1.0 }

规则：
- 只选直接相关的，不要扩大范围
- confidence < 0.6 时，系统会让用户确认
`;
```

**这个调用的本质是：从一个 200-500 行的列表中选 1-5 行。** 这是 LLM 最擅长的任务之一，准确率极高，延迟 < 2 秒。

不需要向量化，不需要 Elasticsearch，不需要 pgvector。

## 三个机制合为一体

现在把前面的方案和你的需求整合成一个统一架构：

```
┌─────────────────────────────────────────────────────────────┐
│                    分治编辑架构（完整版）                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  用户输入："修复副菜单过滤 BUG"                               │
│         │                                                   │
│         ▼                                                   │
│  ┌─────────────────────────────────┐                        │
│  │ Step 1: 节点定位                 │                        │
│  │ buildNodeSummaryList(ir) → LLM   │ ← 200-500 行列表选择题 │
│  │ 输出：["menu_sub_filter"]        │                        │
│  └────────────┬────────────────────┘                        │
│               ▼                                             │
│  ┌─────────────────────────────────┐                        │
│  │ Step 2: Agent 路由               │                        │
│  │ 根据节点类型 → 确定哪个 Agent    │ ← 类型→Agent 映射表     │
│  │ menu_sub_filter: RuleNode        │                        │
│  │ → 路由到：规则引擎 Agent          │                        │
│  └────────────┬────────────────────┘                        │
│               ▼                                             │
│  ┌─────────────────────────────────┐                        │
│  │ Step 3: 提取 Agent 切片           │                        │
│  │ agentScope.extractSlice(ir)      │ ← 只提取相关子树        │
│  │ 输出：menu_sub_filter 节点 +     │                        │
│  │       其引用的 2 个 Component     │                        │
│  └────────────┬────────────────────┘                        │
│               ▼                                             │
│  ┌─────────────────────────────────┐                        │
│  │ Step 4: Agent 生成编辑指令       │                        │
│  │ 输入：切片 + 变更请求             │                        │
│  │ 输出：IREditPatch（2 条操作）    │                        │
│  └────────────┬────────────────────┘                        │
│               ▼                                             │
│  ┌─────────────────────────────────┐                        │
│  │ Step 5: 应用 + 验证 + 展示       │                        │
│  │ applyPatch → validator → vue-tsc │ ← 确定性，不依赖 LLM   │
│  │ → IR Diff Viewer → 用户确认      │                        │
│  └─────────────────────────────────┘                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**整个链路中 LLM 只出现两次：**
1. 节点定位（列表选择题，< 2s）
2. 生成编辑指令（微型生成任务，< 10s）

其余全部是确定性代码。

| 能力          | V1（当前实现）                    | V2（节点 >1000 或准确率不足时升级）  |

## 这个方案的三个核心特征

**简洁**：不引入新的基础设施（无 Elasticsearch、无 pgvector、无向量数据库）。所有逻辑在现有 SQL Server + 内存 + LLM 调用范围内完成。

**好工程化**：六个步骤每一步都有明确的输入输出类型、明确的函数签名、明确的成功/失败条件。开发者拿到接口定义就能编码。

**可演进**：V1 用最简单的方式跑通全链路，V2 的每个升级点（向量索引、多 Agent 并行编辑、语义冲突检测）都是在 V1 基础上的增量扩展，不需要重写。
