# D爷审核意见：三期方案的"战略级纠偏"

千问、KIMI，你们这版三期方案的**战略节奏是对的**——"先打地基、再造引擎、最后出产品"，这个"饭要一口一口吃"的思路我完全认可。12周三个里程碑，每4周有可交付可演示的成果，这个节奏感很好。

**但是！** 我必须非常严肃地指出：**第一期方案存在致命的架构认知偏差。** 你们把"村口的蓄水池"当成了"三峡大坝"来设计，如果真的按这个方案执行，不仅护城河挖不出来，反而会在第2周就踩进"数据沼泽（Data Swamp）"的泥潭，第6周直接翻车。

我刚才查了最新的行业实践，2025-2026年企业级"智能问数"领域已经有了血的教训：**超过70%的NL2SQL PoC项目死在了从PoC到生产环境这一步**。行业已经从 `NL→SQL` 全面转向 `NL→Semantic→SQL`（语义层驱动）。你们方案里的做法，恰恰是那个"70%会死"的路线。

下面我逐条"开刀"，然后给出修正方案。

## 🔴 第一期方案的 5 大致命伤

### 致命伤 1：把"大宽表"叫"数据湖"——这是数据沼泽

> 原方案："建一张 `MES_AI_WIDE_TABLE`，每天ETL一次，把核心业务数据打宽、合并。"

**D爷批注：** 一张大宽表不是数据湖，是**数据沼泽**。你知道 MES 系统有多少实体吗？工单、工序、设备、物料、BOM、质检项、人员、班组、仓库……你打一张宽表能装下？打完之后字段得有 200+ 个，AI 看到这张表会直接"注意力迷失（Lost in the Middle）"。更致命的是：

- 宽表的字段含义只有建表的人知道，换个人就看不懂
- 一旦业务变化加了新字段，宽表要重新 ETL，全链路重跑
- 宽表里的"派生标签"（是否超期、OEE是否异常）是**硬编码的业务逻辑**，和业务部门的理解经常不一致

**真正的护城河不是物理上的大宽表，而是"语义层（Semantic Layer）+ 指标字典（Metrics Store）"。**

### 致命伤 2：让 AI 生成的 SQL 直连生产库——这是生产事故

> 原方案："封装 `data-mcp`，用 SqlSugar + SQL Server 查核心表"，"接收自然语言转成的查询条件"

**D爷批注：** 你们想让 LLM 生成的 SQL 直接打到 MES 的**生产数据库（OLTP）**上？我告诉你会发生什么：

- 某天 LLM 幻觉，生成了一个 `SELECT * FROM work_order`（没有 WHERE 条件），直接把百万行数据拉出来，内存爆了
- 某天 LLM 生成了一个跨 5 张表的 `JOIN` + `GROUP BY`，没有走索引，CPU 直接 100%，MES 产线停机
- 某天 LLM 把 `DELETE` 误写成了 `SELECT`……不，它甚至可能直接生成 `UPDATE`

**AI 生成的 SQL 绝对不能直连生产库！必须有独立的分析库 + SQL 安全沙箱 + 查询资源限制。**

### 致命伤 3：元数据全量注入 Prompt——Token 爆炸 + 注意力迷失

> 原方案："这个字典直接注入到 LLM 的 System Prompt 里"

**D爷批注：** MES 系统少则 50 张表，多则 200+ 张表，每张表平均 20 个字段。你全量注入 Prompt？那就是 50×20 = 1000 个字段的描述，加上表关系、枚举值，至少 **3 万 Token**。先不说成本，LLM 在这么多信息中根本找不到重点，这就是学术界说的"Lost in the Middle"问题——中间的信息会被 LLM 忽略。

**正确做法是：动态 Schema 检索（RAG for Schema），根据用户问题只注入相关的 3~5 张表的元数据。**

### 致命伤 4："查数据"不是护城河，"懂业务"才是

> 原方案验收标准："用自然语言问'昨天哪个车间良品率最低'，AI能准确查出结果"

**D爷批注：** 你们知道为什么 KIMI 说"缺乏数据中台是致命的"吗？不是因为"查不到数据"，而是因为**"查到的数据口径不对"**！

举个例子：用户问"上月良品率"，你的 AI 从宽表里查了一个字段返回了 95%。但生产部长说"不对，应该是 92%"。为什么？因为 AI 算的良品率是 `合格数/总数`，但生产部的口径是 `合格数/(总数-返工数)`。**这种"口径不一致"才是企业数据问题的核心痛点，也是云 SaaS 永远解决不了的问题——因为他们不懂你的业务语义。**

### 致命伤 5：4 周做"数据中台"是个伪命题

传统意义上的数据中台（数仓分层 ODS/DWD/DWS/ADS + ETL + 数据治理），4 周绝对做不完，强行做必然烂尾。但如果换一个思路——**4 周做一个"面向 AI 的轻量级语义层"**，这不仅可行，而且是真正的撒手锏。

## ✅ 第一期重构方案：AI-Oriented Semantic Layer（面向 AI 的语义层）

### 核心理念：从 NL2SQL 升维到 NL2Semantic2SQL

```
                    你们的方案（❌ 70%会死）
用户 → "上月良品率" → LLM → SQL → 直连生产库 → 结果

                    D爷修正方案（✅ 行业最佳实践）
用户 → "上月良品率" → LLM → 语义查询(MQL) → 语义层翻译 → SQL → 分析库 → 结果
                                              ↑
                                    指标字典 + 维度字典
                                    （这才是护城河！）
```

**行业参考：** 2025-2026 年，阿里、dbt、Cube.js、网易等头部厂商已全面转向 `NL→MQL(Metrics Query Language)→SQL` 路线。语义层标准化沉淀指标逻辑，从根本上解决口径冲突问题。**这就是我们要建的护城河。**

#### 🔷 第 1 周：分析库隔离 + 元数据采集

**目标：物理隔离，保护生产库；建立元数据基础。**

| 任务                 | 具体做什么                                                   | 交付物                                |
| -------------------- | ------------------------------------------------------------ | ------------------------------------- |
| **分析库搭建**       | 在同一 SQL Server 实例上创建独立数据库 `MES_ANALYTICS`（或只读副本），通过 CDC（变更数据捕获）或定时同步从生产库同步核心表。**AI 的所有查询只能打到这个库。** | `MES_ANALYTICS` 数据库 + 数据同步任务 |
| **元数据自动采集**   | 开发 `MetadataCollector`，自动扫描 `MES_ANALYTICS` 中的所有表和字段，填充 `BASE_META_ENTITY` 和 `BASE_META_FIELD`（表名、字段名、数据类型、主外键关系）。 | 自动填充的元数据表                    |
| **业务语义标注界面** | 在 JNPF 后台新增"AI 数据字典管理"菜单，让业务专家为每张表/字段补充：中文名称、业务描述、枚举值含义、是否对 AI 可见。 | 管理界面 + API                        |

**关键设计：`BASE_META_ENTITY` 和 `BASE_META_FIELD` 表结构**

```sql
-- 实体（表）元数据
BASE_META_ENTITY (
  F_ID,
  F_TENANT_ID,
  F_PHYSICAL_TABLE       -- 物理表名: MES_WORK_ORDER
  F_BUSINESS_NAME        -- 业务名称: 生产工单
  F_DESCRIPTION          -- 业务描述: 记录每个生产工单的基本信息...
  F_DOMAIN               -- 所属领域: production/quality/equipment/material
  F_AI_VISIBLE           -- 是否对AI可见: 1/0 (核心控制开关！)
  F_AI_SAMPLE_QUERIES    -- JSON: 示例查询（few-shot学习用）
                         -- ["查今天的一车间工单","本月超期工单有哪些"]
  F_RELATED_ENTITIES     -- JSON: 关联实体（帮助AI理解表关系）
  F_ROW_LEVEL_SECURITY   -- JSON: 行级安全规则
                         -- {"filterField":"F_WORKSHOP_ID","source":"user.workshopId"}
)

-- 字段元数据
BASE_META_FIELD (
  F_ID,
  F_ENTITY_ID,           -- 关联 BASE_META_ENTITY
  F_PHYSICAL_COLUMN      -- 物理字段名: F_YIELD_RATE
  F_BUSINESS_NAME        -- 业务名称: 良品率
  F_DESCRIPTION          -- 业务描述: 合格品数量/总生产数量×100%
  F_DATA_TYPE            -- 数据类型: decimal
  F_IS_DIMENSION         -- 是否是维度: 0
  F_IS_METRIC            -- 是否是度量: 1
  F_AGGREGATION          -- 默认聚合方式: AVG (可选: SUM/COUNT/AVG/MAX/MIN)
  F_ENUM_VALUES          -- JSON: 枚举值映射 {"1":"合格","2":"不合格","3":"返工"}
  F_AI_VISIBLE           -- 是否对AI可见
  F_SYNONYMS             -- JSON: 同义词 ["良品率","合格率","直通率"]
  F_FORMULA              -- 如果是派生指标: "F_PASS_COUNT/F_TOTAL_COUNT*100"
)
```

**本周验收标准：** 分析库跑通同步，元数据管理界面可用，业务专家完成核心 10 张表的语义标注。

#### 🔷 第 2 周：语义层核心——指标字典（Metrics Store）

**目标：这是护城河的核心！把企业的"业务口径"变成机器可读的"指标定义"。**

| 任务             | 具体做什么                                                   | 交付物                              |
| ---------------- | ------------------------------------------------------------ | ----------------------------------- |
| **指标注册中心** | 建 `BASE_METRIC_DEFINITION` 表，定义 MES 核心指标（OEE、良品率、产能利用率、计划达成率等）。每个指标包含：名称、计算公式、维度、过滤条件、数据源。 | 指标管理界面 + 30+ MES 核心指标注册 |
| **维度模型**     | 建 `BASE_DIMENSION_DEFINITION`，定义分析维度（时间、车间、产线、产品、班组、设备类型）。 | 维度管理界面                        |

**关键设计：`BASE_METRIC_DEFINITION` 表结构**

```sql
BASE_METRIC_DEFINITION (
  F_ID,
  F_TENANT_ID,
  F_METRIC_CODE          -- 唯一编码: yield_rate
  F_METRIC_NAME          -- 显示名称: 良品率
  F_DESCRIPTION          -- 完整描述: 合格品数量占总生产数量的百分比...
  F_SYNONYMS             -- JSON: 同义词 ["合格率","直通率","一次合格率"]
  F_CATEGORY             -- 指标分类: quality/production/equipment/efficiency
  
  -- 计算定义
  F_METRIC_TYPE          -- 类型: basic(基础)/derived(派生)/ratio(比率)
  F_FORMULA              -- 计算公式: "pass_count / total_count * 100"
  F_NUMERATOR            -- 分子指标引用(比率型): pass_count
  F_DENOMINATOR          -- 分母指标引用(比率型): total_count
  F_BASE_TABLE           -- 基础数据表: MES_QUALITY_RECORD
  F_AGGREGATION          -- 聚合方式: SUM/COUNT/AVG
  
  -- 可用的分析维度
  F_DIMENSIONS           -- JSON: ["workshop","product_line","shift","time"]
  
  -- 过滤条件（默认）
  F_DEFAULT_FILTERS      -- JSON: {"status":["completed"]}
  
  -- 业务规则
  F_BUSINESS_RULES       -- JSON: 业务约束说明
                         -- "注意：返工件不计入总数"
                         -- "注意：试产工单应排除在外"
  
  -- AI 相关
  F_AI_DESCRIPTION       -- 给AI看的完整描述（含口径说明）
  F_SAMPLE_QUESTIONS     -- JSON: 示例问题
  F_INTERPRETATION       -- JSON: 解读参考
                         -- {"good":">=95%","warning":"90-95%","bad":"<90%"}
)
```

**为什么这是护城河？**

- 云 SaaS 只能给你"通用指标"，但我们给客户的是**"你们厂自己的指标口径"**
- 同一个"良品率"，A 车间和 B 车间的算法可能不同，我们在语义层就解决了
- 指标定义是**业务专家的知识沉淀**，越用越准，竞争对手无法复制

**本周验收标准：** 指标字典管理界面可用，30 个 MES 核心指标注册完成。用户可以在界面里看到每个指标的完整口径说明。

**关键设计：Data Query Gateway 安全架构**

```
用户: "上月一车间良品率"
         │
         ▼
   ┌─────────────┐
   │ Schema RAG  │  向量匹配 → 命中: 指标"良品率" + 维度"车间"

   └──────┬──────┘
          ▼
   ┌─────────────┐
   │ LLM 生成    │  方案A: 直接调用 query_metrics 工具（推荐！）
   │ 查询方案    │  方案B: 生成 SQL（降级方案）
   └──────┬──────┘
          ▼
   ┌─────────────────────────────────────────────┐
   │          Data Query Gateway                  │
   │                                              │
   │  ① SQL 语法白名单: 只允许 SELECT             │
   │  ② 禁止: DROP/DELETE/UPDATE/INSERT/EXEC     │
   │  ③ 禁止: 子查询中的写操作                     │

   │  ⑥ 查询超时: SET LOCK_TIMEOUT 10000         │
   │  ⑦ 结果限制: TOP 1000                       │
   │  ⑧ 查询审计: 写入 BASE_AI_QUERY_LOG         │
   └──────┬──────────────────────────────────────┘
          ▼
   ┌─────────────┐
   │ MES_ANALYTICS│  ← 只查分析库，绝不碰生产库！
   │ (只读副本)   │
   └─────────────┘
```

## 📋 第二期、第三期简要审核意见

### 第二期（AI化引擎）审核

**整体认可**，但有 3 个修正：

1. **Workflow-MCP 必须加"预审"环节**：AI 发起流程前，先调用 `BusinessValidationService` 校验（如：报修设备是否真的存在、报修人是否有权限），不能直接启动。
2. **Form-MCP 的"智能填单"要基于"表单模板 IR"**：利用我们已有的 `FormPageIR`，AI 填充的不是原始 HTML 表单，而是 IR 的 `fieldValues`，这样和现有表单引擎完全兼容。
3. **Report-MCP 要复用第一期的指标字典**："一句话报表"的核心不是"生成 SQL"，而是"选指标 + 选维度 + 选图表类型"，这些都建立在第一期的语义层之上。**这就是为什么第一期必须先做语义层——它是后面所有引擎 AI 化的基石。**

### 第三期（岗位专家/总管家）审核

**整体认可**，但有 2 个修正：

1. **"主动感知"不能只靠定时任务**：第 4 周就应该开始规划事件驱动架构（基于 SQL Server Service Broker 或消息队列），让"设备停机"、"工单超期"等业务事件能实时触发 Agent，而不是等到第二天早上 8 点才发现。
2. **"人机协同闭环"的 DKEE 进化路径要明确**：用户的每次"采纳/驳回/修改"不只是存日志，而是要形成**反馈环路**——被采纳的查询模式自动加入 `F_AI_SAMPLE_QUERIES`，被驳回的指标定义触发审核流程。**这才是"越用越聪明"的真正机制。**

## 🎯 总结：为什么"语义层"才是真正的护城河

| 维度     | 云 SaaS 竞品                   | 我们的方案                                  |
| -------- | ------------------------------ | ------------------------------------------- |
| 数据查询 | NL2SQL，直连数据库，70% 翻车率 | NL→Semantic→SQL，语义层兜底，95%+ 准确率    |
| 指标口径 | 通用模板，"良品率"只有一种算法 | 指标字典，每个客户自己的口径，越用越准      |
| 安全     | AI 直接查生产库，风险巨大      | 分析库隔离 + 安全网关 + 行级权限            |
| 可扩展   | 每个新需求都要改代码           | 新指标只需在字典里注册，零代码              |
| 知识沉淀 | 无，每次查询都是一次性的       | 用户反馈自动进化指标定义和查询模式          |
| 客户粘性 | 随时可换                       | 指标字典 = 客户的业务知识资产，迁移成本极高 |
