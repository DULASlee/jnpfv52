# 第一章 · 文档概述

## 1.1 编写目的

本说明书是 JNPF 运行态智能层第一期的**第一份正式需求文档**，目的是：

1. **统一认知**——将分散在 33 号白皮书、35 号施工计划中的需求描述收敛为一份**单一真源**
2. **明确边界**——清晰区分"目标一（本期）"与"目标二~四（后续）"，避免研发越界
3. **驱动后续**——为架构设计说明书、详细设计说明书提供需求层输入
4. **验收对齐**——为 M-G1 里程碑提供可验证的需求条目

## 1.2 系统范围与边界

### 1.2.1 系统定义

**JNPF 运行态智能层**是在已有 JNPF 手工低代码平台（VisualDev / 流程 / 权限 / 报表）之上增量建设的**数据智能层**。运行态与开发态**正交**：

| 维度 | 开发态（10~12 号） | 运行态（本文 + 35~38 号） |
|------|-------------------|--------------------------|
| **关注点** | 平台如何把需求变成可部署系统 | 交付物上线后是否具备 AI 智能 |
| **产出** | 传统 MES 包（表单+流程+看板+移动） | 同一 MES 叠加数据湖 / 岗位专家 / 企业专家 / IoT |
| **用户** | 开发者 / IT | 业务人员 / 管理层 |
| **依赖** | 无（独立施工） | 依赖已有 MES 源表（手工或 10~12 产出均可） |

**第一期（目标一）**定位：在已运行的 MES 业务库之上，建设 **L1→L5 轻量数据湖**，交付 **MetricIR Studio** + **DataQueryGateway(MQL)** + **data-mcp 三工具**，使全厂离散指标**口径统一、可查询、可仿真**。

### 1.2.2 本期做

| # | 交付物 | IR / 组件 | 说明 |
|---|--------|-----------|------|
| D1 | L1→L2 CDC + SchemaGovernor | DATA_SYNC_TASK | P0/P1/P2 分级同步 |
| D2 | MetricIR 持久化 + Studio 设计器 | MetricIR | 公式/维度/同义词/Few-Shot |
| D3 | L4 语义层 Qdrant 双模 + Channel 同步 | Qdrant | 裁定2 Hybrid Search |
| D4 | DataQueryGateway + MqlTranslator | MQL | NL→MQL(JSON)→SQL |

| D7 | DashboardIR 单指标卡片编译 | CompileGateway | MetricIR→编译→看板卡 |

### 1.2.4 与开发态的关系

运行态第一期与开发态（10~12 号）**正交**，可**并行**施工：

- 10~12 编译出的 FormPageIR **可引用** MetricIR；但编译完成 ≠ 指标层已建
- 运行态第一期**不依赖**阶段五~六先完成
- 依赖条件仅为：已有 MES 源表（手工或 10~12 产出均可）

### 1.2.5 与第二~四期的关系

```
目标一（本文）→ 目标二（36号）→ 目标三（37号）→ 第四期（38号）
```

# 第二章 · 业务背景与产品定位

## 2.1 行业现状与痛点

### 2.1.1 传统 MES 的数据困境

当前国内 MES 系统已普遍解决"工单/报工/质检/设备"的流程管理，但在**数据智能层**普遍缺位：

| 痛点 | 现状 | 影响 |
|------|------|------|
| **指标口径不统一** | OEE 在报表、看板、领导汇报中数值不一致 | 管理层不信任数据 |
| **取数靠人工** | 选菜单→筛条件→导出→Excel 分析 | 效率低、响应慢 |
| **预警靠人盯** | 异常发生后人工发现、人工处理 | 错过最佳处理时机 |
| **知识不沉淀** | 老师傅经验在脑子里，新人无从学习 | 人员流动导致经验流失 |
| **AI 是外挂** | AI 功能独立于业务系统，数据不通 | AI 产出不可信 |

### 2.1.2 数据智能的正确范式

2026 年制造业数据智能的共识路线：**统一指标口径 → NL 问数 → 岗位专家 → 企业专家 → IoT 预测**。JNPF 运行态走这条路，并叠加两层差异化：

1. **造车间非造车厢**——平台提供 MetricIR/AgentIR/AlertRuleIR Studio，业务人员零代码配置；禁止内置"张总管子"式 Demo
2. **AI-off 零事故**——切断 LLM/Qdrant/MCP 后，表单/流程/Job/预聚合/VisualDev 零 Exception

## 2.2 产品定位

### 2.2.1 一句话定位

**JNPF 运行态第一期是 MES 的"数据湖基座"——在已有 MES 业务表之上，建设 L1→L5 轻量数据湖，使全厂离散指标口径统一、可查询、可仿真；业务人员 30 分钟内零代码完成指标配置。**

### 2.2.2 目标客户

| 客户类型 | 典型场景 | 价值主张 |
|---------|---------|----------|
| **制造企业 IT 部门** | MES 已上线，需要数据智能层 | 在不改 MES 的前提下叠加指标层 |
| **MES 厂商** | 给客户提供增值能力 | 标准化指标 + NL 问数 |
| **系统集成商** | 给客户交付数据中台 | 30 标准指标模板开箱即用 |

### 2.2.3 与友商对比

| 维度 | 传统 BI 工具 | 独立数据中台 | **JNPF 运行态第一期** |
|------|-------------|-------------|----------------------|
| 与 MES 集成 | 需定制对接 | 独立部署，数据搬运 | **原生叠加**，不改 MES |
| 指标口径 | 各模块各算 | 统一但需开发 | **MetricIR Studio 零代码** |
| NL 问数 | ❌ | 部分支持 | **MQL 白名单 + LLM 辅助** |
| AI-off 可用 | ✅ | ❌ | ✅ **预聚合 Job 独立运行** |
| 多租户 | ❌ | 部分 | **Schema 隔离** |

## 2.3 业务约束

### 2.3.1 强约束（33 号白皮书六大底线约束）

| 约束 | 内容 | 对第一期的影响 |
|------|------|---------------|
| **约束一 · JNPF 增量生存** | AI 挂时 VisualDev/流程/权限 100% 可用 | 预聚合 Job 独立于 LLM |
| **约束二 · 运行态红线** | 目标定义仅 33 号第二部分 §0.4 | 不做 Agent/Alert/IoT |
| **约束三 · 造车间非造车厢** | 业务人员通过 Studio 配置能力 | 禁止内置"张总管子" Demo |
| **约束五 · IR 互通** | 数据/规则/逻辑互相引用、同一口径 | MetricIR.code 全链路一致 |
| **约束六 · AI-off 零事故** | 切断 LLM 后零 Exception | 预聚合 + 看板卡独立运行 |
| **约束八 · 可观测性** | OTel + Prometheus + /health + /ready | 第一期必须就绪 |

### 2.3.2 架构裁定（33 号白皮书十二大裁定，第一期涉及项）

| 裁定 | 要点 | 第一期影响 |

| **裁定12 · 数据安全** | PII 脱敏 + SQL 注入防护 | DataQueryGateway 白名单 |

## 3.2 角色详细说明

### 3.2.1 MES 管理员

- **典型用户**：客户方的 IT 经理、数据库管理员
- **技能门槛**：懂数据库、懂 MES 业务表结构
- **核心场景**：
  - 配置 SchemaGovernor：设置租户 Schema 模板、同步策略
  - 监控 CDC 同步：查看 DATA_SYNC_TASK 水位、P0/P1/P2 延迟
  - 容量规划：查看 L1 明细行数、L3 预聚合行数、L4 Qdrant 向量数
  - 告警处理：P0 延迟>10s 自动降级告警

### 3.2.2 业务人员

- **典型用户**：生产经理、质量工程师、设备管理员
- **技能门槛**：懂业务指标含义，不懂代码
- **核心场景**：
  - MetricIR Studio：零代码新建/修改指标（code、口径、维度、同义词）
  - 指标仿真：在 Studio 中预览指标计算结果
  - 看板消费：查看 DashboardIR 单指标卡片
  - 30 标准指标导入：一键导入 ISA-95 / GB/T 标准指标模板

### 3.2.3 IT 运维

- **典型用户**：平台运维工程师
- **技能门槛**：懂 SQL Server 运维、懂监控告警
- **核心场景**：
  - 数据库维护：L1 明细归档、L3 预聚合表维护
  - 同步链路监控：CDC Worker 状态、Channel 同步队列深度
  - 告警处理：ALERT_LOG 查询、告警确认与恢复
  - 健康检查：/health、/ready 端点监控

## 3.3 使用场景

### 3.3.1 场景 A：业务人员"零代码配指标"

```
1. 业务人员登录 → 进入 MetricIR Studio
2. 点击"新建指标"
3. 填写：code=oee, 名称=设备综合效率, 口径=实际产量/理论产量, 维度=车间/产线
4. 添加同义词：设备利用率、综合效率
5. 点击"仿真" → 预览计算结果

```

```
  ↓

  ↓
```

```
  - P0：工单/报工/质检 → 实时同步（P95≤30s）
```

### 9.1.1 核心功能验收

- [ ] MetricIR Studio：业务人员新建/修改指标，**无需开发**
- [ ] 30 标准指标导入 + 仿真 **30/30** 通过
- [ ] MQL→SQL 网关：注入拦截 100%
- [ ] data-mcp 三工具 MCP 握手 + 单元测试
- [ ] Qdrant 熔断 → CONTAINS 降级演练通过
- [ ] **禁止**以「语音问 OEE Demo」替代 Studio 验收

### 9.1.2 D爷审查项（新增必验）

- [ ] **CDC 选型 ADR**：已写入 docs/架构迭代/，明确 Change Tracking vs Debezium 选择及理由
- [ ] **P0 降级演练**：模拟 P0 延迟>30s → 自动转 P1 + 告警触达 → 恢复 P0，全程无人工介入
- [ ] **LLM 推理路径标签**：route:rule / route:llm 分别在日志中可查
- [ ] **存储成本模拟**：R1-S4 压测报告含「中型 MES 1 年 L1 行数预测 + 冷归档策略」
- [ ] **IrDependencyGraph POC**：MetricIR 发布时触发下游检测（第二期完整实现；本期 POC 验证可行性）
- [ ] **PII 脱敏验证**（裁定12）：随机抽 10 条含手机号的业务记录，LLM 收到的 Prompt 中手机号已替换为 [MASKED_PHONE]；AI_PII_MASK_LOG 有记录
- [ ] **EvalSet 基线**（裁定11）：30 条黄金问答对录入 AI_EVAL_LOG；LLM-as-Judge 准确率 ≥80%
- [ ] **SUS 易用性评分**：招募≥3 名真实业务人员完成 UAT 操作；SUS 量表 10 题互评，目标分≥68
- [ ] **安全基线验证**：① 随机构造含手机号的查询，DataQueryGateway 拦截确认；② Prompt Injection 模拟测试；③ /health 和 /ready 端点正常响应；④ 查询 Trace ID 在 OpenTelemetry 可见
- [ ] **可观测性就绪**：Prometheus /metrics 端点正常吐出 QPS/延迟/Token 消耗；AI_INFERENCE_LOG 有 TraceID 字段；Grafana 基础面板可访问

## 9.2 Sprint 0 POC 门禁

| POC | 验收 | 失败回退 |
|-----|------|----------|
| SchemaGovernor 批量 DDL | 3 租户并发隔离 | 应用层临时兜底 |
| CDC 工具选型 | SQL Server Change Tracking 首选；P95<1min | 串行 worker |
| P0 自动降级演练 | 模拟 P0 延迟>10s → 自动转 P1 + 告警 | 告警写 ALERT_LOG |
| 6000 万行/日压测 | 7×24 无 OOM | 分库 Plan B |
| 规则+主模型分类 | 200 条真实问句命中率≥85% | 全云端 |
| P0/P1/P2 延迟 | P0≤30s · P1≤5min · P2=凌晨 | P0 降为 5min 增量 |
