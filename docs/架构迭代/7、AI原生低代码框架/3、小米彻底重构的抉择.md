### 任务 1.1 增强 SqlSugarConfigureExtensions.cs

**这是整个架构迭代的第一个编码任务。** 它为所有后续的数据访问层工作奠定基础。

**文件：** `JNPF.Extras.DatabaseAccessor.SqlSugar` 项目中的 `SqlSugarConfigureExtensions.cs`

**修改内容（一次性完成以下全部）：**

**A）`SetDbConfig` 方法增强：**

- 从 `appsettings.json` 读取连接池配置（`Database:MaxPoolSize`、`Database:MinPoolSize`、`Database:ConnectTimeout`），有默认值
- 将连接池参数注入到连接字符串中
- 保留现有的 Oracle 类型映射和列配置逻辑（`EntityService` 回调）
- 保留现有的 `IsAutoCloseConnection`、`MoreSettings` 配置

**B）`SetDbAop` 方法增强：**

- `OnLogExecuting`：保留现有逻辑
- `OnLogExecuted`：保留现有慢查询检测，阈值改为从 `Database:SlowQueryThreshold` 配置读取（默认 1000ms）
- `OnError`：保留现有逻辑
- **新增 `OnDiffLog`：** 注册数据变更日志回调。开关通过 `Database:EnableDiffLog` 配置控制。变更事件通过 EventBus 发布（不直接写表），与后续 Outbox 模式联动
- **新增 `OnExecutingChangeSql`：** Oracle 场景的参数适配从 Repository 构造函数移到此处全局配置

**C）新增公共方法 `AppendDataExecutingHandler`：**

```
方法签名：public static void AppendDataExecutingHandler(SqlSugarScopeProvider db, Action<object, EntityColumnInfo> newHandler)

实现逻辑：
  1. 保存 db.Aop.DataExecuting 现有值为 oldHandler
  2. db.Aop.DataExecuting = (oldValue, entityInfo) => {
       oldHandler?.Invoke(oldValue, entityInfo);  // 先执行已有回调
       newHandler(oldValue, entityInfo);           // 再执行新回调
     }

用途：Repository 中的多维度过滤器（租户、系统、软删除等）通过此方法追加，
     互不覆盖。这是解决 AOP 回调覆盖冲突的基础设施。
```

**D）修改 `SqlSugarConfigure` 注册方法：**

- 将 `ISqlSugarClient` 的注册方式从 `AddSingleton` 改为 `AddScoped`
- **原因：** SqlSugarScope 虽然是单例设计，但 Scoped 注册可以让每个请求通过 `CopyNew()` 获得独立的上下文实例，从根本上解决并发状态泄漏问题
- 如果评估后发现 SqlSugar 不支持 Scoped 生命周期（需要验证），则保持 Singleton 但添加文档说明"所有使用 ISqlSugarClient 的地方必须调用 CopyNew()"——此决策在阶段 0 的评估中已确定

**E）同步修改 `SqlSugarRepository` 的 DI 注册：**

- 确认 `services.AddScoped(typeof(ISqlSugarRepository<>), typeof(SqlSugarRepository<>))` 保持不变

**本次修改后，此文件达到最终形态。后续所有阶段不再修改此文件。**

**验收标准：**
- 编译通过
- 已有的集成测试全部通过
- `AppendDataExecutingHandler` 有对应的单元测试：验证链式调用不丢失回调

**预估工时：** 2 天

### 任务 2.3 新建 TenantContext 服务族

**新建文件清单：** `JNPF.Extras.DatabaseAccessor.SqlSugar` 项目中新建目录

```
JNPF.Extras.DatabaseAccessor.SqlSugar/
└── TenantContext/
    ├── ITenantContext.cs
    ├── TenantContext.cs
    ├── ITenantResolver.cs
    ├── ClaimTenantResolver.cs
    ├── CacheTenantResolver.cs
    ├── ITenantIsolationStrategy.cs
    ├── ColumnIsolationStrategy.cs
    └── SchemaIsolationStrategy.cs
```

**各文件职责与核心契约：**

**`ITenantContext.cs`：**
```
属性：
  TenantId (string)
  ConnectionConfigId (string)
  IsolationType (int) — 0=默认, 1=字段隔离, 2=Schema 隔离
  IsolationFieldValue (string)
  SystemId (string)
  IsMultiTenant (bool)
  IsMultiSystem (bool)

方法：
  Task ResolveAsync() — 从当前请求解析所有上下文
  bool IsDefaultTenant()
```

**`TenantContext.cs`（Scoped 生命周期）：**
- 注入 `IHttpContextAccessor`、`ICacheManager`、`IOptions<TenantOptions>`、`IOptions<ConnectionStringsOptions>`
- `ResolveAsync()` 方法封装当前 `SqlSugarRepository` 构造函数中的全部租户解析逻辑：
  - 从 JWT Claims 获取 TenantId
  - 从缓存获取租户连接配置
  - 判断隔离类型
  - 获取 SystemId（从缓存或 JWT Claims）
  - 处理 `orgSystem` 等特殊逻辑
- **封装所有 `App.HttpContext`、`App.GetConfig`、`App.GetOptions` 的调用**，Repository 不再直接使用这些静态方法

**`ITenantResolver.cs`：**
```
方法：
  string ResolveTenantId(HttpContext httpContext)
  Task<TenantConnectionInfo> ResolveConnectionAsync(string tenantId, ICacheManager cache)
```

**`ClaimTenantResolver.cs`：**
- 从 JWT Claims 中提取 TenantId、UserId、SystemId

**`CacheTenantResolver.cs`：**
- 从缓存中查询 `jnpf:global:tenant` 获取租户连接配置
- 处理租户不存在、配置不合法等异常情况

**`ITenantIsolationStrategy.cs`：**
```
方法：
  void ApplyQueryFilter(ISqlSugarClient db, ITenantContext context)
  void ApplyWriteProtection(ISqlSugarClient db, ITenantContext context)
  void ConfigureConnection(ConnectionConfig config, ITenantContext context)
```

**`ColumnIsolationStrategy.cs`：**
- `ApplyQueryFilter`：通过 `QueryFilter.AddTableFilter<ITenantFilter>(it => it.TenantId == context.IsolationFieldValue)`
- `ApplyWriteProtection`：通过 `AppendDataExecutingHandler`（阶段 1 的基础设施）注册 TenantId 自动写入回调
- `ConfigureConnection`：使用默认连接

**`SchemaIsolationStrategy.cs`：**
- `ApplyQueryFilter`：通过 `AsTenant().GetConnectionScope()` 切换到对应 Schema
- `ApplyWriteProtection`：不需要额外处理（Schema 隔离天然隔离）
- `ConfigureConnection`：设置 Schema 名称

**DI 注册方式：**
```
services.AddScoped<ITenantContext, TenantContext>();
services.AddScoped<ITenantResolver, ClaimTenantResolver>();
services.AddScoped<ColumnIsolationStrategy>();
services.AddScoped<SchemaIsolationStrategy>();
```

**验收标准：**
- `TenantContext` 在模拟 HTTP 请求上下文中能正确解析 TenantId
- `ColumnIsolationStrategy` 的 `ApplyQueryFilter` 正确注册了租户过滤器
- `ColumnIsolationStrategy` 的 `ApplyWriteProtection` 通过 `AppendDataExecutingHandler` 注册回调，不覆盖已有回调
- 有对应的单元测试

**预估工时：** 3 天

### 任务 5.3 一体化事件可靠性管道（Outbox + 退避重试 + 幂等消费）

**目的：** 将 Outbox 模式、指数退避重试、幂等消费作为一个完整的事件管道一次性建设，避免接口反复调整。

**新建文件清单：**

```
JNPF.Extras.EventBus.RabbitMQ/
├── Outbox/
│   ├── EventOutboxMessage.cs          — Outbox 表实体
│   ├── IEventOutboxStore.cs           — Outbox 存储接口
│   ├── SqlSugarEventOutboxStore.cs    — 基于 SqlSugar 的实现
│   └── EventOutboxDispatcher.cs       — 后台投递服务（BackgroundService）
├── Retry/
│   ├── PollyRetryHandlerExecutor.cs   — 替代 RetryEventHandlerExecutor
│   └── CircuitBreakerState.cs         — 熔断器状态管理
└── Idempotency/
    ├── ProcessedEvent.cs              — 已处理事件记录实体
    └── IdempotentEventHandler.cs      — 幂等检查中间件
```

**整体管道设计：**

```
业务代码发布事件
       ↓
EventOutboxStore.WriteAsync(event)     ← 与业务操作在同一个事务中
       ↓
EventOutboxDispatcher 轮询（每5秒）
       ↓
PollyRetryHandlerExecutor 投递        ← 指数退避 + 熔断
       ↓  失败时
回到 Outbox，标记失败，等待重试         ← 最多重试5次
       ↓  超过5次
标记为 DeadLetter                     ← 死信，等待人工处理
       ↓  成功时
IdempotentEventHandler 幂等检查       ← 检查 ProcessedEvent 表
       ↓  未处理过
执行事件处理器
       ↓
写入 ProcessedEvent 记录
```

**各组件职责：**

**`EventOutboxMessage.cs`：**
```
Id (Guid, PK)
EventName (string)
EventPayload (string — JSON)
CreatedAt (DateTime)
ProcessedAt (DateTime?)
RetryCount (int)
MaxRetryCount (int)
Status (int) — Pending=0, Processing=1, Completed=2, Failed=3, DeadLetter=4
Error (string?)
```

**`IEventOutboxStore.cs`：**
```
Task WriteAsync(string eventName, object payload)  — 写入 Outbox
Task<IList<EventOutboxMessage>> GetPendingAsync(int batchSize)  — 获取待投递
Task MarkCompletedAsync(Guid id)  — 标记完成
Task MarkFailedAsync(Guid id, string error)  — 标记失败
Task MarkDeadLetterAsync(Guid id)  — 标记死信
Task<IList<EventOutboxMessage>> GetDeadLettersAsync()  — 获取死信列表
Task RetryDeadLetterAsync(Guid id)  — 重试死信
```

**`EventOutboxDispatcher.cs`：**
- 继承 `BackgroundService`
- 每 `Database:OutboxPollingInterval`（默认 5 秒）轮询一次
- 批量获取 Pending 状态的消息
- 逐条通过 `PollyRetryHandlerExecutor` 投递
- 投递成功标记 Completed，失败标记 Failed
- 超过 `MaxRetryCount` 标记 DeadLetter

**`PollyRetryHandlerExecutor.cs`：**
- 替代现有的 `RetryEventHandlerExecutor`
- 使用 Polly 的 `RetryAsync` + `CircuitBreakerAsync` 策略
- 退避策略：指数退避 + 随机抖动
- 熔断策略：连续 10 次失败后熔断 30 秒
- 所有参数通过 `EventBus` 配置节外部化

**`IdempotentEventHandler.cs`：**
- 在事件处理管道中，执行前检查 `ProcessedEvent` 表
- 检查 Key = EventId + HandlerName
- 不存在则执行处理并写入记录
- 存在则跳过（返回）

**`ProcessedEvent.cs`：**
```
EventId (string, PK)
HandlerName (string, PK)
ProcessedAt (DateTime)
```

**修改已有文件：**
- `RetryEventHandlerExecutor.cs`：标记为 `[Obsolete]`，保留向后兼容
- `LogEventSubscriber.cs`：改为通过 Outbox 发布日志事件（而非直接写数据库），或标记为 `[BypassOutbox]`（低价值日志可绕过）

**验收标准：**
- 模拟数据库提交成功但 EventBus 暂时不可用：事件持久化到 Outbox 表
- EventBus 恢复后：Dispatcher 自动投递之前的消息
- 模拟同一事件投递两次：第二次被幂等检查跳过
- 模拟持续失败：退避间隔递增，达到阈值后熔断
- 超过最大重试次数：事件标记为死信，可通过管理端 API 查看

**预估工时：** 5 天

for (const file of allSchemas) {
  const schemaPath = path.join(SCHEMAS_DIR, file);
  const schema = JSON.parse(fs.readFileSync(schemaPath, 'utf-8'));

  let ir;
  try {
    ir = cleanSchema(schema);
  } catch (e) {
    results.push({
      schema: file, fields: 0, mappedFields: 0,
      unmappedFields: ['CLEAN_FAIL'], files: 0,
      issues: [(e as Error).message], evalCount: -1, insertPointCount: 0,
    });
    continue;
  }

  const compiler = new Vue3Compiler({
    entity: file.replace('schema-', '').replace('.json', ''),
    entityLabel: file,
  });

  let result;
  try {
    result = compiler.compile(ir);
  } catch (e) {
    results.push({
      schema: file, fields: ir.fields.length, mappedFields: 0,
      unmappedFields: ir.fields.map(f => f.model),
      files: 0, issues: [`COMPILE_FAIL: ${(e as Error).message}`],
      evalCount: -1, insertPointCount: 0,
    });
    continue;
  }

  // 统计
  let evalCount = 0;
  let insertPointCount = 0;
  for (const [, content] of result.project) {
    if (content.match(/\beval\s*\(/)) evalCount++;
    if (content.includes('@jnpf-gen:insert-point')) insertPointCount++;
  }

  results.push({
    schema: file,
    fields: ir.fields.length,
    mappedFields: ir.fields.length, // cleanSchema 能解析的都算 mapped
    unmappedFields: [],
    files: result.project.size,
    issues: result.warnings,
    evalCount,
    insertPointCount,
  });

  // 写入输出目录
  const outDir = path.join(OUTPUT_DIR, file.replace('.json', ''));
  for (const [filePath, content] of result.project) {
    const fullPath = path.join(outDir, filePath);
    fs.mkdirSync(path.dirname(fullPath), { recursive: true });
    fs.writeFileSync(fullPath, content, 'utf-8');
  }
}

// 输出报告
console.log('Schema | Fields | Files | Eval | InsertPt | Issues');
console.log('-------|--------|-------|------|----------|-------');
for (const r of results) {
  console.log(
    `${r.schema.padEnd(35)} | ${String(r.fields).padEnd(6)} | ${String(r.files).padEnd(5)} | ${String(r.evalCount).padEnd(4)} | ${String(r.insertPointCount).padEnd(8)} | ${r.issues.length > 0 ? r.issues.join('; ') : '✅'}`
  );
}

// 通过阈值检查
const p0Results = results.filter(r => P0_SCHEMAS.includes(r.schema));
const p0SchemasAvailable = p0Results.filter(r => r.files > 0);
const allP0Pass = p0SchemasAvailable.every(r =>
  r.evalCount === 0 && r.files > 0 && r.issues.length === 0
);

const totalFields = results.reduce((s, r) => s + r.fields, 0);
const mappedFields = results.reduce((s, r) => s + r.mappedFields, 0);
const coverageRate = totalFields > 0 ? (mappedFields / totalFields * 100).toFixed(1) : '0';

console.log('\n=== 阈值检查 ===');
console.log(`P0 Schema 可用: ${p0SchemasAvailable.length}/${P0_SCHEMAS.length}`);
console.log(`P0 全部通过: ${allP0Pass ? '✅' : '❌'}`);
console.log(`字段覆盖率: ${coverageRate}% (目标 ≥80%)`);
console.log(`eval/Function: ${results.reduce((s, r) => s + Math.max(0, r.evalCount), 0)} (目标 0)`);

// 写入报告文件
const reportPath = path.resolve(__dirname, '../docs/adr-017-diff-report.md');
const report = [
  '# ADR-017 双路径 Diff 报告',
  `> 生成时间: ${new Date().toISOString()}`,
  '',
  `## 总览`,
  `- Schema 总数: ${results.length}`,
  `- 字段总数: ${totalFields}`,
  `- 已映射: ${mappedFields} (${coverageRate}%)`,
  `- P0 通过: ${allP0Pass ? '是' : '否'}`,
  '',
  '## 详细结果',
  '| Schema | Fields | Files | Eval | Issues |',
  '|--------|--------|-------|------|--------|',
  ...results.map(r =>
    `| ${r.schema} | ${r.fields} | ${r.files} | ${r.evalCount} | ${r.issues.length > 0 ? r.issues.join('; ') : '✅'} |`
  ),
].join('\n');

fs.mkdirSync(path.dirname(reportPath), { recursive: true });
fs.writeFileSync(reportPath, report, 'utf-8');
console.log(`\n报告已写入: ${reportPath}`);
