## 二、详细裁决

### I-05 OTel跨服务追踪传递机制

**裁决：采用方案A，全链路覆盖，分阶段实施**

| 方案  | 采纳部分     | 说明                                                |
| ----- | ------------ | --------------------------------------------------- |
| 方案A | ✅ 全链路覆盖 | 包含HTTP、Hangfire、LLM网关、SignalR、熔炉5个边界点 |
| 方案B | ❌ 暂不采纳   | 前端和熔炉延后会导致P-05范围缩减，与议题1锁定项冲突 |

**核心设计**：
- **传递标准**：W3C TraceContext（行业标准，兼容性最好）
- **注入方式**：拦截器/中间件自动注入（非侵入，开发无感）
- **验证方式**：链路追踪平台可视化（Jaeger/Grafana）

**分阶段实施计划**：

| 阶段 | 边界点                                     | 完成时间            | 状态     |
| ---- | ------------------------------------------ | ------------------- | -------- |
| P0   | HTTP前端→后端、后端→Hangfire、后端→LLM网关 | 本周五前            | ✅ 执行   |
| P1   | 后端→SignalR推送                           | M1前                | ⏳ 待执行 |
| P2   | Studio→Foundry（熔炉推送）                 | M5前（依赖FM3联调） | ⏳ 待执行 |

**关键约束**：
- `BASE_AI_CALL_LOG` 新增 `F_TRACE_ID NVARCHAR(50)` + `F_TRACE_SOURCE NVARCHAR(20)` 字段（议题1 P-05已锁定）
- Hangfire JobFilter 实现Trace上下文传递
- 前端Vue3 + SSE + 熔炉Python作为P2任务延后

**责任人**：后端工程师（核心实现）+ 前端工程师（P2任务）+ 熔炉工程师（P2任务）
**截止时间**：本周五前完成P0核心链路，M1前完成P1，M5前完成P2

### I-06 性能容量规划和衰减曲线

**裁决：采用方案A，3等级容量模型 + 1/2/5沙箱并发实测**

| 方案  | 采纳部分                   | 说明                                                         |
| ----- | -------------------------- | ------------------------------------------------------------ |
| 方案A | ✅ 3等级容量模型 + 衰减矩阵 | 轻/中/重3级，1/2/5沙箱并发实测矩阵                           |
| 方案B | ❌ 暂不采纳                 | “阶段六部署后实测”等于不测，衰减矩阵实测数据是M5 H6性能门禁的必要输入 |

**3等级容量规划**：

| 等级                 | 流水线数 | 同时活跃沙箱 | DB连接数 | CPU峰值 | 内存峰值 | 验收性能                       |
| -------------------- | -------- | ------------ | -------- | ------- | -------- | ------------------------------ |
| **轻度（开发）**     | 10       | 2            | 20       | 30%     | 4GB      | §10.1.1 全部基线               |
| **中度（生产目标）** | 100      | 5            | 50       | 60%     | 8GB      | §10.1.1 基线 × 1.5             |
| **重度（扩展边界）** | 1000     | 10           | 100      | 85%     | 16GB     | §10.1.1 基线 × 3.0（允许降级） |

**1/2/5沙箱并发衰减矩阵**（需实测）：

| 指标                          | 1沙箱 | 2沙箱 | 5沙箱 | 衰减率 |
| ----------------------------- | ----- | ----- | ----- | ------ |
| DB CPU                        | 15%   | 25%   | 50%   | +35%   |
| DB P95查询                    | 100ms | 130ms | 200ms | +100%  |
| BASE_AI_PIPELINE 单条查询     | 80ms  | 100ms | 180ms | +125%  |
| BASE_AI_PIPELINE_MESSAGE 分页 | 200ms | 280ms | 500ms | +150%  |
| LLM 单次对话 P95              | 45s   | 48s   | 60s   | +33%   |
| 沙箱创建                      | 20s   | 25s   | 30s   | +50%   |
| SSE checkpoint推送            | 150ms | 180ms | 280ms | +87%   |
| 内存峰值                      | 3GB   | 5GB   | 9GB   | +200%  |

**关键约束**：
- 基准指标定为 **1000并发**（满足M5发布预期）
- 压测作为P2任务延后，阶段六部署后实测
- 新增 `BENCHMARK_BASELINE` 表存储基线数据
- 告警阈值：DB CPU > 70%，DB P95 > 300ms，内存 > 12GB

**责任人**：测试工程师（压测脚本）+ 后端工程师（衰减矩阵实测）+ 运维工程师（告警配置）
**截止时间**：本周五前完成表格定义，阶段五W2完成实测，M2前完成基线接入

### I-07 降级性能指标定义

**裁决：采用方案A，5级降级链，与议题1 P-05对齐**

| 方案  | 采纳部分    | 说明                                                     |
| ----- | ----------- | -------------------------------------------------------- |
| 方案A | ✅ 5级降级链 | L0-L5完整链路，与§7.7降级链对齐                          |
| 方案B | ❌ 暂不采纳  | 3级与议题1 P-05锁定的5级降级链冲突，会造成文档与代码脱节 |

**5级降级性能指标**：

| 降级级别                | 供应商          | 触发条件         | P95延迟预算             | Token成本上限 | 用户感知                                     |
| ----------------------- | --------------- | ---------------- | ----------------------- | ------------- | -------------------------------------------- |
| **Level 0（首选）**     | MiMo V2.5 Pro   | 默认             | **< 60s**               | 标准价        | 正常                                         |
| **Level 1（首次降级）** | DeepSeek V4 Pro | MiMo 连续3次失败 | **< 80s**（+20s容忍）   | 标准价        | toast.warning "已切换备用模型"               |
| **Level 2（深度降级）** | OpenAI GPT-4o   | DeepSeek也失败   | **< 100s**（+40s容忍）  | 1.5x          | toast.warning "使用高级模型，成本增加"       |
| **Level 3（兜底降级）** | Qwen-Max        | OpenAI也失败     | **< 120s**（+60s容忍）  | 标准价        | toast.warning "模型稳定性下降，建议稍后重试" |
| **Level 4（最终兜底）** | Ollama本地      | 所有云供应商失败 | **< 180s**（+120s容忍） | 0（本地）     | 强制切"无AI专家模式"提示                     |
| **Level 5（无AI）**     | 无              | 所有供应商不可用 | **响应 = 0**            | 0             | 弹"AI不可用，请手工编辑IR"对话框             |

**关键约束**：
- 与议题1 P-05锁定的5级降级链完全对齐
- 降级时必须toast.warning通知，不能静默降级
- 降级过程SSE必须推送 `model_changed` 事件（议题4 B-06已锁定）
- 降级审计字段：`BASE_AI_CALL_LOG.F_FALLBACK`（0/1/2标记降级级别）

**责任人**：后端工程师（降级逻辑）+ 前端工程师（toast+SSE推送）
**截止时间**：本周五前完成指标定义，M1前完成toast推送，M2前完成SSE事件推送
