### 2.2 关键技术决策(ADR)

#### ADR-001: 向量库选型 —— **SQL Server 2019+ 内置 JSON + 自建倒排索引**

**决策**: 不引入独立向量库(Qdrant/Milvus/Pgvector 全部否决),用 SQL Server 2019+ 的 `JSON_VALUE` + `ISJSON` + 自建简单倒排索引(关键词+权重)。

**理由**:
- 我们的向量量级: 30 个指标 × 平均 200 字描述 + 50 张表 × 平均 10 个字段 = **6,100 个节点**,完全不需要 ANN 索引
- 简单倒排索引召回率 > 95%,延迟 < 10ms
- 零额外基础设施,零运维成本
- 与 SQL Server 原生事务一致,**双库一致性问题彻底解决**

**实现**:
```sql
-- 关键词倒排索引表
BASE_SEMANTIC_KEYWORD_INDEX (
  F_ID              BIGINT IDENTITY PRIMARY KEY,
  F_TENANT_ID       NVARCHAR(50),
  F_NODE_TYPE       NVARCHAR(20),     -- 'metric'/'field'/'entity'
  F_NODE_ID         NVARCHAR(50),
  F_KEYWORD         NVARCHAR(100),    -- 分词后的关键词
  F_WEIGHT          DECIMAL(3,2),     -- TF-IDF 权重
  INDEX IX_KEYWORD_TENANT (F_TENANT_ID, F_KEYWORD)
)

-- 同义词扩展表
BASE_SYNONYM_DICT (
  F_ID              NVARCHAR(50) PRIMARY KEY,
  F_TENANT_ID       NVARCHAR(50),
  F_STANDARD_WORD   NVARCHAR(100),    -- 标准词
  F_SYNONYM         NVARCHAR(100),    -- 同义词/黑话
  F_WEIGHT          DECIMAL(3,2),     -- 匹配置信度
  UNIQUE INDEX IX_SYNONYM (F_TENANT_ID, F_SYNONYM)
)
```

**Schema RAG 检索流程**:
1. 用户输入 → 关键词分词(中英文 + 同义词扩展)
2. 查 `BASE_SEMANTIC_KEYWORD_INDEX` 找 Top-10 节点
3. 查 `BASE_SYNONYM_DICT` 做同义词扩展
4. 取 Top-3 表 + Top-3 指标 + Top-3 字段的元数据,组装成 LLM Prompt(总 < 1500 Token)
5. LLM 输出 MQL → MQL 引擎 → SQL

#### ADR-002: 双库一致性 —— **逻辑联邦,Prompt 层缝合**

**决策**: 指标字典、MQL 公式、Schema RAG 全部在 SQL Server,**不再引入独立向量库**。

**理由**:
- 关系库 + 向量库的双库联邦会带来跨库一致性、链路延迟、运维复杂度 3 个问题
- 我们的向量量级根本不需要独立向量库
- 用 SQL Server 自身的 `JSON_VALUE` + 倒排索引,性能足够

**实现**: 业务知识(`BASE_KNOWLEDGE_*`)仍可在第二期单独建表,但**物理上都在 SQL Server**,通过外键关联(`F_KNOWLEDGE_NODE_ID`)。

#### ADR-003: LLM 部署 —— **分场景选型,默认 DeepSeek-V3**

**决策**: 见 1.4 节 LLM 基线表

**关键约束**:
- 私有化部署必须支持**离线运行**(无外网),采用 Qwen 系列
- 云端 API 必须支持**审计日志回传**,便于排查问题
- LLM 推理延迟 P95 < 3s,否则触发降级(见第八章)

#### ADR-004: 不开发可视化语义画布 —— **配置即代码**

**决策**: 第一期用 JNPF 代码生成器做 CRUD 界面,数据按未来 SemanticIR 的 JSON Schema 设计,第二期再补 UI。

**理由**: 拖拽画布需要 6-8 周,会拖死工期。配置即代码用 1 周搞定。

**演进路径**: 数据结构完全按未来 `SemanticIR` 设计,第二期直接用这些表做画布,数据兼容。

#### ADR-005: 不让 LLM 写 SQL —— **NL → LLM → MQL → .NET → SQL**

**决策**: 强制采用 `NL → LLM → MQL(JSON) → .NET 引擎 → SQL` 的链路。

**理由**:
- LLM 直出 SQL 的 PoC 70% 死在生产环境
- MQL 是结构化 JSON,LLM 输出 100% 可控
- .NET 引擎基于预定义公式,100% 安全,50ms 内完成

### 2.3 与 JNPF V5.2 的衔接(4 条铁律)

| 铁律                 | 实施细节                                                     |
| -------------------- | ------------------------------------------------------------ |
| **① 多租户铁律**     | 所有新建表必须含 `F_TENANT_ID`,实体类继承 `TenantEntity`,复用 `ITenantFilter` |

## 八、降级与容错方案(分)

> **千问 v1.0 完全没提降级,生产环境必出问题**

### 8.1 LLM 不可用降级

```
正常路径: NL → LLM → MQL → SQL
降级路径: NL → 模板匹配 → MQL → SQL

触发条件: LLM 调用超时(>5s)或连续失败(>3 次)
降级行为: 切换到"模板查询"模式
  - 用户在 UI 上看到"模板查询"按钮
  - 预置 20 个常用查询模板
  - 用户手动选择模板,跳过 LLM 意图识别
```

### 8.2 向量/索引检索不可用降级

```
正常路径: NL → Schema RAG(倒排索引) → Top-3 → LLM
降级路径: NL → 全量元数据注入 → LLM

触发条件: Schema RAG 服务异常
降级行为: 直接把当前租户所有指标和字段描述注入 LLM(可能 5000+ Token)
影响: 推理成本上升,但功能可用
```

### 8.3 同步延迟过高降级

```
正常路径: AI 查询走分析库
降级路径: AI 查询走生产库只读副本

触发条件: 分析库数据延迟 > 30 分钟
降级行为: 临时切换到生产库只读副本查询
影响: 性能略降,但数据实时
恢复: 同步恢复正常后自动切回
```

### 8.4 数据库故障降级

```
正常路径: 分析库查询
降级路径: Redis 缓存 → 返回历史数据(标注"数据时间")

触发条件: 分析库不可用
降级行为: 返回 Redis 缓存数据,并在 UI 标注"数据时间:XX"
```
