D爷的方案确实抓住了核心——**"骨架催化"让SA九步从无源之水变成有根之木**。但要真正落地，有几个关键细节需要完善，否则会在工程实现时踩坑。

以下是我的深度分析和完整细节补充。

---

## 一、对D爷方案的深度分析

### 1.1 三个核心优势（必须保留）

**优势一：骨架先于细节，降低LLM幻觉率**

没有骨架时，SA九步的DFD/数据字典是从零生成，LLM容易"凭空捏造"实体。有了骨架后，DFD是在已识别的实体和流程上"细化"，幻觉空间被压缩了80%。

**优势二：事件级对话比全局对话精准10倍**

全局需求对话时，LLM的注意力被分散在所有业务领域。按事件切分后，每个对话窗口只聚焦一个业务场景，上下文更短、更精准、Token消耗更低。

**优势三：主外键即业务规则**

骨架中的表结构草案自带主外键关系，这直接成为Stage 2追问的锚点——"work_order.part_id关联了零件表，当零件有版本时怎么处理？"——这种追问比泛泛地问"还有什么需求"有效得多。

### 1.2 六个必须完善的风险点

| #      | 风险                                                         | 影响                                                 | 完善方向                                                     |
| ------ | ------------------------------------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------ |
| **R1** | 骨架提取是冷启动——没有行业知识注入，每个租户的骨架质量取决于LLM的通用能力 | 医疗行业和制造业的骨架质量差异巨大                   | 骨架提取Prompt必须注入知识图谱的领域模式                     |
| **R2** | 60个事件×4轮对话=240轮交互，用户疲劳度爆炸                   | 用户第10个事件就不想回答了                           | 需要事件分级：简单事件自动填充，只有复杂事件才多轮对话       |
| **R3** | 事件之间有依赖关系——"报工"依赖"工单创建"，"质检"依赖"报工"   | 按事件独立精炼会忽略上下游数据流依赖                 | 需要事件依赖图，精炼时注入上游事件的产出                     |
| **R4** | SA九步中不是所有步骤都能按事件拆分                           | Scope、数据字典、ER图是全局的，DFD、判定表是事件级的 | 需要明确：哪些步骤per-event、哪些global、哪些"先per-event再merge" |
| **R5** | 骨架中的表结构草案是LLM推测的，字段类型/约束可能不准确       | 如果骨架表结构有误，后续所有追问都建立在错误基础上   | 骨架表结构通过DictValidator预校验，不合格的标记为"待确认"    |
| **R6** | Stage 3驳回后回退到Stage 2的具体事件，但驳回可能涉及多个事件的关联修改 | 用户改了事件A的表结构，事件B的DFD也需要同步更新      | 需要"影响范围分析"——变更传播机制                             |

## 二、六个关键细节完善

### 完善一：骨架提取必须注入知识图谱

**问题**：D爷的骨架提取Prompt是纯通用的，没有利用平台积累的领域知识。

**完善方案**：骨架提取时，从BASE_KNOWLEDGE_NODE检索当前行业的领域模式，注入到Prompt中作为"参考骨架"。

```typescript

    .getContext(tenantId);
  
  // ★ 注入术语表（确保骨架使用正确的业务术语）

    .getTerms(tenantId);

  const systemPrompt = `
你是一个企业管理系统业务架构师。

【行业背景】
${tenantIndustry ?? '未设置'}

【该行业常见领域模式（仅供参考，不要照搬，必须基于用户实际需求）】
${domainPatterns.map(p => `- ${p.name}: ${p.description}`).join('\n')}

你的任务是从用户提供的原始需求材料中，提取精准的"业务与数据骨架"。

  validateSkeleton(skeleton); // 门禁校验
  return skeleton;
}
```

**关键区别**：知识图谱的注入方式是"参考但不照搬"。Prompt明确说"仅供参考，必须基于用户实际需求"，防止LLM套模板。

### 完善二：事件分级——不可能60个事件全部多轮对话

**问题**：60个事件×4轮=240轮，用户会崩溃。

**完善方案**：骨架提取后，对事件进行复杂度分级，不同级别不同策略。

```typescript
// event_complexity_classifier.ts

interface EventClassification {
  event: BusinessEvent;
  complexity: 'auto' | 'simple' | 'complex';
  reason: string;
  estimatedRounds: number;
}

function classifyEventComplexity(
  event: BusinessEvent,
  skeleton: Skeleton
): EventClassification {
  let score = 0;
  const reasons: string[] = [];

  // 1. 涉及角色数量
  if (event.involved_roles.length > 3) {
    score += 2;
    reasons.push('涉及角色多(>3)');
  }

  // 2. 是否涉及状态扭转
  const relatedFlow = skeleton.core_business_flows.find(f =>
    f.steps.some(s => s.by === event.primary_actor));
  if (relatedFlow?.steps.length > 5) {
    score += 2;
    reasons.push('流程步骤多(>5)');
  }

  // 3. 是否有异常分支
  if (relatedFlow?.exception_branches?.length > 2) {
    score += 2;
    reasons.push('异常分支多(>2)');
  }

  // 4. 是否涉及多张表关联
  if (event.related_entities.length > 3) {
    score += 1;
    reasons.push('涉及实体多(>3)');
  }

  // 5. 是否涉及金额/数量/状态机
  const relatedTables = skeleton.database_schema_draft.tables.filter(t =>
    event.related_entities.includes(t.table_name));
  const hasAmountField = relatedTables.some(t =>
    t.fields.some(f => /amount|qty|price|cost/i.test(f.name)));
  if (hasAmountField) {
    score += 1;
    reasons.push('涉及金额/数量字段');
  }

  // 6. 是否有并发风险
  const hasConcurrentRisk = relatedTables.some(t =>
    t.fields.some(f => /status|inventory|stock/i.test(f.name)));
  if (hasConcurrentRisk) {
    score += 1;
    reasons.push('有并发风险（状态/库存）');
  }

  // 分级
  if (score <= 1) return { event, complexity: 'auto', reason: reasons.join('; ') || '简单CRUD', estimatedRounds: 0 };
  if (score <= 4) return { event, complexity: 'simple', reason: reasons.join('; '), estimatedRounds: 2 };
  return { event, complexity: 'complex', reason: reasons.join('; '), estimatedRounds: 4 };
}
```

**三级策略**：

| 复杂度      | 事件占比(预估) | 策略                                      | 用户交互         |
| ----------- | -------------- | ----------------------------------------- | ---------------- |
| **auto**    | ~30%           | LLM自动填充《事件需求规格》，用户只需确认 | 0轮对话，1次确认 |
| **simple**  | ~40%           | LLM提2个关键问题，用户回答后自动完成      | 2轮对话          |
| **complex** | ~30%           | 完整4轮对话（流程→FK→字段→确认）          | 4轮对话          |

**60个事件的实际对话量**：auto 0轮×18 + simple 2轮×24 + complex 4轮×18 = **120轮**，比240轮减半。而且auto的18个事件可以批量确认，用户实际操作只有**约60次交互**。

### 完善三：事件依赖图——精炼时注入上游产出

**问题**："报工"事件精炼时，应该知道"工单创建"事件已经确认了哪些字段和规则。

**完善方案**：骨架提取后，构建事件依赖图；精炼每个事件时，注入其上游事件的已确认产出。

```typescript
// event_dependency_builder.ts

interface EventDependency {
  eventId: string;
  dependsOn: string[];       // 上游事件ID列表
  sharedEntities: string[];  // 共享的实体表
  dataFlowDirection: string; // 数据流向描述
}

function buildEventDependencies(
  events: BusinessEvent[],
  skeleton: Skeleton
): EventDependency[] {
  const deps: EventDependency[] = [];

  for (const event of events) {
    const relatedEntities = new Set(event.related_entities);
    const dependsOn: string[] = [];
    const sharedEntities: string[] = [];

    // 找到与当前事件共享实体的其他事件
    for (const other of events) {
      if (other.event_id === event.event_id) continue;
      const shared = other.related_entities.filter(e => relatedEntities.has(e));
      if (shared.length > 0) {
        // 判断依赖方向：如果当前事件读取其他事件写入的数据
        // 简单启发式：如果当前事件的角色不同于上游，且共享实体有状态字段
        const isDownstream = isLikelyDownstream(event, other, skeleton);
        if (isDownstream) {
          dependsOn.push(other.event_id);
          sharedEntities.push(...shared);
        }
      }
    }

    deps.push({
      eventId: event.event_id,
      dependsOn,
      sharedEntities: [...new Set(sharedEntities)],
      dataFlowDirection: dependsOn.length > 0
        ? `依赖上游事件产出的 ${sharedEntities.join(', ')}`
        : '无上游依赖'
    });
  }

  // 拓扑排序，确定精炼顺序
  topologicalSort(deps);
  return deps;
}
```

**精炼顺序示例**：

```
工单创建 → 物料领用 → 工序报工 → 质量检验 → 成品入库
                      ↑
                      └── 设备故障（可并行，不依赖报工）
```

精炼"工序报工"时，System Prompt自动注入：

```
【上游已确认事件】
1. 工单创建（EVT001）：
   - 工单表确认字段：work_order_id, part_id, quantity, status, due_date
   - 状态流转：已创建 → 已下发 → 生产中 → 已完工
   - 业务规则：工单数量必须大于0，到期日不能早于创建日

2. 物料领用（EVT002）：
   - 领料单确认字段：material_requisition_id, work_order_id(FK), material_id, qty
   - 业务规则：领料数量不能超过工单BOM用量的110%

现在基于以上上游产出，针对"工序报工"事件进行深度确认...
```

### 完善四：SA九步的per-event vs global分层

**问题**：SA九步不是都能按事件拆分。需要明确每步的执行策略。

**完善方案**：

| SA步骤                 | 执行策略                           | 原因                                         |
| ---------------------- | ---------------------------------- | -------------------------------------------- |
| **Step 0: Scope**      | **Global**（跑一次）               | 系统边界是全局的，不能按事件切               |
| **Step 1: DFD**        | **Per-event → Merge**              | 每个事件有独立的数据流，最终合并为全局DFD    |
| **Step 2: 业务流程图** | **Per-event → Merge**              | 每个事件有独立流程，合并时处理跨事件连接     |
| **Step 3: 数据字典**   | **Global**（基于合并后的DFD）      | 数据字典必须全局唯一，不能有同名不同义的字段 |
| **Step 4: PSPEC**      | **Per-event**                      | 每个事件的加工逻辑独立                       |
| **Step 5: 判定表**     | **Per-event**                      | 每个事件的业务规则独立                       |
| **Step 6: ER图**       | **Global**（基于数据字典）         | ER图是全局的实体关系，不能按事件切           |
| **Step 7: 状态机**     | **Per-entity**（按实体，非按事件） | 一个实体（如工单）的状态机跨多个事件         |
| **Step 8: UI原型**     | **Per-event**                      | 每个事件对应一组UI界面                       |

```typescript

  eventSpecs: EventSpecification[],
  deps: EventDependency[]
): Promise<SAOutput> {

    // ===== Global Steps =====

    // Step 0: Scope (global, 一次)
    const scope = guardScope(await callLLM(SCOPE_PROMPT, {
      requirement: req.requirementText,
      events: eventSpecs.map(e => e.summary),
      skeleton: req.skeleton
    }));
    const scopeId = await saveScope(scope, trx);

    // ===== Per-Event Steps (按拓扑序) =====

    // Step 1: DFD (per-event → merge)
    const perEventDFDs: Map<string, DFD> = new Map();
    for (const spec of eventSpecs) {
      const upstreamSpecs = getUpstreamSpecs(spec, deps, eventSpecs);
      const dfd = guardDFD(await callLLM(DFD_PROMPT, {
        eventSpec: spec,
        upstreamDFDs: upstreamSpecs.map(u => perEventDFDs.get(u.eventId)),
        scope
      }));
      perEventDFDs.set(spec.eventId, dfd);
    }
    const mergedDFD = mergeDFDs([...perEventDFDs.values()]);
    const dfdId = await saveDFD(mergedDFD, scopeId, trx);

    // Step 2: 业务流程图 (per-event → merge)
    // ...类似逻辑

    // ===== Global Steps (基于merged结果) =====

    // Step 3: 数据字典 (global, 基于merged DFD)
    const dataDict = guardDataDict(await callLLM(DATA_DICT_PROMPT, {
      mergedDFD,
      skeleton: req.skeleton,  // ★ 骨架中的表结构草案作为参考
      eventSpecs
    }));
    const dictId = await saveDataDict(dataDict, trx);

    // Step 4: PSPEC (per-event)
    for (const spec of eventSpecs) {
      const pspec = guardPSPEC(await callLLM(PSPEC_PROMPT, {
        eventSpec: spec,

      }));
      await savePSPEC(pspec, spec.eventId, trx);
    }

    // Step 5: 判定表 (per-event)
    // ...类似

    // ===== Global Steps =====

    // Step 6: ER图 (global, 基于数据字典)
    const er = guardER(await callLLM(ER_PROMPT, {
      dataDict,
      skeletonTables: req.skeleton.database_schema_draft.tables  // ★ 骨架表作为参考
    }));
    await saveER(er, trx);

    // Step 7: 状态机 (per-entity, 不是per-event)
    const entitiesWithState = dataDict.dataStores.filter(s =>

      const relatedEvents = eventSpecs.filter(s =>
        s.relatedEntities.includes(entity.name));
      const std = guardSTD(await callLLM(STD_PROMPT, {
        entity,
        relatedEvents,

    }

    await recordAnalysisRun(req, version, trx);
```

### 完善五：骨架表结构预校验——防止错误骨架污染后续

**问题**：D爷的validateSkeleton只检查"有没有"，不检查"对不对"。LLM生成的字段类型可能不合理（如VARCHAR(1)存姓名）。

**完善方案**：骨架表结构通过简化版DictValidator预校验，不通过的标记为"待确认"。

```typescript
// skeleton_table_validator.ts

interface SkeletonValidationResult {
  tableName: string;
  isValid: boolean;
  warnings: SkeletonFieldWarning[];   // 不阻塞，但需要用户确认
  errors: SkeletonFieldError[];        // 阻塞，必须修正
}

interface SkeletonFieldWarning {
  fieldName: string;
  issue: string;
  suggestion: string;
}

function validateSkeletonTables(
  tables: SkeletonTable[]
): SkeletonValidationResult[] {
  return tables.map(table => {
    const warnings: SkeletonFieldWarning[] = [];
    const errors: SkeletonFieldError[] = [];

    // 1. 主键检查
    const hasPK = table.fields.some(f => f.constraints?.includes('PRIMARY KEY'));
    if (!hasPK) errors.push({ issue: '缺少主键' });

    // 2. 字段类型合理性
    for (const field of table.fields) {
      // NVARCHAR 必须有长度
      if (/^NVARCHAR$/i.test(field.type) && !field.type.includes('(')) {
        warnings.push({
          fieldName: field.name,
          issue: 'NVARCHAR缺少长度定义',
          suggestion: `建议 NVARCHAR(50) 或 NVARCHAR(200)`
        });
      }

      // 外键引用的表是否存在
      const fkMatch = field.constraints?.match(/FOREIGN KEY\s*→\s*(\w+)\.(\w+)/i);
      if (fkMatch) {
        const refTable = fkMatch[1];
        if (!tables.some(t => t.table_name === refTable)) {
          errors.push({
            fieldName: field.name,
            issue: `外键引用的表 ${refTable} 不存在于骨架中`,
            suggestion: '请补充引用表或修正外键关系'
          });
        }
      }

      // 状态字段建议用枚举
      if (/status/i.test(field.name) && /^NVARCHAR/i.test(field.type)) {
        warnings.push({
          fieldName: field.name,
          issue: '状态字段建议定义枚举值',
          suggestion: '建议在事件精炼阶段确认状态枚举（如：draft/submitted/approved/rejected）'
        });
      }

      // 金额/数量字段建议精度
      if (/(amount|qty|quantity|price|cost)/i.test(field.name)) {
        if (/INT/i.test(field.type)) {
          warnings.push({
            fieldName: field.name,
            issue: '金额/数量字段用INT会丢失精度',
            suggestion: '建议 DECIMAL(18,2)'
          });
        }
      }
    }

    // 3. 命名规范
    if (/[a-z][A-Z]/.test(table.table_name)) {
      warnings.push({
        fieldName: table.table_name,
        issue: '表名使用了驼峰命名',
        suggestion: 'JNPF规范使用大写+下划线（如 work_order → WORK_ORDER）'
      });
    }

    return {
      tableName: table.table_name,
      isValid: errors.length === 0,
      warnings,
      errors
    };
  });
}
```

**输出给用户**：

```
骨架表结构预校验结果：

✅ work_order（4个字段，主键完整）
⚠️ operation_report
   - NVARCHAR 缺少长度定义 → 建议 NVARCHAR(50) 或 NVARCHAR(200)
   - status 字段建议定义枚举值
   - defective_qty 用 INT 会丢失精度 → 建议 DECIMAL(18,2)
❌ quality_inspection
   - 外键引用的表 defect_type 不存在于骨架中
```

### 完善六：变更传播机制——驳回时的影响范围分析

**问题**：用户在Stage 3驳回《需求分析说明书》中"工序报工"的判定表，但"质量检验"事件的DFD依赖报工的输出数据流。

**完善方案**：记录事件间的数据依赖关系，驳回时自动分析影响范围。

```typescript
// change_impact_analyzer.ts

interface ChangeImpact {
  rejectedEventId: string;
  rejectedStep: string;              // 被驳回的SA步骤
  directlyAffected: AffectedItem[];  // 直接影响
  indirectlyAffected: AffectedItem[]; // 间接影响
  recommendedAction: 're-refine-event' | 're-run-step' | 'manual-review';
}

interface AffectedItem {
  eventId: string;
  step: string;
  reason: string;
}

function analyzeChangeImpact(
  rejectedEventId: string,
  rejectedStep: string,
  eventDependencies: EventDependency[],
  analysisRun: AnalysisRun
): ChangeImpact {
  const directlyAffected: AffectedItem[] = [];
  const indirectlyAffected: AffectedItem[] = [];

  // 找到依赖被驳回事件的所有下游事件
  const downstreamEvents = eventDependencies.filter(d =>
    d.dependsOn.includes(rejectedEventId));

  for (const dep of downstreamEvents) {
    // 直接影响：共享实体的同一步骤
    directlyAffected.push({
      eventId: dep.eventId,
      step: rejectedStep,
      reason: `共享实体 ${dep.sharedEntities.join(', ')}，${rejectedStep}产出可能变化`
    });

    // 间接影响：下游事件的后续步骤
    const affectedSteps = getDownstreamSteps(rejectedStep);
    for (const step of affectedSteps) {
      indirectlyAffected.push({
        eventId: dep.eventId,
        step,
        reason: `上游${rejectedStep}变更可能影响${step}`
      });
    }
  }

  // 推荐操作
  const recommendedAction = directlyAffected.length > 2
    ? 're-refine-event'  // 影响面大，建议重新精炼
    : directlyAffected.length > 0
      ? 're-run-step'     // 影响面可控，只重跑受影响步骤
      : 'manual-review';   // 无直接影响，人工确认即可

  return {
    rejectedEventId,
    rejectedStep,
    directlyAffected,
    indirectlyAffected,
    recommendedAction
  };
}
```

## 七、与D爷原方案的差异对照

| 维度       | D爷原方案              | 完善后                                                       |
| ---------- | ---------------------- | ------------------------------------------------------------ |
| 骨架提取   | 纯通用Prompt           | **注入知识图谱+行业知识+术语表**                             |
| 事件精炼   | 全部4轮对话            | **三级分级：auto(0轮)/simple(2轮)/complex(4轮)**             |
| 事件依赖   | 未考虑                 | **依赖图+拓扑排序+上游产出注入**                             |
| SA九步拆分 | 笼统"按事件拆分再汇总" | **明确每步策略：global/per-event/per-entity/先per-event再merge** |
| 骨架校验   | 仅检查"有没有"         | **增加表结构预校验：类型合理性+FK引用+命名规范+精度**        |
| 驳回机制   | 简单回退               | **影响范围分析+变更传播+推荐操作**                           |
| 数据库     | 提到sa_event_spec      | **3张新表完整DDL：sa_skeleton/sa_event_spec/sa_change_impact** |
| 前端       | 未涉及                 | **2个核心新组件：SkeletonViewer/EventRefinementPanel**       |
| Sprint     | 5个里程碑              | **6个Sprint，13.5周**                                        |

D爷的方案方向完全正确，这些完善是把它从"高阶设计"推进到"可直接开工的施工图纸"。骨架驱动的核心理念没有变，只是让骨架更精准、精炼更高效、九步更严谨、驳回更智能。
