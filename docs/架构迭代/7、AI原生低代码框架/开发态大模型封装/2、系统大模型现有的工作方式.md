# 基于参考内容，回答"裸 LLM 能否落地复杂系统生成"及平台目标如何实现

---

## 一、参考内容中的核心设计理念：LLM 不是裸跑的

参考内容对此有非常明确的架构回答。五阶段流水线的设计初衷就不是让裸 LLM 直接生成三份文档，而是通过**四重约束机制**让 LLM 在严格框架内工作：

**第一重：角色约束（Prompt 模板）**

需求分析师的 System Prompt 明确规定了工作方式：
> "1. 先理解用户的核心诉求（不要急于给方案）。2. 主动追问关键问题（至少 3 个问题）。3. 基于领域知识提供策略选项（不是唯一方案）。4. 分析每个选项的利弊和影响。5. 让用户做最终决策。"

架构师的 System Prompt 则硬编码了技术约束：
> "EAB（企业架构基准）约束：部署架构：模块化单体（非微服务）；数据库：SQL Server + SQLSugar ORM……输出格式必须从 EAB 白名单中选择。"

**第二重：上下文注入（AgentContext）**

`BaseAgent.resolveVariable()` 方法将知识图谱和 EAB 数据注入 prompt：
- `{{domains}}` ← 平台支持的业务领域列表
- `{{domainPatterns}}` ← 已有的领域模式（来自知识图谱）
- `{{technicalConstraints}}` ← 平台的技术约束
- `{{eab}}` ← 企业架构基准配置

**第三重：结构化输出（JSON Schema 约束）**

每个智能体的输出都被严格限定为 JSON 格式。需求分析师必须输出包含 `understanding`、`questions`、`proposedDomainModel`、`strategies`、`userStories` 等字段的结构化数据，架构师必须输出包含 `architecture`、`ir`、`techstack`、`decisions` 的结构化数据。

**第四重：人类确认（分阶段推进）**

> 第二篇 §3.1 明确："客户面对分阶段进度条，非单一聊天框；每阶段须客户确认方可推进。"

## 二、复杂行业系统如何落地：参考内容设计了两条核心路径

### 路径一：DKEE（领域知识进化引擎）——解决"LLM 不懂行业"的根本问题

参考内容 F-9.10 明确设计了这一机制：

> "1. 记录人类在配置中心做出的规则修改。2. 从修改中提炼领域模式。3. 将模式沉淀到知识图谱。4. 下次同类场景主动调用。"

`observeAndExtract()` 函数会分析人类操作（创建、修改、删除），当发现创建了新实体或新规则时，自动提炼为 `DomainPattern` 并存入知识图谱。

**这意味着**：做第一个眼镜店系统时，LLM 确实不懂验光处方流转，但人类专家在"业务规则配置中心"修正了 AI 生成的规则，这些修正会被 DKEE 自动提炼为"眼镜验配"领域的 DomainPattern。做第二个眼镜店系统时，知识图谱已有种子模式，LLM 的表现就会显著提升。

### 路径二：Foundry 自博弈引擎——自动化领域知识积累

第二篇 §4 描述了四大智能体的闭环：

| 智能体 | 职责                                              |
| ------ | ------------------------------------------------- |
| 攻击者 | "对抗需求 + 历史失败 RAG"，生成刁钻的业务场景     |
| 构建者 | "IR 补丁 + EAB 约束 + 自修复"，自动构建并部署系统 |
| 判官   | "生成式测试 + 因果图 + R"，执行业务语义验证       |
| 蒸馏师 | "candidate/verified + 遗忘"，从博弈结果中提炼知识 |

> "冷启动：5-10 条种子 DomainPattern + RAG 历史 IR 案例"
> "RAG 增强于自博弈：BASE_KNOWLEDGE_NODE 第一天就做'需求→历史 IR 案例' few-shot 检索注入"

**关键信息**：内容中确定的自博弈训练引擎选择"智能更衣柜"作为首个训练领域，理由是：
> "逻辑相对封闭、核心场景清晰（借用、异常、多人共享、支付）、适合验证自博弈引擎的可行性。"

训练计划分四轮递进难度，目标是"完成至少 10000 次自博弈循环，形成包含 100+ 领域模式的知识图谱，通过率从初始的 60% 提升到 95%+"。

## 四、关于"跨行业复杂系统（眼镜店、周黑鸭、电商）是否可行"

**参考内容中未直接讨论具体行业场景的可行性分析。** 但内容中提供了以下与可扩展性相关的设计机制：

1. **租户定制菜单**（C 阶段）：`BASE_TENANT_INDUSTRY` 表允许每个租户配置行业知识描述，`BASE_TENANT_GLOSSARY` 表允许配置业务术语表，这些会注入 AI 的 System Prompt。

2. **DomainPattern 的来源三类**：`ai-discovered`（AI 发现）、`human-created`（人类创建）、`self-play`（自博弈产生）。这说明领域知识的积累是多来源的，不是仅靠 LLM 推理。

3. **知识图谱的遗忘与版本管理**：内容中设计了"verified 半衰期 → deprecated"机制和版本快照，防止过时的领域模式干扰新需求。

## 五、内容中关于"平台目标如何落地"的直接回答

内容中五阶段流水线的阶段 5 明确了交付物：

> "测试 URL、ZIP 导出、增量回退阶段 1"

这意味着平台的落地目标不是"LLM 一次性生成完美系统"，而是：

1. LLM 在严格约束下生成 IR
2. IR 经编译器编译为可运行代码
3. 部署到沙箱供用户测试
4. 用户在业务规则配置中心精修
5. 精修结果被 DKEE 提炼为领域模式
6. 领域模式注入下一轮 AI 流水线

顶级专家审核意见也确认了这一路径的优先级：

> "'生成→验证→自修复'环路是最大杠杆：一条 83 测试覆盖的纯函数确定性管线（cleanSchema → validateIR → compile），让 LLM 生成 IR 后由 validator.ts + vue-tsc 程序化打错误、自动重试 N 轮，质量收益远超任何自博弈。"

---

## 总结

参考内容中的设计**从未假设裸 LLM 能独立生成完整的企业级系统**。平台落地的核心路径是：Prompt 模板约束 + 知识图谱注入 + IR 编译验证 + 人类确认精修 + DKEE 领域知识沉淀的**渐进式闭环**。SKILL 和 MCP 在内容中被设计为管理入口已定义但实现细节未展开的增强层，而真正决定平台能否覆盖复杂行业的，是 `DomainPattern` 的积累深度和质量——这需要通过真实项目的交付来逐步构建，而非一步到位。
