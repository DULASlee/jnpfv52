# 完整的SA步骤

你说得对,而且这一问直接把我之前那套七步法又**升了一档**。

但我得先**校准一件事**:业务流程图和 PSPEC 不是替代关系,是**配对关系**。

- **业务流程图**:**角色视角**,看"谁、什么时候、做什么"——给业务方看的"剧本"
- **PSPEC**:**逻辑视角**,看"每个活动内部怎么判定"——给开发看的"代码骨架"

我之前说"用业务流程图代替 PSPEC"是错的——它们是同一份数据字典的两种投影,一个对外,一个对内。

---

### 业务流程图加在哪

加在 **Step 2 和 Step 3 之间**,作为 DFD 的**物理/角色视图**——对应 Gane & Sarson 经典 SA 里"逻辑 DFD ↔ 物理 DFD"的二分。

```
Step 0   可行性研究 & 范围定义
Step 1   Context 图(顶层 DFD)
Step 2   DFD 分层(逻辑视图)            ← 看"系统做什么"
         ↓
Step 2.5 业务流程图(物理/角色视图)      ★ 新增 ← 看"谁/什么时候/怎么做"
         ↓
Step 3   数据字典
Step 4   PSPEC(原子过程伪代码)          ← 流程图节点的内部逻辑
Step 5   判定表
Step 6   ER 图 + 3NF
Step 7   STD
Step 8   UI 原型
```

**Step 2.5 是 Step 4 的"前置剧本"**——流程图画每个活动,PSPEC 写每个活动内部的判定逻辑。

---

### 祖父级 SA 下的业务流程图画法规范

不是 BPMN 那套花哨的 event/gateway,而是**经典泳道图(Swim Lane)**:

1. **泳道划分**:每个角色一条横向泳道(工人 / 班组长 / 质检员 / 计划员),系统单独一条
2. **活动用矩形**:动词开头("扫工序码"、"提交报工"、"终核")
3. **决策用菱形**:YES/NO 两条出路
4. **箭头方向**:实线主流程,虚线异常/驳回
5. **步骤编号**:1、2、3... 业务方一眼能跟读

**三个铁律**:

- 流程图里**只能出现数据字典里定义过的数据载体**(工单、报工单、校验结果...)
- 流程图里**每个活动节点必须在 DFD 里有对应过程**
- 流程图里**每个状态变化必须能在 STD 里找到**

### 业务流程图 / DFD / PSPEC:三件套分工

| 维度         | DFD              | 业务流程图       | PSPEC             |
| ------------ | ---------------- | ---------------- | ----------------- |
| **视角**     | 系统逻辑         | 角色 + 时序      | 活动内部          |
| **回答**     | 系统做什么       | 谁/什么时候做    | 怎么做            |
| **粒度**     | 过程 + 数据流    | 活动 + 步骤      | 原子过程的伪代码  |
| **谁来看**   | 架构师           | 业务方 + 开发    | 开发              |
| **节点对应** | P1 / P2.1 / P4.3 | "扫工序"、"终核" | P2.1 内部 if-else |
| **数据载体** | 数据字典         | 数据字典         | 数据字典          |

**三件套指向同一份数据字典,这就是 SA "一源到底"的核心**。

### 抓一个"业务流程图自相矛盾"的经典 bug

**Bug:驳回流丢了班组长复核**

画流程图时,业务方随手画"质检驳回 → 工人重新报工"——但**实际业务里质检驳回后班组长要先复核,工人才能改**。少了一个节点,直接绕过管控。

**第六重校验(业务流程图 ↔ DFD)拦截**:

> 业务流程图节点 "7.驳回" 直接连到工人,但 P2.2 判定表第 4 / 6 / 7 行存在"挂起待查"分支,需要班组长二次审核节点。**业务流程图缺失"班组长复核"节点,要求补充**。

**没这张流程图,这个 bug 极难发现——只有出质量事故后翻审批记录才会察觉**。

# 步骤太多复杂系统会不会爆掉

不好意思,上一轮我太抽象了——堆了一堆表格和术语,但没真给你跑一遍,**你听了当然糊涂**。

我用最具体的方式重新讲一遍:**挑 3 个真实业务事件,一个一个过那 6 问**,你看完就懂"分层"是什么意思了。

---

## 先用一个比喻打底

把 MES 系统想象成**一栋 60 个房间的办公大楼**:

- **Project 级 = 大楼的地基 + 主体结构 + 公共管网**(水管、电线、消防)——**盖一次,所有房间都用**
- **Event 级 = 每个房间的精装修**——每房间搞一次,但**不动大楼结构**
- **Process 级 = 复杂房间的定制设计**(比如总裁办公室)——只在需要时搞

**关键:你不会每装一个房间就重新打地基、重新铺总管。** 但很多人做 SA 就是这么干的——每来一个事件就重画数据字典、重画 ER,这就是 AI "空转"的根。

---

## Project 级资产长什么样(盖一次,60 个事件都用)

**1. 数据字典骨架**(80 个公共字段)

工单编号、操作员ID、时间戳、租户ID、状态... 60 个事件**全都用到这些字段**,盖一次就够。

**2. DFD 主图**(60 个事件共用一张)

所有事件都先经过 P0 公共框架(用户认证、权限、租户隔离),然后接自己的业务过程。

**3. ER 主图**(6 张核心表)

`WorkOrder` / `ProductionReport` / `Material` / `User` / `Tenant` / `Process`——6 张表,所有事件都基于它们关联。

**4. STD 骨架**(3-5 个核心状态机)

工单状态机、报工状态机、物料消耗状态机、批次状态机。

**这 4 样建好,2 周投入。** 后面 60 个事件的工作量立刻减半。

## 拿 3 个真实事件跑一遍 6 问

### 事件 A:工单进度查询(简单事件)

**业务**:计划员打开"工单进度看板",看所有工单的当前进度。

```
□ Q1. 涉及哪些数据流?
    答: [查询请求] → [进度数据]
    现有 DFD 里 P3 进度查询已经覆盖 → DFD 不动 ✅

□ Q2. 流程图上哪个泳道、哪个节点?
    答: 计划员泳道新增"打开进度看板" 1 个节点 → 流程图加 1 节点 ✅

□ Q3. PSPEC 怎么写?
    答: 走标准查询模板:
        SELECT 工单号, 状态, 已报工数量, 计划数量
        FROM WorkOrder LEFT JOIN ProductionReport
        WHERE 租户 = 当前用户.租户
    模板化,5 分钟 ✅

□ Q4. 有复杂业务规则吗?
    答: 没有 → 跳过判定表 ✅

□ Q5. 涉及哪些 UI 屏?字段都在字典里吗?
    答: 一张看板屏,字段全是字典里有的 → UI 直接生成 ✅

□ Q6. 会改变任何实体的状态吗?
    答: 不会,纯查询 → 跳过 STD ✅
```

**总耗时:5-10 分钟**。AI 全自动,人工扫一眼 SQL 就行。

---

### 事件 B:工序报工录入(中等事件)

**业务**:工人在 PAD 端扫工单条码 + 工序条码 + 填合格/报废数量,提交报工。

```
□ Q1. 涉及哪些数据流?
    答: [待校验报工单] → P1
    现有 DFD 里 P1 已经覆盖 → DFD 不动 ✅

□ Q2. 流程图上哪个泳道、哪个节点?
    答: 工人泳道的"扫工序码"+"提交报工" 2 个节点
    现有流程图里 P1 段已经有了 → 检查,没漏就跳过 ✅

□ Q3. PSPEC 怎么写?
    答: 半模板:
        IF 工单编号 NOT IN D1 → 报工=false,提示"无效"
        IF 数量 < 0 → 报工=false,提示"数量无效"
        IF 报废数量 > 0 AND 报废原因为空 → 报工=false
        报工 = true
    半模板,30 分钟 ✅

□ Q4. 有复杂业务规则吗?
    答: 没有(只基本字段校验)→ 跳过判定表 ✅

□ Q5. 涉及哪些 UI 屏?字段都在字典里吗?
    答: PAD 录入屏 1 张
    字段:工单号、工序号、合格数量、报废数量、报废原因、操作员、时间戳
    全部字典里有的 → UI 直接生成 ✅

□ Q6. 会改变任何实体的状态吗?
    答: 会!报工状态从"无"变成"待校验"
    → 更新报工 STD(增加"待校验"状态)
    现有 STD 里已经有了,只需确认 → 5 分钟 ✅
```

**总耗时:30-60 分钟**。AI 写 PSPEC + UI 草案,人工 review。

---

### 事件 C:物料倒冲 + 反冲(复杂事件)

**业务**:工人完工报工后,系统自动倒冲扣库存;后续质检驳回时,自动反冲还库存。

```
□ Q1. 涉及哪些数据流?
    答: [完成事件] → P4.3 倒冲
         [驳回事件] → P4.3.5 反冲
    现有 DFD 里 P4.3 已经覆盖
    但要新增:[批次已消耗转待重工] 这条新数据流 → DFD 增量 1 个流

□ Q2. 流程图上哪个泳道、哪个节点?
    答: 系统泳道的"11.触发倒冲" + "12.扣库存" + "15.反冲" 3 个节点
    现有流程图里 P4.3 段已经有了 → 检查,补 1-2 个节点

□ Q3. PSPEC 怎么写?
    答: 不能走模板,完整手写(就是我们之前讨论的 P4.3.1 / P4.3.5)
    2-3 小时完整 PSPEC

□ Q4. 有复杂业务规则吗?
    答: 有!批次选择、库存扣减、反冲处理都要判定表
    → 跑 3 张判定表(批次选择 / 库存扣减 / 反冲处理)

□ Q5. 涉及哪些 UI 屏?字段都在字典里吗?
    答: 主要是后台过程,UI 屏很少
    1 张倒冲监控屏 + 1 张反冲查询屏
    字段基本是 D7 字段,字典里都有 → 1 小时

□ Q6. 会改变任何实体的状态吗?
    答: 会,而且是多个实体:
        - 物料消耗状态机:新增"已倒冲"、"已反冲"
        - 库存:数量增减
        - 报工:质检驳回时回到"待终核"
    → 更新 3 个 STD(物料消耗 STD 要扩充,这是大改动)
```

**总耗时:2-3 天**(主要是 PSPEC + 3 张判定表 + 3 个 STD 更新)。

## 核心洞察

**"8 步 SA 全跑"是给教科书看的,"6 问事件清单"是给工程看的。**

8 步是完整理论框架(对单个复杂系统),但工业项目 60 个事件要落地,必须:

1. **Project 级 4 大件先做扎实**(地基)——2 周
2. **每个事件过 6 问**(装修)——简单 5 分钟、中等 1 小时、复杂 2-3 天
3. **复杂事件才回头补 Process 级**(定制)——按需
4. **AI 在每一步做"模板/增量",不做"重画"**(避免空转)

**60 个事件里,简单+中等占 70-80%(每个 5-60 分钟),真正"重"的复杂事件只有 10-20%(每个 2-3 天)。**
