# JNPF AI数据中台与现有V5.2重构计划融合核查报告

经过对《JNPF V5.2全栈底层架构迭代开发计划（v5.0）》（包含第一篇F-0~F-10、第二篇Studio/Foundry）的深度核查，针对“第一期AI-Oriented数据中台（轻量数据湖）”方案，得出以下结论：

## 核心结论

**1. 是否能融合？**
**答：高度融合，且互为战略支撑。** 数据中台方案在技术栈（SQL Server + .NET 8 + SqlSugar）、多租户架构（TenantId全链路）、AI基础设施（LlmGateway + BASE_KNOWLEDGE_*）上与现有V5.2计划**100%同构**。它不仅不会破坏现有架构，反而是现有“五阶段AI流水线”和“岗位专家Agent”从“造软件”走向“懂业务”的**必经数据底座**。

**2. 现有计划哪些地方需要修改？**
**答：现有V5.2计划（49周+16周）中完全缺失“数据分析与语义层”的施工包。** 需要将数据中台作为**新增工作线H**插入，并对现有的IR体系、大屏数据源、知识图谱和MCP工具链进行**5处关键的接口级增补**。

## 二、 现有计划需要修改/增补的 5 个关键点

尽管底层基因一致，但现有的V5.2计划是面向“软件生成”的，缺乏“数据分析”的闭环。必须进行以下修改：

### 修改点 1：IR 体系必须新增 `ReportIR`（或扩展 `DashboardIR`）

- **现状**：现有的 `DashboardIR` 侧重于“绝对定位的大屏可视化”，数据源配置（`DashboardDataSource`）只支持 API/WebSocket/Static，**不支持直接绑定“语义层指标（MQL）”**。
- **修改方案**：在 `src/core/ir/dashboard-types.ts` 中扩展数据源类型，新增 `type: 'semantic-metric'`，允许大屏组件直接绑定指标字典中的 `metric_code`。
- **影响范围**：阶段一（F-6a 大屏IR定义）、阶段四（CompileGateway）。

### 修改点 2：知识图谱（BASE_KNOWLEDGE_*）需扩展“数据域”节点类型

- **现状**：Sprint 0-B 规划的 `BASE_KNOWLEDGE_NODE` 主要面向“领域模式（DomainPattern）”和“代码/架构知识”。
- **修改方案**：在知识图谱的节点类型枚举中，新增 `metric`（指标）、`dimension`（维度）、`data_entity`（数据表）。让五阶段流水线中的“需求分析师Agent”在分析需求时，能RAG检索到企业已有的指标口径。
- **影响范围**：Sprint 0-B（地桩3）、阶段五（AI流水线Prompt注入）。

### 修改点 3：阶段五 AI 流水线需新增“数据分析师 Agent”角色

- **现状**：阶段五（F-9）规划了需求分析师、架构师、UI/UX、数据库设计师。但**没有专门针对数据报表和指标分析的Agent**。
- **修改方案**：在 `Stage3OrchestratorService`（总体设计阶段）中，新增 `DataAnalystAgent`。当用户需求包含“报表、统计、趋势、看板”时，该Agent负责调用 `data-mcp` 验证指标是否存在，并生成 `DashboardIR` 的数据源配置。
- **影响范围**：阶段五（F-9.3 智能体编排）。

### 修改点 4：MCP 工具链需将 `data-mcp` 纳入标准注册表

- **现状**：现有计划提到了AI调用外部工具，但没有明确的 MCP (Model Context Protocol) Server 注册机制。
- **修改方案**：在后端模块化目录（`modularity/`）中新增 `JNPF.Modularity.Mcp` 模块，将 `data-mcp`（查指标）、`workflow-mcp`（发流程）作为首批标准 MCP Server 注册，供未来的“岗位专家Agent”调用。
- **影响范围**：后端架构、阶段六（Studio API）。

### 修改点 5：全局时间线需插入“数据中台 Sprint”

- **现状**：49周计划排满了编译器、后端清零和AI流水线。
- **修改方案**：数据中台（4周）不应阻塞前端编译器（阶段一~四）的开发。建议将其作为**并行的“工作线 H”**，安排在 **Sprint 0-B 之后、阶段五（AI流水线）启动之前**完成。因为阶段五的Agent需要依赖数据中台的 `data-mcp` 才能进行数据相关的 Evals 测试。

## 三、 架构决策记录 (ADR)

为了将上述修改固化到架构文档中，建议新增以下 ADR：

### ADR-019: 引入 AI-Oriented 语义层作为企业数据唯一查询通道

- **状态**: 提议 (Proposed)

- **上下文**: JNPF 平台缺乏统一的数据分析层。AI 大模型直接生成 SQL 查询生产库（NL2SQL）存在极高的安全风险（SQL注入、拖库）和口径不一致问题（幻觉）。客户（如MES企业）对“良品率、OEE”等指标有严格的业务定义。

- 决策

  :

  1. **废止** AI 直接生成 SQL 直连生产库的路线。
  2. **采纳** `NL -> Semantic (MQL) -> SQL` 架构。所有 AI 数据查询必须经过“语义层（指标字典）”翻译，并经过“安全网关（L3）”注入 TenantId 和行列权限。
  3. 分析库（`MES_ANALYTICS`）必须与生产库物理/逻辑隔离，采用 SQL Server 同实例独立 DB，通过 CDC/增量同步数据。

- 后果

  :

  - **正面**: 彻底解决 AI 数据查询的安全问题和口径冲突；沉淀的指标字典成为极高的竞争壁垒（护城河）。
  - **负面**: 增加了 4 周的数据中台开发工期；需要业务专家参与配置指标字典。

### ADR-020: 报表/大屏数据源 IR 扩展支持语义层指标绑定

- **状态**: 提议 (Proposed)
- **上下文**: 现有的 `DashboardIR` 数据源仅支持 REST API 和 WebSocket。AI 生成的报表无法直接映射到语义层的指标字典。
- **决策**: 在 `DashboardDataSource` 接口中新增 `type: 'semantic-metric'`。当 type 为 semantic-metric 时，`params` 字段接收 MQL (Metrics Query Language) JSON 结构，运行时由后端的 `MetricsQueryEngine` 翻译为安全 SQL 执行。
- **后果**: 前端大屏编译器（F-6a）需增加对 semantic-metric 数据源的 Hook 生成逻辑；后端需提供 `/api/data/query-metric` 统一接口。

## 五、 最终执行建议（给 D 爷的汇报）

1. **战略定位**：数据中台**不是**现有V5.2计划的“累赘”，而是让 V5.2 的 AI 流水线从“只能画空壳页面”进化为“能填充真实业务数据”的**核心引擎**。

2. **工期安排**：建议将数据中台（4周）作为**并行工作线**，在 **Sprint 0-B 完成后立即启动**，与阶段一~四（前端编译器）并行开发。这样在**阶段五（AI流水线）启动时**，`data-mcp` 和指标字典已经就绪，可以直接用于 AI Evals 的 golden set 测试。

3. 行动项

   ：

   - 批准 **ADR-019** 和 **ADR-020**。
   - 在现有的 `src/core/ir/dashboard-types.ts` 中预留 `semantic-metric` 接口。
   - 在 Sprint 0-B 的 `BASE_KNOWLEDGE_NODE` 表设计中，预留数据域（Metric/Dimension）的字段扩展。

**结论：方案完全可行，且能极大提升 JNPF 在工业/MES 领域的竞争壁垒。请求批准按修正后的并行时间线执行。**
