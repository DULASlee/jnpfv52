## 评审一：五阶段流水线状态机完整性

### 🔴 严重缺陷：状态机存在"死胡同"和未定义路径

**问题 1：stale 状态的处理不完整**

文档中 `stale` 只能从 `stage1` 和 `stage2` 进入（7天超时），但：
- `stage3` 只有 3 天超时 → stale，文档 §4.1.0 确认
- `stage4` 和 `stage5` **没有定义 stale 路径**
- `stale` 只能回到 `stage1`（重新响应），**无法从 stale 回到其他阶段**

```
状态图实际可达路径：
draft → running → stage1 → stage2 → stage3 → stage4 → stage5 → completed
   ↓       ↓        ↓        ↓        ↓        ↓        ↓
blocked   stale    stale    [无]     [无]     [无]    [可回滚到stage4]
   ↑       ↑
人工重置  仅回stage1
```

**问题 2：stage3→stage4 的"自动完成"与人工确认门禁矛盾**

§4.1.0 表格说 stage3→4 需要"业务专家确认"，但 §4.6 状态图说 `stage3 --> stage4: 自动完成（无需人工确认）`。

**这是致命矛盾。**

**问题 3：blocked 状态缺乏"放弃"路径**

当前 blocked 只能 `blocked --> running: 人工重置`，但如果用户不想继续了呢？没有 `abandoned` 终止状态。

**问题 4：stage5 的 completed 不可回退**

§4.6 显示 `stage5 --> completed: ZIP 导出`，但 completed 之后没有路径。如果用户发现 ZIP 有问题想修改，必须走增量修改回退到 stage4，但增量修改是从 stage5 触发的——这意味着 completed 后还能触发增量修改，但状态图上没有这条边。

### 🟡 中等缺陷：状态转换条件未精确定义

| 转换            | 当前描述                          | 缺失                                               |
| --------------- | --------------------------------- | -------------------------------------------------- |
| stage2→stage3   | "业务专家确认 + 开发者评审(可选)" | 开发者否决后如何修改？重审流程？                   |
| stage4→stage5   | "管理员/创始人审批"               | 审批通过的标准是什么？测试报告阈值？               |
| blocked→running | "人工重置"                        | 谁可以重置？创始人/管理员/业务专家？权限矩阵未映射 |

### ✅ 正确设计

```
修正后的状态机：

[*] --> draft
draft --> running: 启动
running --> stage1: 执行需求分析

stage1 --> stage2: 业务专家确认 + 追问闭环
stage1 --> blocked: llm_timeout×3 或 validation_failure×3
stage1 --> stale: 7天无响应

stage2 --> stage3: 业务专家确认 + (开发者评审通过或无需评审)
stage2 --> stage2: 开发者否决 → 修改后重审
stage2 --> blocked: validation_failure×3
stage2 --> stale: 7天无响应

stage3 --> stage4: 业务专家确认
stage3 --> blocked: compile_failure×3
stage3 --> stale: 3天无响应

stage4 --> stage5: 沙箱健康检查通过 + 管理员/创始人审批
stage4 --> blocked: sandbox_failure×3
stage4 --> stage4: 编译失败 → 修改IR重试

stage5 --> completed: ZIP导出成功
stage5 --> stage4: 管理员回滚
stage5 --> stageN: 增量修改(1/2/3/4)

completed --> stage4: 增量修改触发

stale --> stage1: 业务专家重新响应
stale --> abandoned: 30天无响应

blocked --> running: 创始人或管理员重置
blocked --> abandoned: 用户主动放弃

abandoned --> [*]
```

## 评审二：并行智能体依赖关系合理性

### 🔴 严重缺陷：批次 2 对批次 1 的依赖定义模糊

§3.2.5a 和 §4.1 描述的 6 SubAgent 并行：

```
批次1（无依赖，并行）: FunctionalModule + BusinessProcess + DatabaseAgent
批次2（依赖批次1）: UIDesignAgent + PermissionAgent + ApiDesignAgent
```

**问题 1：批次 2 到底依赖批次 1 的什么产出？**

文档没有明确定义批次 2 的每个 Agent 需要批次 1 的哪些具体产物作为输入：

| 批次 2 Agent    | 需要批次 1 的什么？                | 文档是否明确？ |
| --------------- | ---------------------------------- | -------------- |
| UIDesignAgent   | 功能模块划分？业务流程？数据库表？ | ❌ 未明确       |
| PermissionAgent | 功能模块？数据库表？               | ❌ 未明确       |
| ApiDesignAgent  | 功能模块？数据库表？业务流程？     | ❌ 未明确       |

**问题 2：如果批次 1 某个 Agent 失败，批次 2 如何处理？**

假设 `DatabaseAgent` 失败（blocked），`UIDesignAgent` 和 `ApiDesignAgent` 是否还能执行？它们可能不需要数据库设计（UI 设计可能只需要功能模块划分）。

当前设计是"批次 1 全部完成才启动批次 2"，这是**过度串行化**，损失了并行度。

**问题 3：DocumentMergerService 的合并策略未定义**

6 个 Agent 产出合并为一份 Markdown 设计说明书，但：
- 如果两个 Agent 对同一模块有不同设计怎么办？
- 合并是简单拼接还是有冲突解决策略？
- 合并失败怎么办？

### 🟡 中等缺陷：缺少 Agent 失败的部分降级机制

```
当前设计：
批次1: [A, B, C] 并行
  ↓ 全部成功
批次2: [D, E, F] 并行
  ↓ 全部成功
合并
```

**更合理的设计（允许部分成功）：**

```
批次1: [A, B, C] 并行
  ↓
每个 Agent 独立判定成功/失败
批次2: [D, E, F] 仅依赖其需要的批次1产物
  ↓
部分合并：成功的 Agent 产出合并，失败的标记为 partial
```

例如：
- `DatabaseAgent` 失败 → `ApiDesignAgent` 可以基于功能模块做初步 API 设计（无数据库细节），标记为 `partial_api_design`
- `FunctionalModuleAgent` 失败 → 整个流水线 blocked（因为所有后续都依赖它）

批次1 产出物定义：

│ UIDesignAgent   │ ModuleDefinition[] (知道有哪些页面要设计)        │
│                 │ ProcessFlow[] (知道页面间跳转关系)               │

## 评审三：增量修改流程可落地性

### 🔴 严重缺陷：全量替换 IR 的设计与"增量修改"语义矛盾

§4.7.2 说：**"决定：全量替换 IR，不部分更新"**

但章节标题叫"增量修改流程"，用户期望的是**局部修改**（如"把请假表加一个字段"），而不是重新生成整个 IR。

**实际场景冲突：**
- 用户从 stage5 回退到 stage3，修改一个按钮的文字
- 全量替换意味着重新运行 stage3 的所有 6 个 Agent
- 但用户只改了很小的一点，重新生成全部 IR 是浪费且可能引入回归

**问题 1：IR 版本快照存储在 BASE_AI_PIPELINE_MESSAGE 的合理性**

§4.7.5 定义了 `BASE_IR_VERSION` 表，但 §4.7.2 又说快照存在 `BASE_AI_PIPELINE_MESSAGE`（`F_ROLE = 'system'`）。这是**两个存储位置**，需要统一。

**问题 2：版本清理策略"每阶段每流水线最多10个版本"存在竞争条件**

```
场景：流水线A在stage3有10个版本
- 用户触发第11次增量修改
- 系统需要删除最早的非active版本
- 同时另一个用户在查看版本历史
```

需要定义：
- 删除是物理删除还是标记删除？
- 是否有并发控制（乐观锁）？

**问题 3：上游产物自动升级的实现复杂度**

§4.7.3 说回退时"自动替换为该阶段最新 approved 版本"。但：
- 如果阶段 2 有 v1(superseded) 和 v2(approved)，回退到阶段 3 时自动用 v2
- 但阶段 3 之前是基于 v1 运行的，用 v2 作为输入可能导致阶段 3 的产出与之前不兼容

**缺少兼容性检查。**

### 🟡 中等缺陷：沙箱销毁时序存在用户体验问题

§4.7.4 的时序：
```
1. 点击增量修改 → 弹出选择器（沙箱仍在运行）
2. 选择目标阶段 → 弹出确认
3. 点击确认 → 保存快照 → 销毁沙箱
4. 重新执行 → 创建新沙箱
```

**问题**：步骤 1→2 之间用户可能花很长时间思考（甚至离开电脑），这段时间沙箱一直在占用资源（SemaphoreSlim 的一个槽位）。如果 5 个槽位都被这种"思考中"占用，新流水线无法创建沙箱。

**建议**：点击增量修改时先**预占**一个沙箱槽位（或检查是否有可用槽位），避免选择完目标阶段后发现没槽位了。

### 🟡 中等缺陷：BASE_IR_VERSION 表缺少关键字段

当前 DDL：
```sql
CREATE TABLE BASE_IR_VERSION (
  F_ID, F_TENANT_ID, F_PIPELINE_ID, F_STAGE, F_VERSION,
  F_IR_CONTENT, F_STATUS, F_CREATED_AT
);
```

**缺失字段：**
- `F_TRIGGERED_BY`：谁触发了这次版本（用户ID / Agent名称 / 系统自动）
- `F_CHANGE_SUMMARY`：变更摘要（用于版本历史展示）
- `F_PARENT_VERSION`：父版本号（用于构建版本树）
- `F_DIFF`：与上一版本的差异（JSON Patch格式，避免存储完整IR两次）

### ✅ 修正后的增量修改流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    增量修改流程 v2（可落地版）                    │
├─────────────────────────────────────────────────────────────────┤
│ 1. 用户在 stage5 点击"修改"                                     │
│    └─> 系统检查沙箱槽位可用性（SemaphoreSlim.CurrentCount > 0） │
│    └─> 无可用槽位：提示"当前沙箱繁忙，请稍后"                    │
│                                                                  │
│ 2. 弹出"修改范围选择器"                                          │
│    ├─ 小修改（局部）：选择具体要改的模块/页面/组件               │
│    │   └─> 进入"分治编辑模式"（§4.7b 六步流程）                  │
│    │   └─> 仅重新运行相关 Agent，保留其他 Agent 产出              │
│    │   └─> 适用：改文字、改字段、改权限                          │
│    │                                                           │
│    └─ 大修改（全量）：选择回退到 stage 1/2/3/4                  │
│        └─> 进入"全量替换模式"                                    │
│        └─> 重新运行目标阶段及后续全部 Agent                       │
│        └─> 适用：架构调整、需求变更                              │

│ 3. 用户确认 + 输入修改原因（必填，用于审计）                      │
│                                                                  │
│ 4. 保存当前 IR 快照到 BASE_IR_VERSION                            │
│    └─> 同时写入 F_CHANGE_SUMMARY 和 F_TRIGGERED_BY               │
│                                                                  │
│ 5. 销毁沙箱（仅在确认后）                                        │
│                                                                  │
│ 6. 执行修改                                                      │
│    ├─ 分治模式：路由到对应 Agent → 输出 IREditPatch              │
│    │   → applyPatch → validate → 编译 → 部署                    │

│                                                                  │
│ 7. 新沙箱创建成功 → 保存新版本快照 → 旧版标记 superseded          │
│                                                                  │
│ 8. 用户测试 → 满意则完成 / 不满意可再次修改或回滚                 │
└─────────────────────────────────────────────────────────────────┘
```

### 一、Agent 视图机制评审（§3.2.5b）

#### ✅ 正确之处

- 视图注册表的设计理念正确：基于 IR 类型系统推导，每个 Agent 定义 `ownedNodeTypes / readableNodeTypes / writableNodeTypes`，`applyPatch` 拒绝修改 Agent 视图外的节点，实现了**最小权限原则**。
- 6 类节点类型（Requirement、ModuleDefinition、TableDefinition、Component、DataSource、WorkflowStep、RuleNode）覆盖了 IR 类型系统的核心实体。

#### 🔴 严重问题：视图注册表与后端 SubAgent 清单严重不匹配

| 维度    | §3.2.5b 视图注册表中的 Agent                           | §3.2.4 后端已实现的 6 SubAgent            |
| ------- | ------------------------------------------------------ | ----------------------------------------- |
| Agent 1 | **RequirementAnalyst**（可写 Requirement）             | **FunctionalModuleAgent**（功能模块划分） |
| Agent 2 | **Architect**（可写 ModuleDefinition+TableDefinition） | **BusinessProcessAgent**（业务流程设计）  |
| Agent 3 | **UIAgent**（可写 Component）                          | **DatabaseAgent**（数据库 DDL）           |
| Agent 4 | **DatabaseAgent**（可写 TableDefinition+DataSource）   | **UIDesignAgent**（前端页面布局）         |
| Agent 5 | **WorkflowAgent**（可写 WorkflowStep）                 | **PermissionAgent**（角色权限矩阵）       |
| Agent 6 | **RuleEngineAgent**（可写 RuleNode）                   | **ApiDesignAgent**（RESTful API 契约）    |

**具体缺陷：**

1. **名称错位**：视图注册表中的 `RequirementAnalyst`、`Architect`、`WorkflowAgent`、`RuleEngineAgent` 在后端 SubAgent 清单（§3.2.4）中**不存在**。后端实际的功能模块/业务流程/权限/API 四个 Agent 在视图注册表中**没有对应的视图定义**。
2. **V2 Agent 混入**：`WorkflowAgent` 在 §1.3.2a 中已明确标记为 **🔷 V2（FlowIR 编译器未完成）**，不应出现在本期视图注册表中。
3. **缺失视图**：`FunctionalModuleAgent`、`BusinessProcessAgent`、`PermissionAgent`、`ApiDesignAgent` 四个已实现的后端 Agent **完全没有视图约束定义**，意味着它们调用 `applyPatch` 时没有写权限边界。

| Agent                 | ownedNodeTypes              | writableNodeTypes             |
| --------------------- | --------------------------- | ----------------------------- |
| FunctionalModuleAgent | ModuleDefinition            | ModuleDefinition              |
| BusinessProcessAgent  | BusinessProcess             | BusinessProcess, WorkflowStep |
| DatabaseAgent         | TableDefinition, DataSource | TableDefinition, DataSource   |
| UIDesignAgent         | Component, FormPageIR       | Component                     |
| PermissionAgent       | PermissionMatrix            | PermissionMatrix, RoleNode    |
| ApiDesignAgent        | ApiEndpoint                 | ApiEndpoint                   |

### 二、校验链约束评审（§3.2.5 + §3.2.5a）

#### ✅ 正确之处

- **D-01 强制约束**定义清晰：所有 IR 产出路径（前端 Agent 对话模式、后端 StageService 流水线模式、开发者手工编辑模式）必须经过 `cleanSchema() → validateIR() → vue-tsc --noEmit` 三步校验链，任何路径不得跳过。
- §8.1 角色入口矩阵中，每个用户操作都标注了对应的校验链，追溯完整。

#### 🔴 遗漏 1：DocumentMergerService 合并后缺少二次校验

§3.2.5a 依赖图显示：6 SubAgent 产出 → `DocumentMergerService` 合并 Markdown。但：

- 如果 6 个 Agent 各自产出的 IR 片段在合并时发生**字段冲突**（如 DatabaseAgent 定义的 TableDefinition 与 UIDesignAgent 引用的 DataSource 不一致），合并后的 IR **是否需要重新走一遍完整校验链？**
- 当前文档中 `DocumentMergerService` 之后直接结束，**没有校验节点**。

#### 🔴 遗漏 2：KnowledgeIntegrationService AOP 注入后的 Prompt 变异未设防

§3.2.5a 明确推荐 AOP 模式："LlmGatewayService 在每次 ChatAsync 前自动调用 KnowledgeIntegration，将知识片段注入 System Prompt"。但：

- 注入的知识片段可能包含**与 EAB 硬约束冲突的内容**（如知识库中某条过时的规则建议 `techStack.framework = "微服务"`，违反 ADR-016 模块化单体约束）。
- 当前校验链仅校验**LLM 输出的 IR**，不校验**注入知识后 System Prompt 的一致性**。如果知识片段污染了 Prompt，LLM 可能产出违规 IR，虽然会被 `validateIR` 拦截，但会导致**无意义的重试浪费 Token**。

#### 🟡 遗漏 3：§4.7 增量修改的分治编辑校验链不完整

§4.7b 定义了分治编辑六步流程：`buildNodeSummaryList → routeToAgent → extractSlice → Agent输出IREditPatch → applyPatch → validateAfterPatch`。但：

- `validateAfterPatch` 仅描述为"验证"，**未明确是否等同于完整三步校验链**（cleanSchema → validateIR → vue-tsc）。
- 如果 `applyPatch` 只修改了单个节点（如一个 Component），是否还需要 `vue-tsc --noEmit` 全量类型检查？文档未给出**增量校验 vs 全量校验**的策略。

#### 📌 修正建议

1. 在 `DocumentMergerService` 输出端增加 `→ cleanSchema → validateIR → vue-tsc` 合并后校验节点
2. AOP 注入知识片段前增加 `EAB 合规预检`（检查知识片段是否包含与 ARC-016 等硬约束冲突的关键词）
3. §4.7b 的 `validateAfterPatch` 明确定义为完整三步校验链，或给出增量校验的判定条件

## 二、第四章·流程顺畅性审查
### 🔴 审判令一：业务专家"确认疲劳"——4 道人工门禁过重
**问题定位**：§4.1.0 流水线角色门控矩阵定义了 4 道人工确认（阶段 1→2、2→3、3→4、4→5），业务专家需在 3 个节点上做出决策。
**顺畅性分析**：
| 门禁                                                         | 确认者          | 用户看到什么                      | 用户需要理解什么   | 认知负担                   |
| ------------------------------------------------------------ | --------------- | --------------------------------- | ------------------ | -------------------------- |
| 1→2                                                          | 业务专家        | AI 复述需求 + 追问汇总            | 需求是否被正确理解 | 🟢 低                       |
| 2→3                                                          | 业务专家+开发者 | 低保真线框图 + ER 图 + 模块划分   | 技术架构是否合理   | 🔴 高——业务专家需理解 ER 图 |
| 3→4                                                          | 业务专家        | 高保真页面预览 + 与阶段 2 的 diff | 设计是否满足需求   | 🟡 中                       |
| 4→5                                                          | 业务专家+管理员 | 沙箱应用 + 测试报告               | 是否可以上线       | 🟡 中                       |
| **核心矛盾**：阶段 2→3 的确认者包含"业务专家"，但确认依据包含"ER 图"——这是**开发者视角**的产物。业务专家看 ER 图无法做出有效判断，要么机械点"确认"（形同虚设），要么卡住不敢确认（流程阻塞）。 |                 |                                   |                    |                            |
| **裁定**：                                                   |                 |                                   |                    |                            |
> **D-R1-001**：阶段 2→3 的门禁拆分为两步——
> 1. 业务专家仅确认"业务语言模块划分说明 + 用户故事覆盖度"（不暴露 ER 图）
> 2. 开发者独立确认"ER 图 + 技术架构"（可选评审，不阻断流水线）
>
> 前端需实现**双角色确认面板**：同一阶段产出，按角色展示不同确认视图。
---
### 🔴 审判令二：增量修改流程的"盲盒确认"问题
**问题定位**：§4.7 增量修改流程中，用户选择回退目标后直接确认→销毁沙箱→重建。用户无法在确认前**预览变更影响范围**。
**顺畅性分析**：
```
当前流程：选择回退阶段 → 确认弹窗（"沙箱将重建，测试数据不保留"）→ 销毁 → 重建
用户心理模型：
  "我只想改一个字段名，为什么要重建整个沙箱？"
  "回退到阶段 3 后，我会得到什么？和现在差多少？"
  "上次修改后效果不好，能撤回吗？"
```
**缺失的交互节点**：
| 缺失环节     | 影响                            | 严重度 |
| ------------ | ------------------------------- | ------ |
| 变更影响预览 | 用户不知道回退后哪些页面/表会变 | 🔴      |
| 最小回退推荐 | 系统未推荐"最小代价回退目标"    | 🟡      |
| 回退后预览   | 用户无法在确认前看到新产出预览  | 🟡      |
| **裁定**：   |                                 |        |
> **D-R1-002**：在"确认弹窗"与"销毁沙箱"之间，增加**变更影响预览步骤**：
> 1. 用户选择回退目标后，系统调用 `buildDependencyGraph` + `propagateImpact`（§4.7a 已有算法）计算受影响节点
> 2. 前端展示**影响清单**：哪些页面会变、哪些表会变、哪些流程会变（用业务语言，不暴露 IR JSON）
> 3. 用户确认影响范围后，才进入沙箱销毁环节
>
> 对应新增接口：`POST /api/pipeline/{id}/preview-rollback` → 返回 `ImpactPreviewResult`
---
### 🔴 审判令三：blocked 状态下的用户"无助感"
**问题定位**：§4.0 全局熔断规则中，流水线进入 `blocked` 状态后，通知推送给租户管理员和平台管理员，但**触发操作的业务专家本人不在通知列表中**。
**顺畅性分析**：
```
场景：业务专家点击"应用快速生成" → 30 秒后收到通知"流水线已 blocked"
业务专家能做什么？——文档未定义
谁来解决？——管理员手动重置
业务专家如何知道恢复？——未定义
```
**裁定**：
> **D-R1-003**：blocked 通知机制补充三要素：
> 1. **通知对象增加**：触发该流水线的业务专家本人（无论角色）
> 2. **可操作指引**：blocked 通知中包含"联系管理员"按钮（预填流水线 ID + 失败摘要）
> 3. **恢复通知**：管理员重置为 pending 后，自动通知原业务专家"流水线已恢复，是否继续"
>
> 对应接口变更：`POST /api/pipeline/{id}/reset` 新增 `notifyOriginator: true` 参数
---
### 🟡 审判令四：缺少"取消流水线"流程
**问题定位**：第四章所有流程图中，没有"用户主动取消正在运行的流水线"的路径。
| 场景                             | 当前处理                            | 问题                         |
| -------------------------------- | ----------------------------------- | ---------------------------- |
| 业务专家发现需求输入错误，想重来 | 等待 blocked 或等阶段完成后增量修改 | 用户被锁死                   |
| 开发者发现 AI 走偏，想终止       | 无 API 支持终止                     | 资源浪费（LLM Token + 沙箱） |
| **裁定**：                       |                                     |                              |
> **D-R1-004**：状态机增加 `cancelling → cancelled` 转换：
> - 用户点击"取消" → 状态变 `cancelling` → 正在执行的 LLM 调用等完成后不再继续 → 销毁沙箱（如有）→ 状态变 `cancelled`
> - 已完成的阶段产物保留（可供下次复用）
> - 对应接口：`POST /api/pipeline/{id}/cancel`
---
### 🟡 审判令五：AI 顾问（对话模式）流程缺失
**问题定位**：§8.1 明确定义了"AI 顾问"入口（`/dev/ai-advisor`，开发者角色使用），但第四章**只描述了自动流水线流程**，没有对话模式的交互流程。
