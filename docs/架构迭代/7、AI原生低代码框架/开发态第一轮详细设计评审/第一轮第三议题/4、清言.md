## 🔴 B-03：全量替换 IR vs 增量修改语义矛盾
**核心矛盾**：§4.7.2 文档决定"全量替换 IR"，但用户期望"增量修改"是局部修改。两者不能二选一，必须共存。
### 怎么改
**双模式并存**，用操作类型区分：
| 模式                 | 触发方式                        | 数据处理                                                  | 适用场景                   |
| -------------------- | ------------------------------- | --------------------------------------------------------- | -------------------------- |
| **全量回退**         | 用户选择回退到阶段 N → 重新生成 | 全量替换 IR，旧版本存入 `BASE_IR_VERSION`                 | 架构级变更，需要重新生成   |
| **分治编辑**         | 用户在当前 IR 上指定修改点      | 生成 `IREditPatch`（JSON Patch RFC 6902），只修改指定节点 | 字段名修改、组件替换等小改 |
| **数据层关键设计**： |                                 |                                                           |                            |
```sql
-- 新增：IR 编辑补丁表（分治编辑的产物）
CREATE TABLE BASE_IR_EDIT_PATCH (
    F_ID BIGINT PRIMARY KEY,
    F_TENANT_ID NVARCHAR(50) NOT NULL,
    F_PIPELINE_ID BIGINT NOT NULL,
    F_IR_VERSION_ID BIGINT NOT NULL,          -- 基于哪个 IR 版本
    F_AGENT_NAME NVARCHAR(50),                 -- 哪个 Agent 执行的编辑
    F_OPERATION NVARCHAR(20) NOT NULL,         -- 'replace' | 'add' | 'remove'
    F_PATH NVARCHAR(500) NOT NULL,             -- JSONPath，如 '$.pages[0].components[2].props.label'
    F_OLD_VALUE NVARCHAR(MAX),                 -- 旧值（自动填充，用于回滚）
    F_NEW_VALUE NVARCHAR(MAX) NOT NULL,        -- 新值
    F_REASON NVARCHAR(500),                    -- 修改原因
    F_STATUS NVARCHAR(20) DEFAULT 'pending',   -- pending | applied | reverted | failed
    F_APPLIED_AT DATETIME,
    F_REVERTED_AT DATETIME,
    F_CREATED_AT DATETIME NOT NULL,
    INDEX IDX_PIPELINE (F_PIPELINE_ID),
    INDEX IDX_VERSION (F_IR_VERSION_ID),
    INDEX IDX_STATUS (F_STATUS)
);
```
**分治编辑流程**（与 §4.7b 对齐）：
```
1. buildNodeSummaryList → 前端展示可编辑节点清单
2. routeToAgent → 根据 nodeType 路由到对应 Agent
3. extractSlice → 提取该节点的 IR 切片
4. Agent 输出 IREditPatch → 写入 BASE_IR_EDIT_PATCH
5. applyPatch → 校验 Agent 视图边界（ownedNodeTypes）→ 应用修改
6. validateAfterPatch → cleanSchema → validateIR → vue-tsc
7. 校验通过 → 自动创建新 IR 版本快照（BASE_IR_VERSION）
```
**谁来改**：首席架构师（§4.7 补充分治编辑流程）+ 后端工程师（`IREditPatchService` + `BASE_IR_EDIT_PATCH` DDL）
**什么时候改**：P0，**DDL 今天定**，分治编辑的 Agent 路由逻辑阶段五实现

## 🟡 I-09：BASE_IR_VERSION 表缺失关键字段
### 怎么改
当前 §4.7.5 的 DDL 只有 7 个字段，缺少审计和追溯必需的字段。补充如下：
```sql
CREATE TABLE BASE_IR_VERSION (
    F_ID BIGINT PRIMARY KEY,
    F_TENANT_ID NVARCHAR(50) NOT NULL,
    F_PIPELINE_ID BIGINT NOT NULL,
    F_STAGE NVARCHAR(20) NOT NULL,
    F_VERSION INT NOT NULL DEFAULT 1,
    F_IR_CONTENT NVARCHAR(MAX) NOT NULL,
    F_STATUS NVARCHAR(20) DEFAULT 'active',     -- active / superseded / archived / invalid
    
    -- ↓ 新增字段 ↓
    F_PARENT_VERSION_ID BIGINT,                  -- 父版本 ID（构建版本树）
    F_TRIGGERED_BY NVARCHAR(50) NOT NULL,        -- 触发来源：用户ID / Agent名称 / 'system_auto'
    F_CHANGE_TYPE NVARCHAR(20) NOT NULL,         -- 'full_rollback' | 'surgical_edit' | 'stage_advance' | 'auto_snapshot'
    F_CHANGE_SUMMARY NVARCHAR(500),              -- 变更摘要（如"回退到 stage2 重新生成"）
    F_EDIT_PATCH_ID BIGINT,                      -- 关联的编辑补丁 ID（分治编辑时有值）
    F_DIFF NVARCHAR(MAX),                        -- 与父版本的 JSON Patch（RFC 6902）
    F_VALIDATION_RESULT NVARCHAR(MAX),           -- 校验链结果 JSON（cleanSchema/validateIR/vue-tsc 三个布尔值 + 错误详情）
    F_SNAPSHOT_AT DATETIME NOT NULL DEFAULT GETDATE(),
    
    -- 审计字段
    F_IS_DELETED BIT DEFAULT 0,
    F_CREATE_USER_ID NVARCHAR(50),
    F_CREATE_TIME DATETIME,
    F_MODIFY_USER_ID NVARCHAR(50),
    F_MODIFY_TIME DATETIME,
    
    INDEX IDX_PIPELINE (F_PIPELINE_ID, F_STAGE, F_VERSION),
    INDEX IDX_TENANT (F_TENANT_ID),
    INDEX IDX_PARENT (F_PARENT_VERSION_ID),
    INDEX IDX_STATUS (F_STATUS)
);
```
**谁来改**：后端工程师（DDL + `IRVersionService` 补充字段写入逻辑）
**什么时候改**：P0，**DDL 今天定**，代码本周

## 🟡 I-10：版本清理策略存在竞争条件
### 怎么改
当前 §4.7.5 说"每个阶段每个流水线最多保留 10 个版本，超量自动清理最早的非 active 版本"。问题：
1. **竞争条件**：两个并发的阶段流转同时写入快照，可能都认为自己不是第 11 个
2. **物理删除风险**：清理时如果物理删除，审计链断裂
**解决方案：标记删除 + 乐观锁 + 分级保留**
```sql
-- 不物理删除，用 F_STATUS = 'archived' 标记
-- 清理策略改为：
保留规则（按优先级）：
  1. F_STATUS = 'active' → 永远保留（当前版本）
  2. F_STATUS = 'superseded' + F_VERSION 是该阶段最新 3 个 → 保留
  3. F_STATUS = 'invalid' → 保留 30 天后归档
  4. 其余 → 标记为 'archived'（不删除，只读）
并发控制：
  -- 使用 F_VERSION 乐观锁，不用额外的锁表
  INSERT 前：
    SELECT MAX(F_VERSION) FROM BASE_IR_VERSION 
    WHERE F_PIPELINE_ID = @id AND F_STAGE = @stage
  INSERT 时：
    F_VERSION = @maxVersion + 1
  如果并发插入导致版本号冲突 → 重试（最多 3 次）
```
**谁来改**：后端工程师（`IRVersionService.cleanUpAsync` + 乐观锁逻辑）
**什么时候改**：P1，阶段五并行。但 **保留规则今天定**

## 🟡 I-11：admin/admin123 自动创建的数据流没说清
### 怎么改
§4.7.4 说"自动创建 admin/admin123"，但以下问题未定义：
| 问题                 | 当前状态   | 必须定义                                                     |
| -------------------- | ---------- | ------------------------------------------------------------ |
| admin 属于哪个租户？ | 未定义     | 属于 `sandbox_{tenantId}` 的沙箱 DB，**不属于 master 的任何租户** |
| 密码策略？           | 硬编码 123 | 首次登录强制修改密码（`F_MUST_CHANGE_PASSWORD = 1`）         |
| 权限范围？           | 未定义     | 仅沙箱内管理员权限，**不可访问 master DB**                   |
| 生命周期？           | 未定义     | 沙箱销毁时同步删除                                           |
| **数据流子流程**：   |            |                                                              |
```
SandboxDeploymentService.DeployAsync()
  │
  ├── 1. docker run → 创建容器
  ├── 2. CREATE DATABASE sandbox_{tenantId} → 创建沙箱 DB
  ├── 3. dotnet ef database update → 初始化表结构
  ├── 4. INSERT INTO BASE_USER (F_ACCOUNT='admin', F_PASSWORD=Hash('admin123'), 
  │     F_MUST_CHANGE_PASSWORD=1, F_ROLE_ID='sandbox_admin')
  │     → 写入沙箱 DB（不是 master）
  ├── 5. INSERT INTO BASE_ROLE (F_CODE='sandbox_admin', F_NAME='沙箱管理员')
  │     → 权限：仅沙箱内 CRUD，不可访问系统配置
  ├── 6. Health Check → 确认 /health 返回 200
  └── 7. 返回 sandboxUrl + admin 账号信息
```
**DDL 补充**（`BASE_USER` 在沙箱 DB 中）：
```sql
-- 沙箱 DB 中的 BASE_USER 增加：
ALTER TABLE BASE_USER ADD F_MUST_CHANGE_PASSWORD BIT DEFAULT 0;
ALTER TABLE BASE_USER ADD F_SANDBOX_SCOPE BIT DEFAULT 1;  -- 标记为沙箱范围用户
```
**谁来改**：后端工程师（`SandboxDeploymentService` 补全子流程 + DDL）
**什么时候改**：P1，阶段五并行。但 **数据流子流程今天定**（影响沙箱安全边界）

## 🟡 I-12：blocked 状态的数据落点三处不一致
### 怎么改
当前 blocked 状态的失败数据散落在三个地方，且格式不统一：
| 位置                                               | 当前内容                  | 问题             |
| -------------------------------------------------- | ------------------------- | ---------------- |
| `PipelineState.FailureCounts`（内存）              | `Dictionary<string, int>` | 服务重启丢失     |
| `BASE_AI_PIPELINE_MESSAGE`                         | 纯文本消息                | 无结构化失败信息 |
| `BASE_AI_CALL_LOG`                                 | 单次调用日志              | 无聚合视图       |
| **统一方案：失败计数归入 `BASE_AI_PIPELINE` 主表** |                           |                  |
```sql
ALTER TABLE BASE_AI_PIPELINE ADD F_FAILURE_COUNTS NVARCHAR(MAX);
-- JSON 格式：
-- {
--   "llm_timeout": 2,
--   "compile_failure": 0,
--   "sandbox_failure": 1,
--   "validation_failure": 0,
--   "lastFailureAt": "2026-06-20T10:00:00Z",
--   "lastFailureType": "sandbox_failure",
--   "lastFailureDetail": "docker run exit code 137 (OOM)"
-- }
```
**数据同步规则**：
```
1. 每次操作失败 → 更新 F_FAILURE_COUNTS（原子操作：JSON_MODIFY）
2. 任一类型计数 ≥ 3 → 触发 blocked 状态转换
3. 操作成功 → 对应类型计数归零（其他类型保留）
4. PipelineState 内存缓存仍保留（性能优化），但从 DB 加载为准
5. 服务重启 → 从 BASE_AI_PIPELINE.F_FAILURE_COUNTS 恢复内存缓存
```
**谁来改**：后端工程师（`PipelineEngineService` 失败计数逻辑 + DDL）
**什么时候改**：P0，**跟 I-05 同步改**（议题1已裁决合并），DDL 今天定

## 🟡 I-13：stale 状态没有触发数据流
> 注意：议题1已裁决 B-02+I-13 合并。此处仅补充数据层细节。
### 怎么改（数据层补充）
`StaleMonitorService` 的 SQL 扫描逻辑需要 `BASE_AI_PIPELINE` 表增加字段：
```sql
ALTER TABLE BASE_AI_PIPELINE ADD F_STALE_FROM_STAGE NVARCHAR(20);
-- 记录进入 stale 前的阶段，用于 resume 时自动回填 targetStage
ALTER TABLE BASE_AI_PIPELINE ADD F_STALE_AT DATETIME;
-- 进入 stale 的时间，用于 30 天超时判定
-- 复合索引（清言已补充，我确认必要）：
CREATE INDEX IDX_STALE_CHECK ON BASE_AI_PIPELINE(F_STAGE_STATUS, F_MODIFY_TIME, F_CURRENT_STAGE);
```
**StaleMonitorService 数据流**：
```
每小时执行：
  1. SELECT F_ID, F_CURRENT_STAGE, F_MODIFY_TIME, F_TENANT_ID, F_USER_ID
     FROM BASE_AI_PIPELINE
     WHERE F_STAGE_STATUS NOT IN ('stale', 'abandoned', 'completed')
       AND F_IS_DELETED = 0
       
  2. 对每条记录，计算是否超时：
     stage1/2: F_MODIFY_TIME + 7天 < NOW()
     stage3: F_MODIFY_TIME + 3天 < NOW()
     stage4: F_MODIFY_TIME + 7天 < NOW()
     stage5: F_MODIFY_TIME + 14天 < NOW()
     
  3. 超时 → 批量更新：
     UPDATE BASE_AI_PIPELINE SET
       F_STAGE_STATUS = 'stale',
       F_STALE_FROM_STAGE = F_CURRENT_STAGE,
       F_STALE_AT = GETDATE()
     WHERE F_ID IN (...)
     
  4. 批量通知：
     SignalR 推送 pipeline_stale 事件（给创建者 + 租户管理员）
     INSERT INTO BASE_AI_PIPELINE_MESSAGE (F_ROLE='system', F_CONTENT={type:'alert', status:'stale', ...})
     
  5. 检查 30 天超时：
     SELECT F_ID FROM BASE_AI_PIPELINE
     WHERE F_STAGE_STATUS = 'stale' AND DATEDIFF(day, F_STALE_AT, GETDATE()) > 30
     → 自动 abandoned
```
**谁来改**：后端工程师（`StaleMonitorService` + DDL + Hangfire 注册）
**什么时候改**：P0，**跟 B-02 同步改**（议题1已裁决）
