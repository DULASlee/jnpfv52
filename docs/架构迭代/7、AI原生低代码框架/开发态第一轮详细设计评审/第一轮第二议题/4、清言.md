## 🔴 B-08：输入输出契约——必须定义 6 个 Agent 的 Schema
**千问方案缺陷**：只说"明确定义契约 Schema"，没给出具体字段。这是编码的基石，今天必须锁定。
### 清言补充：6 SubAgent 输入输出契约（强制锁定）
#### 批次 1（无前置依赖，并行执行）
**FunctionalModuleAgent**
```typescript
Input:  { requirement: string, domain: string, eab: EABConfig }
Output: { modules: ModuleDefinition[], moduleRelations: DependencyEdge[] }
```
**BusinessProcessAgent**
```typescript
Input:  { requirement: string, domain: string, modules: ModuleDefinition[] }  // 可选依赖 FunctionalModuleAgent
Output: { processes: ProcessFlow[], processModuleMapping: Record<ProcessId, ModuleId[]> }
```
**DatabaseAgent**
```typescript
Input:  { requirement: string, domain: string, modules: ModuleDefinition[] }  // 可选依赖 FunctionalModuleAgent
Output: { tables: TableDefinition[], relations: TableRelation[], dataSources: DataSource[] }
```
#### 批次 2（强制依赖批次 1，并行执行）
**UIDesignAgent**
```typescript
Input:  { modules: ModuleDefinition[], tables: TableDefinition[], processes: ProcessFlow[] }
Output: { pages: PageLayout[], components: Component[] }
```
**PermissionAgent**
```typescript
Input:  { modules: ModuleDefinition[], tables: TableDefinition[], processes: ProcessFlow[] }
Output: { roles: RoleDefinition[], permissionMatrix: PermissionMatrix }
```
**ApiDesignAgent**
```typescript
Input:  { modules: ModuleDefinition[], tables: TableDefinition[], processes: ProcessFlow[] }
Output: { endpoints: APIEndpoint[], dataContracts: DataContract[] }
```
### 关键依赖约束
> **B-08-R1**：批次 2 的 3 个 Agent **强制依赖**批次 1 的全部输出。批次 1 任一 Agent 失败 → 批次 2 全部跳过（不进入 partial_success，直接进入批次 1 的重试逻辑）。
>
> **B-08-R2**：`DetailedDesignOrchestrator` 必须在批次 1 完成后、批次 2 启动前，执行一次**中间校验**：验证 `modules`、`tables`、`processes` 三个数组不为空且 schema 合法。校验失败 → 不启动批次 2，直接报错。
> **谁来改**：首席架构师（写入 §3.2.5a）+ 后端工程师（`DetailedDesignOrchestrator` 依赖注入 + 中间校验）
> **什么时候改**：P0，今天定 Schema，明天改代码

## 🔴 B-09：DocumentMerger 二次校验——必须定义失败处理策略
**千问方案缺陷**：只说"中断流水线并报错"，但没定义报错后的处理。结合议题1的校验链拦截器决议，需要明确：合并后校验失败，是重试还是降级？
### 清言补充：三级校验 + 分级处理
| 校验环节        | 失败性质                                     | 处理策略                        | 重试次数                      |
| --------------- | -------------------------------------------- | ------------------------------- | ----------------------------- |
| `cleanSchema()` | 清洗问题（多余字段、格式错误）               | **自动修复**后重试              | 3 次（指数退避）              |
| `validateIR()`  | 结构错误（必填字段缺失、引用断裂）           | **回退到 Agent** 重新生成该部分 | 2 次（指定失败的 Agent 重跑） |
| `vue-tsc`       | 类型错误（组件引用不存在、Props 类型不匹配） | **人工介入**（无法自动修复）    | 0 次（直接 blocked）          |
### 裁决约束
> **B-09-R1**：DocumentMerger 合并后，校验链执行顺序必须是 `cleanSchema → validateIR → vue-tsc`，**不可跳过、不可调序**。
>
> **B-09-R2**：`validateIR` 失败时，系统必须**精确定位**是哪个 Agent 的产出导致失败（基于 `ownedNodeTypes` 映射），仅重跑该 Agent，不重跑全部。
>
> **B-09-R3**：`vue-tsc` 失败时，IR 版本快照仍需保存（标记 `status: invalid`），供开发者手动排查。不进入 `blocked`，而是进入 `review` 态（开发者可见类型错误，决定是否手动修正或放弃）。
> **谁来改**：后端工程师（`DocumentMergerService` + 校验链编排 + Agent 级错误定位）
> **什么时候改**：P0，今天定策略，明天改代码

## 🟡 I-07：批次 1 部分失败降级——需要细化影响传播
**千问方案缺陷**：只说了"部分成功降级"，但没定义影响传播逻辑。批次 1 有 3 个 Agent 并行，失败组合有 7 种（$2^3-1$），需要分类处理。
### 清言补充：7 种失败组合的处理策略
| 失败组合                           | 影响                             | 处理策略                                                     |
| ---------------------------------- | -------------------------------- | ------------------------------------------------------------ |
| 仅 FunctionalModule 失败           | 批次 2 全部无法执行              | 🔴 重试 FunctionalModule（最多 2 次），仍失败 → blocked       |
| 仅 BusinessProcess 失败            | UIDesign/Permission 无法执行     | 🟡 降级：跳过 BusinessProcess，批次 2 中 UIDesign/Permission 的 `processes` 输入为空数组（前端无流程绑定），API Agent 仍可执行 |
| 仅 Database 失败                   | UIDesign/Permission/API 无法执行 | 🔴 重试 Database（最多 2 次），仍失败 → blocked（数据库是硬依赖） |
| FunctionalModule + BusinessProcess | 批次 2 全部无法执行              | 🔴 blocked                                                    |
| FunctionalModule + Database        | 批次 2 全部无法执行              | 🔴 blocked                                                    |
| BusinessProcess + Database         | UIDesign/Permission/API 无法执行 | 🔴 blocked                                                    |
| 全部失败                           | —                                | 🔴 blocked                                                    |
### 简化规则
> **I-07-R1**：降级判定简化为一条规则——**FunctionalModule 和 Database 是硬依赖，任一失败即 blocked；BusinessProcess 是软依赖，失败可降级（processes 输入为空数组）**。
> **谁来改**：首席架构师（写入 §3.2.5a 降级策略）+ 后端工程师（`DetailedDesignOrchestrator` 分支逻辑）
> **什么时候改**：P1，阶段五并行

## 🟡 I-08：EAB 合规预检——需要定义预检规则来源
**千问方案缺陷**：只说"增加 EAB 合规预检"，但没定义预检规则的来源和格式。
### 清言补充：预检规则从 EAB Config 动态读取
**EAB 配置结构**（已有，§2.2 层 1）：
```json
{
  "techStack": {
    "framework": "modular-monolith",
    "ui": "ant-design-vue",
    "database": "sqlserver",
    "language": "csharp"
  },
  "hardConstraints": [
    "禁止 AddMicroservice",
    "禁止手写 Controller",
    "禁止 PostgreSQL"
  ]
}
```
**预检逻辑**：
1. AOP 切面在 `LlmGatewayService.ChatAsync` 前执行
2. 从 `BASE_AI_PROMPT_TEMPLATE` 读取当前 Agent 的 EAB 约束
3. 检查待注入的知识片段是否包含 `hardConstraints` 中的关键词
4. 冲突 → 拒绝注入 + 写入 `BASE_AI_CALL_LOG`（`F_ERROR` 字段记录冲突详情）+ 降级到无知识的裸调用
### 裁决约束
> **I-08-R1**：预检规则**不从代码硬编码**，从 `BASE_AI_PROMPT_TEMPLATE.F_VARIABLES` 的 `eab_config` 字段动态读取。这样 EAB 变更时只需改 Prompt 模板，不改代码。
> **谁来改**：后端工程师（`LlmGatewayService` AOP 切面 + EAB 预检逻辑）
> **什么时候改**：P1，阶段五并行。但 **EAB 配置结构今天定**（影响 Prompt 模板设计）
