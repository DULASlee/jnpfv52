## 我的补充预案（议题 2 · 5 项）

### B-07（视图注册表不匹配）
千问的修正方向对。我补架构层：
- **怎么改**：**前端 AgentViewRegistry 不要再写死**，改成启动时调用 `GET /api/founder/ai/agents/list` 从后端动态拉取 SubAgent 清单。后端是 single source of truth，前端只是镜像。这样以后后端改名/增删，前端不会脱节。
- **接口补**：GET `/api/founder/ai/agents/list`，响应 `{ agents: [{name, type, batch, capabilities, status}] }`
- **谁来改**：首席架构师（文档）+ 后端工程师（新增接口）+ 前端工程师（改造 AgentViewRegistry）
- **什么时候改**：P0，**接口契约今天定**；前端改造可放到阶段五并行（先用静态表兜底）

### B-08（输入输出契约未定义）
千问的方向对。我强补契约必须包含的 4 个字段，否则就是半成品：
- **怎么改**：每个 Agent 的契约必须明确定义：
  1. **输入**：JSON Schema + 数据源（哪个表的哪个字段）+ 上游依赖 Agent 列表
  2. **输出**：JSON Schema + 落点表（如 `BASE_AI_PIPELINE_MESSAGE` 或 `BASE_IR_VERSION`）+ 下游消费者
  3. **校验点**：cleanSchema → validateIR → vue-tsc 三选哪些
  4. **失败码**：枚举值（如 `schema_violation` / `version_mismatch` / `empty_output`）
- **关键补丁**：Batch 2 依赖 Batch 1 的 `Schema_Version` 字段——**建议加 `IR_SCHEMA_VERSION` 全局常量**（放在 `core/ir/ir-version.ts`），所有 Agent 启动时校验版本一致性。这样以后 IR schema 升版，能立刻知道影响范围。
- **谁来改**：首席架构师（写 §3.2.5a 契约 Schema）+ 后端工程师（实现参数校验 + 版本常量）
- **什么时候改**：P0，**今天必须定稿**

### B-09（DocumentMerger 无二次校验）
千问的"强制拦截器"方向对。我补短路逻辑 + 熔断集成：
- **怎么改**：
  - 校验链必须**短路**（任一失败立即中断），不能"全跑完再汇总"——节省资源，也便于定位失败点
  - 每步失败要写 `BASE_AI_PIPELINE_MESSAGE`（F_ROLE='system', F_CONTENT 含 `{type:'validation_failure', step, error, agent}`）
  - **纳入 §4.0 全局熔断**：连续 3 次 validation_failure → blocked（这跟我之前提的 I-12 同源）
- **谁来改**：后端工程师（短路逻辑 + 错误落点 + 熔断集成）
- **什么时候改**：P0，**今天定方案**，明天修代码

### I-07（部分失败降级）
千问的方向对。我补数据层 + 状态机细节：
- **怎么改**：
  - `partial_success` **不是终态**，是过渡态。明确下一步：要么"重试失败子 Agent"（→blocked 或回退重跑），要么用户手动"接受当前进度"（→stage4 接续）
  - `BASE_AI_PIPELINE` 加 2 列：`F_PARTIAL_STAGES JSON`（哪些子阶段成功/失败）+ `F_DOWNLOADABLE_ARTIFACTS JSON`（哪些产物可下载）
  - 新增接口：GET `/api/pipeline/{id}/partial-artifacts`（返回可下载清单 + 下载链接）
- **谁来改**：首席架构师（策略 + 状态机扩展）+ 后端工程师（DDL + 接口）
- **什么时候改**：P1，阶段五并行

### I-08（Prompt 污染风险）
千问的"合规预检"方向对。我补**双层校验**：
