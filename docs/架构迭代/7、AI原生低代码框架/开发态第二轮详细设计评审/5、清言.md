## 🟡 P1 重要：阶段五并行前必须补齐
### I-DB-01：BASE_SANDBOX 双层模式缺少并发控制与性能设计
**问题定位**：§6.6.2的双层模式设计（内存ConcurrentDictionary + DB持久化）在以下场景有风险：
| 场景               | 风险                                                         | 当前设计                 |
| ------------------ | ------------------------------------------------------------ | ------------------------ |
| 服务重启恢复       | 逐一`docker inspect`验证容器存活，如果有10个running沙箱，耗时30-60s | 未考虑批量验证           |
| 并发Create+Destroy | 内存缓存与DB的同步未加锁，可能导致内存有但DB无（或反之）     | 未定义同步锁             |
| 容器意外死亡       | Docker OOM Kill导致容器消失，但DB仍为running                 | 仅在GetStatusAsync时验证 |
| **怎么改**：       |                                                              |                          |
1. **重启恢复优化**：并行验证 + 超时兜底
```csharp
// SandboxManager.StartupRecoveryAsync()
var runningSandboxes = await db.Query<BASE_SANDBOX>()
    .Where(s => s.F_STATUS == "running" && !s.F_IS_DELETED)
    .ToListAsync();
// 并行验证，最多 30s
var parallelOptions = new ParallelOptions { MaxDegreeOfParallelism = 5 };
await Parallel.ForEachAsync(runningSandboxes, parallelOptions, async (sandbox, ct) =>
{
    var alive = await DockerInspectAsync(sandbox.F_CONTAINER_ID, timeout: 3000);
    if (!alive)
    {
        sandbox.F_STATUS = "destroyed";
        sandbox.F_DESTROYED_AT = DateTime.UtcNow;
        // 不从内存加，只更新DB
    }
    else
    {
        _memoryCache.TryAdd(sandbox.F_SANDBOX_ID, sandbox);
    }
});
await db.SaveChangesAsync();
```
2. **并发同步锁**：在CreateAsync/DestroyAsync中使用`SemaphoreSlim` + DB事务
```csharp
// 创建时：先INSERT DB → 再docker run → 成功后加入内存
// 销毁时：先docker stop → 再UPDATE DB → 最后从内存移除
// 任何一步失败，回滚对应操作
```
3. **健康巡检**：增加定时任务（每5分钟），验证内存中的沙箱容器仍存活
**谁来改**：后端工程师（`SandboxManager` 重构）
**什么时候改**：P1，阶段五第2周

### I-DB-02：知识图谱UPSERT原子性未保证
**问题定位**：§6.6.3的UPSERT流程是"先INSERT备份表，再UPDATE主表"。如果备份成功但UPDATE失败（版本冲突），备份表会留下脏数据。
**怎么改**：用事务包裹备份+更新：
```sql
BEGIN TRANSACTION;
-- 1. 备份旧版本
INSERT INTO BASE_KNOWLEDGE_NODE_BACKUP (...)
SELECT ... FROM BASE_KNOWLEDGE_NODE WHERE F_NODE_ID = @nodeId;
-- 2. 乐观锁更新
UPDATE BASE_KNOWLEDGE_NODE 
SET F_CONTENT = @newContent, F_VERSION = F_VERSION + 1, ...
WHERE F_ID = @id AND F_VERSION = @currentVersion;
-- 如果 affected rows = 0 → ROLLBACK（备份也回滚）
IF @@ROWCOUNT = 0
BEGIN
    ROLLBACK;
    -- 返回版本冲突
END
ELSE
BEGIN
    COMMIT;
END
```
**谁来改**：后端工程师（`KnowledgePatchService.ApplyAsync`）
**什么时候改**：P1，阶段五第2周

### I-DB-04：BASE_FOUNDER_AUTH_LOG 触发器DDL缺失
**问题定位**：§6.5.1注释写了"不可删审计：DB触发器禁止DELETE / TRUNCATE"，但未给出触发器DDL。工程师不知道怎么实现"不可删"。
**怎么改**：补齐触发器DDL
```sql
-- 禁止 DELETE
CREATE TRIGGER TRG_FOUNDER_AUTH_LOG_NO_DELETE
ON BASE_FOUNDER_AUTH_LOG
INSTEAD OF DELETE
AS
BEGIN
    RAISERROR('BASE_FOUNDER_AUTH_LOG is immutable. DELETE is prohibited.', 16, 1);
    ROLLBACK TRANSACTION;
END;
-- 禁止 TRUNCATE（通过禁止 ALTER TABLE 方式间接防护）
-- SQL Server 不支持 TRUNCATE 触发器，改用权限控制：
-- 1. 仅 sysadmin 可 TRUNCATE
-- 2. 应用服务账号不授予 ALTER 权限
-- 3. 增加监控：DDL触发器监控 TRUNCATE TABLE 操作
CREATE TRIGGER TRG_PREVENT_TRUNCATE
ON DATABASE
FOR DROP_TABLE, ALTER_TABLE
AS
BEGIN
    IF EVENTDATA().value('(/EVENT_INSTANCE/ObjectName)[1]', 'nvarchar(100)') = 'BASE_FOUNDER_AUTH_LOG'
    BEGIN
        RAISERROR('Cannot DROP or ALTER BASE_FOUNDER_AUTH_LOG. This table is immutable.', 16, 1);
        ROLLBACK;
    END
END;
```
**谁来改**：DBA
**什么时候改**：P1，阶段五第1周（与建表同步）
