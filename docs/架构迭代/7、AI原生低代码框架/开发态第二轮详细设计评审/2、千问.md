#### 1. 关于 80+ 张表的完整性与核心表遗漏核查

*   **现状核查**：
    文档统计了 80+ 张表（system 8张 + workflow 18张 + visualdev 3张 + inteAssistant 7张 + oauth 2张 + ...），覆盖了从基础权限到AI核心能力的全链路。
*   **缺失项排查**：
    *   **发现缺口**：在 §6.9 评测模块中，仅定义了 `EVAL_GOLDEN_SET`（黄金集）和 `EVAL_RUN_LOG`（运行日志），**缺少 `EVAL_METRIC`（评分指标定义表）**。
    *   **理由**：根据 §11.3.1 评测基准设计，评分维度包含“准确率、可编译率、合规率”，这些指标的元数据（权重、阈值、计算公式）需要持久化存储，不能硬编码。
*   **修正建议（P0）**：
    *   **新增表**：`EVAL_METRIC`。
    *   **DDL**：
        ```sql
        CREATE TABLE EVAL_METRIC (
          F_ID BIGINT PRIMARY KEY,
          F_NAME NVARCHAR(50) NOT NULL, -- 指标名：accuracy, compilable_rate, compliance
          F_DESCRIPTION NVARCHAR(200),
          F_WEIGHT DECIMAL(3,2) DEFAULT 1.0, -- 权重
          F_THRESHOLD DECIMAL(3,2), -- 阈值 (e.g., 0.8)
          F_IS_ENABLED BIT DEFAULT 1,
          F_CREATE_TIME DATETIME
        );
        ```
    *   `EVAL_RUN_LOG` 需增加 `F_METRIC_ID` 外键关联。

#### 2. BASE_SANDBOX 双层模式设计（D-03）合理性验证

*   **设计回顾**：
    采用“DB持久化 + 内存缓存（ConcurrentDictionary）”双层模式。服务重启时从 DB 恢复状态，通过 `docker inspect` 验证容器存活。
*   **风险点分析**：
    *   **状态不一致风险**：如果数据库记录为 `running`，但 Docker 容器已被 `kill -9` 或宿主机宕机，内存中的 `ConcurrentDictionary` 会加载一个“僵尸”实例。此时用户访问沙箱 URL 会 502，但系统认为它在运行。
    *   **性能瓶颈**：`ConcurrentDictionary` 是纯内存操作，但在高并发（5+ 沙箱）下，如果频繁遍历所有沙箱状态（如管理员看监控），会增加 GC 压力。
*   **修正建议（P1）**：
    *   **引入健康检查代理（HealthCheck Proxy）**：
        在 `SandboxManager` 中增加一个轻量级后台服务（`SandboxHealthMonitor`），定期（每 10s）对 DB 中状态为 `running` 的沙箱执行 `docker inspect` 或 HTTP `curl /health`。
    *   **状态修正机制**：
        如果 DB=running 但 Docker=dead，则自动更新 DB 状态为 `destroyed` 并清理内存缓存。
    *   **索引优化**：
        确保 `BASE_SANDBOX` 表的 `F_STATUS` 和 `F_TENANT_ID` 有**联合索引**，以加速状态查询。

#### 3. BASE_IR_VERSION（§6.6.4）与增量修改需求对齐

*   **设计回顾**：
    用于存储 IR 快照，支持增量修改时的回滚与 Diff。
*   **需求验证（增量修改）**：
    *   **需求点**：用户从阶段 5 回退到阶段 3，需要保留阶段 4 的快照，并标记旧版本为 `superseded`。
    *   **当前设计**：`F_STATUS` (active/superseded) + `F_PARENT_VERSION` (链式追溯)。
*   **风险点**：
    *   **Diff 性能**：`F_DIFF` 字段存储的是 JSON Patch (RFC 6902)。如果直接存大文本，在生成预览（§4.7.5）时，应用层需要解析巨大的 JSON 字符串，性能差。
    *   **版本爆炸**：如果用户频繁进行“修改-回退”循环，单个流水线的版本数可能无限增长，导致表膨胀。
*   **修正建议（P0）**：
    *   **增加版本清理策略字段**：
        在 `BASE_IR_VERSION` 中增加 `F_RETENTION_POLICY` (e.g., "keep_last_10") 或在应用层逻辑中强制：**每个流水线每个阶段最多保留 10 个版本**，超出自动删除（或归档）。
    *   **F_DIFF 存储格式**：
        建议存储为 **JSON 类型**（SQL Server 2016+ 支持）而非 `NVARCHAR(MAX)`，以便数据库层提供 JSON_VALUE 等函数加速查询特定节点的变更。
    *   **关键索引**：
        必须增加复合索引：`IDX_PIPELINE_STAGE_VERSION (F_PIPELINE_ID, F_STAGE, F_VERSION)`，确保能快速定位到特定阶段的最新版本。

#### 4. 知识图谱并发控制方案（§6.6.3）落地验证

*   **设计回顾**：
    采用 **乐观锁 (Optimistic Locking)** + **版本字段 (F_VERSION)** + **备份表 (BASE_KNOWLEDGE_NODE_BACKUP)**。
*   **可行性分析**：
    *   **RAG 场景适配**：RAG V1 是“读多写少”场景（后台定时/手动导入补丁，前台高频检索）。乐观锁非常适合此场景，避免了悲观锁（行锁）导致的检索性能下降。
    *   **熔断机制**：当前设计中，如果 `UPDATE` 影响行数为 0（版本冲突），直接返回失败。但在知识补丁合并场景（§4.4），我们通常希望**“后来者居上”**（即强制覆盖）或**“自动合并”**。
*   **修正建议（P0）**：
    *   **调整冲突处理策略**：
        不要直接抛出异常阻断流程。建议在 `KnowledgePatchService` 中实现 **“强制更新”** 逻辑：
        1.  查询当前最新 `F_VERSION`。
        2.  将补丁数据的 `F_VERSION` 设置为 `current_version + 1`。
        3.  执行 `UPDATE ... SET F_CONTENT = @newContent, F_VERSION = @newVersion WHERE F_ID = @id`（不检查旧版本号）。
        *   *理由：知识补丁是经过熔炉验证的“权威数据”，不需要像银行转账那样严格检查中间状态，直接覆盖即可。*
    *   **备份表触发器**：
        建议将“插入备份表”的逻辑由应用层代码改为 **DB 触发器 (Trigger)**。
        *   *理由：防止应用层代码遗漏或被绕过（如直接 DBA 操作），确保所有变更 100% 留痕。*
