## 二、BASE_SANDBOX 双层模式 🔴 阻塞 2 项 / 🟡 警告 5 项

### 🔴 阻塞

**S-1. §6.6.1 DDL 缺 8 个关键字段**

对照 §6.0.2 其他表都有的审计四件套（CREATE_USER_ID / CREATE_TIME / MODIFY_USER_ID / MODIFY_TIME），**BASE_SANDBOX 一项都没有**——审计无法追溯谁创建了沙箱。同时缺：

| 缺失字段                                                     | 用途                        | 影响                                            |
| ------------------------------------------------------------ | --------------------------- | ----------------------------------------------- |
| F_AI_PIPELINE_ID BIGINT                                      | 外键，关联 BASE_AI_PIPELINE | §6.8 ER 图已画关系但 DDL 无外键，参照完整性丢失 |

| F_CREATE_USER_ID / CREATE_TIME / MODIFY_USER_ID / MODIFY_TIME | 审计四件套                  | 无审计                                          |

**S-2. §6.6.2 双层模式缺并发计数字段**

§6.6.2 提了 SemaphoreSlim(5) 并发限制，但 BASE_SANDBOX 表**没有"当前活跃并发数"字段**。如果只靠内存 ConcurrentDictionary，重启后并发计数丢失，可能瞬间过载（5 → 5 个僵尸沙箱 + 5 个新请求 = 10 个）。

补救字段：`F_ACTIVE_BUILD_COUNT INT DEFAULT 0`（当前该 tenant 的活跃构建数）+ 租户级 `F_MAX_CONCURRENT INT DEFAULT 5`。

### 🟡 警告

**S-3. 缺复合索引**
IDX_TENANT + IDX_STATUS 都有，但**高频查询 `WHERE F_TENANT_ID=? AND F_STATUS='running'`** 没有复合索引，会走两个单列索引 + 书签查找。补 `IDX_TENANT_STATUS (F_TENANT_ID, F_STATUS)`。

**S-4. 缺端口唯一约束**
F_PORT 没有 UNIQUE 约束。如果 BASE_SANDBOX 跨多 host 部署可能撞端口。建议加 `UNIQUE (F_HOST, F_PORT)` 约束。

**S-5. 双层模式"复活"逻辑有竞态**
§6.6.2 流程：DB 加载 → docker inspect → 已死则标 destroyed。但**复活过程中如果有新请求来创建沙箱怎么办？** 建议加分布式锁或租户级信号量：
```sql
-- 或在内存加 SemaphoreSlim(perTenantId)
```

**S-6. 缺 DB_NAME 命名规范**
F_DB_NAME 写成 `sandbox_{tenantId}`——但**多租户隔离下应该是 `sandbox_{tenantId}_{sandboxId}`**（避免同租户多沙箱共享一个 DB 名）。

**S-7. 缺沙箱超时字段**
BASE_SANDBOX 没有 F_EXPIRES_AT，沙箱永久存活会耗资源。建议加 `F_EXPIRES_AT DATETIME NULL`（默认 24h 后过期）+ 后台清理任务。

## 四、知识图谱并发控制（§6.6.3）🟡 警告 5 项

### 🟡 警告

**K-1. BASE_KNOWLEDGE_NODE_BACKUP 缺关键索引**

UPSERT 流程每次按 F_ORIGINAL_ID 查询，但 BACKUP 表**只有 F_ID 主键**，没建索引：

```sql
-- 必须补：
INDEX IDX_BACKUP_ORIGINAL (F_ORIGINAL_ID, F_BACKUP_AT DESC),
INDEX IDX_BACKUP_TENANT (F_TENANT_ID, F_BACKUP_AT)
```

**K-2. UPSERT 三步事务边界不清**

文档写"备份 → UPDATE"，但没说**是否在同一事务里**。如果第 2 步备份成功、第 3 步 UPDATE 失败，会留下孤儿备份。**强烈建议**：
```sql
BEGIN TRANSACTION
  INSERT INTO BASE_KNOWLEDGE_NODE_BACKUP ...
  UPDATE BASE_KNOWLEDGE_NODE SET F_VERSION = F_VERSION + 1 WHERE ...
COMMIT
```

**K-3. 缺物理删除策略**

文档只写"备份旧版用于回滚"，但**备份表会无限增长**。建议：
- F_BACKUP_AT 后 90 天物理删除（异步任务）
- 或按 F_ORIGINAL_ID 保留最近 10 个版本

**K-4. 缺读写隔离机制**

RAG 查询（读）和 KnowledgePatch 合并（写）之间**没有版本快照隔离**。建议：
- RAG 查询走**快照隔离级别**（SQL Server `SET TRANSACTION ISOLATION LEVEL SNAPSHOT`）
- 或加 `F_PUBLISHED_AT` 字段，只查询已发布的版本

**K-5. 缺审计**

KnowledgePatch UPSERT 没看到审计日志——按 §6.5.1 BASE_FOUNDER_AUTH_LOG 规范，合规事件应该写审计。建议 UPSERT 后写一条 `BASE_FOUNDER_AUTH_LOG.F_ACTION='upsert_knowledge'` 记录。

## 五、主键策略 🟡 警告 4 项

### 🟡 警告

**P-1. 雪花算法选型依据缺失**

§6.1 说"F_ID BIGINT（雪花算法）"，但**没写选型对比**——SQL Server 的 `uniqueidentifier`（GUID/UUID）和 BIGINT 雪花各有优劣：
- 雪花：可排序、紧凑（8 字节）、但依赖 workerId 配置
- GUID：分布式友好、不依赖时钟，但 16 字节、不可排序

**建议**：明确"雪花 + 配置中心分配 workerId"作为最终决策，**禁用时钟回拨**（Snowflake 算法需要 NTP 严格同步）。

**P-2. 缺租户基类 DDL**

§6.1 说"所有业务表继承租户基类（含 F_TENANT_ID）"——但**没看到 CREATE TABLE BASE_ENTITY** 的定义。租户基类的字段应该集中定义：

```sql
CREATE TABLE BASE_ENTITY (  -- 抽象基类，不直接建表
  F_ID BIGINT PRIMARY KEY,
  F_TENANT_ID NVARCHAR(50) NOT NULL,
  F_IS_DELETED BIT DEFAULT 0,
  F_CREATE_USER_ID NVARCHAR(50),
  F_CREATE_TIME DATETIME,
  F_MODIFY_USER_ID NVARCHAR(50),
  F_MODIFY_TIME DATETIME
);
-- 业务表使用继承语法：CREATE TABLE BASE_USER (...) INHERITS BASE_ENTITY;
-- SQL Server 用视图或触发器模拟继承
```

**P-3. 雪花 workerId 分配方案缺失**

多实例部署时 workerId 怎么分配？建议：
- 配置中心（如 Nacos/Consul）注册时分配
- 或数据库自增序列获取（`SELECT NEXT VALUE FOR SEQ_WORKER_ID`）

**P-4. BIGINT 主键做聚集键的页分裂问题**

SQL Server 主键默认聚集。**BIGINT 雪花不是严格自增**（workerId 不同会乱序），频繁 INSERT 会导致页分裂。建议：
- 主键聚集 → 自增 INT
- 雪花 ID 放 UNIQUE 列 `F_SNOWFLAKE_ID BIGINT UNIQUE`

## 六、索引设计 🟡 警告 6 项

### 🟡 警告

**X-1. 缺 F_MODIFY_TIME 索引**

增量同步、stale 检测、审计日志都依赖 F_MODIFY_TIME 排序。**多张核心表（BASE_AI_PIPELINE / BASE_USER / BASE_KNOWLEDGE_NODE）都缺这个索引**。

**X-2. 缺 F_MODIFY_TIME + F_TENANT_ID 复合索引**

stale 检测高频查询：`WHERE F_TENANT_ID=? AND F_MODIFY_TIME < ? AND F_STATUS='active'`。建议：
```sql
CREATE INDEX IDX_PIPELINE_TENANT_MODIFY ON BASE_AI_PIPELINE(F_TENANT_ID, F_MODIFY_TIME);
```

**X-3. 缺全文索引**

BASE_KNOWLEDGE_NODE.F_NAME / F_DESCRIPTION 没全文索引，但 §1.3.2 B-06 写"RAG V1 用 SQL LIKE 搜索"——LIKE '%xxx%' **走不了 B-Tree 索引**，大表上会全表扫描。建议：
- V1 阶段加 `CREATE FULLTEXT INDEX ON BASE_KNOWLEDGE_NODE(F_NAME, F_DESCRIPTION)`
- 或 V2 用向量数据库（Milvus）

**X-4. 缺覆盖索引**

BASE_AI_PIPELINE_MESSAGE 高频查询 `WHERE F_SESSION_ID=? ORDER BY F_TIMESTAMP`。建议覆盖索引：
```sql
CREATE INDEX IDX_MSG_SESSION_TIME ON BASE_AI_PIPELINE_MESSAGE(F_SESSION_ID, F_TIMESTAMP) INCLUDE (F_ROLE, F_CONTENT);
```

**X-5. 缺过滤索引**

大表 + 软删除场景：`WHERE F_IS_DELETED=0` 是高频条件。建议：
```sql
CREATE INDEX IDX_USER_ACTIVE ON BASE_USER(F_TENANT_ID) WHERE F_IS_DELETED=0;
```

**X-6. 缺 IR_CONTENT 大字段存储策略**

BASE_IR_VERSION.F_IR_CONTENT 是 NVARCHAR(MAX)，IR 完整快照可能 100KB+。SQL Server NVARCHAR(MAX) 默认存储在行内（in-row），超过 8KB 才溢出到 LOB。**建议强制 LOB 存储 + 启用表压缩**：
```sql
EXEC sp_tableoption 'BASE_IR_VERSION', 'large value types out of row', 1;
ALTER TABLE BASE_IR_VERSION REBUILD WITH (DATA_COMPRESSION = PAGE);
```
