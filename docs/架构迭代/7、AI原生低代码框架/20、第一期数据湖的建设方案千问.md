# JNPF 企业管理系统 · AI-Oriented 数据中台核心架构设计

## 总体纲要（先总）

------

### 第一部分：核心概念对齐——我们必须先回答"是什么"和"为什么"

在动手写任何一行代码之前，所有专家和架构师必须对以下 **5 个核心概念** 达成完全一致的认知。这是消除理解偏差和歧义的基础。

------

#### 概念 1：我们说的"数据中台"到底是什么？

> **定义：数据中台 ≠ 数据仓库 ≠ 数据湖 ≠ BI 报表平台**

| 概念                     | 本质                                                         | 面向                    | 核心能力                               |
| ------------------------ | ------------------------------------------------------------ | ----------------------- | -------------------------------------- |
| **数据仓库**             | 面向分析的结构化数据存储                                     | BI 分析师               | SQL 查询、OLAP 多维分析                |
| **数据湖**               | 原始数据的全量存储（结构化+非结构化）                        | 数据工程师/算法工程师   | 海量存储、批流计算                     |
| **数据中台**             | **将数据转化为可复用的业务能力的组织机制和技术平台**         | **业务人员 + AI Agent** | **数据服务化、指标标准化、语义统一化** |
| **AI-Oriented 数据中台** | 在数据中台之上，增加 **语义层（Semantic Layer）** 和 **指标字典（Metrics Store）**，使 AI 大模型能"听懂业务语言、安全查询数据、输出可信结论" | **AI Agent + 业务人员** | NL→Semantic→SQL、口径共识、安全沙箱    |

**我们的定位：** 我们要建的，不是传统意义上动辄投入千万、耗时一年的"重型数据中台"，而是一个 **"轻量级、AI 原生、语义驱动"** 的数据服务平台。

**一句话总结：**

> **数据中台的本质是"让数据说业务语言"，AI 数据中台的本质是"让 AI 也能听懂这门语言"。**

------

#### 概念 2：为什么"语义层（Semantic Layer）"是核心中的核心？

2025-2026 年，行业已经形成了一个铁律：

> **NL→SQL（自然语言直接生成 SQL）的 PoC 项目，超过 70% 死在了从 PoC 到生产的路上。**
> **活下来的那 30%，几乎全部采用了 NL→Semantic→SQL（语义层驱动）架构。**

行业参考：

- **dbt Semantic Layer**：2024-2026 年持续将 MetricFlow + Semantic Graph 推为统一语义层标准
- **美团 BI**：2026 年公开分享——以指标平台为核心的新一代 BI 架构，"定义即研发"，自动语义能力贯穿指标定义→模型关联→查询语义构建全流程
- **Databricks Genie**：要求领域专家维护 datasets、sample queries、text guidelines 和 knowledge store
- **Gartner ABI 报告**：2025 年将 Metrics Layer 列为 BI 常见能力的**第一位**

**核心问题：** 为什么 NL→SQL 直连会失败？

```
用户说: "上月良品率"

❌ NL→SQL 直连的问题：
  - LLM 不知道"良品率"的分子是什么、分母是什么
  - LLM 不知道"良品率"要排除试产工单和返工件
  - LLM 不知道"上月"应该用 F_CREATE_TIME 还是 F_COMPLETE_TIME
  - LLM 可能生成一个跨 5 张表 JOIN 的 SQL，把生产库打爆
  → 结果：数字看着像对的，但口径不对，业务人员不信

✅ NL→Semantic→SQL 的做法：
  - 语义层告诉 LLM："良品率"= pass_count / total_count * 100
  - 语义层告诉 LLM：要排除 F_ORDER_TYPE='试产' 的记录
  - 语义层告诉 LLM：时间维度统一用 F_COMPLETE_TIME
  - 语义层自动翻译为经过安全校验的 SQL
  → 结果：口径精确，业务人员认可，AI 可信
```

**语义层 = 企业业务口径的"法律文本"。** 它不是给程序员看的，它是给 AI 和业务人员看的——让两者对"什么叫良品率"达成完全一致的共识。

#### 概念 3：我们的"数据湖"不是 Hadoop/Spark 集群，而是"轻量湖仓"

| 维度       | 传统数据湖（Hadoop/Spark/MinIO）    | 我们的轻量湖仓（适合 JNPF 客户）                |
| ---------- | ----------------------------------- | ----------------------------------------------- |
| 规模       | PB 级，数百台服务器                 | GB ~ TB 级，单台或少数几台                      |
| 数据类型   | 结构化 + 非结构化（图片/视频/日志） | **以结构化为主**（MES/ERP/OA 业务数据）         |
| 计算引擎   | Spark/Flink/Presto                  | **SQL Server 内置引擎 + 轻量 ETL**              |
| 运维复杂度 | 极高（需专业大数据团队）            | **极低（DBA 即可运维）**                        |
| 成本       | 百万级起步                          | **几乎零额外成本**（复用客户已有的 SQL Server） |
| 适用客户   | 互联网/金融/电信                    | **制造业/建筑/政务/园区**（我们的客户画像）     |

**我们的定位：**

> **不引入 Hadoop/Spark 生态，基于客户已有的 SQL Server 构建"轻量级湖仓一体"——通过 CDC 数据同步 + 列式索引视图 + 分区表实现分析隔离，本质上是一个"分析型数据库（OLAP）"而非"原始数据湖"。**

------

#### 概念 4：指标字典（Metrics Store）——这才是真正的护城河

> **数据本身不值钱，"对数据的共识"才值钱。**

指标字典不是简单的"字段列表"，它是企业**业务知识的结构化沉淀**：

```
┌─────────────────────────────────────────────────────────┐
│                  指标字典的本质                            │
│                                                          │
│  "良品率" 不是一个数据库字段                               │
│  "良品率" 是一个业务共识：                                  │
│                                                          │
│  ① 计算公式：合格数 / (总数 - 试产数 - 返工数) × 100      │
│  ② 适用维度：车间 / 产线 / 班组 / 产品 / 时间              │
│  ③ 数据源表：MES_QUALITY_RECORD + MES_WORK_ORDER          │
│  ④ 过滤条件：F_ORDER_TYPE NOT IN ('试产','实验')          │
│  ⑤ 时间口径：按 F_COMPLETE_TIME（完成时间），非创建时间    │
│  ⑥ 达标标准：≥95% 优秀，90-95% 警告，<90% 异常            │
│  ⑦ 业务解读：连续 3 天 <90% 需触发设备巡检流程             │
│                                                          │
│  以上 7 条信息 = 企业独有的业务知识                         │
│  云 SaaS 永远不知道这些 → 这就是护城河                      │
└─────────────────────────────────────────────────────────┘
```

**关键认知：**

- **L1 数据源层**：客户已有的业务系统，我们不动它们
- **L2 分析存储层**：从生产库隔离出来的分析数据库，保护生产环境
- **L3 安全网关层**：所有 AI 查询必须经过的安全屏障
- **L4 语义层**：**核心护城河**——让 AI 懂业务语言
- **L5 数据消费层**：AI Agent、报表、工作台、大屏等消费方

> **五层架构，每一层解决什么问题、边界在哪里，所有架构师必须完全对齐。**

## 第二部分：技术选型——结合 JNPF 平台选择最合适的组件（后分）

------

### 选型原则

在选型之前，我们必须确立 **4 个不可动摇的选型原则**：

| 原则                         | 说明                                           | 否决项                               |
| ---------------------------- | ---------------------------------------------- | ------------------------------------ |
| **① 客户零额外基础设施成本** | 复用客户已有的 SQL Server + Windows Server     | 不引入 Hadoop/Spark/Kafka 等重型组件 |
| **② 团队零新技术栈学习成本** | 全部基于 .NET 8 + SQL Server + SqlSugar 技术栈 | 不引入 Python 大数据生态（除非必要） |
| **③ 4 周内可见 MVP**         | 每个组件都必须能在 4 周内产出最小可用版本      | 不做"先花 3 个月搭基建"的方案        |
| **④ 渐进式扩展能力**         | 初期轻量，但架构不能堵死未来扩展的路           | 不做"写死在代码里"的方案             |

------

### 各层技术选型详表

#### L1 数据源层：连接与采集

| 组件         | 选型                                      | 理由                                               |
| ------------ | ----------------------------------------- | -------------------------------------------------- |
| 数据库连接器 | **SqlSugar**（已有）                      | JNPF 现有 ORM，支持多租户、多数据库                |
| CDC 数据同步 | **SQL Server CDC（Change Data Capture）** | SQL Server 原生功能，零额外成本，实时捕获变更      |
| 备用同步方案 | **SqlSugar + 定时任务**（增量同步）       | 对于不支持 CDC 的旧版 SQL Server，用时间戳增量同步 |
| API 数据源   | **HttpClient + JNPF 定时任务引擎**        | 对于 IoT/API 数据源，定时拉取写入分析库            |
| 文件数据源   | **Excel/CSV 导入**（JNPF 已有）           | 复用现有导入功能                                   |

#### L2 分析存储层：隔离与优化

| 组件         | 选型                                              | 理由                                                         |
| ------------ | ------------------------------------------------- | ------------------------------------------------------------ |
| 分析数据库   | **SQL Server 同实例独立数据库 `MES_ANALYTICS`**   | 零额外成本，DBA 熟悉，权限隔离简单                           |
| 数据同步引擎 | **SQL Server CDC + SqlSugar 增量同步服务**        | CDC 处理高频变更表，增量同步处理低频表                       |
| 预聚合       | **SQL Server 索引视图（Indexed Views）**          | SQL Server 原生功能，自动维护聚合，查询性能提升 10-100 倍    |
| 分区表       | **SQL Server Table Partitioning**                 | 按时间分区历史数据，提升大表查询性能                         |
| 列式索引     | **SQL Server Columnstore Index**                  | 对分析型查询（SUM/AVG/COUNT）性能提升 10-50 倍               |
| 向量存储     | **SQL Server 2025 Vector Support 或 轻量 Milvus** | 用于 Schema RAG 的向量检索；如果客户是 SQL Server 2025，可直接用内置向量功能 |

#### L3 安全网关层：防护与审计

| 组件         | 选型                                          | 理由                                           |
| ------------ | --------------------------------------------- | ---------------------------------------------- |
| SQL 安全校验 | **自研 `SqlSafetyValidator`（.NET）**         | 基于 SQL 语法树分析，白名单模式，只允许 SELECT |
| 行级权限     | **JNPF `ITenantFilter` 扩展**                 | 复用现有多租户过滤机制，自动注入 WHERE 条件    |
| 查询资源限制 | **SQL Server `RESOURCE_GOVERNOR` + 连接超时** | 限制 AI 查询的 CPU/内存使用，超时自动 kill     |
| 审计日志     | **`BASE_AI_QUERY_LOG` 表 + 异步写入**         | 记录每次 AI 查询的 SQL、耗时、结果行数、用户   |

#### L4 语义层：核心护城河（自研）

| 组件             | 选型                                             | 理由                                                         |
| ---------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| 元数据管理       | **自研 `MetadataRegistry`（.NET + SQL Server）** | 基于 `BASE_META_ENTITY` / `BASE_META_FIELD` 表，提供 CRUD API |
| 指标字典         | **自研 `MetricsStore`（.NET + SQL Server）**     | 基于 `BASE_METRIC_DEFINITION` 表，管理指标口径               |
| 维度模型         | **自研 `DimensionModel`（.NET）**                | 基于 `BASE_DIMENSION_DEFINITION` 表                          |
| 语义关系图谱     | **自研 `SemanticGraph`（.NET 内存图结构）**      | 表关系、字段同义词、指标关联——全部在内存中构建，查询极快     |
| Schema RAG 检索  | **Embedding + 向量检索**                         | 将元数据向量化，根据用户问题动态检索 Top-K 相关表/字段/指标  |
| MQL→SQL 翻译引擎 | **自研 `MqlTranslator`（.NET）**                 | 接收结构化语义查询，基于指标字典翻译为安全 SQL               |
| Embedding 模型   | **通义 text-embedding-v3 或 BGE-M3**             | 用于元数据和指标描述的向量化                                 |

#### L5 数据消费层：AI 接口

| 组件             | 选型                                    | 理由                                                         |
| ---------------- | --------------------------------------- | ------------------------------------------------------------ |
| data-mcp Server  | **自研 MCP Server（.NET）**             | 封装 3 个标准工具：`query_metrics` / `query_data` / `list_metrics` |
| NL→Semantic 解析 | **LLM（DeepSeek/通义）+ Schema RAG**    | LLM 理解用户意图，输出结构化 MQL                             |
| 结果解读         | **LLM + 指标字典的 `F_INTERPRETATION`** | LLM 基于数据结果 + 指标达标标准生成业务解读                  |
| 前端展示         | **JNPF Vue3 组件**                      | `AiDataInsightCard.vue` / `AiChartCard.vue`                  |

## 第三部分：构建方案——五层架构逐层施工详图

------

### 3.1 L1 数据源层：连接与采集（施工详图）

#### 3.1.1 要做什么

从客户现有的 MES/ERP/OA 等业务系统中，将数据"搬"到分析库中。核心原则：**只读不写、只同步不迁移**。

#### 3.1.2 数据同步策略矩阵

| 数据类型                          | 同步方式         | 同步频率     | 技术方案                                  |
| --------------------------------- | ---------------- | ------------ | ----------------------------------------- |
| 高频变更表（工单状态、设备状态）  | **CDC 实时同步** | 秒级~分钟级  | SQL Server CDC → 捕获变更 → 写入分析库    |
| 中频变更表（质检记录、报工记录）  | **增量同步**     | 每 5~15 分钟 | 按 `F_MODIFY_TIME` 增量查询 → 批量 Upsert |
| 低频变更表（产品目录、BOM、人员） | **全量同步**     | 每天凌晨     | 全表 Truncate + 全量导入                  |
| API 数据源（IoT 传感器）          | **定时拉取**     | 可配置       | HttpClient 调用 API → 写入分析库          |
| 手工数据（Excel 导入）            | **手动触发**     | 按需         | JNPF 导入功能 → 写入分析库                |

#### 3.1.3 需要新增的后端服务

| 服务                   | 职责                                               | 关键技术                                |
| ---------------------- | -------------------------------------------------- | --------------------------------------- |
| `DataSyncOrchestrator` | 同步编排器：管理所有同步任务的调度、监控、重试     | JNPF 定时任务引擎 + Quartz.NET          |
| `CdcConsumer`          | CDC 消费者：读取 SQL Server CDC 变更表，写入分析库 | `sys.fn_cdc_get_all_changes` + SqlSugar |
| `IncrementalSyncer`    | 增量同步器：按时间戳增量查询，批量 Upsert          | SqlSugar BulkCopy                       |
| `SyncMonitor`          | 同步监控：延迟告警、失败重试、数据一致性校验       | 内存指标 + 日志                         |

#### 3.1.4 需要新增的数据表

```sql
-- 同步任务配置表
DATA_SYNC_TASK (
  F_ID                     NVARCHAR(50) PRIMARY KEY,
  F_TENANT_ID              NVARCHAR(50),
  F_TASK_NAME              NVARCHAR(200),        -- 任务名称: "MES工单同步"
  F_SOURCE_DB              NVARCHAR(200),        -- 源数据库连接标识
  F_SOURCE_TABLE           NVARCHAR(200),        -- 源表: dbo.MES_WORK_ORDER
  F_TARGET_TABLE           NVARCHAR(200),        -- 目标表: dbo.DW_WORK_ORDER
  F_SYNC_MODE              NVARCHAR(20),         -- 'cdc' / 'incremental' / 'full' / 'api'
  F_SYNC_INTERVAL          INT,                  -- 同步间隔(秒), CDC 模式忽略
  F_INCREMENTAL_FIELD      NVARCHAR(100),        -- 增量同步的时间戳字段: F_MODIFY_TIME
  F_LAST_SYNC_TIME         DATETIME2,            -- 上次同步时间
  F_LAST_SYNC_STATUS       NVARCHAR(20),         -- 'success' / 'failed' / 'partial'
```

#### 3.2.3 预聚合索引视图（关键性能优化手段）

```sql
-- 示例：车间日产量预聚合视图
-- 这个视图由 SQL Server 自动维护，查询时直接命中，无需实时计算
CREATE VIEW VW_DAILY_WORKSHOP_OUTPUT
WITH SCHEMABINDING AS
SELECT
  F_TENANT_ID,
  F_WORKSHOP_ID,
  CAST(F_COMPLETE_TIME AS DATE) AS F_DATE,
  COUNT_BIG(*) AS F_TOTAL_COUNT,
  SUM(F_PASS_QTY) AS F_PASS_QTY,
  SUM(F_REWORK_QTY) AS F_REWORK_QTY,
  SUM(F_PLAN_QTY) AS F_PLAN_QTY
FROM dbo.DW_WORK_ORDER
WHERE F_ORDER_STATUS = 'completed'
  AND F_ORDER_TYPE NOT IN ('试产', '实验')
GROUP BY F_TENANT_ID, F_WORKSHOP_ID, CAST(F_COMPLETE_TIME AS DATE);

-- 创建唯一聚簇索引使其成为"索引视图"（物化视图）
CREATE UNIQUE CLUSTERED INDEX IX_VW_DAILY_OUTPUT
ON VW_DAILY_WORKSHOP_OUTPUT (F_TENANT_ID, F_WORKSHOP_ID, F_DATE);
```

#### 3.3.2 `DataQueryGateway` 核心设计

```

│                   DataQueryGateway 处理流程                    │
│                                                               │

│                                                               │
│  Step 6: 审计日志写入                                          │
│    ├── 记录: 用户ID / 原始SQL / 最终SQL / 耗时 / 行数         │
```

#### 3.4.4 组件 3：语义关系图谱（Semantic Graph）

**设计原理：** 在内存中构建一个图结构，节点是"表/字段/指标/维度"，边是"关联关系/包含关系/计算依赖"。

```typescript
// 语义图谱核心数据结构（.NET 实现为 C# class）

interface SemanticGraph {
  nodes: SemanticNode[];
  edges: SemanticEdge[];

  // 核心查询方法
  findRelatedEntities(question: string, topK: number): SemanticNode[];
  findMetricByName(nameOrSynonym: string): MetricNode | null;
  getQueryPlan(metric: MetricNode, dimensions: DimensionNode[]): QueryPlan;
}

interface SemanticNode {
  id: string;
  type: 'entity' | 'field' | 'metric' | 'dimension';
  name: string;
  businessName: string;
  description: string;
  synonyms: string[];
  embedding: number[];  // 向量表示
}

interface SemanticEdge {
  source: string;
  target: string;
  relation: 'contains' | 'references' | 'joins' | 'computes_from';
  joinCondition?: string;  // 如: "DW_WORK_ORDER.F_EQUIPMENT_ID = DW_EQUIPMENT.F_ID"
}
```

**图谱构建流程：**

1. 系统启动时，从 `BASE_META_*` + `BASE_METRIC_*` + `BASE_DIMENSION_*` 加载所有元数据
2. 根据 `F_RELATED_ENTITIES` 和 `F_FORMULA` 构建边
3. 对每个节点的 `name + businessName + description + synonyms` 生成 embedding
4. 缓存在内存中，元数据变更时触发增量更新

#### 3.4.5 组件 4：Schema RAG 检索引擎

**核心职责：** 用户说一句话 → 找到最相关的 3~5 张表 + 相关字段 + 相关指标 → 只把这些元数据注入 LLM Prompt。

```
用户输入: "上月一车间良品率"
          │
          ▼
   ┌─────────────────┐
   │ Embedding 生成   │  调用 Embedding 模型，生成用户问题的向量
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ 向量相似度检索   │  在语义图谱的所有节点中，找 Top-K 最相似的
   │                  │  命中: 指标"良品率"(0.92) + 维度"车间"(0.88)
   │                  │       + 表"DW_WORK_ORDER"(0.85)
   │                  │       + 表"DW_QUALITY_RECORD"(0.82)
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ 图谱扩展         │  从命中的节点出发，沿边扩展 1 跳
   │                  │  补充: DW_WORK_ORDER → DW_EQUIPMENT (通过设备ID关联)
   │                  │  补充: 良品率 → 可用维度: 车间/产线/班组/时间
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ 元数据裁剪       │  只保留相关字段（排除 AI_VISIBLE=0 的字段）
   │                  │  最终输出约 800~1500 Token 的元数据描述
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ 注入 LLM Prompt │  System Prompt 中只包含：
   │                  │  · 2~3 张表的字段描述
   │                  │  · 1~2 个指标的计算公式和口径说明
   │                  │  · 相关的维度信息
   │                  │  → Token 可控、注意力集中、准确率高
   └─────────────────┘
```

#### 3.4.6 组件 5：MQL 解析引擎（MQL→SQL Translator）

**MQL（Metrics Query Language）设计：**

```json
// MQL 示例：用户问"上月各车间良品率排名"
{
  "metrics": ["yield_rate"],
  "dimensions": ["workshop"],
  "timeRange": {
    "field": "F_COMPLETE_TIME",
    "start": "2026-05-01",
    "end": "2026-05-31"
  },
  "filters": [
    { "field": "F_ORDER_TYPE", "operator": "not_in", "values": ["试产", "实验"] }
  ],
  "orderBy": { "metric": "yield_rate", "direction": "desc" },
  "limit": 20
}
```

**翻译流程：**

```
MQL 输入
    │
    ▼
┌─────────────────┐
│ 1. 指标解析      │  从指标字典查找 yield_rate:
│                  │  → 类型: ratio
│                  │  → 分子: pass_count (SUM)
│                  │  → 分母: total_count (COUNT)
│                  │  → 基础表: DW_WORK_ORDER
└────────┬────────┘
         ▼
┌─────────────────┐
│ 2. 维度解析      │  从维度字典查找 workshop:
│                  │  → 来源字段: DW_WORK_ORDER.F_WORKSHOP_ID
│                  │  → 关联表: DW_WORKSHOP.F_NAME (用于显示名称)
└────────┬────────┘
         ▼
┌─────────────────┐
│ 3. SQL 组装      │  基于指标定义 + 维度定义 + 过滤条件 + 时间范围
│                  │  自动组装为安全 SQL:
│                  │
│                  │  SELECT ws.F_NAME AS 车间,
│                  │    SUM(wo.F_PASS_QTY)*100.0 /
│                  │    NULLIF(SUM(wo.F_COMPLETED_QTY), 0) AS 良品率
│                  │  FROM DW_WORK_ORDER wo
│                  │  INNER JOIN DW_WORKSHOP ws
│                  │    ON wo.F_WORKSHOP_ID = ws.F_ID
│                  │  WHERE wo.F_TENANT_ID = @TenantId
│                  │    AND wo.F_COMPLETE_TIME >= '2026-05-01'
│                  │    AND wo.F_COMPLETE_TIME < '2026-06-01'
│                  │    AND wo.F_ORDER_TYPE NOT IN ('试产','实验')
│                  │  GROUP BY ws.F_NAME
│                  │  ORDER BY 良品率 DESC
└────────┬────────┘
         ▼
┌─────────────────┐
│ 4. 交给安全网关  │  SQL 通过 DataQueryGateway 执行
│   (L3) 执行      │  → 安全校验 → 权限注入 → 资源限制 → 执行
└─────────────────┘
```

#### 3.4.7 验收标准

-  元数据管理界面可用，业务专家可在线标注表/字段的业务含义
-  指标字典管理界面可用，至少注册 30 个 MES 核心指标
-  维度模型管理界面可用，至少注册 8 个核心分析维度
-  Schema RAG 检索准确率 ≥ 85%（用 50 个测试问题评测）
-  MQL→SQL 翻译引擎支持 5 种指标类型（basic/derived/ratio/cumulative/conversion）
-  端到端：自然语言 → Schema RAG → LLM 生成 MQL → 翻译 SQL → 执行 → 返回结果，准确率 ≥ 80%
