## 第三块：五阶段流水线

**一句话：把自然语言需求一步步变成可运行的应用。**

这是系统的**核心主干**，用户感知到的就是一个分阶段推进的进度条：

| 阶段           | 干什么                                                    | 谁干的                                               | 文档锚点                 |
| -------------- | --------------------------------------------------------- | ---------------------------------------------------- | ------------------------ |
| **1 需求分析** | 用户说模糊想法 → AI 追问 → 出需求文档 + 领域模型          | RequirementAnalystAgent                              | F-9.4；§3.1 Stage1       |
| **2 架构设计** | 基于需求 → AI 出架构方案（模块、数据库、API）→ 用户确认   | ArchitectAgent                                       | F-9.5；§3.1 Stage2       |
| **3 总体设计** | 多个子 Agent **并行**出数据库/页面/工作流/大屏/小程序设计 | OrchestratorAgent 调度 DB/UI/Flow/Dashboard 子 Agent | F-9.6 F-9.7；§3.1 Stage3 |
| **4 自动开发** | IR → 编译 → 部署到沙箱 → 自动测试                         | Stage4DevEngineService                               | §3.1 Stage4              |
| **5 交付验收** | 沙箱 URL + 增量修改 + ZIP 导出                            | 交付引擎                                             | §3.1 Stage5              |

用户交互方式：
- 每阶段完成后**需要用户确认**才推进下一阶段
- AI 对话是富媒体的（不是纯文本聊天），可预览 IR、查看文档
- SSE 流式输出，实时看到 AI 在思考什么

## 第十一块：自博弈训练引擎（Foundry 侧）

**一句话：AI 自己当刁钻客户、自己搭系统、自己测试，自动进化。**

### 四个角色构成闭环：

```
攻击者 ──生成刁钻需求──→ 构建者 ──自动搭系统──→ 判官 ──测试验证──→ 蒸馏师
  ↑                                                                    │
  └──────────────── 学习失败模式 ←─────────────────────────────────────────┘
```

| 角色           | 干什么                                                       | 文档锚点             |
| -------------- | ------------------------------------------------------------ | -------------------- |
| **需求攻击者** | 从知识库学业务，创造性生成刁钻场景（矛盾需求、极端边缘案例、故障场景），难度 1-10 分级 | F-10.2 AttackerAgent |
| **系统构建者** | 接收攻击者的需求 → 自动调四个 Agent → IR → 编译 → 部署到沙箱，全自动 | F-10.3 SystemBuilder |
| **对抗性判官** | 根据攻击意图生成测试用例 → 执行 → AI 做业务语义验证（不是简单的 HTTP 断言）→ 分析失败原因 → 给修复建议 | F-10.4 JudgeAgent    |
| **知识蒸馏师** | 观察人类修改/测试结果 → 按奖励值分级处理（低奖励只存池、高奖励生 candidate、超高奖励生 verified）→ 因果图挖掘 | §2.1 蒸馏师闭环      |

### 自博弈引擎本身：

| 子功能                                       | 文档锚点                    |
| -------------------------------------------- | --------------------------- |
| 自动循环（攻击→构建→测试→修复→沉淀，循环跑） | F-10.5 SelfPlayEngine.run() |
| 难度递增（通过率 >80% → 自动提升难度）       | F-10.5 difficulty 递增逻辑  |
| 沙箱自动创建/销毁（每轮结束清理）            | F-10.5 destroyAll()         |
| 统计报告（通过率、修复缺陷数、新模式数）     | F-10.5 SelfPlayReport       |

### 深度业务测试：

| 子功能                                            | 文档锚点                                                     |
| ------------------------------------------------- | ------------------------------------------------------------ |
| 不是简单 API 测试，而是语义级验证                 | F-10.6 "1000 次插单测试中 VIP 订单完成时间必须始终早于普通订单" |
| 覆盖四类：功能 / 边界 / 并发 / 安全               | F-10.4 TestCase.type                                         |
| 业务语义断言（AI 验证"这个结果从业务角度对不对"） | F-10.4 semanticAssertions                                    |

这就是你们系统里**真真实实存在的全部功能**，一个不多一个不少。菜单怎么排、叫什么名字是后面的事，先把这 13 块功能本身做好、做完整才是根本。
