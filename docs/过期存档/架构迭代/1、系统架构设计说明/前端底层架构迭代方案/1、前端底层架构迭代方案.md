## 零、认知跃迁：从"修桥"到"造船"

之前的方案（包括我自己签发的）有一个根本性的认知局限——**都在优化现有的架构，而不是重新定义架构应该是什么样的。**

```
过去的认知层次：

Level 1：修补（给 eval 加白名单）
Level 2：替换（用安全表达式引擎替换 eval）
Level 3：重建（用 Schema 渲染引擎重建运行时）  ← 我的方案停在了这里
Level 4：重生（运行时 + 代码生成双轨制）        ← 这才是真正的方向
Level 5：超越（AI 驱动的代码生成 + 反向回写）   ← 终极目标

Level 3 解决的是"平台跑得更好"
Level 4 解决的是"平台活得更久"
Level 5 解决的是"平台不可替代"
```

**OutSystems / Mendix / Power Platform 为什么稳坐企业市场？** 不是因为它们的运行时有多好，而是因为用户用低代码配置，生成的是真代码——可以脱离平台运行、可以本地调试、可以二次开发、可以回写到平台。**这才是"用户黏性"的真正来源——不是锁定，而是双向自由。**

JNPF 必须走到 Level 4。

## 一、终极架构：双轨制平台

### 1.1 核心理念

```
一条配置，两个出口：

  用户配置（JSON Schema / 可视化设计器）
         │
         ▼
  ┌──────────────────────┐
  │   IR（中间表示）      │  ← 框架无关的抽象层
  │   这是真正的"心脏"    │
  └──────────┬───────────┘
         │
    ┌────┴────┐
    ▼         ▼
┌────────┐ ┌────────────┐
│ 运行时  │ │ 代码生成器  │
│ 渲染模式 │ │ 源码模式    │
└────────┘ └────────────┘
    │         │
    ▼         ▼
 在线预览   下载源码
 (平台内)   (脱离平台运行)
    │         │
    └────┬────┘
         │
         ▼
   ┌──────────────┐
   │  反向回写     │ ← 用户修改源码后同步回平台
   │  (双向护城河) │
   └──────────────┘
```

**双轨制的商业价值：**

```
对客户：
  "我用 JNPF 配置了一个管理系统，不满意的地方直接改源码，
   改完还能同步回平台继续用低代码维护。"
  → 这是 OutSystems 级别的体验

对 JNPF：
  "客户离不开我们，不是因为被锁死，
   而是因为双向同步的效率远高于从零开发。"
  → 这是真正的护城河
```

### 1.2 IR（中间表示）——双轨制的灵魂

```
IR 不是 JSON Schema（那是配置格式）
IR 不是 Vue SFC（那是产物格式）
IR 是两者之间的"中间语言"——框架无关、可序列化、可分析、可编译

IR 设计原则：
  1. 框架无关（不绑定 Vue/React/UniApp）
  2. 可逆（JSON Schema → IR → JSON Schema）
  3. 可编译（IR → Vue SFC / IR → uvue / IR → React）
  4. 可分析（可以静态检查 IR 的正确性）
  5. 可比较（两个 IR 可以 diff，用于反向回写）
```

**IR 核心类型定义：**

```typescript
// ====== 项目级 IR ======

interface IRProject {
  type: 'form' | 'table' | 'dashboard' | 'app-page';
  version: '2.0';
  name: string;
  description: string;
  metadata: IRMetadata;
  components: IRComponent[];
  dataSources: IRDataSource[];
  actions: IRAction[];
  styles: IRStyle[];
}

interface IRMetadata {
  author: string;
  createdAt: string;
  updatedAt: string;
  tags: string[];
  targetPlatforms: ('web' | 'h5' | 'weixin' | 'app')[];
}

// ====== 组件级 IR ======

interface IRComponent {
  id: string;
  type: string;                    // 组件类型（从注册表解析）
  category: 'form' | 'data' | 'layout' | 'chart' | 'custom';
  props: Record<string, IRProp>;
  slots: Record<string, IRSlot>;
  events: IREvent[];
  children: IRComponent[];
  
  // 数据绑定
  dataBinding?: IRDataBinding;
  
  // 逻辑控制
  visibility?: IRExpression;       // 显隐表达式
  disabled?: IRExpression;         // 禁用表达式
  computed?: Record<string, IRExpression>;  // 计算属性
  
  // 样式
  style?: IRStyle;
  className?: string;
}

interface IRProp {
  value: unknown;
  type: 'static' | 'expression' | 'binding';
}

// ====== 表达式 IR ======

interface IRExpression {
  type: 'safe-expr';
  source: string;                  // 原始表达式字符串
  deps: string[];                  // 依赖追踪
  compiled?: CompiledExpr;         // 预编译结果
}

// ====== 数据源 IR ======

interface IRDataSource {
  id: string;
  type: 'api' | 'websocket' | 'sse' | 'polling' | 'static' | 'computed';
  config: IRDataSourceConfig;
  transformer?: IRExpression;      // 数据转换表达式
  refreshStrategy?: {
    type: 'manual' | 'interval' | 'realtime';
    interval?: number;             // 轮询间隔(ms)
    reconnect?: boolean;           // WebSocket 重连
  };
}

// ====== 事件 IR ======

interface IREvent {
  trigger: 'click' | 'change' | 'submit' | 'mounted' | 'destroyed';
  action: IRAction;
}

interface IRAction {
  type: 'navigate' | 'api-call' | 'set-state' | 'show-message' 
      | 'emit-event' | 'run-expression' | 'custom';
  config: Record<string, unknown>;
}

// ====== 样式 IR ======

interface IRStyle {
  layout?: 'flex' | 'grid' | 'absolute';
  responsive?: Record<string, IRStyle>;  // 响应式断点
  tokens?: Record<string, string>;       // 设计 Token 引用
}
```

**为什么 IR 这么重要？**

```
没有 IR（当前状态）：
  JSON Schema ──直接渲染──→ DOM
  JSON Schema ──Velocity──→ 粗糙的源码（85% 重复）

有了 IR：
  JSON Schema ──解析──→ IR ──编译──→ 运行时渲染（快速预览）
                      ↓
                      IR ──生成──→ Vue SFC 源码（可独立运行）
                      ↓
                      IR ──生成──→ uvue 源码（UniApp）
                      ↓
                      IR ──生成──→ React JSX（未来扩展）
                      ↓
                      IR ──diff──→ 与用户的修改合并（反向回写）

IR 是一次设计，终身受益的架构决策。
```

### 2.4 反向回写——双向护城河

```
这是双轨制最核心的能力，也是同行无人做到的能力。

场景：
  1. 用户用 JNPF 配置了一个表单 → 下载源码
  2. 在 VS Code 中修改了源码（添加了自定义校验逻辑）
  3. 想把修改同步回 JNPF 平台

反向回写的技术路径：

Step 1：AST Diff
  将用户修改后的源码解析为 AST
  与原始生成的 AST 对比
  识别差异部分

Step 2：差异分类
  差异分为三类：
  a. 可回写的差异（改了字段名、改了验证规则、改了样式）
     → 转换为 IR 变更 → 更新 JSON Schema
  
  b. 不可回写的差异（添加了全新的自定义函数）
     → 标记为"自定义代码块" → 保留在 JSON Schema 的 ext 字段中
  
  c. 冲突的差异（删除了平台生成的代码）
     → 标记为冲突 → 让用户手动选择保留哪边

Step 3：IR 合并
  将用户的修改合并到 IR 中
  生成新的 JSON Schema
  平台可以继续用低代码方式编辑这个已修改的表单

Step 4：增量同步
  下次用户在平台修改了某个字段
  只更新该字段的 IR，不影响用户的自定义代码

反向回写的架构保障：

  IR 是双向可逆的：
    正向：JSON Schema → IR → Vue SFC
    反向：Vue SFC → AST → Diff → IR Diff → JSON Schema Diff → 合并
  
  关键技术：
    recast：保留原始代码格式的 AST 操作（用户修改的代码不会被格式化掉）
    @vue/compiler-sfc：解析 .vue 文件
    ast-grep：高效的 AST 搜索
    JSON Patch：JSON Schema 的增量更新
```

## 三、数字大屏——专属引擎方案

### 3.1 大屏≠表单——需要独立的引擎

```
大屏和表单是完全不同的渲染域：

表单：纵向布局、字段驱动、用户交互密集
大屏：绝对定位、数据驱动、视觉效果密集

把它们放在同一个渲染引擎里 → 两边都做不好。
必须拆分为独立的引擎。
```

### 3.2 大屏专属组件技术选型

#### 第一梯队：核心替换（低风险，高收益）

```
当前问题 → 推荐方案 → 替换难度 → 收益

ECharts 散装配置（eval 拼 option）
  → vue-echarts + ECharts 5（TypeScript 类型安全的 option）
  → ⭐ 低（API 一致，直接替换）
  → 消除 eval + 类型安全

自写 div + CSS 边框
  → @jiaminghi/data-view（DataV 风格的科技感边框和装饰）
  → ⭐ 低（复制即用）
  → 瞬间提升大屏科技感

requestAnimationFrame 自写数字滚动
  → @vueuse/core useTransition
  → ⭐ 低（10 行代码）
  → 优雅的数字滚动效果

setInterval 轮询
  → @vueuse/core useWebSocket + 订阅模式
  → ⭐⭐ 中（需要重构轮询逻辑）
  → 实时数据 + 节省带宽

重建 DOM 主题切换
  → CSS Variables + 设计 Token
  → ⭐ 低（改造样式系统）
  → 瞬间切换主题，零闪烁

自算 scale 缩放
  → v-scale-screen（Vue 3 版）
  → ⭐ 低（替换缩放组件）
  → 开箱即用的自适应方案

不统一的动效
  → @vueuse/motion
  → ⭐ 低（统一动效 API）
  → 滚动入场、数字跳动、元素过渡
```

#### 第二梯队：3D 杀手锏（差异化核心）

```
这是大屏从"好看"到"震撼"的关键。

TresJS（Three.js 的 Vue 封装）：
  - 官网：https://tresjs.org
  - API 是 Vue 风格（不是 Three.js 的命令式 API）
  - 可以在 Vue 组件中直接使用 3D 场景
  - 支持 GLSL 着色器（高级视觉效果）

JNPF 大屏可提供的 3D 能力：

  3D 地球：
    <TresCanvas>
      <TresMesh>
        <TresSphereGeometry :args="[1, 64, 64]" />
        <TresMeshStandardMaterial :map="earthTexture" />
      </TresMesh>
      <!-- 数据飞线 -->
      <FlyLine v-for="line in flyLines" :from="line.from" :to="line.to" />
      <!-- 城市光点 -->
      <CityPoint v-for="city in cities" :position="city.position" :value="city.value" />
    </TresCanvas>

  3D 柱状图：
    <TresCanvas>
      <TresGroup v-for="(item, i) in data">
        <TresMesh :position="[i * gap, item.height / 2, 0]">
          <TresBoxGeometry :args="[barWidth, item.height, barDepth]" />
          <TresMeshStandardMaterial :color="item.color" />
        </TresMesh>
      </TresGroup>
    </TresCanvas>

  粒子效果：
    <TresCanvas>
      <TresPoints>
        <TresBufferGeometry>
          <TresBufferAttribute :args="[positions, 3]" />
        </TresBufferGeometry>
        <TresPointsMaterial :size="0.02" :color="'#1890ff'" />
      </TresPoints>
    </TresCanvas>

引入策略：
  Phase 1：3D 地球（最直观的视觉冲击）
  Phase 2：3D 柱状图/饼图（数据可视化的 3D 版本）
  Phase 3：粒子效果/飞线（装饰性动效）
  Phase 4：自定义 3D 模型（如建筑/设备的 3D 展示）
```

#### 第三梯队：性能增强（大数据量场景）

```
@unovis/vue：
  - 性能比 ECharts 高 3-5 倍（大数据点场景）
  - Vue 3 原生支持（无 wrapper）
  - 体积小（按需引入）
  - 特别适合：时序数据、地理数据、关系图

使用策略：
  数据点 < 1000、图表类型标准 → 继续用 ECharts（保守）
  数据点 > 5000、追求性能      → 切换到 @unovis/vue（性能）
  需要 3D 效果                 → 使用 TresJS（差异化）
```

## 四、UniApp——真正的跨端方案

### 4.1 当前问题的根本原因

```
JNPF app 的根本问题不是"UI 库选得不好"，
而是"架构假设就是错的"——

错误假设：Web 组件可以运行在 UniApp 中
现实：小程序的 JSCore 没有 DOM、没有 eval、没有 window

所以当前架构在小程序端"能跑通就是奇迹"。
```

### 4.2 UniApp 技术选型全面升级

#### 基础框架：uni-app x（uvue + uts）

```
uni-app x 是 DCloud 2023-2025 年的新物种：

核心变化：
  uvue → 编译到原生视图（Swift/Kotlin/小程序原生组件）
  uts  → TypeScript 强类型语言，编译到各端原生代码

对 JNPF 的战略价值：
  1. 性能提升 2-5 倍（逻辑层不经过 JSCore 中转）
  2. Web 端 Vue 组件可零成本编译成原生 App
  3. 小程序端使用原生组件（不再依赖 Web 模拟）
  4. TypeScript 原生支持（不是 .d.ts 桥接）

迁移策略：
  新模块/新功能 → 使用 uni-app x（uvue + uts）
  老模块/已稳定 → 保持传统 uniapp，逐步迁移
  不强制一次性切换
```

#### 请求库：Alova

```
Alova 是请求策略的代际升级——不是又一个 axios 替代品，
而是一个"请求策略引擎"。

内置 uniapp 适配器（@alova/adapter-uniapp）

对 JNPF 的直接收益：

  1. 自动 Loading（不需要手动管理 loading 状态）
  2. 自动缓存（stale-while-revalidate 策略）
  3. 自动重试（网络抖动自动恢复）
  4. 内置轮询策略（替代 setInterval 手写轮询）
  5. 内置离线队列（弱网/断网不丢请求）
  6. 内置 Token 刷新（自动排队，防并发刷新）

代码量变化：
  当前：request.ts（100+ 行） + 50+ 个 API 文件
  之后：request.ts（20 行） + 50+ 个 API 文件（声明式）
  
  每个 API 文件减少 30-50% 代码
```

#### UI 组件库：wot-design-uni

```
wot-design-uni 是目前 UniApp 生态中质量最高的 Vue 3 组件库：

特点：
  - 60+ 组件（覆盖常用场景）
  - Vue 3 Composition API
  - TypeScript 原生支持
  - 支持 H5 + 微信小程序 + App
  - 主题定制（CSS 变量）
  - 国际化

替换当前的自写组件 + 部分 vk-uview-ui
```

#### 原子化 CSS：UnoCSS

```
替代散装 SCSS：
  当前：每个页面一堆 .scss 文件
  之后：UnoCSS 原子类 + 少量自定义样式

优势：
  - 按需生成（只生成使用的类）
  - 体积极小（比 Tailwind 小 100 倍）
  - Vite 集成（HMR 极快）
  - 预设规则可自定义（适配 JNPF 设计规范）
```

### 4.3 UniApp 代码生成的特殊处理

```
UniApp 代码生成不能简单复用 Web 的模板——
必须处理以下差异：

1. 路由系统差异
   Web：Vue Router（动态注册）
   UniApp：pages.json（静态配置）
   
   生成器需要：
     从 IR 的路由定义 → 生成 pages.json 的 pages 数组
     同时生成 TabBar 配置（如有）

2. 组件差异
   Web：<div> <span> <input>
   UniApp：<view> <text> <uni-easyinput>
   
   生成器需要：
     组件映射层（IR Component Type → 各端组件名）
     同一个 IR type "input:text"
     → Web 端生成 <el-input>
     → UniApp 端生成 <uni-easyinput>

3. 平台条件编译
   某些组件在特定平台不可用（如 WebGL 在小程序受限）
   
   生成器需要：
     根据目标平台过滤 IR 中的组件
     或生成条件编译代码 <!-- #ifdef H5 -->

4. 分包策略
   微信小程序主包 2MB 限制
   
   生成器需要：
     分析页面引用关系
     自动拆分分包
     生成 subpackages 配置

5. 样式差异
   Web：CSS Modules / SCSS / UnoCSS
   UniApp：rpx 单位 / 原子化 CSS
   
   生成器需要：
     样式单位转换（px → rpx）
     适配各端的样式方案
```

## 七、最终对照表

```
维度              | 之前的方案（运行时）          | 新方案（双轨制）
───────────────── | ──────────────────────────── | ────────────────────────────────
核心理念          | 让平台跑得更好               | 让平台活得更久
用户黏性来源      | 平台锁定                     | 双向自由（逃离通道=护城河）
表单              | Schema 渲染引擎              | IR + 渲染引擎 + 代码生成器
大屏              | ECharts 统一                 | ECharts + TresJS 3D + DataV 装饰
UniApp            | 通用方案                     | uni-app x + Alova + wot + UnoCSS
代码生成          | Velocity 模板（85%重复）     | IR + EJS + AST 增强（零重复）
产物质量          | 粗糙、不可维护               | 可读可改可独立运行的工程级代码
调试体验          | 只能改配置                   | IDE 全功能断点调试
SEO / 分享        | 动态渲染全废                 | 生成静态页面
复杂定制          | 平台不支持就死               | 生成源码后自由改造
性能天花板        | JSON 运行时解析               | 生成代码=原生性能
平台与用户关系    | 平台是牢笼                   | 平台是阶梯（上去容易下来也容易）
```
