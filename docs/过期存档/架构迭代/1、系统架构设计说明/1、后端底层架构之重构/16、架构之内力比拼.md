## 维度 1：AOT 编译就绪度

### 当前状态推断

Furion 框架大量使用了以下运行时反射特性：

```csharp
// Furion 典型写法——运行时程序集扫描
App.EffectiveTypes  // 扫描所有加载的程序集，提取有效类型
    .Where(u => u.IsInterface && typeof(IDynamicApiController).IsAssignableFrom(u))
    .ToList();

// 运行时动态创建 Controller
builder.Services.AddDynamicApiControllers();

// 运行时获取特性标注
var attrs = method.GetCustomAttributes<ApiDescriptionSettingsAttribute>();
```

**这在 .NET 8 AOT 编译下会大面积失败。**

AOT 编译在编译期就把 IL 代码编译为原生代码，运行时没有 JIT，没有完整的反射元数据。以下操作在 AOT 下不可靠或直接崩溃：

| 反射操作                              | AOT 兼容性                          | Furion 中的使用频率 |
| ------------------------------------- | ----------------------------------- | ------------------- |
| `typeof(T).IsAssignableFrom()`        | ⚠️ 部分支持（需裁剪提示）            | 极高                |
| `Assembly.GetTypes()` / 程序集扫描    | ❌ 大概率失败                        | 极高                |
| `Activator.CreateInstance()` 动态创建 | ❌ 需 `[DynamicallyAccessedMembers]` | 高                  |
| `Emit` 动态生成代码                   | ❌ 完全不支持                        | 中                  |
| `Expression Tree` 编译                | ⚠️ 部分场景失败                      | 中                  |
| `JsonSerializer` 反射序列化           | ⚠️ 需 Source Generator               | 高                  |

### ABP VNext 怎么做的

```csharp
// ABP VNext 从 v7 开始逐步适配 AOT
// 核心策略：用 Source Generator 替代运行时反射

// 1. 依赖注入注册——用编译期代码生成替代运行时扫描
// ABP 的 Auto API Controllers 虽然也用了动态注册
// 但 ABP 8.0 开始提供 AOT 友好的注册方式：
[Dependency(ServiceLifetime.Transient)]  // 编译期可发现
public class MyService : IMyService { }

// 2. AutoMapper → Mapster 或手写映射（AOT 友好）
// ABP 从 v7 推荐用 ObjectMapping.SourceGenerator

// 3. JSON 序列化——System.Text.Json Source Generator
[JsonSerializable(typeof(MyDto))]
[JsonSerializable(typeof(PagedResultDto<MyDto>))]
internal partial class MyJsonContext : JsonSerializerContext { }

// 4. Minimal API 替代动态 Controller（天然 AOT 友好）
app.MapGet("/api/customer/{id}", async (Guid id, ICustomerService service) =>
{
    return await service.GetAsync(id);
});
```

### MASA Framework 怎么做的

```csharp
// MASA Framework 从设计之初就考虑了云原生和 AOT

// 1. 最小化反射——依赖编译期泛型特化而非运行时类型发现
services.AddScoped(typeof(IRepository<>), typeof(Repository<>));

// 2. 使用 Dapr Sidecar 处理服务通信，减少应用层反射
// gRPC 通信通过 Protobuf（编译期生成代码），完全 AOT 安全

// 3. CQRS 模式中，Command/Handler 通过接口约束而非运行时扫描注册
public class CreateOrderCommandHandler : ICommandHandler<CreateOrderCommand>
{
    // Handler 通过泛型接口在编译期确定，不需要运行时扫描
}
```

### JNPF 应该怎么改

```
AOT 就绪度改造路线图：

P0（阻塞性）:
├── 审计所有 Assembly.GetTypes() / AppDomain.CurrentDomain.GetAssemblies() 调用
│   → 列表化，逐一评估 AOT 兼容性
├── 审计所有 Activator.CreateInstance() 调用
│   → 改为 DI 容器解析或泛型工厂
└── 审计所有动态 Emit / Expression Tree 调用
    → 改为 Source Generator 预生成

P1（重要）:
├── JSON 序列化迁移到 System.Text.Json + Source Generator
│   替代 Newtonsoft.Json（如果还在用）
├── AutoMapper 替换为 Mapster.SourceGenerator 或手写映射
└── 为 SqlSugar 确认 AOT 兼容性（SqlSugar 的 AOT 支持情况需要验证）

P2（增强）:
├── 核心路径用 BenchmarkDotNet 验证 AOT 前后性能差异
└── 发布 AOT 编译的生产镜像（容器体积可减小 50%+，启动速度提升 5-10x）
```

**为什么这很重要：** AOT 不仅是性能优化，它是架构健康度的"压力测试"。如果你的代码能在 AOT 下正常工作，说明你没有滥用运行时反射——这意味着更可预测的性能、更小的容器镜像、更快的冷启动。反过来，如果 AOT 编译大面积失败，说明架构中隐藏了过多的"运行时魔法"，这些魔法在出了问题时极难调试。

## 维度 2：依赖注入容器深度运用

### 当前状态推断

Furion 对 DI 容器做了一层自己的封装：

```csharp
// Furion 风格的 DI——通过接口标记自动注册
// 服务实现标记 ITransient / IScoped / ISingleton
public class UserService : ITransient
{
    // Furion 在启动时扫描所有实现这些接口的类，自动注册到 DI 容器
}

// 或者用特性标注
[Injection(InjectType.Transient)]
public class UserService { }
```

**问题诊断：**

```
问题 2.1：DI 注册的"隐式约定"代替"显式声明"

Furion 的自动注册意味着：
├── 你打开 Program.cs，看不到系统到底注册了哪些服务
├── 新人加入团队，问"这个服务是怎么注册的？"
│   答案是"你不需要知道，它自动注册的"——这是反工程的
├── 注册冲突很难发现——两个类实现了同一个接口，
│   自动注册时谁被选中？取决于扫描顺序？不可预测
└── 测试时很难 mock——你不知道注入的是哪个实现

ABP 的做法（显式 + 可发现）：
┌─────────────────────────────────────────────────┐
│ // ABP 模块中显式注册                            │
│ public override void ConfigureServices(          │
│     ServiceConfigurationContext context)         │
│ {                                                │
│     context.Services.AddTransient<ICustomerAppService, │
│         CustomerAppService>();                   │
│                                                  │
│     // 或者批量注册——但也是显式的                │
│     context.Services.AddAssemblyOf<              │
│         CustomerApplicationModule>();            │
│ }                                                │
│                                                  │
│ // 打开任何一个 ABP Module，你一眼就能看到       │
│ // 这个模块注册了什么、替换了什么、配置了什么     │
└─────────────────────────────────────────────────┘


问题 2.2：DI 容器生命周期管理

JNPF 需要审计的核心问题：
├── ISqlSugarClient 的注册生命周期是什么？
│   ├── 如果是 Singleton：
│   │   └── 所有请求共享一个 DbContext → 线程安全问题
│   │       SqlSugar 的 DbContext 不是线程安全的
│   │
│   ├── 如果是 Scoped（每次请求一个）：
│   │   └── 正确，但需要确认连接池配置合理
│   │
│   └── 如果是 Transient（每次注入都创建）：
│       └── 可能导致连接泄露——多个 DbContext 同时打开
│
├── ICurrentUserService（当前用户）的注册生命周期？
│   ├── 必须是 Scoped（每个请求独立的用户上下文）
│   └── 如果是 Singleton → 多用户串数据（灾难性Bug）
│
├── ILogger<T> 是否正确使用了内置 DI？
│   ├── .NET 内置的日志工厂是 Singleton
│   └── 如果 Furion 包装了自己的日志接口，是否保持了相同的生命周期？
│
└── 事件处理器（EventBus handler）的生命周期？
    ├── 如果 Singleton handler 注入了 Scoped 服务
    │   → 运行时访问已释放的对象 → ObjectDisposedException
    └── 这是 .NET DI 最经典的陷阱


问题 2.3：IServiceProvider 的直接解析（Service Locator 反模式）

搜索以下代码模式：
var service = App.GetService<T>();           // Furion 的静态服务定位
var service = HttpContext.RequestServices     // 手动从根容器解析
    .GetRequiredService<T>();
var scope = serviceProvider.CreateScope();   // 手动创建作用域

// 这些都是 Service Locator 反模式
// 正确做法是构造函数注入：
public class MyController : ControllerBase
{
    private readonly IMyService _service;
    public MyController(IMyService service)  // ← 构造函数注入
    {
        _service = service;
    }
}
```

### 审计操作

```bash
# 搜索 Furion 的 App.GetService 等静态服务定位调用
grep -rn "App\.GetService\|App\.GetRequiredService\|App\.RootServices" --include="*.cs" | wc -l

# 搜索手动从 IServiceProvider 解析服务
grep -rn "ServiceProvider.*GetService\|ServiceProvider.*GetRequiredService\|RequestServices.*GetService" --include="*.cs" | wc -l

# 搜索不通过构造函数注入的服务使用
grep -rn "new .*Service()\|new .*Repository()" --include="*.cs" | grep -v test | wc -l
```

**产出：** 服务定位反模式使用清单 + 每个实例改为构造函数注入的方案。

### 审计点 3.1：EventId 的系统化使用

```csharp
// ❌ 当前可能的写法——没有 EventId，日志是一堆无结构的文本
_logger.LogInformation("用户登录成功");
_logger.LogInformation("查询客户列表");
_logger.LogInformation("流程审批通过");

// 无法按事件类型聚合查询
// 无法设置告警规则："EventId 10003 在 5 分钟内出现超过 10 次就告警"
// 无法做运营统计："今天有多少次 10001（登录成功）事件"

// ✅ 宗师级做法——每个业务事件有唯一 EventId
public static class JnpfEventIds
{
    // ===== 认证模块 1000-1999 =====
    public static readonly EventId LoginSuccess = new(1000, nameof(LoginSuccess));
    public static readonly EventId LoginFailed = new(1001, nameof(LoginFailed));
    public static readonly EventId TokenRefreshed = new(1002, nameof(TokenRefreshed));
    public static readonly EventId TokenExpired = new(1003, nameof(TokenExpired));
    public static readonly EventId PasswordChanged = new(1004, nameof(PasswordChanged));
    
    // ===== 流程模块 2000-2999 =====
    public static readonly EventId FlowCreated = new(2000, nameof(FlowCreated));
    public static readonly EventId FlowApproved = new(2001, nameof(FlowApproved));
    public static readonly EventId FlowRejected = new(2002, nameof(FlowRejected));
    public static readonly EventId FlowTimeout = new(2003, nameof(FlowTimeout));
    
    // ===== 数据操作模块 3000-3999 =====
    public static readonly EventId DataCreated = new(3000, nameof(DataCreated));
    public static readonly EventId DataUpdated = new(3001, nameof(DataUpdated));
    public static readonly EventId DataDeleted = new(3002, nameof(DataDeleted));
    public static readonly EventId DataExported = new(3003, nameof(DataExported));
    
    // ===== 系统运维模块 9000-9999 =====
    public static readonly EventId SlowQuery = new(9000, nameof(SlowQuery));
    public static readonly EventId CacheHit = new(9001, nameof(CacheHit));
    public static readonly EventId CacheMiss = new(9002, nameof(CacheMiss));
    public static readonly EventId UnhandledException = new(9999, nameof(UnhandledException));
}

// 使用时：
_logger.LogInformation(JnpfEventIds.LoginSuccess,
    "用户 {UserId} 从 {IpAddress} 登录成功，耗时 {Elapsed}ms",
    userId, ip, elapsed);

// 现在可以按 EventId 做告警、统计、聚合查询
// Serilog 可以按 EventId 过滤和聚合
```

### 审计点 3.2：结构化日志的数据丰富度

```csharp
// ❌ 原始写法——纯文本，无法被日志系统结构化查询

// ✅ 结构化日志——每个变量都是可索引的字段

// 日志系统（Serilog/Elasticsearch）可以：

// - 按 ElapsedMs 排序：找出最慢的查询
// - 按 EntityName 聚合：哪些实体被查询最多
// - 按 UserId 统计：某个用户的操作频率
```

### 审计点 3.3：日志分级与采样策略

```
生产环境的日志量级：
├── 1000 并发用户 × 每用户每分钟 10 个操作 = 10000 条/分钟
├── 每条日志平均 500 字节 → 5MB/分钟 → 7.2GB/天
└── 加上 SQL 日志、请求日志 → 可能 20-50GB/天

必须有策略：
├── Debug 日志：生产环境关闭，或只对特定模块开启
├── Information 日志：正常业务操作，保留
├── Warning 日志：异常但可恢复的情况，需要关注
├── Error 日志：异常且影响功能，需要立即处理
│
├── 采样策略（Serilog 支持）：
│   ├── 慢查询日志：全部记录（不采样）
│   ├── 正常请求日志：采样 10%
│   └── 缓存命中日志：采样 1% 或关闭
│
└── 动态日志级别：
    ├── 生产环境默认 Information
    ├── 出问题时可以不重启动态调整为 Debug
    └── Serilog 支持 LoggingLevelSwitch
```

## 维度 4：异常拦截器与错误边界

### 审计点 4.1：异常过滤器的层次设计

```csharp
// ❌ Furion 可能的全局异常处理方式——一个大 catch 处理所有异常
app.UseExceptionHandler(appError =>
{
    appError.Run(async context =>
    {
        context.Response.StatusCode = 500;
        await context.Response.WriteAsJsonAsync(new { code = 500, message = "系统错误" });
    });
});

// 这种方式的问题：
// 1. 所有异常都返回 500，没有区分业务异常、认证异常、验证异常
// 2. 没有日志记录（或者记录了但没有分类）
// 3. 没有 HTTP 状态码的语义化使用

// ✅ 宗师级做法——分层异常体系
┌──────────────────────────────────────────────────────────┐
│                    异常层次体系                            │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  Layer 1: 基础异常类型                                    │
│  ├── JnpfException : Exception                           │
│  │   ├── Code: int (业务错误码)                           │
│  │   ├── Message: string (用户友好消息)                    │
│  │   └── Details: object? (附加信息，不对外暴露)           │
│  │                                                       │
│  ├── BusinessException : JnpfException                   │
│  │   └── 可恢复的业务逻辑错误（如"编码已存在"）           │
│  │                                                       │
│  ├── ValidationException : JnpfException                 │
│  │   ├── Errors: IDictionary<string, string[]>           │
│  │   └── 参数校验失败                                    │
│  │                                                       │
│  ├── NotFoundException : JnpfException                   │
│  │   └── 资源不存在                                      │
│  │                                                       │
│  ├── ForbiddenException : JnpfException                  │
│  │   └── 权限不足                                        │
│  │                                                       │
│  ├── TenantNotFoundException : JnpfException             │
│  │   └── 租户不存在或已停用                              │
│  │                                                       │
│  └── ConcurrencyException : JnpfException                │
│      └── 并发冲突（乐观锁失败）                          │
│                                                          │
│  Layer 2: 全局异常处理器（中间件/过滤器）                  │
│                                                          │
│  catch (ValidationException ex)                          │
│  │   → 400 Bad Request + { errors: ex.Errors }           │
│  │                                                       │
│  catch (NotFoundException ex)                            │
│  │   → 404 Not Found + { message: ex.Message }           │
│  │                                                       │
│  catch (ForbiddenException ex)                           │
│  │   → 403 Forbidden + { message: ex.Message }           │
│  │                                                       │
│  catch (BusinessException ex)                            │
│  │   → 200 OK + { code: ex.Code, message: ex.Message }   │
│  │   （业务异常用200+错误码，前端统一判断 code）          │
│  │                                                       │
│  catch (ConcurrencyException ex)                         │
│  │   → 409 Conflict + { message: "数据已被他人修改" }     │
```

```csharp
public abstract class CrudAppService<TEntity, TDto, TGetInput, TCreateInput, TUpdateInput>

    protected virtual Task OnCreatingAsync(TEntity entity, TCreateInput input)

        return Task.CompletedTask;
    }

    protected virtual IQueryable<TEntity> ApplyDataPermission(IQueryable<TEntity> query)
    {
        // 默认实现：按当前用户的组织过滤
        if (CurrentUser.OrganizeId.HasValue)
            query = query.Where(e => e.OrganizeId == CurrentUser.OrganizeId);
        return query;
    }
    
    // 标准 CRUD——自动包含日志、权限、异常处理
    public virtual async Task<TDto> CreateAsync(TCreateInput input, CancellationToken ct = default)
    {
        // 1. 参数验证（自动通过 FluentValidation 触发）
        
        // 2. 实体映射
        var entity = MapToEntity(input);
        
        // 3. 创建前钩子
        await OnCreatingAsync(entity, input);
        
        // 4. 审计字段
        entity.CreatorUserId = CurrentUser.UserId;
        entity.CreateTime = DateTime.Now;
        
        // 5. 持久化
        await Repository.InsertAsync(entity, ct);
        
        // 6. 日志
        Logger.LogInformation(JnpfEventIds.DataCreated,
            "创建 {EntityName}，Id={Id}，操作人={UserId}",
            typeof(TEntity).Name, entity.Id, CurrentUser.UserId);
        
        // 7. 创建后钩子（子类可覆盖，用于发送事件、更新关联数据等）
        await OnCreatedAsync(entity, input);
        
        return MapToDto(entity);
    }
```

```csharp
// 1. 权限树构建——从扁平列表到树结构
// ❌ 低效做法——递归查数据库

        .Where(m => m.ParentId == parentId)

    {

    }

// ✅ 宗师级做法——一次查询 + 内存树构建
List<MenuTree> BuildMenuTree(List<SysMenu> allMenus)
{
    // 一次查出所有菜单，在内存中用字典构建树
    // 时间复杂度 O(n)，空间复杂度 O(n)
    var dict = allMenus.ToDictionary(m => m.Id);
    var roots = new List<MenuTree>();
    
    foreach (var menu in allMenus)
    {
        if (menu.ParentId == null || menu.ParentId == Guid.Empty)
        {
            roots.Add(MapToTree(menu));
        }
        else if (dict.TryGetValue(menu.ParentId.Value, out var parent))
        {
            parent.Children ??= new();
            parent.Children.Add(MapToTree(menu));
        }
    }
    
    return roots;
}

// 2. 数据权限——组织树的"本部门及以下"查询
// ❌ 递归查数据库获取所有下级部门
async Task<List<Guid>> GetDescendantOrgIds(Guid orgId)
{
    var result = new List<Guid> { orgId };
    var children = await _db.Queryable<SysOrganize>()
        .Where(o => o.ParentId == orgId)
        .ToListAsync();
    foreach (var child in children)
    {
        result.AddRange(await GetDescendantOrgIds(child.Id)); // 递归查DB
    }
    return result;
}

// ✅ 宗师级做法——一次查全表 + 内存遍历（组织树通常不大，100-10000个节点）
async Task<List<Guid>> GetDescendantOrgIds(Guid rootOrgId)
{
    // 从缓存获取完整组织树（登录时加载，变更时刷新）
    var allOrgs = await _cache.GetOrCreateAsync("org:tree", async () =>
    {
        return await _db.Queryable<SysOrganize>()
            .Where(o => o.DeleteMark == false)
            .Select(o => new { o.Id, o.ParentId })
            .ToListAsync();
    }, TimeSpan.FromHours(1));
    
    // BFS 遍历获取所有后代——O(n)
    var result = new List<Guid>();
    var queue = new Queue<Guid>();
    queue.Enqueue(rootOrgId);
    
    while (queue.Count > 0)
    {
        var current = queue.Dequeue();
        result.Add(current);
        
        foreach (var org in allOrgs.Where(o => o.ParentId == current))
        {
            queue.Enqueue(org.Id);
        }
    }
    
    return result;
}

// 3. 代码生成器中的字符串算法
// 生成 Entity 类名时：table_name → TableName (PascalCase)
// 生成字段名时：user_name → UserName
// 生成路由时：customer_management → customer-management (kebab-case)

// 用 Span<T> 和栈分配优化字符串操作（热路径上避免堆分配）
static string ToPascalCase(ReadOnlySpan<char> input)
{
    Span<char> result = stackalloc char[input.Length];
    bool capitalizeNext = true;
    int j = 0;
    
    for (int i = 0; i < input.Length; i++)
    {
        if (input[i] == '_' || input[i] == '-')
        {
            capitalizeNext = true;
            continue;
        }
        
        result[j++] = capitalizeNext ? char.ToUpperInvariant(input[i]) : input[i];
        capitalizeNext = false;
    }
    
    return new string(result[..j]);
}
```

```csharp
// 3. 租户 ID 的获取策略
public class TenantResolver
{
    // 解析优先级：
    // 1. HTTP Header: X-Tenant-Id（多租户 SaaS 场景）
    // 2. JWT Claims: tenant_id
    // 3. 域名映射：tenant1.jnpf.com → tenant1
    // 4. 子路径映射：jnpf.com/tenant1/ → tenant1
    
    public Guid? Resolve(HttpContext context)
    {
        // 优先从 Header 获取
        if (context.Request.Headers.TryGetValue("X-Tenant-Id", out var headerValue)
            && Guid.TryParse(headerValue, out var tenantFromHeader))
            return tenantFromHeader;
        
        // 其次从 JWT 获取
        var claim = context.User.FindFirst("tenant_id");
        if (claim != null && Guid.TryParse(claim.Value, out var tenantFromJwt))
            return tenantFromJwt;
        
        return null;
    }
}

// 4. 租户切换的安全审计
// 当管理员切换到其他租户查看数据时：
// 必须有授权检查——只有平台管理员才能跨租户
// 切换操作必须记录审计日志
// 切换后的所有操作都带新租户的 TenantId

// 5. 无租户数据（系统级数据）
// 字典表、系统配置等公共数据不属于任何租户
// 全局过滤器中需要处理这种情况：
db.QueryFilter.AddTableFilter<IMultiTenant>(entity =>
    entity.TenantId == currentTenantId || entity.TenantId == Guid.Empty);
    // Guid.Empty 表示系统级公共数据，所有租户可见
```

```csharp
// ❌ 可能的现状——Furion 的事件总线
// 通过 IFurionEventBus 或类似的接口发布/订阅事件

// 问题：
// 1. 事件处理器与事件发布者紧耦合（在同一进程中）
// 2. 事件处理器失败后，主操作是否回滚？语义不清晰

public interface IEventBus
{
    // 同步发布——等待所有处理器完成
    Task PublishAsync<TEvent>(TEvent @event, CancellationToken ct = default)
        where TEvent : IEvent;

// 事件总线实现的关键设计：
public class EventBus : IEventBus
{
    private readonly IServiceProvider _serviceProvider;
    private readonly ILogger<EventBus> _logger;
    private readonly Channel<IEventEnvelope> _channel; // System.Threading.Channels
    
    public EventBus(IServiceProvider serviceProvider, ILogger<EventBus> logger)
    {
        _serviceProvider = serviceProvider;
        _logger = logger;
        _channel = Channel.CreateUnbounded<IEventEnvelope>();
        
        // 后台消费者
        _ = ProcessBackgroundEventsAsync();
    }
    
    public async Task PublishAsync<TEvent>(TEvent @event, CancellationToken ct)
        where TEvent : IEvent
    {
        // 从 DI 获取所有该事件的处理器
        using var scope = _serviceProvider.CreateScope();
        var handlers = scope.ServiceProvider.GetServices<IEventHandler<TEvent>>();
        
        foreach (var handler in handlers)
        {
            try
            {
                await handler.HandleAsync(@event, ct);
            }
            catch (Exception ex)
            {
                // 单个处理器失败不阻塞其他处理器
                _logger.LogError(JnpfEventIds.UnhandledException, ex,
                    "事件 {EventType} 处理器 {HandlerType} 执行失败",
                    typeof(TEvent).Name, handler.GetType().Name);
                
                // 可选：重试策略
                // 可选：放入死信队列
            }
        }
    }
}
```

## 维度 13：数据总线设计

### 审计点：数据总线 vs 事件总线的区分

```
很多系统混淆了这两个概念：

事件总线（EventBus）：发布-订阅模式，一对多通知
├── 用途：当某事发生时，通知所有关心的订阅者
├── 特点：发布者不知道、不关心谁在消费
├── 例子：订单创建后，通知库存模块、通知模块、统计模块
└── 可靠性要求：中等（进程内即可，关键事件用消息队列）

数据总线（DataBus）：点对点数据传输，解决跨模块/跨服务的数据共享
├── 用途：大数据块的传输（附件、报表、批量数据）
├── 特点：不适合放在消息体中（消息应该轻量）
├── 例子：流程引擎需要传递表单数据的完整快照给下一个审批人
└── 实现方式：
    ├── 小数据：消息体中直接携带
    ├── 中等数据：消息中携带 ID，消费者通过 ID 从数据库/缓存获取
    └── 大数据：上传到对象存储（MinIO/OSS），消息中携带 URL

JNPF 需要审计的问题：
├── 流程审批中，表单数据的传递方式
│   ├── 如果是消息队列中携带完整JSON——数据量大时性能差
│   └── 如果是只传ID，接收方重新查DB——查询路径是否一致？
│
├── 代码生成的产物（.zip文件）传输
│   ├── 是内存中生成后直接返回？
│   └── 还是先存临时文件，再返回文件流？
│
└── 大屏数据的实时推送
    ├── WebSocket 推送的是完整数据还是增量数据？
    └── 1000个大屏客户端同时订阅，推送性能如何？
```
