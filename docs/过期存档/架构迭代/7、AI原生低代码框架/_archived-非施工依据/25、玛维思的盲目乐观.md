## 1.2 v2.0 的 7 个致命漏洞(为什么承载不住)

### 漏洞 1:SqlSugar + 单机 CDC 撑不住 100 租户 × 150 张表

- v2.0 假设 SqlSugar 单机同步 5-10 张表,延迟 < 1 分钟
- 真实场景: 100 租户 × 150 表 = **15000 张源表**,SqlSugar 同步一次要几小时
- 多租户循环:100 租户 × 150 表 × 全量校验 = 单机跑不动
- **必须用分布式 CDC**: Debezium + Kafka,或云服务(阿里云 DTS/AWS DMS)

### 漏洞 2:SQL Server 单机分析库扛不住 50 亿行 + 500 QPS

- v2.0 假设 SQL Server + Columnstore + 索引视图够用
- SQL Server 单机上限: 100-200 QPS(分析查询),超过必须集群化
- 100 租户共享分析库:租户间资源争抢(锁等待、CPU 抢占)
- **必须引入 OLAP 引擎**: ClickHouse / Doris / StarRocks,适合宽表 + 高并发分析
- 或: 保留 SQL Server 索引视图做"租户级缓存",ClickHouse 做"全局分析"

### 漏洞 3:"100 租户共享库 + F_TENANT_ID"的安全风险被严重低估

- v2.0 默认"继承 TenantEntity + ITenantFilter"就完事
- 真实风险:
  - 一次 SQL 注入/权限漏洞 = 100 租户数据全泄露
  - 单租户 OOM/慢查询拖垮全租户
  - 等保三级、GDPR 审计要求每租户独立审计
- **必须分阶段**:
  - 阶段一(0-50 租户): 共享库 + 强 RLS
  - 阶段二(50-200 租户): 大租户独立库 + 小租户共享
  - 阶段三(200+ 租户): 完整分库分表

### 漏洞 4:LLM 调用成本和延迟在 100 租户下不可行

- v2.0 说"用 DeepSeek-V3 API,P95 < 3s"
- 真实成本:
  - 5 万次/天 × 3000 Token/次 × 30 天 = 450 亿 Token/月
  - DeepSeek-V3 价格 1 元/百万 Token → **4.5 万/月 LLM 成本**
  - 还要叠加:输入/输出比、长尾请求、Few-Shot Token 加成
  - **真实成本: 10-30 万/月**,这部分客户不会付,SaaS 公司自己扛
- 真实延迟:
  - 云端 API 高峰期排队,500 QPS 必触发限流
  - 客户敏感数据(订单、产能)上传到云端,合规风险
- **必须重构**:
  - 小模型(Qwen-7B-int4)本地做意图识别(80% 流量)
  - 大模型 API 只做结果解读(20% 流量)
  - 强 Prompt 缓存 + 结果缓存,目标 60%+ 命中

### 漏洞 5:Redis 单机缓存扛不住 100 租户的 key 空间

- v2.0 说"Redis 缓存高频查询,TTL 5-15 分钟"
- 真实场景:
  - 100 租户 × 1万 指标查询模板 × 5 分钟 TTL = **100 万 key**
  - 每 key 平均 2 KB(查询结果),总内存 2 GB → 加上索引 5-10 GB
  - 单机 Redis 撑得住,但**多租户 key 互相影响**(大 key、热点 key)
- **必须**: Redis Cluster(3 主 3 从)+ 多级缓存(L1 本地 + L2 Redis)

### 漏洞 6:Schema RAG 倒排索引在 100 租户下会内存爆

- v2.0 说"用 SQL Server 倒排索引,6000 节点够用"
- 真实场景:
  - 100 租户 × 6000 节点 = **60 万节点**(每租户独立倒排索引)
  - 加上同义词、业务规则、样本查询,SQL Server 内存要 20+ GB
  - 租户级冷启动: 新租户接入,索引重建要 2-3 小时
- **必须**:
  - 共享倒排索引(全局)+ 租户级过滤(成本低、隔离差)
  - 或: 关键租户独立倒排 + 小租户共享(折中)
  - 引入增量构建,避免每次重启重建

### 漏洞 7:早报批处理任务会把分析库打爆

- v2.0 说"早 8 点自动跑早报"
- 真实场景:
  - 100 租户同时跑早报 = 100 个并发批处理任务
  - 每个早报要查 5-10 个指标 × 多个维度,实际是 50-100 个查询
  - 100 × 50 = **5000 个并发查询** 集中在 8:00-8:05
  - 任何分析库都扛不住
- **必须**:
  - 早报任务错峰(7:30 开始,每 10 秒 1 个租户)
  - 早报结果预计算(凌晨 3:00 算好,8:00 直接推送)
  - 早报查询走专用通道(限流 + 资源隔离)

## 1.3 你的担心是对的

按 v2.0 直接交付 100 租户 SaaS MES,大概率:
- **第 1 个月**: 0-10 租户演示还行
- **第 3 个月**: 30 租户时数据库开始卡
- **第 6 个月**: 50 租户时早报任务超时、查询慢、客服投诉
- **第 12 个月**: 80 租户时 LLM 成本失控、租户串数据、SLA 崩溃

**v2.0 是"单租户 POC 级"方案,不是"SaaS 平台级"方案**。这是我必须承认的设计失误。

# 二、v3.0 修订:SaaS 100 租户 MES 数据中台架构

> **核心思路**: v2.0 的"指标字典护城河"和"MQL 翻译引擎"设计是对的(产品价值层),但**基础设施层必须重做**(数据规模、并发隔离、成本控制、运维平台)。
>
> **采用"演进式架构"**: 不是一步到位建"重型中台",而是设计一条**可平滑扩展的演进路径**,在 0-100 租户阶段用最小成本启动,在 100+ 租户时不需要推倒重来。

## 2.2 阶段一(0-20 租户,v2.0 改良版): 6 周可启动

> **保留 v2.0 的产品价值层,补齐 SaaS 多租户的基础设施**
>
> **目标**: 用 6 周完成 20 租户的 POC,跑通商业模型,验证产品价值

### 2.2.1 阶段一的关键设计决策

| 决策项         | v2.0(单租户)    | v3.0 阶段一(0-20 租户)                    | 理由                         |
| -------------- | --------------- | ----------------------------------------- | ---------------------------- |
| **租户隔离**   | 单租户          | **共享 OLTP 库 + 共享分析库 + 强化 RLS**  | 成本最低,20 租户风险可控     |

### 2.2.2 阶段一必须的 6 个补强

**补强 1:多租户强化隔离(2 周)**

```sql
-- 资源隔离: 每租户限制最大资源
CREATE RESOURCE POOL TenantPool_Max
WITH (MIN_CPU_PERCENT = 0, MAX_CPU_PERCENT = 5);  -- 每租户最多 5% CPU

-- 行级安全: 强制 TenantId 过滤(防止代码漏写)
CREATE SECURITY POLICY TenantFilterPolicy
ADD FILTER PREDICATE dbo.fn_tenantAccessPredicate(F_TENANT_ID)
ON dbo.DW_WORK_ORDER,
   dbo.DW_QUALITY_RECORD, ...;

-- 审计强化: 每租户独立审计表(分表存储,便于导出)

  UNION ALL SELECT * FROM BASE_AI_QUERY_LOG_T002
```

**补强 2:异步同步队列(1 周)**

```csharp
// 用 System.Threading.Channels 实现异步削峰
public class CdcSyncService : BackgroundService
{
    private readonly Channel<SyncTask> _queue = Channel.CreateBounded<SyncTask>(
        new BoundedChannelOptions(1000) { FullMode = BoundedChannelFullMode.Wait });

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        // 多个消费者并行处理
        await Task.WhenAll(
            ConsumeQueue(stoppingToken, 1),
            ConsumeQueue(stoppingToken, 2),
            ConsumeQueue(stoppingToken, 3));
    }
}
```

**补强 3:LLM 智能路由(1 周)**

```csharp
// 小模型做意图识别(本地,免费),大模型只做结果解读(API,付费)
public class LlmRouter
{
    public async Task<MqlResult> ProcessAsync(string nlQuery)
    {
        // 1. 小模型本地推理(Qwen-7B-int4,Ollama 部署)
        var mql = await _localLlm.GenerateMql(nlQuery);  // < 500ms

        // 2. 简单查询:本地直接返回(不调大模型)
        if (mql.IsSimple && !mql.NeedsInterpretation)
            return await ExecuteMql(mql);

        // 3. 复杂查询:调大模型做解读
        var data = await ExecuteMql(mql);
        var insight = await _remoteLlm.GenerateInsight(data);  // DeepSeek-V3

        return new MqlResult { Data = data, Insight = insight };
    }
}
```

**预期效果**:
- 80% 简单查询走本地,零 LLM 成本
- 20% 复杂查询走 API,成本下降 70%
- 端到端延迟:简单查询 < 1s,复杂查询 < 4s

**补强 4:早报错峰调度(3 天)**

```csharp
// 早报任务调度:7:30 开始,每 30 秒触发 1 个租户
public class MorningBriefingScheduler
{
    public async Task StartAsync()
    {
        var tenants = await _tenantService.GetActiveTenantsAsync();
        var startTime = DateTime.Today.AddHours(7).AddMinutes(30);
        
        for (int i = 0; i < tenants.Count; i++)
        {
            var delay = TimeSpan.FromSeconds(i * 30);  // 错峰
```

# 五、给客户的诚实结论

**1. v2.0 的"轻量"是设计失误**
我之前按"单租户 POC"思维设计了 v2.0,直接套到 100 租户 SaaS MES 上会塌方。你这次的质疑救了我和项目,谢谢。

**2. v3.0 的真实定位**
v3.0 不是"轻量数据湖",而是"**SaaS 100 租户演进式数据中台**"——
- 阶段一(0-20 租户,6-8 周): 用最小的成本跑通商业模型
- 阶段二(20-50 租户,8-10 周触发): 引入分布式组件
- 阶段三(50-100+ 租户,平台化): 完整分库分表 + 智能调度

**3. 第一期 8 周可交付**
第一期 v3.0 在 8 周内交付 20 租户可商用的数据中台,单租户月摊销成本 3000-4000 元。

**4. 必须承认的隐性约束**
- LLM 成本: 即使优化,20 租户月均 LLM 成本 2-3 万,SaaS 公司需要自己扛
- 团队能力: 阶段二需要 Kafka、ClickHouse、分布式经验,提前培养或外包
- 合规成本: 等保三级、GDPR 审计一次性 5-10 万,必须预算

**5. 风险预警**
如果客户要求"4 周交付 100 租户生产可用",我必须明确说:**做不到,接了这个需求就是烂尾的开始**。
