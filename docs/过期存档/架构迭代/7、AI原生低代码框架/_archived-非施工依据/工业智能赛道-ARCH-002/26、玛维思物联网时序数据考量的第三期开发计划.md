# 一、诚实的反思:v3.0 完全没考虑时序数据

## 1.1 业务数据(MES) vs 时序数据(IIoT) 的本质差异

| 维度         | 业务数据(MES/ERP)        | 时序数据(IIoT 传感器)         | 量级差异   |
| ------------ | ------------------------ | ----------------------------- | ---------- |
| **数据本质** | 离散事件(工单创建、报工) | 连续波形(振动、温度、电流)    | -          |
| **采样频率** | 秒级~分钟级              | **1Hz-10kHz**(振动可达 10kHz) | 100-10000× |
| **数据形态** | 结构化行(几十列)         | 标签+时间戳+值(三元组)        | -          |
| **写入模式** | 低频 INSERT/UPDATE       | **高频 APPEND-ONLY**          | -          |
| **查询模式** | 按业务维度聚合           | **按时间窗口聚合**            | -          |
| **数据保留** | 7 年(合规)               | 1-3 年(成本约束)              | -          |
| **数据规模** | 千万级/租户              | **百亿-千亿级/工厂**          | 100-1000×  |
| **存储格式** | 行式(SQL Server)         | **列式/专用时序库**           | -          |
| **延迟要求** | 秒级                     | **毫秒级(实时监控)**          | -          |
| **分析工具** | SQL + MQL                | **时序查询 + FFT + ML**       | -          |

## 1.2 真实数据规模估算(你描述的场景)

**接入规模**:
- 100 台机床 × 10-20 个传感器/台 = **1000-2000 个传感器**
- 传感器类型: 振动(10kHz)、温度(1Hz)、压力(10Hz)、电流(100Hz)、电压(100Hz)、流量(10Hz)、功率(10Hz)、位置(100Hz)...

**中位场景估算**(假设 50% 高频 + 50% 低频):
- 1000 传感器 × 50Hz 平均 = **5 万点/秒**
- 一天: 5万 × 86400 = **432 亿点/天**
- 存储: 每点 100 字节 → **4.3 TB/天 = 1.5 PB/年**

**高频场景**(重型机床,振动密集):
- 1000 传感器 × 200Hz 平均 = **20 万点/秒**
- 一天: 20万 × 86400 = **1728 亿点/天**
- 存储: 100字节/点 → **17 TB/天 = 6 PB/年**

**这是 v3.0 设计的 SQL Server 单机分析库根本撑不住的数据量级**。

## 1.3 v3.0 现有架构在时序场景下的 8 个致命漏洞

### 漏洞 1:SQL Server 单机写入上限 ~3 万 TPS
- 你的场景: 中位 5 万点/秒 = **18 万 TPS**(带标签和元数据)
- SQL Server 单机写入瓶颈: ~3 万 TPS(含索引维护)
- **结论: 写 1 天数据,SQL Server 要 6 天才能追上,数据必然积压**

### 漏洞 2:CDC 同步模式完全不适配
- CDC 是"变更捕获"(从日志里捞变更行)
- 时序数据是"连续流"(每秒万级新数据点)
- 用 CDC 处理时序: 数据库事务日志爆炸、CDC 捕获表膨胀、性能崩塌

### 漏洞 3:指标字典(MES 指标)只覆盖离散业务
- MES 指标: 良品率、OEE、计划达成率(来自工单/报工)
- IIoT 指标: 振动 RMS、峰值因子、温度梯度、能耗强度(来自传感器)
- 现有 `BASE_METRIC_DEFINITION` 表的 `F_FORMULA` 字段是 SQL 表达式,装不下 FFT、滑动窗口、阈值占比等时序计算

### 漏洞 4:MQL 翻译引擎不支持时序查询
- 现有 MQL: `metrics + dimensions + timeRange + filters`
- 时序查询需要: `metric + timeWindow(1m/5m/1h) + aggregation(avg/max/min/percentile) + downsample(1s→1m) + groupBy(sensor/tag) + retentionPolicy`
- 几乎是另一种查询语言(类似 PromQL/InfluxQL)

### 漏洞 5:data-mcp 只有 3 个工具,完全不够
- 现有:`list_metrics` / `query_metrics` / `query_data`
- 时序场景需要:
  - `query_timeseries` - 时序数据查询
  - `get_latest_reading` - 实时最新值
  - `detect_anomaly` - 异常检测
  - `forecast_remaining_life` - 预测剩余寿命
  - `compute_energy_efficiency` - 能效分析
  - `run_digital_twin_simulation` - 数字孪生仿真

### 漏洞 6:LLM 不知道怎么查询时序数据
- 用户问:"3号机主轴振动过去1小时趋势,有没有异常?"
- 现有 LLM Prompt 注入的元数据是 MES 字段和指标
- LLM 不知道有"振动"这个传感器、不知道采样率、不知道阈值
- 必须新增"时序 Schema RAG":传感器字典、设备模型、信号特征库

### 漏洞 7:预测维修需要 ML 平台,v3.0 完全没规划
- 振动分析: FFT → 频谱特征 → 故障分类(轴承、齿轮、不平衡)
- 温度预测: LSTM/Transformer → 预测温度曲线 → 异常检测
- 剩余寿命(RUL): 退化模型 + 生存分析
- 需要: 特征工程、模型训练、模型部署、模型监控、MLOps 完整链路
- v3.0 没有 GPU 资源规划、没有 ML 工程师、没有特征库、没有模型注册表

### 漏洞 8:电力损耗优化需要数字孪生
- 设备级孪生: 物理参数 + 实时数据 + 退化模型
- 工厂级孪生: 设备网络 + 物料流 + 能量流
- 优化算法: 运筹学(线性规划/整数规划)、强化学习
- 这是 v3.0 完全没考虑的领域,需要专门的工业自动化 + 运筹学团队

# 二、v4.0 第三期独立方案:IIoT + 工业智能数据栈

> **核心定位**: 第三期不再是 v3.0 的"延伸",而是一个**完全独立的工程**,需要独立团队、独立预算、独立工期、独立技术栈。

> **建议组织模式**: 第三期单独成立"工业智能事业部",与"企业管理系统事业部"并列,直接向 CTO 汇报。

## 2.2 时序数据栈(独立技术选型)

### 2.2.1 数据接入层(2-3 个月专项工程)

**核心挑战**: 100 台机床 × 多种工业协议适配,每种机床的通信接口都不一样

| 协议类型           | 适用场景           | 选型                  | 工期   |
| ------------------ | ------------------ | --------------------- | ------ |
| **OPC UA**(主流)   | 95% 的现代数控机床 | Kepware/Ignition 网关 | 4 周   |
| **Modbus TCP/RTU** | 传统 PLC、老旧设备 | Modbus 网关           | 3 周   |
| **MTConnect**      | 美国标准机床       | MTConnect Agent       | 2 周   |
| **三菱 MitsuFX**   | 三菱机床           | 三菱专用协议          | 2 周   |
| **西门子 S7**      | 西门子机床         | S7 协议库             | 3 周   |
| **发那科 FOCAS**   | 发那科机床         | FOCAS 接口            | 2 周   |
| **MQTT 私有协议**  | 自研设备           | EMQX 接入             | 2 周   |
| **5G/TSN**         | 新建工厂           | 5G 专网               | 4-8 周 |

**关键交付物**:
- `EquipmentConnector` 设备连接器(支持 8+ 协议)
- `SensorRegistry` 传感器注册中心(每台机床的传感器清单)
- `ProtocolAdapter` 协议适配器(每种协议一个适配器)
- `DataQualityChecker` 数据质量检查(传感器离线、异常值、漂移)

### 2.2.2 消息队列层(必备)

**选型**: Apache Kafka(或 Pulsar)

**为什么不用 MQTT 直转数据库**:
- MQTT 是设备协议,不适合后端大规模数据流
- Kafka 提供: 削峰、解耦、重放、分区并行、多消费者
- 一个工厂需要: 3-5 节点 Kafka 集群(每节点 1TB 存储)

**Topic 设计**:
```
raw-sensor-data          # 原始传感器数据(保留 7 天)
sensor-cleaned-data      # 清洗后数据(保留 30 天)
feature-engineered       # 特征工程后数据(保留 90 天)
anomaly-alerts           # 异常告警(保留 1 年)
```

### 2.2.3 流处理层(实时特征 + 异常检测)

**选型**: Apache Flink(或 Kafka Streams)

**核心功能**:
- **滑动窗口聚合**: 1分钟/5分钟/1小时的均值、峰值、均方根
- **FFT 频谱分析**: 振动信号频域特征(对轴承/齿轮故障至关重要)
- **阈值告警**: 实时检测超阈值
- **简单异常检测**: 基于 3σ 规则、IQR 规则

**关键交付物**:
- `StreamingFeatureEngine` 流式特征引擎
- `RealTimeAnomalyDetector` 实时异常检测器
- `WindowAggregator` 时间窗口聚合器

### 2.2.4 时序存储层(分层存储)

**选型**:**InfluxDB + ClickHouse + S3/OSS 三层架构**

| 数据温度               | 保留期   | 存储选型                         | 压缩比  | 月成本/工厂        |
| ---------------------- | -------- | -------------------------------- | ------- | ------------------ |
| **热数据**(0-7 天)     | 7 天     | InfluxDB Enterprise              | 5-10×   | 0.5 万             |
| **温数据**(7-90 天)    | 90 天    | ClickHouse                       | 10-20×  | 0.8 万             |
| **冷数据**(90 天-3 年) | 3 年     | S3 + Parquet + ClickHouse 冷查询 | 50-100× | 0.3 万             |
| **归档**(>3 年)        | 7 年合规 | S3 Glacier                       | 100×+   | 0.1 万             |
| **总计**               | -        | -                                | -       | **1.7 万/月/工厂** |

**关键设计**:
- 自动数据降级: 7 天前自动从 InfluxDB 迁到 ClickHouse,90 天前归档到 S3
- 数据生命周期由 `DataLifecycleManager` 统一管理
- 冷数据查询通过 ClickHouse 透明访问 Parquet 文件

### 2.2.5 ML 平台(独立工程)

**核心组件**:

| 组件         | 选型                           | 用途                     |
| ------------ | ------------------------------ | ------------------------ |
| **特征库**   | Feast / 自研                   | 特征版本管理、特征复用   |
| **模型训练** | MLflow + Ray                   | 分布式训练、超参搜索     |
| **模型部署** | Triton Inference Server / vLLM | 低延迟推理(实时异常检测) |
| **模型监控** | Evidently AI / 自研            | 漂移检测、性能监控、A/B  |
| **数据标注** | Label Studio                   | 故障样本标注(持续积累)   |

**核心模型**:
- **振动异常检测**: 1D-CNN / Transformer(无监督预训练 + 监督微调)
- **轴承剩余寿命(RUL)**: LSTM / Transformer + 退化曲线拟合
- **温度预测**: Transformer / N-BEATS
- **故障分类**: 多分类 CNN(轴承、齿轮、不平衡、松动...)
- **多模态融合**: 振动+温度+电流 → 综合健康度评分

**关键交付物**:
- `ModelRegistry` 模型注册表
- `FeatureStore` 特征库
- `InferenceService` 推理服务(P95 < 100ms)
- `DriftMonitor` 漂移监控

### 2.2.6 数字孪生引擎

**选型**: 自研(基于 Unity/Unreal 3D 可视化 + 物理模型)

**核心组件**:
- `EquipmentTwin` 设备孪生(物理参数 + 实时数据 + 健康度)
- `FactoryTwin` 工厂孪生(设备网络 + 物料流 + 能量流)
- `SimulationEngine` 仿真引擎(物理仿真 + 离散事件仿真)
- `OptimizationEngine` 优化引擎(运筹学 + 强化学习)

**应用**:
- 设备孪生: 3D 可视化 + 实时状态 + 退化模拟
- 工厂孪生: 物料流仿真 + 瓶颈识别
- 优化引擎: 排产优化、能耗优化、调度优化

## 2.3 三个智能应用的具体方案

### 2.3.1 设备预测维修助手

**核心能力**:
1. **实时健康度监控**: 每台设备健康评分(0-100)
2. **故障预警**: 提前 7-30 天预警轴承/齿轮故障
3. **剩余寿命预测**: RUL 预测,辅助备件管理
4. **维修工单自动生成**: 异常 → 工单 → 派工
5. **维修知识库**: 历史故障 + 维修方案检索

**数据流**:
```
传感器 → Kafka → Flink(特征) → 时序库
                              ↓
                       异常检测模型 → 告警
                              ↓
                       故障诊断模型 → 故障类型 + 置信度
                              ↓
                       RUL 预测模型 → 剩余天数
                              ↓
                       维修知识库检索 → 维修方案
                              ↓
                       工单系统(对接 JNPF workflow-mcp)
```

**与第一期数据中台的融合**:
- 工单状态、设备履历、维修历史来自 MES
- 实时数据来自时序栈
- 融合查询: "3 号机主轴振动异常,过去 30 天维修过几次?"

### 2.3.2 工厂生产流程优化助手

**核心能力**:
1. **实时瓶颈识别**: 工位状态 + WIP 分析
2. **排产优化**: 多目标优化(交期 + 产能 + 能耗)
3. **预测性调度**: 基于设备健康度 + 订单优先级
4. **工艺参数推荐**: 基于历史最优参数

**技术栈**:
- 实时瓶颈: Flink 实时聚合 + 工厂孪生
- 排产优化: Google OR-Tools(运筹学) + 强化学习
- 工艺推荐: 协同过滤 + 强化学习

### 2.3.3 设备电力损耗优化助手

**核心能力**:
1. **能耗基线建模**: 设备空载/负载/待机能耗
2. **异常用电检测**: 空载运行、待机浪费
3. **峰谷优化**: 智能调度,避峰填谷
4. **节能策略**: 变频器参数优化、空压机联动
5. **碳排放核算**: 实时碳足迹

**技术栈**:
- 能耗基线: 时序特征 + 回归模型
- 异常检测: 实时规则 + 统计模型
- 优化策略: 线性规划 + 强化学习
- 碳核算: GHG Protocol 标准

## 2.5 跨域查询协调器(融合关键)

**核心抽象**: 一个查询可能跨业务数据 + 时序数据 + ML 推理

**示例查询**: "3 号机主轴振动异常,过去 30 天维修过几次?"

**查询分解**:
1. **业务数据**(MES): 查询 3 号机过去 30 天维修工单
2. **时序数据**(IIoT): 查询 3 号机主轴振动特征 + 异常告警
3. **ML 推理**: 振动异常检测 + RUL 预测
4. **融合**: 把三类结果组装成完整回答

**跨域查询协调器设计**:
```python
class CrossDomainQueryOrchestrator:
    async def process(self, nl_query):
        # 1. LLM 解析意图,识别需要的数据域
        intent = await self.llm.parse_intent(nl_query)
        # 2. 路由到不同数据域
        tasks = []
        if intent.needs_business:
            tasks.append(self.business_query(intent))
        if intent.needs_timeseries:
            tasks.append(self.timeseries_query(intent))
        if intent.needs_ml:
            tasks.append(self.ml_inference(intent))
        # 3. 并行执行
        results = await asyncio.gather(*tasks)
        # 4. LLM 融合结果
        return await self.llm.fuse_results(results)
```
