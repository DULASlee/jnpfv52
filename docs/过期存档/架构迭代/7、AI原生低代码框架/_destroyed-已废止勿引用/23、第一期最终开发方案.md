#### 1. 关于修正1（SemanticIR融入编译期）：战略上接受，战术上“降级”

- **清言的理想**：开发一个全新的“语义建模画布设计器”，定义 `SemanticIR`，修改 `CompileGateway` 编译流水线。

- **务实的衡量（周期风险）**：开发一个带拖拽、连线、公式校验的前端画布设计器，加上修改底层编译器，**至少需要 6-8 周**。第一期如果做这个，数据湖根本建不起来。

- 千问的最终裁决（配置即代码）

  ：第一期

  绝对不动编译器

  ```

  ```

  。

  - **先进性保证**：对外暴露标准的 MCP 接口，AI 依然能完美调用。
  - **演进预留**：表结构完全按照未来 `SemanticIR` 的 JSON Schema 设计。第二期再开发可视化画布，直接读写这些表，**实现“数据兼容，UI后补”**。

#### 2. 关于修正2（指标字典与知识图谱物理统一）：坚决拒绝物理统一，采用“逻辑联邦”

- **清言的理想**：把“指标公式、维度”和“专家经验”全部塞进 `BASE_KNOWLEDGE_NODE`（图结构），用图查询一把梭。

- **务实的衡量（体验与性能风险）**：指标字典是**高频、强结构化、需要复杂聚合计算**的数据（MQL引擎要瞬间解析公式并翻译成SQL）。如果把它塞进图数据库（或SQL Server模拟的图节点），MQL引擎每次查指标都要做图遍历，**查询延迟会从 50ms 飙升到 2000ms，AI 会卡死！**

- 千问的最终裁决（双库联邦架构）

  ：

  - **关系库（SQL Server）**：存放 `BASE_METRIC_DEFINITION`（指标、维度、公式）。保证 MQL 翻译**极快（<50ms）**。
  - **图/向量库**：存放 `BASE_KNOWLEDGE_*`（专家经验、故障案例）。
  - **先进性保证（AI不笨）**：在 LLM 的 Prompt 组装层做 **“结果缝合”**。AI 查数据时走关系库（快），需要归因分析时走向量库检索经验（准）。用户看到的是完美的融合回答，但底层是两套高性能引擎在并行工作。

#### 3. 关于修正3（事件流抽象）与选型风险：全盘接受，采用“旁路计算”

- **务实的衡量**：不用重型 Flink，也不在应用层死磕滑动窗口。
- **千问的最终裁决**：采用 **“CDC + 旁路特征表”**。CDC 捕获变更，丢进内存队列（Channel），后台单线程消费者做简单的滑动平均计算，结果直接 Update 到 `MES_ANALYTICS` 的“特征宽表”里。AI 查特征直接查表，**绝不实时算，保证不卡**。

### 二、 功能先进性保证：如何让 AI 显得“极其聪明”？

用户觉得 AI 聪明，不是因为它能写复杂的 SQL，而是因为它 **“懂行话、会对比、能给建议”**。我们在第一期通过以下三个“低成本、高收益”的设计锁死先进性：

1. “行话”映射（同义词与黑话字典）

   ：

   - 在指标表中增加 `F_SYNONYMS`（同义词）和 `F_SLANG`（车间黑话）。
   - 用户问：“帮我看看昨天的**拉胯率**”，AI 通过向量匹配，精准识别“拉胯率” = “废品率”，并回复：“为您查询昨日废品率...”。这种“懂黑话”的体验会让客户极度震撼。

2. 强制“对比与归因”输出模板

   ：

   - 在 LLM 的 System Prompt 中**硬编码**输出规范：当用户查询单一指标时，AI **必须**自动附带“环比/同比对比”和“阈值判定”。
   - 用户问：“一车间OEE多少？” AI 绝不只回答“85%”，而是回答：“一车间OEE为85%（⚠️低于90%警戒线），环比昨日下降4%，主要异常停机发生在3号机。”（通过 MQL 自动触发关联查询）。

3. Few-Shot（少样本）动态注入

   ：

   - 在指标表中维护 3-5 个“标准提问与标准 MQL”的示例。Schema RAG 检索时，把最相似的示例喂给 LLM，将 MQL 生成的准确率从 70% 强行拉升到 **95% 以上**。

### 三、 用户体验（不卡）保证：三道性能防线

AI 系统最怕“转圈圈”。为了保证第一期交付的系统“丝滑”，我们设立三道防线：

| 防线                            | 解决的痛点              | 技术实现手段                                                 | 预期性能             |
| ------------------------------- | ----------------------- | ------------------------------------------------------------ | -------------------- |
| **第一道：Schema RAG 极速裁剪** | LLM 思考慢（Token太多） | 放弃全量元数据注入。使用轻量级 Embedding（如 BGE-M3），将元数据向量化。用户提问后，**只提取 Top-3 相关表和指标（约 800 Token）** 喂给 LLM。 | LLM 意图识别 < 1.5秒 |
| **第二道：MQL 引擎直译**        | 复杂 SQL 生成慢且易错   | **不让 LLM 写 SQL！** LLM 只输出结构化 JSON（MQL），后端的 .NET MQL 引擎基于预定义的公式，**纯内存拼装 SQL**。 | MQL 转 SQL < 50毫秒  |
| **第三道：分析库物化视图**      | 跨表 Join 查询慢        | 在 `MES_ANALYTICS` 中，针对高频指标（如日产量、良品率）建立 **SQL Server 索引视图（Indexed Views）**。查询直接命中预计算结果。 | 数据查询返回 < 1秒   |

**综合体验**：用户提问后，1.5秒出思考过程，2.5秒出数据图表，整体响应控制在 **3-4秒** 内，达到行业顶尖水平。

### 一、 无缝衔接的 4 条“铁律”（防冲突核查报告）

在下发代码前，我们必须向全体开发人员明确以下 4 条铁律，确保 Sprint 1 的产物完美嵌入 V5.2 基座：

1. **多租户铁律**：所有新建表（无论是配置表还是分析表）**必须**包含 `F_TENANT_ID`，且实体类**必须**继承现有的 `TenantEntity`。绝不能绕过现有的 `ITenantFilter` 拦截器，否则会导致跨租户数据泄露。
2. **主键与审计铁律**：放弃自增 ID。主键统一采用 `NVARCHAR(50)` (雪花算法/UUID)。必须包含标准审计字段（`F_CREATE_TIME`, `F_CREATOR_ID`, `F_MODIFY_TIME`, `F_MODIFIER_ID`, `F_DELETE_MARK`），复用现有的 `EntityBase`。
3. **ORM 映射铁律**：全面适配 **SqlSugar**。使用 `[SugarTable]` 和 `[SugarColumn]` 特性，确保与 V5.2 的 `SqlSugarScope` 多租户/多库路由机制兼容。
4. **物理隔离铁律**：**“配置数据”与“分析数据”分库**。指标字典（`BASE_METRIC_*`）属于平台配置，放在**主业务库**；数据湖宽表（`DW_*`）属于分析数据，放在**分析库（MES_ANALYTICS）**。通过 SqlSugar 的 `[TenantAttribute]` 实现路由。

### 二、 数据库建表脚本 (SQL Server)

#### 2.1 主业务库：语义层配置表（设计态/配置态）

*存放指标字典、元数据，供 Studio 后台管理和 AI Schema RAG 检索使用。*

```sql
-- ========================================
-- 1. 数据实体(表)元数据定义
-- ========================================
CREATE TABLE BASE_META_ENTITY (
    F_ID                     NVARCHAR(50)   NOT NULL PRIMARY KEY,
    F_TENANT_ID              NVARCHAR(50)   NOT NULL,          -- [铁律1] 多租户隔离
    F_PHYSICAL_TABLE         NVARCHAR(200)  NOT NULL,          -- 物理表名 (如: DW_WORK_ORDER)
    F_BUSINESS_NAME          NVARCHAR(200)  NOT NULL,          -- 业务名称 (如: 生产工单)
    F_DESCRIPTION            NVARCHAR(MAX)  NULL,              -- 业务描述 (喂给LLM)
    F_DOMAIN                 NVARCHAR(50)   NULL,              -- 领域: production/quality/equipment
    F_AI_VISIBLE             BIT            DEFAULT 1,         -- 是否对AI可见
    F_AI_SAMPLE_QUERIES      NVARCHAR(MAX)  NULL,              -- JSON: 示例提问
    F_RELATED_ENTITIES       NVARCHAR(MAX)  NULL,              -- JSON: 关联实体及Join条件
    F_DELETE_MARK            INT            DEFAULT 0,         -- [铁律2] 软删除
    F_CREATE_TIME            DATETIME       NULL,
    F_CREATOR_ID             NVARCHAR(50)   NULL,
    F_MODIFY_TIME            DATETIME       NULL,
    F_MODIFIER_ID            NVARCHAR(50)   NULL
);
CREATE INDEX IX_META_ENTITY_TENANT ON BASE_META_ENTITY(F_TENANT_ID, F_DOMAIN);

-- ========================================
-- 2. 指标字典 (核心护城河)
-- ========================================
CREATE TABLE BASE_METRIC_DEFINITION (
    F_ID                     NVARCHAR(50)   NOT NULL PRIMARY KEY,
    F_TENANT_ID              NVARCHAR(50)   NOT NULL,
    F_METRIC_CODE            NVARCHAR(100)  NOT NULL,          -- 唯一编码 (如: yield_rate)
    F_METRIC_NAME            NVARCHAR(200)  NOT NULL,          -- 显示名称 (如: 良品率)
    F_SYNONYMS               NVARCHAR(MAX)  NULL,              -- JSON: 同义词/黑话 ["合格率","直通率"]
    F_CATEGORY               NVARCHAR(50)   NULL,              -- quality/production/efficiency
    
    -- 计算定义 (MQL引擎依赖)
    F_METRIC_TYPE            NVARCHAR(20)   NOT NULL,          -- basic(基础)/derived(派生)/ratio(比率)
    F_FORMULA                NVARCHAR(MAX)  NULL,              -- 公式 (如: pass_qty / total_qty * 100)
    F_BASE_TABLE             NVARCHAR(200)  NOT NULL,          -- 基础数据表 (关联 F_PHYSICAL_TABLE)
    F_AGGREGATION            NVARCHAR(20)   NULL,              -- SUM/COUNT/AVG/MAX/MIN
    
    -- 维度与过滤
    F_AVAILABLE_DIMENSIONS   NVARCHAR(MAX)  NULL,              -- JSON: 可用分析维度 ["workshop","line"]
    F_DEFAULT_FILTERS        NVARCHAR(MAX)  NULL,              -- JSON: 默认过滤 (如排除试产工单)
    F_TIME_FIELD             NVARCHAR(100)  NOT NULL,          -- 统一时间口径字段
    
    -- 主动感知预埋 (第二期)
    F_ALERT_THRESHOLD        NVARCHAR(MAX)  NULL,              -- JSON: 预警阈值 {"min":90, "max":100}
    
    -- AI 增强 (Schema RAG 依赖)
    F_AI_DESCRIPTION         NVARCHAR(MAX)  NULL,              -- 给AI的完整口径说明
    F_SAMPLE_MQL             NVARCHAR(MAX)  NULL,              -- JSON: Few-Shot 示例MQL
    
    -- 知识图谱关联预留 (与 Sprint 0-B 衔接)
    F_KNOWLEDGE_NODE_ID      NVARCHAR(50)   NULL,              -- 关联 BASE_KNOWLEDGE_NODE 的ID

    F_DELETE_MARK            INT            DEFAULT 0,
    F_CREATE_TIME            DATETIME       NULL,
    F_CREATOR_ID             NVARCHAR(50)   NULL,
    F_MODIFY_TIME            DATETIME       NULL,
    F_MODIFIER_ID            NVARCHAR(50)   NULL
);
CREATE UNIQUE INDEX IX_METRIC_CODE ON BASE_METRIC_DEFINITION(F_TENANT_ID, F_METRIC_CODE);
```

#### 2.2 分析库 (MES_ANALYTICS)：数据湖宽表（运行态）

*存放从生产库同步过来的业务数据，供 MQL 引擎查询。*

```sql
-- 在 MES_ANALYTICS 数据库中执行
-- ========================================
-- 数据湖宽表：生产工单 (示例)
-- ========================================
CREATE TABLE DW_WORK_ORDER (
    F_ID                     NVARCHAR(50)   NOT NULL PRIMARY KEY,

    F_WORKSHOP_ID            NVARCHAR(50)   NULL,              -- 车间ID (维度)
    F_PRODUCT_LINE_ID        NVARCHAR(50)   NULL,              -- 产线ID (维度)
    F_PRODUCT_ID             NVARCHAR(50)   NULL,              -- 产品ID (维度)
    F_ORDER_STATUS           NVARCHAR(50)   NULL,              -- 状态
    F_ORDER_TYPE             NVARCHAR(50)   NULL,              -- 类型 (正常/试产)
    
    -- 度量值 (Metrics)
    F_PLAN_QTY               INT            NULL,              -- 计划数量
    F_COMPLETED_QTY          INT            NULL,              -- 完成数量
    F_PASS_QTY               INT            NULL,              -- 合格数量
    F_REWORK_QTY             INT            NULL,              -- 返工数量
    
    -- 时间维度 (统一口径)
```

### 六、 架构师的“避坑”特别提示（防烂尾指南）

1. **关于 JSON 字段的编辑**：`F_SYNONYMS` 和 `F_SAMPLE_MQL` 是 JSON 字符串。在 JNPF 前端生成表单时，**不要**让业务人员直接手敲 JSON（极易格式错误导致系统崩溃）。**必须**使用 JNPF 现有的“子表格/动态标签”组件，在前端组装成数组后，`JSON.stringify()` 传给后端。
2. **关于分析库的权限**：`MES_ANALYTICS` 数据库的 SQL 账号，**绝对不能**赋予 `db_owner` 权限。只赋予 `db_datareader`（读）和特定表的 `db_datawriter`（写）。从物理层面杜绝 AI 误操作删库的可能。
3. **关于多租户同步**：增量同步服务在拉取生产库数据时，**必须**带上 `TenantId` 过滤！千万不要把 A 租户的生产数据，同步到了 B 租户的分析库里。这是 SaaS 系统的死穴。
