## 一、总体纲要(总)

### 1.1 项目定位

> **在 8 周内交付一个面向 100 租户 SaaS MES 的"轻量级 AI 数据中台",支持业务数据(非传感器数据)的自然语言查询、口径治理、跨租户隔离、成本可控,具备 0→100 租户平滑演进能力。**

**三大铁律**(不可妥协):

| 铁律         | 内容                                                        | 否决项                          |
| ------------ | ----------------------------------------------------------- | ------------------------------- |
| **轻量起步** | 阶段一用最小必要组件,SQL Server + Redis + 小模型 + 异步队列 | 不引入 Hadoop/Spark/Kafka/Flink |
| **平滑演进** | 所有组件通过标准接口接入,阶段一应用代码不重写               | 不做"写死在代码里"的方案        |
| **成本可控** | 单租户月摊销 ≤ 1500 元,LLM 成本 ≤ 总运营 30%                | 不做"无限制 Token 消耗"的方案   |

### 1.2 范围与边界(明确)

**做**(第一期 8 周):
- ✅ 100 租户 SaaS 多租户架构
- ✅ MES 业务数据(工单/报工/质检/设备主数据/物料主数据/人员主数据/排班/库存)
- ✅ 30 个 MES 核心指标(预定义 + 业务可配置)
- ✅ 自然语言查询(AI 业务助手)
- ✅ 主动预警(简化版)
- ✅ 跨租户隔离 + 审计

**不做**(明确划清边界):
- ❌ **传感器数据接入**(留给"工业智能事业部",v4.0 已规划)
- ❌ **预测维修 / 设备健康度**(留给 v4.0 第三期)
- ❌ **生产流程优化 / 排产优化**(留给 v4.0 第三期)
- ❌ **电力损耗优化**(留给 v4.0 第三期)
- ❌ **数字孪生 / 3D 可视化**(留给 v4.0 第三期)
- ❌ **时序数据库 / 流处理 / ML 平台**(留给 v4.0 第三期)
- ❌ **流程/表单/报表引擎 AI 化**(留给第二期)
- ❌ **移动端集成**(留给第二期)

### 1.3 关键名词定义(消除歧义)

| 名词            | 定义                                                         | 不包含                             |
| --------------- | ------------------------------------------------------------ | ---------------------------------- |
| **轻量数据湖**  | 基于 SQL Server + Redis + 小模型的轻量化数据中台,服务 MES 业务数据 | 不包含时序库、Hadoop、Spark        |
| **AI 业务助手** | 基于自然语言的 MES 业务数据查询工具                          | 不包含控制设备执行、写入数据       |
| **业务数据**    | 来自 MES/ERP/OA 的离散业务数据(工单、报工、质检)             | 不包含 IoT 传感器连续流数据        |
| **指标**        | 可量化的业务度量(良品率、OEE、计划达成率)                    | 不包含设备物理参数(振动、温度)     |
| **AI 推理**     | 基于 LLM 的意图识别、结果解读                                | 不包含 ML 模型训练/部署(留给 v4.0) |

### 3.2 关键架构原则

1. **共享库优先**: 阶段一(0-20 租户)用共享库 + 强化 RLS,降低运维成本
2. **资源严格隔离**: 每租户最大 5% CPU,单租户异常不影响其他租户
3. **缓存多层**: L1 本地 + L2 Redis,目标命中率 ≥ 70%
4. **异步削峰**: 同步链路 Channel 异步队列,避免冲击分析库
5. **LLM 分流**: 80% 简单查询走本地小模型,20% 复杂查询走云端大模型
6. **接口标准化**: 所有组件通过标准接口(SQL/HTTP)接入,阶段二/三可平滑替换

### 3.3 租户隔离的分级设计

```
┌─────────────────────────────────────────────────────┐
│  阶段一(0-20 租户): 共享 OLTP + 共享 OLAP            │

│  · 资源池隔离(每租户 5% CPU)                        │
│  · 审计日志分租户表存储                              │

  MIN_CPU_PERCENT = 0,
  MAX_CPU_PERCENT = 5,           -- 最大 5% CPU
  MIN_MEMORY_PERCENT = 0,
  MAX_MEMORY_PERCENT = 5         -- 最大 5% 内存
);

CREATE WORKLOAD GROUP TenantGroup_T001
USING TenantPool_T001;

-- 分类器函数:根据登录名自动路由
CREATE FUNCTION dbo.RG_TenantClassifier()
RETURNS SYSNAME
WITH SCHEMABINDING
AS
BEGIN
  DECLARE @group SYSNAME = 'default';
  IF SUSER_NAME() LIKE 'tenant_user_%'
  BEGIN
    SET @group = 'TenantGroup_' + SUBSTRING(SUSER_NAME(), 13, 10);
  END
  RETURN @group;
END;

ALTER RESOURCE GOVERNOR WITH (CLASSIFIER_FUNCTION = dbo.RG_TenantClassifier);
ALTER RESOURCE GOVERNOR RECONFIGURE;

### 5.4 限流策略(Sentinel 配置)

// 租户级限流规则
var rules = new List<FlowRule>
{
    // 全局:总 QPS 上限 1000
    new FlowRule("global_ai_query")
        .SetGrade(RuleConstant.FLOW_GRADE_QPS)
        .SetCount(1000),
    
    // 租户级:单租户 QPS 上限
    new FlowRule($"tenant_{tenantId}_ai_query")
        .SetGrade(RuleConstant.FLOW_GRADE_QPS)
        .SetCount(50),  // 单租户 50 QPS
    
    // 慢查询熔断
    new DegradeRule($"tenant_{tenantId}_slow")
        .SetGrade(RuleConstant.DEGRADE_GRADE_RT)
        .SetCount(5000)  // 响应时间 > 5s 熔断
        .SetMinRequestAmount(10)
        .SetStatWindowMs(30000)
        .SetSlowRatioThreshold(0.5),  // 50% 慢查询熔断
};

## 七、运维与监控(分)

### 7.1 监控指标体系(三层)

**L1 基础设施层**:
- CPU / 内存 / 磁盘 / 网络
- 数据库连接数 / 死锁 / 慢查询
- 缓存命中率 / 内存使用

**L2 应用层**:
- 同步延迟 / 同步失败率 / 死信队列长度
- 端到端 P50/P95/P99 延迟
- LLM 推理延迟 / Token 消耗
- SQL 查询 P50/P95/P99

**L3 业务层(按租户)**:
- 每租户查询 QPS / 延迟
- 每租户 LLM Token 消耗
- 每租户同步延迟
- 每租户缓存命中率
- 每租户异常率

### 7.2 告警分级

| 级别        | 触发条件                             | 通知方式    | 响应时间 |
| ----------- | ------------------------------------ | ----------- | -------- |
| **L1 紧急** | 同步中断 / 数据库宕机 / 多租户故障   | 钉钉 + 电话 | 5 分钟   |
| **L2 警告** | P95 超阈值 / 单租户异常 / 成本超预算 | 钉钉        | 30 分钟  |
| **L3 提示** | 缓存命中率低 / 资源利用率高          | 邮件        | 4 小时   |

### 7.3 降级方案(四级)

```
正常: NL → LLM → MQL → SQL → DB
  ↓ LLM 不可用
降级一: NL → 模板匹配 → MQL → SQL → DB
  ↓ Schema RAG 不可用
降级二: NL → 全量元数据 → LLM → MQL → SQL
  ↓ 同步延迟过高
降级三: NL → LLM → MQL → 生产库只读副本
  ↓ 分析库不可用
降级四: 缓存 → 返回历史数据(标注时间)
```

## 十、演进路径:0 → 20 → 50 → 100 租户(总)

### 10.1 阶段一(0-20 租户,本计划 8 周)

- **架构**: 共享库 + 强化 RLS + 单机 SQL Server + Redis + Ollama
- **能力**: 30 个指标 + 自然语言查询 + 主动预警
- **成本**: 4.8 万/月,单租户 2400 元/月
- **风险**: 中(RLS 测试覆盖度决定)

### 10.2 阶段二(20-50 租户,触发式演进,8-10 周)

**触发条件**(满足任一):
- 租户数 > 20
- 总日增量 > 1 亿行
- 单租户 QPS > 50
- 大租户(年付 > 50 万) > 3 个

**架构演进**:
- 大租户独立 OLAP 库(资源物理隔离)
- Redis Cluster(3 主 3 从)
- AlwaysOn 读写分离(只读副本承担分析查询)
- Schema RAG 改为共享倒排 + 租户级二级索引
- 早报预计算(凌晨 3:00 算好)

**成本**: 8 万/月,单租户 1600 元/月

### 10.3 阶段三(50-100 租户,触发式演进,8-10 周)

**触发条件**(满足任一):
- 租户数 > 50
- 大租户 > 10 个
- 任意租户数据 > 10 亿行
- 月 LLM 成本 > 5 万

**架构演进**:
- 引入 ShardingSphere 分库分表
- ClickHouse 集群(分析查询专用)
- Kafka 替换 Channel(分布式消息队列)
- 边缘 LLM 缓存 + 结果预计算
- 跨租户全局查询独立集群
- 灰度发布平台 + 租户级 SLA 监控

**成本**: 14.6 万/月,单租户 1460 元/月

### 10.4 演进路径图

```

  ┌──────────────────────────┐
