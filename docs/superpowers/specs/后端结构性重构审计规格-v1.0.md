# 后端结构性重构审计规格 v1.0

**日期**：2026-08-25
**阶段**：S1-Final — Backend Structural Refactoring Audit（Audit / Discovery Only）
**前置**：D1 战役已关闭（5 条复杂度基线销账），S2 数据访问抽象闸门关闭
**核心原则**：只识别、不实施；先建立全后端重构地图，再由人工决定哪些必须在 S2 前处理。

---

## 1. 目标与最终回答的问题

对整个后端项目进行一次系统性的、可复核的结构性重构审计，识别与 D1 五项复杂度重构同类的问题、以及影响后续 S2「数据访问抽象」的候选重构点，形成自包含的《设计规格 + 扫描计划 + 候选问题登记表》。最终回答：

1. D1 已发现的五类问题是否只是局部问题，还是后端存在更广泛的同类结构性问题？
2. 除已完成的五项外，后端是否还有 P0/P1 级别的结构性重构点？
3. Q1-Q11 及 D1 期间发现的既有异常行为，哪些应进入 Legacy Behavior Registry？
4. 是否还有数据访问、租户、权限、序列化、条件构造、Repository/Service 耦合等问题，必须在 S2 前处理？
5. 哪些问题可以延期到 S2 或以后，不应阻塞当前架构演进？
6. 当前后端是否已具备进入 S2「数据访问抽象」设计阶段的条件？

## 4. D1 五方法背后的结构性问题模式（Refactoring Smell Pattern）

扫描必须按模式找，而非按名字找：

- **P1 高复杂度多分支**：大型 switch / 深层 if-else / 多级条件 / 条件组合爆炸
- **P2 单方法多职责**：一个方法同时承担解析/校验/转换/查询/权限/映射/序列化/错误处理/默认值
- **P3 门面+隐藏复杂逻辑**：表面方法短，内部调用复杂 Helper 链（门面 CC 低 ≠ 无问题）
- **P4 巨型 switch / 策略分派**：QueryType/ConditionalType/FieldType/ControlType/Enum/Type switch，检查是否应拆 Strategy/Handler/Resolver/Mapper/Registry（只识别不实施）
- **P5 数据结构/JSON 隐式契约**：anonymous object / JObject / JSON string / ToJsonString / Deserialize / Serialize / Dictionary&lt;string,object&gt; / object / 字符串承载结构化数据；「属性名+JSON+枚举数值」隐式跨层契约
- **P6 数据访问与业务逻辑混合**：Service 直接操作 ORM / Service 直接构造 DB 条件 / Repository 混入业务规则 / Helper 同时做业务+DB / 数据访问对象携带业务语义（S2 前最重要候选）

## 6. 扫描指标（复杂度盘点）

- Cyclomatic Complexity（复用 `CyclomaticComplexityWalker` 同源口径）
- Cognitive Complexity：**[NOT MEASURED]**（工具不支持，以嵌套深度+分支数近似并如实标注）
- 方法长度（LOC）、参数数量、嵌套深度、分支数、switch case 数、if/else 数、try/catch 数、return 数、调用数
- 分层：A 类 CC≥30 / B 类 20-29 / C 类 15-19
- **禁止只按 CC 排名决定优先级**，必须结合职责/依赖/行为风险/调用范围判断

## 7. 候选分级标准

| 等级 | 定义 |
|------|------|
| **P0** | S2 前必须处理：数据权限语义可能在 S2 被破坏 / 租户边界不清 / 严重跨层依赖 / 隐式契约无保护 / 高复杂度+高扇出+核心链路 |
| **P1** | 强烈建议 S2 前处理：职责明显混杂 / 高复杂度 / 数据访问与业务严重耦合 / 重复策略 / 大型分派器 |
| **P2** | 后续技术债，不阻塞 S2 |
| **P3** | 优化项，不进入本战役 |

登记表字段：ID / 方法或类 / 问题类型 / CC / 影响范围 / 行为风险 / S2 风险 / 建议等级。

## 8. 排除/冻结清单（Freeze）

- 已完成 D1 且通过等价证明的代码
- 关键兼容接口、外部 API、序列化契约、数据权限契约
- Legacy Behavior（L0/L1 级）
- 第三方集成边界
- 暂无充分测试保护的核心逻辑
- 原则：**没有行为保护，就不能因为静态指标漂亮而直接重构**

## 9. Legacy Behavior Registry 分级

| 级 | 定义 |
|----|------|
| L0 | 必须保持，任何阶段禁止改变 |
| L1 | S2 期间必须有回归测试 |
| L2 | 已知异常，暂不修复 |
| L3 | 未来行为变更候选 |

登记项：Q1-Q11 + D1 施工期发现（空 between 抛异常 / 真实嵌套数组抛异常 / Contains default / "null" 字符串 / 非列表 Equal fallback / 特殊 whereType）+ 扫描新发现。**不允许因行为「看起来错误」自动修复。**

## 10. S2 准入判定（Gate A-G）

| Gate | 问题 | 判定 |
|------|------|------|
| A | 结构债务 | 是否还有 P0/P1 |
| B | 数据访问 | 是否存在未解决的关键数据访问耦合 |
| C | 租户/权限 | 是否已明确数据权限与租户不变量 |
| D | 行为 | Q1-Q11 是否全部登记并具有必要测试保护 |
| E | 隐式契约 | 关键隐式契约是否已识别 |
| F | 测试 | 关键链路是否有足够特征/契约测试 |
| G | 架构 | 是否存在尚未解决的跨层依赖 |

最终只允许输出 **S2 READY** 或 **S2 BLOCKED**，禁止模糊输出；BLOCKED 必须列出解除条件。

## 11. 证据要求

所有重要结论必须可追溯到：文件 / 类 / 方法 / 行号 / 测试 / 工具输出 / git commit。禁止「看起来复杂」；必须形如 `xxx.cs:L123-L218，CC=37，Fan-in=12，直接依赖 IRepository+SqlSugar，已有测试 X/Y，属于 P1`。

## 12. F1/F3 纪律

- **F1 实测优先**：静态推断 ≠ 实际行为时，以实际代码/测试/执行结果为准；不得为符合预期修改实现。
- **F3 规格偏差必须停**：发现既有规格与实际不一致 / 原始 DoD 不可达 / 架构边界与文档不一致 / 既有假设被源码推翻 → 停止该项判断、记录事实、给出影响、提出选项、等待人工裁决。禁止擅自降低标准/修改规格/重登基线/开始重构。

## 14. 停止条件（最重要的规则）

无论审计结果如何，都不得自行进入 S2；发现 P0/P1 → 停止提交候选清单等人工批准；无 P0/P1 → 也停止提交 S2 Readiness Review 等人工批准。

```text
Audit → Report → STOP → Human Decision
```
