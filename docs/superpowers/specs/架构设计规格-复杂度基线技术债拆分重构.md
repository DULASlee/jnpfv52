## 3. 拆分设计：职责划分与方法边界（P3 接口契约级）

**总模式**：表驱动 + 分派器（复杂 switch → 纯映射查表 + 专项发射器）；**原公开方法保留为薄门面**，内部委托新私有/内部静态成员；无新增公共 API、无 DI、无状态（纯静态纯函数）。以下签名均为契约（禁止方法体先行实现之外的语义偏移）。

### 3.1 Rewrite（CC 84 → 目标：门面 ≤ 10，最大子方法 ≤ 14）

## 5. 测试与验收标准

每方法统一验收（逐项硬门控）：

1. **特征等价**：重构前捕获的全分支特征集，重构后逐条字节等价（JSON 用 `ToJsonStringOld` 原文比对）；
2. **既有测试全绿**：对应测试项目 `dotnet test` 0 失败（VisualDev/Common 套件）；
3. **复杂度实证**：拆分后门面与全部子方法 CC < 30（CI `/p:CI_BUILD=true` 通过且基线条目下调/移除后不再豁免）；
4. **基线销账**：`complexity-baseline.json` 对应条目移除（或先行下调至实测值），方法 TODO 注释同步清除；
5. **契约不变**：签名反射断言测试（参数表/返回类型逐字一致）；
6. **全解构建 0 错** + 路由快照与基线零 diff（`JNPF.Startup.Benchmarks --mode routes`，1077/107）。

战役级验收：5 方法全部完成上述 6 项 + `TECH-DEBT.md` 卡片移入「已解决」区 + 分析器测试 23/23 绿。

## 6. 回滚方案

- 每方法独立提交（含：拆分代码 + 特征用例 + 基线变更），`git revert <hash>` 单点回滚即恢复原实现 + 原基线豁免（基线条目在同一提交内变更，回滚自洽）；
- 重构期间基线条目保持冻结值不动，直到该方法验收通过才在同一提交内销账 → 任何中间态均不产生 CI 破窗；
- 若单方法拆分后特征比对失败：直接丢弃工作区变更（提交前门禁），不进入提交历史。

## 7. 优先级与执行节点

| 波次 | 方法 | 优先级 | 理由 |
|------|------|--------|------|
| Wave 1（P0） | **Rewrite CC84 → ≤10**、**Bind CC82 → ≤12** | 最高 | 复杂度显著偏高（用户特别关注）；收益最大；已有较强测试安全网 |
| Wave 2（P1） | ApplyMapRules CC37 → ≤10、ValidateBatchUnique CC35 → ≤12 | 中 | 中等超标；导入/迁移链路 |
| Wave 3（P2） | Append CC31 → ≤8 | 常规 | 超标幅度最小；但处数据权限核心链路，单独一波次保证回归专注度 |

**执行节点**（防遗忘硬绑定）：

1. 战役启动节点 = **本战役（运行时基座与 RunService 引擎化）Task 3.6 S1 门禁通过后的下一工作日**，以独立战役 `D1` 立项施工，不与在途战役混提交；
2. 每波次为一个**节点审批单元**：波次完成 → 提交「业务实现 + 质量自检 + 功能证据 + 验收对照」→ 用户审批 → 下一波次；
3. 销账闭环：每方法验收通过即从基线移除条目并更新 `TECH-DEBT.md`；Wave 3 完成后债务卡片整体移入「已解决」；
4. 若 D1 启动前任何方法因其他战役被触及，按「只许下降」纪律顺带改善并在看板登记，不等 D1。
