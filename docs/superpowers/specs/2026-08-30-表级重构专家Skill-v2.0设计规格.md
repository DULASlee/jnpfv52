把 v1.0 的 **Database Audit Skill** 升级为 **Schema Evolution Skill**：

| 维度 | v1.0（已冻结） | v2.0（本规格） |
|------|---------------|---------------|

| **Security 优先级** | 与性能并列 | **优先于一切** |

```
IRON-TABLE-09  Evidence Over Declaration      完成声明必须绑定证据
IRON-TABLE-10  Batch Completion Requires Representative Proof  1 复杂 + 1 普通 + 1 动态
```

## 1. 升级背景与必要性

### 1.1 v1.0 暴露的结构性缺陷（Phase 8 反查实证）

**v1.0 错误收敛**：

```
表级重构（意图）
    ↓ 收敛为
数据库治理 + 索引优化 + 台账化改造（v1.0 实际产出）
```

**v1.0 缺少的 4 类能力**：

| # | 缺失能力 | Phase 8 实证 |
|---|---------|--------------|
| 1 | **Target Schema Contract** | 17/244 处"SchemaChange=Yes"全是列名代理绕过（F_ApplyUser→F_InputPerson），无真源 |
| 2 | **No-Change 证明机制** | 154 张 NO-CHANGE 表只证明"没找到问题"，未证明"符合目标" |
| 3 | **Schema Migration 分类治理** | 静态命名错误 + 业务语义变化 + 低代码动态字段 混为一谈 |
| 4 | **Performance Measurement** | "加索引=加速"是逻辑错误，但 v1.0 无验证机制 |

### 1.2 JNPF 低代码平台的特殊性

**v1.0 误判**：把所有表当通用业务表处理。

**JNPF 真实情况**：

```
数据库字段
    ↓
动态表单（lowcode 表）
    ↓
动态权限（authorize 表）
    ↓
流程引擎（flow 表）
    ↓
SQL 生成器（codegen 表）
```

→ 直接 ALTER COLUMN 会破坏动态配置链路。

### 1.3 v2.0 必须解决的 3 类问题

```
Q1: 什么字段可以安全改名？什么字段禁止改名？
    → Schema Migration Governance 三分类

Q2: NO-CHANGE 如何证明？证据是什么？
    → Target Schema Contract 8 维度验收

Q3: 加了索引真能加速吗？加速多少？
    → Before/After Measurement 强制门槛
```

## 4. 10 条 Iron Laws（不可违反）

### IRON-TABLE-01  No Change ≠ No Action

**规则**：NO-CHANGE 是有效的最终状态，但必须证明**符合 Target Schema Contract**。

**禁止**：

```sql
❌ "扫了一遍表，没找到问题" → NO-CHANGE
❌ "表太小（<100行），不需要索引" → NO-CHANGE
❌ "已经有覆盖索引" → NO-CHANGE（未证明符合 Target）
```

**必须**（NO-CHANGE 必须产出 8 维度验收证据）：

```yaml
no_change_evidence:
  column_naming: PASS       # 列名符合 Target Schema Contract
  data_type: PASS           # 数据类型符合 Target Schema Contract
  nullable_contract: PASS   # 必填/可空符合 Target Schema Contract
  tenant_model: PASS        # 租户字段存在 + 类型符合
  audit_model: PASS         # 审计字段存在 + 类型符合
  index_contract: PASS      # 索引符合 Target Schema Contract
  constraint_contract: PASS # 约束符合 Target Schema Contract
  security_boundary: PASS   # 身份/权限字段符合 Security Boundary

verdict: NO-CHANGE          # 全部 PASS 才能下此结论
```

**违反后果**：立即停工，必须补齐缺失的验证维度。

### IRON-TABLE-02  Mapping Is Not Migration

**规则**：列名映射（F_ApplyUser → F_InputPerson 在 SQL 中以 `F_InputPerson AS F_ApplyUser` 形式）**不等于** Schema Migration。

**禁止**：

```sql
❌ CREATE VIEW v_alias AS SELECT F_InputPerson AS F_ApplyUser FROM ...
❌ SELECT F_Name AS F_CaseCode FROM ...  -- 用 F_Name 当 F_CaseCode 用
❌ 在 Entity 层加 [Column("F_InputPerson")] 而 DB 仍是 F_ApplyUser
```

**必须**（三选一）：

```sql
✅ 真迁移（sp_rename）：
   EXEC sp_rename 'dbo.base_user.F_ApplyUser', 'F_InputPerson', 'COLUMN';

✅ 双写兼容（带显式 deprecated 标记）：
   - 新字段 F_InputPerson
   - 旧字段 F_ApplyUser 标记 DEPRECATED
   - 6 个月兼容期
   - 必须有迁移脚本 + Entity 双字段

✅ 业务字段语义变化（增加新字段而非改名）：
   ALTER TABLE wform_contractapproval ADD F_InputPerson nvarchar(50) NULL;
   -- 保留 F_ApplyUser，数据由应用层决定如何处理
```

**判定矩阵**：

| 类型 | 处理 | 示例 |
|------|------|------|
| 纯技术命名错误 | 直接 sp_rename | `f_id` 拼写错误 |
| 业务字段语义变化 | 增加新字段 + 数据迁移 | `F_ApplyUser` → `F_InputPerson`（语义变化） |
| 低代码动态字段 | **禁止自动改名** | `wform_*` 动态表单字段 |
| Entity/Repository 引用字段 | 必须跟随 DB 真名 | SqlSugar `[SugarColumn]` 同步 |

### IRON-TABLE-03  Every Table Needs Target Contract

**规则**：每张被 Skill 处理的表，必须有 Target Schema Contract。

**Target Schema Contract 8 维度**（必须全部填写）：

```yaml
target_schema_contract:
  table_name: base_user
  
  # 维度 1: 列命名规范
  column_naming:
    rule: PascalCase_with_f_prefix
    allowed_patterns: [f_*]
    forbidden_patterns: [F_*, F_*, f_*, all_caps]
  
  # 维度 2: 数据类型规范
  data_type:
    id: nvarchar(50)   # GUID 字符串
    code: nvarchar(50)
    name: nvarchar(200)
    description: nvarchar(500)
    content: nvarchar(max)
    created_time: datetime2(7)   # 必须 datetime2(7)
    amount: decimal(18,4)
    flag: int                    # 0/1 布尔
  
  # 维度 3: 可空契约
  nullable_contract:
    id: NOT NULL
    tenant_id: NOT NULL          # 多租户隔离硬保证
    account: NOT NULL
    f_delete_mark: NOT NULL DEFAULT 0
  
  # 维度 4: 租户模型
  tenant_model:
    type: SHARED_COLUMN          # 共享列式（不是 SHARED_SCHEMA / SHARED_DB）
    column: f_tenant_id
    isolation_level: STRICT      # 不允许 NULL tenant_id
  
  # 维度 5: 审计模型
  audit_model:
    created_at: f_creator_time
    created_by: f_creator_user_id
    updated_at: f_last_modify_time
    updated_by: f_last_modify_user_id
    deleted_at: f_delete_time
    deleted_by: f_delete_user_id
    soft_delete: true            # 软删除模式（vs 硬删除）
  
  # 维度 6: 索引契约
  index_contract:
    primary_key: f_id
    required_indexes:
      - name: UK_tenant_account
        columns: [f_tenant_id, f_account]
        type: UNIQUE
      - name: IDX_tenant_created
        columns: [f_tenant_id, f_creator_time DESC]
    performance_baseline_required: true
  
  # 维度 7: 约束契约
  constraint_contract:
    foreign_keys: []   # 由 Repository 层维护（v2.0 暂不强制 FK）
    check_constraints:
      - name: CK_enabled_mark
        expression: f_enabled_mark IN (0, 1)
      - name: CK_delete_mark
        expression: f_delete_mark IN (0, 1)
  
  # 维度 8: 安全边界
  security_boundary:
    sensitive_columns:
      - f_password_hash       # 必须有 f_password_algo 配套
      - f_secretkey           # Salt 字段
    encryption: REQUIRED       # 必须加密
    password_algorithm:
      current: PBKDF2_SHA256  # 100000 iterations
      forbidden: [MD5, SHA1]  # 禁止弱哈希
```

### IRON-TABLE-04  Security Boundary First

**规则**：任何涉及 Identity / Tenant / Permission / User 的表，必须**最先**审计。

**审计优先级**：

```
P0-Security 边界（必须先做）：
  - base_user / base_organize / base_role / base_authorize
  - 所有含 f_password / f_password_hash 的表
  - 所有含 f_tenant_id 的表
  - 所有含 f_account 的表

P1-Business 核心：
  - flow_task / flow_task_node
  - base_message / base_notice

P2-Business 辅助：
  - wform_* / ext_*
```

**审计清单**（每张 P0 表必须完成）：

```yaml
security_boundary_audit:
  password_storage:
    algorithm: PASS            # PBKDF2 / Argon2id
    field_length: PASS         # >= nvarchar(255)
    salt_separated: PASS       # salt 独立字段
  
  tenant_isolation:
    column_nullable: PASS      # NOT NULL
    unique_with_account: PASS  # UNIQUE(f_tenant_id, f_account)
  
  account_uniqueness:
    constraint_exists: PASS
    covers_soft_delete: PASS   # 部分唯一索引 WHERE f_delete_mark = 0
  
  sensitive_data:
    pii_encryption: PASS       # 手机号/身份证/邮箱至少哈希
    audit_trail: PASS          # 所有修改有 f_creator_time / f_last_modify_time
```

### IRON-TABLE-05  Performance Claim Requires Measurement

**规则**：禁止"加索引 = 性能提升"的逻辑推理。

**必须产出**（每张 REFACTORED 表）：

```yaml
performance_evidence:
  before:
    timestamp: 2026-08-30T10:00:00Z
    query: "SELECT * FROM base_message WHERE f_user_id = 'X' AND f_is_read = 0"
    logical_reads: 128
    cpu_ms: 35
    duration_ms: 42
    execution_plan: plan-before.xml
  
  after:
    timestamp: 2026-08-30T11:00:00Z
    query: 同上
    logical_reads: 12        # 必须下降
    cpu_ms: 5               # 必须下降
    duration_ms: 8          # 必须下降
    execution_plan: plan-after.xml
  
  improvement:
    logical_reads_reduction: 90%      # >= 50% 才算有效
    duration_reduction: 80%
    verified_by: p95_query_benchmark.sql
  
verdict: PERFORMANCE_VERIFIED
```

**禁止**：

```
❌ "添加索引 IDX_X" → 不产出 measurement
❌ "理论上应该更快" → 无证据
❌ "SQL Server 文档说加索引会更快" → 复制文档
```

**测量方法**（标准 SOP）：

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Before / After 都执行同一查询
SELECT TOP 100 * FROM <table> WHERE <query>;
-- 记录：logical reads / CPU time / elapsed time
```

### IRON-TABLE-06  Migration First-Class

**规则**：表级重构的交付物**不是报告**，而是**可执行的 Migration Artifact**。任何 SchemaChange 必须产生完整的 4 件套，否则不算完成。

**强制产出**（每个 SchemaChange）：

```
/database/migrations/
├── V20260831_<change_id>.sql              # Forward Migration
├── V20260831_<change_id>_down.sql         # Rollback Migration
├── V20260831_<change_id>_verify.sql       # Validation Script
└── V20260831_<change_id>_evidence.json    # Evidence Bundle
```

**Evidence Bundle 必须包含**：

```yaml
migration_evidence:
  change_id: "V20260831_base_user_password_fields"
  forward_sql: "scripts/migrations/V20260831_base_user_password_fields.sql"
  rollback_sql: "scripts/migrations/V20260831_base_user_password_fields_down.sql"
  validation_sql: "scripts/migrations/V20260831_base_user_password_fields_verify.sql"
  
  pre_execution:
    schema_snapshot: "snapshots/pre/base_user_schema.json"
    row_count: 12345
    index_snapshot: "snapshots/pre/base_user_indexes.json"
  
  execution:
    timestamp: "2026-08-31T10:00:00Z"
    executor: "AI Engineer (Phase 1 Task 2.2)"
    duration_ms: 234
    tx_status: "COMMITTED"
  
  post_execution:
    schema_snapshot: "snapshots/post/base_user_schema.json"
    row_count: 12345           # 必须 == pre_execution
    index_snapshot: "snapshots/post/base_user_indexes.json"
  
  verification_results:
    - check: "f_password_hash NOT NULL allowed"
      result: PASS
    - check: "f_password_algo = 'LEGACY_MD5' populated"
      result: PASS
    - check: "row count unchanged"
      result: PASS
    - check: "no FK violations"
      result: PASS

verdict: MIGRATION_VERIFIED
```

**禁止**：

```yaml
❌ "已添加索引"  # 无 V*.sql 文件
❌ "已优化表结构"  # 无 rollback 脚本
❌ "已通过验证"  # 无 evidence.json
```

**违反后果**：必须补齐 4 件套，否则 SchemaChange 不计完成。

### IRON-TABLE-07  Runtime Compatibility First

**规则**：任何 Schema 改动必须证明运行时兼容。**不能仅验证 SQL Server 执行成功**。

**JNPF 运行时兼容性链路**（必须全链路验证）：

```
Database
   ↓
ORM（SqlSugar Entity）
   ↓
Repository（IRepository<T>）
   ↓
Dynamic SQL（codegen）
   ↓
Form Engine（lowcode_field）
   ↓
Workflow Engine（flow_form_data_json）
   ↓
Permission Engine（authorize）
```

**必须验证**（每层独立通过）：

```yaml
runtime_compatibility_check:
  db_layer:
    - "DDL 成功执行"
    - "事务原子性"
    - "无死锁"
  
  orm_layer:
    - "SqlSugar Entity 序列化/反序列化一致"
    - "[SugarColumn] 属性正确映射"
    - "Entity 反射契约 5/5 PASS"
  
  repository_layer:
    - "IRepository<T>.GetFirst/Insert/Update/Delete 全部通过"
    - "行数 COUNT 不变"
  
  dynamic_sql_layer:
    - "codegen 生成的 SQL 仍可执行"
    - "SQL 解析器不报错"
  
  form_engine_layer:
    - "lowcode_field 配置不丢"
    - "动态表单仍可加载"
  
  workflow_engine_layer:
    - "flow_form_data_json 引用不破"
    - "流程节点 SQL 仍可执行"
  
  permission_engine_layer:
    - "authorize 关联不破"
    - "权限过滤 SQL 仍可执行"
```

**禁止**：

```
❌ "SQL Server 执行成功" → 忽略其他层
❌ "Repository 测试通过" → 忽略 form/workflow/permission
❌ "单层验证 PASS" → 当作全链路 PASS
```

**违反后果**：必须补齐全链路验证，否则 SchemaChange 不计完成。

### IRON-TABLE-08  Dynamic Platform Exception

**规则**：低代码动态对象**禁止**普通 CRUD 重构规则。JNPF 是低代码平台，必须按对象类型分类治理。

**JNPF 表分类**：

| 类型 | 表名前缀/特征 | 处理规则 |
|------|--------------|---------|
| **系统核心表** | `base_*`（base_user, base_organize, base_module 等）| 严格重构（IRON-TABLE-04 P0-Security）|
| **业务实体表** | 业务模块名（如 `flow_*`, `ext_*` 中非动态部分）| 迁移治理（IRON-TABLE-02/03）|
| **动态表单表** | `wform_*`（内置流程表单动态字段）| 只治理元数据，**禁止自动改字段名** |
| **用户扩展表** | `ext_*` 用户运行时扩展 | 禁止自动改名（运行时创建）|

**Skill 必须识别**：

```python
def classify_table(table_name: str) -> TableType:
    name = table_name.lower()
    
    if name.startswith("wform_") or name.startswith("lowcode_"):
        return TableType.DYNAMIC_FORM  # Type C：禁止自动改
    
    if name.startswith("ext_") and "table_example" not in name:
        return TableType.USER_EXTENDED  # Type C：禁止自动改
    
    if name.startswith("base_") and name in P0_SECURITY_TABLES:
        return TableType.SYSTEM_CORE_SECURITY  # P0-Security 优先
    
    if name.startswith(("flow_", "blade_", "base_")):
        return TableType.BUSINESS_ENTITY  # 迁移治理
    
    if name.startswith(("wh_", "wm_")):
        return TableType.LEGACY_WAREHOUSE  # R3+ 默认 NO-CHANGE
    
    return TableType.UNKNOWN  # 默认 Type B 语义变化
```

**Type C 表 Skill 行为**：

```python
if table_type == TableType.DYNAMIC_FORM:
    return SkillResult(
        verdict="MANUAL_GOVERNANCE_REQUIRED",
        action="SKIP_AUTO_REFACTORING",
        reason="Low-code dynamic form field, runtime-configured"
    )
```

**禁止**：

```
❌ wform_* 表的字段直接 sp_rename
❌ ext_* 表的字段直接 ALTER COLUMN
❌ "AI 自动判断 + 直接执行" 对 Type C 表
```

**违反后果**：必须人工书面审批 + 业务方确认，否则禁止执行。

### IRON-TABLE-09  Evidence Over Declaration

**规则**：完成声明必须绑定证据。**禁止"已治理"等无证据声明**。

**正确格式**：

```yaml

      WHERE COLUMN_NAME = 'f_tenant_id' AND IS_NULLABLE = 'YES'

    validation_result:
      row_count: 0  # 0 行 = 全部 NOT NULL

      - base_user: NOT NULL ✓
      - base_organize: NOT NULL ✓
      - flow_task: NOT NULL ✓

```

**禁止**：

```
❌ "f_tenant_id 已治理"  # 无 SQL 引用
❌ "已完成 P0 修复"  # 无 evidence 文件
```

### IRON-TABLE-10  Batch Completion Requires Representative Proof

**规则**：每个 Batch 关闭必须包含代表性证明（1 复杂 + 1 普通 + 1 动态），**禁止纯 NO-CHANGE 批量关闭**。

**针对 v1 暴露问题**：

```

  11 tables
  ALL NO-CHANGE
```

→ 这是表级重构 Skill v2.0 必须避免的反模式。

**Batch 完成证明结构**：

```yaml
batch_completion_proof:
  batch_id: "Batch-NN"
  
  representative_coverage:
    complex_table:
      table_name: "<复杂表，如 base_user 或 flow_task>"
      decision: REFACTORED
      evidence: "<含完整 4 件套 evidence>"
    
    normal_table:
      table_name: "<普通表，如 base_message 或 ext_order>"

    dynamic_table:
      table_name: "<动态表，如 wform_xxx 或 ext_yyy>"

  total_tables: N
  verdict: BATCH_CLOSED
```

**禁止**：

```
❌ Batch 全部 NO-CHANGE 且无 representative 验证
❌ Batch 全部 SKIP_LOW_CODE_DYNAMIC（说明 Batch 选错了范围）
❌ Batch 关闭无 evidence bundle
```

**违反后果**：Batch 不允许关闭，必须补齐 representative proof。

## 6. Schema Migration Governance 三分类（核心）

### 6.1 类型识别

```
SchemaChange 检测到
    ↓
问三个问题：
  Q1: 这是纯技术命名错误吗？（如拼写错误、缩写不一致）
  Q2: 这是业务字段语义变化吗？（如 F_ApplyUser → F_InputPerson 语义变化）
  Q3: 这是低代码动态字段吗？（如 wform_* 表的动态配置字段）

Q1=Yes → 类型 A: Pure Technical
Q2=Yes → 类型 B: Semantic Change  
Q3=Yes → 类型 C: Low-Code Dynamic
```

### 6.2 类型 A：纯技术命名错误

**特征**：
- 拼写错误（typo）
- 大小写不一致但语义相同
- 命名风格统一化（snake_case → camelCase）

**处理**：

```sql
-- 直接 sp_rename
EXEC sp_rename 'dbo.base_user.fOpenId', 'f_open_id', 'COLUMN';

-- 同步 Entity
[Entity(TableName = "base_user")]
public class BaseUserEntity {
    [SugarColumn(ColumnName = "f_open_id")]  // 同步修改
    public string FOpenId { get; set; }
}
```

**回滚**：

```sql
EXEC sp_rename 'dbo.base_user.f_open_id', 'fOpenId', 'COLUMN';
```

---

### 6.3 类型 B：业务字段语义变化

**特征**：
- 字段名变化但语义变了（如 F_ApplyUser → F_InputPerson）
- 字段定义变化（长度/类型/可空）

**处理**（双写兼容期 6 个月）：

```sql
-- 步骤 1: 增加新字段
ALTER TABLE wform_contractapproval ADD F_InputPerson nvarchar(50) NULL;

-- 步骤 2: 数据迁移
UPDATE wform_contractapproval 
SET F_InputPerson = F_ApplyUser 
WHERE F_InputPerson IS NULL AND F_ApplyUser IS NOT NULL;

-- 步骤 3: 6 个月后（应用层完全切换）
ALTER TABLE wform_contractapproval DROP COLUMN F_ApplyUser;

-- 步骤 4: 标记 DEPRECATED
-- EXEC sp_addextendedproperty 'DEPRECATED', 'Use F_InputPerson instead', 
--     'SCHEMA', 'dbo', 'TABLE', 'wform_contractapproval', 'COLUMN', 'F_ApplyUser';
```

**Entity 双字段**：

```csharp
public class WformContractapprovalEntity {
    [SugarColumn(ColumnName = "F_InputPerson", IsNullable = true)]
    public string FInputPerson { get; set; }
    
    [SugarColumn(ColumnName = "F_ApplyUser", IsNullable = true)]
    [Obsolete("Use FInputPerson. Will be removed in v6.0.")]
    public string FApplyUser { get; set; }
}
```

---

### 6.4 类型 C：低代码动态字段

**特征**：
- 表名以 `wform_*` / `ext_*` / `lowcode_*` 开头
- 字段由低代码设计器生成
- 字段名/类型由配置驱动，DB 仅存储

**处理**：

```sql
❌ 禁止：sp_rename / ALTER COLUMN
❌ 禁止：自动判断为 NO-CHANGE 或 REFACTORED

✅ 必须：标记为 LOW_CODE_DYNAMIC 跳过
✅ 必须：输出 "Low-code dynamic field, manual governance required"
```

**v2.0 SKILL 行为**：

```python
if table_name.startswith(("wform_", "ext_", "lowcode_")):
    return SkillResult(
        verdict="LOW_CODE_DYNAMIC",
        action="MANUAL_GOVERNANCE_REQUIRED",
        reason="Table is dynamically configured by low-code designer"
    )
```

```python
def decide_migration_type(table_name, column_name, current_def, target_def) -> MigrationType:
    # 1. Type C 判定（低代码动态）
    if table_name.startswith(("wform_", "lowcode_")):

    if table_name.startswith("ext_") and is_user_extended(table_name):

    # 4. 默认 Type B（保守）
    return MigrationType.TYPE_B_SEMANTIC
```

#### DoD-05  Evidence Collector（自动收集 SQL + 执行结果 + Benchmark + Diff）

**要求**：Skill 自动收集 4 类证据，**无需人工粘贴**。

**Evidence Bundle 标准结构**（每张 REFACTORED 表）：

```
backend/database/evidence/
└── <table_name>/
    ├── pre-execution/
    │   ├── schema.json              # 当前 schema 快照
    │   ├── row_count.json
    │   ├── index_usage.json
    │   └── performance-before.json
    ├── post-execution/
    │   ├── schema.json
    │   ├── row_count.json
    │   ├── index_usage.json
    │   └── performance-after.json
    ├── diff/
    │   ├── schema-diff.json         # schema 前后差异
    │   ├── index-diff.json          # 索引前后差异
    │   └── data-diff.json           # 数据差异（如有）
    ├── migration/
    │   ├── V<date>_<change_id>.sql  # Forward
    │   ├── V<date>_<change_id>_down.sql
    │   └── V<date>_<change_id>_verify.sql
    └── evidence-bundle.json         # 总索引
```

**Evidence Collector 必须产出**：

```python
class EvidenceCollector:
    def collect_pre_execution(self, table: str) -> EvidenceBundle:
        return EvidenceBundle(
            schema=self.snapshot_schema(table),
            row_count=self.count_rows(table),
            index_usage=self.query_index_usage(table),
            performance=self.benchmark(table, "BEFORE")
        )
    
    def collect_post_execution(self, table: str) -> EvidenceBundle:
        return EvidenceBundle(
            schema=self.snapshot_schema(table),
            row_count=self.count_rows(table),
            index_usage=self.query_index_usage(table),
            performance=self.benchmark(table, "AFTER")
        )
    
    def collect_diff(self, table: str, before: EvidenceBundle, after: EvidenceBundle) -> DiffBundle:
        return DiffBundle(
            schema_diff=diff_json(before.schema, after.schema),
            index_diff=diff_json(before.index_usage, after.index_usage),
            performance_diff=diff_performance(before.performance, after.performance)
        )
```

**验收**：每张表必须产出 `evidence-bundle.json`，路径符合上述结构。

**Skill 实现**：

```python
def execute_migration(change: MigrationChange) -> ExecutionResult:
    if change.requires_human_approval():
        return ExecutionResult(
            status="AWAITING_HUMAN_APPROVAL",
            reason=change.human_approval_reason
        )
    
    if environment == "PRODUCTION":
        return ExecutionResult(
            status="AWAITING_HUMAN_APPROVAL",
            reason="Production environment requires human approval"
        )
    
    return execute_forward(change)
```

**禁止**：

```
❌ AI 自动执行生产 DDL
❌ AI 自动 DROP COLUMN
❌ AI 自动跳过 Human Gate
```

**违反后果**：Skill 输出审计告警，必须人工审批后才能继续。
