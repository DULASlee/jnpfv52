## 2. Schema Migration Governance 三分类（核心）

### 2.1 类型识别

```
SchemaChange 检测到
    ↓
问三个问题：
  Q1: 纯技术命名错误吗？（拼写错误、大小写不一致、命名风格统一）
  Q2: 业务字段语义变化吗？（F_ApplyUser → F_InputPerson 语义不同）
  Q3: 低代码动态字段吗？（表名以 wform_/ext_/lowcode_ 开头）

Q1=Yes → Type A: Pure Technical   → 直接 sp_rename
Q2=Yes → Type B: Semantic Change  → 双写兼容 6 个月
Q3=Yes → Type C: Low-Code Dynamic → 禁止自动改名，标记 MANUAL_GOVERNANCE
```

### 2.2 Type A：纯技术命名错误

**特征**：拼写错误、命名风格统一化

**处理**：直接 `sp_rename`

```sql
EXEC sp_rename 'dbo.base_user.fOpenId', 'f_open_id', 'COLUMN';
-- Entity 层同步修改 [SugarColumn(ColumnName = "f_open_id")]
```

### 2.3 Type B：业务字段语义变化

**特征**：语义变了（不只换名字）

**处理**：双写兼容 6 个月

```sql
-- 步骤 1: 增加新字段
ALTER TABLE wform_contractapproval ADD F_InputPerson nvarchar(50) NULL;

-- 步骤 2: 数据迁移
UPDATE wform_contractapproval SET F_InputPerson = F_ApplyUser WHERE F_InputPerson IS NULL;

-- 步骤 3: 6 个月后（应用层完全切换）
ALTER TABLE wform_contractapproval DROP COLUMN F_ApplyUser;
```

### 2.4 Type C：低代码动态字段

**特征**：表名以 `wform_*` / `ext_*` / `lowcode_*` 开头

**处理**：**禁止自动改名**

```python
if table_name.startswith(("wform_", "ext_", "lowcode_")):
    return SkillResult(
        verdict="LOW_CODE_DYNAMIC",
        action="MANUAL_GOVERNANCE_REQUIRED"
    )
```

**原因**：JNPF 是低代码平台，字段由配置驱动：
```
数据库字段 → 动态表单（lowcode）→ 动态权限 → 流程引擎 → SQL 生成器
直接 sp_rename 会破坏上述全部链路。
```

## 3. P0 必须修（详细）

### 3.1 base_user 安全模型（IRON-TABLE-04）

**当前问题**（实证：`backend/web/主库脚本.sql:2262`）：

```sql
f_password  [nvarchar](50) NULL    -- 长度暗示 MD5/SHA1
f_secretkey [nvarchar](50) NULL    -- Salt 字段独立
f_account   [nvarchar](50) NULL    -- 无 UNIQUE 约束
f_tenant_id [nvarchar](50) NULL    -- 可 NULL（漏租户风险）
```

**修复目标**：

```sql
-- 阶段 2.1 密码字段升级
ALTER TABLE base_user ADD
    f_password_hash nvarchar(255) NULL,
    f_password_algo nvarchar(20) NULL DEFAULT 'LEGACY_MD5',
    f_password_updated_at datetime2(7) NULL,
    f_password_version int NULL DEFAULT 1;

-- 数据回填
UPDATE base_user SET
    f_password_hash = f_password,
    f_password_algo = 'LEGACY_MD5',
    f_password_updated_at = ISNULL(f_change_password_date, SYSUTCDATETIME()),
    f_password_version = 1
WHERE f_password IS NOT NULL AND f_password_hash IS NULL;
```

**6 个月兼容策略**：保留旧 `f_password` 字段，登录流程判定 `f_password_algo`，LEGACY_MD5 用户登录后自动升级到 PBKDF2。

### 3.2 tenant 隔离硬保证（IRON-TABLE-04）

**修复目标**：

```sql
-- 阶段 2.2 数据回填（先填默认值）
UPDATE base_user SET f_tenant_id = 'DEFAULT_TENANT_2026' WHERE f_tenant_id IS NULL OR f_tenant_id = '';

-- 阶段 2.2 NOT NULL 约束
ALTER TABLE base_user ALTER COLUMN f_tenant_id nvarchar(50) NOT NULL;

-- 其他 89+ 张业务表同样处理
-- （完整列表见实施计划 Task 9-10）
```

**保留 ITenantFilter**：应用层冗余，DB 层 NOT NULL 硬保证。

### 3.3 账号唯一约束（IRON-TABLE-04）

**修复目标**：

```sql
-- 阶段 2.3 UNIQUE(f_tenant_id, f_account)
ALTER TABLE base_user ADD CONSTRAINT UK_base_user_tenant_account UNIQUE (f_tenant_id, f_account);
```

**前提**：先做去重检测（`GROUP BY HAVING COUNT > 1`）确认无重复账号。

### 3.4 NO-CHANGE 8 维度证明（IRON-TABLE-01）

**禁止**：

```yaml
❌ "扫描了一遍表，没找到问题" → NO-CHANGE
❌ "表太小（<100行）" → NO-CHANGE
❌ "已经有覆盖索引" → NO-CHANGE（未证明符合 Target）
```

**必须**（NO-CHANGE 必填 8 维度证据）：

```yaml
no_change_evidence:
  column_naming: PASS       # 列名符合 Target Schema Contract
  data_type: PASS           # 数据类型符合 Target
  nullable_contract: PASS   # 必填/可空符合 Target
  tenant_model: PASS        # 租户字段存在 + 类型符合
  audit_model: PASS         # 审计字段存在 + 类型符合
  index_contract: PASS      # 索引符合 Target
  constraint_contract: PASS # 约束符合 Target
  security_boundary: PASS   # 身份/权限字段符合 Security Boundary

verdict: NO-CHANGE          # 全部 PASS 才能下此结论
```

**违反后果**：立即停工，必须补齐缺失的验证维度。

## 4. P1 应该修（详细）

### 4.1 密码哈希升级（IRON-TABLE-04 强化）

**目标**：从 LEGACY_MD5 升级到 PBKDF2_SHA256

**算法选择**：

| 算法 | 输出长度 | 安全性 | 推荐 |
|------|---------|--------|------|
| MD5 | 32 字符 | ❌ 不安全 | 禁止 |
| SHA1 | 40 字符 | ❌ 不安全 | 禁止 |
| PBKDF2_SHA256 | 64-128 字符 | ✅ 标准 | **推荐** |
| Argon2id | 32-64 字符 | ✅ 现代 | 可选 |

**PBKDF2 参数**：100,000 iterations + 16-byte salt（OWASP 推荐）

**登录升级流程**：

```
1. 用户登录（密码明文 + f_account）
   ↓
2. 验证算法
   ├─ LEGACY_MD5 → 旧 MD5 验证 → 成功 → 自动重新哈希为 PBKDF2 → 更新 f_password_hash/algo
   └─ PBKDF2_SHA256 → 标准 PBKDF2 验证 → 成功 → 通过
3. 失败 → 拒绝登录
```

### 4.2 datetime 升级（分领域迁移，不全库）

**目标**：`datetime` → `datetime2(7)`

**策略**：

```
新表：datetime2(7)（强制，Target Schema Contract 已规范）
旧表：按模块分领域迁移（不强制一次性全改）
  ├─ 阶段 3.2.1: system-core 模块（30 张表）
  ├─ 阶段 3.2.2: workflow-engine 模块（12 张表）
  ├─ 阶段 3.2.3: inteAssistant-AI 模块（24 张表）
  └─ 阶段 3.2.4: 其他模块
```

**幂等迁移脚本**：

```sql
-- scripts/database-modernization/phase3-p1-performance/02-datetime-to-datetime2.sql
BEGIN TRAN;
-- IF EXISTS 检查确保幂等
IF EXISTS (SELECT 1 FROM INFORMATION_SCHEMA.COLUMNS
           WHERE TABLE_NAME = 'base_user'
             AND COLUMN_NAME = 'f_creator_time'
             AND DATA_TYPE = 'datetime')
    ALTER TABLE base_user ALTER COLUMN f_creator_time datetime2(7) NOT NULL;
COMMIT;
```

### 4.3 性能 Before/After 强制门槛（IRON-TABLE-05）

**禁止**：

```
❌ "添加索引 IDX_X" → 不产出 measurement
❌ "理论上应该更快" → 无证据
❌ "SQL Server 文档说加索引会更快" → 复制文档
```

**必须**（每张 REFACTORED 表）：

```yaml
performance_evidence:
  before:
    query: "SELECT TOP 100 * FROM base_message WHERE f_user_id = 'X' AND f_is_read = 0"
    logical_reads: 1280
    cpu_ms: 42
    duration_ms: 68
  
  after:
    logical_reads: 14         # 必须下降
    cpu_ms: 3
    duration_ms: 5
  
  improvement:
    logical_reads_reduction: 98.9%    # >= 50% 才算有效
    duration_reduction: 92.6%
  
verdict: PERFORMANCE_VERIFIED
```

**测量方法**（标准 SOP）：

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
SELECT TOP 100 * FROM base_message WHERE f_user_id = 'X' AND f_is_read = 0 ORDER BY f_creator_time DESC;
-- 记录：logical reads / CPU time / elapsed time
```

### 4.4 真实 Schema Migration（取代列名代理）

**16+ 处列名漂移分类**：

| 列名漂移 | 当前类型 | Target 处理 |
|---------|---------|-----------|
| F_ApplyUser → F_InputPerson | **Type B**（业务语义变化） | 双写兼容 6 个月 |
| F_TaskName → F_FullName | Type A（纯命名统一） | 直接 sp_rename |
| F_Name 替代 F_CaseCode | **违规**（Mapping Is Not Migration） | 撤销，恢复真名迁移 |
| F_ProjectId → F_ProjectName | Type A（拼写错误） | 直接 sp_rename |
| F_Status → F_PipelineStatus | **Type B**（语义变化） | 双写兼容 6 个月 |

**关键修正**：v1 阶段 2.4 的"F_Name 替代 F_CaseCode"是违规行为（IRON-TABLE-02），必须撤销。
