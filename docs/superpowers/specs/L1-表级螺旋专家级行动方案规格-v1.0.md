## 1. 索引策略的深度重构（维度 A）

不是"补缺失索引"这种表面功夫，而是**基于真实查询模式的索引体系重建**。

| 技术 | 具体做法 | 触发条件 |
|------|----------|----------|
| **覆盖索引设计** | 分析该表最频繁的查询，设计 INCLUDE 列覆盖查询所需的所有字段，使查询只需访问索引页，不访问数据页 | 某查询被高频执行且回表代价高 |
| **复合索引列序优化** | 基于 WHERE 条件的选择性（Cardinality）和查询频率，重新排列复合索引的列顺序 | 现有复合索引的列序与查询模式不匹配 |
| **过滤索引** | 对高基数列中仅频繁查询某几个值的场景，使用 `WHERE` 子句创建过滤索引，大幅减小索引体积 | 某列 90% 的数据从不被查询，只查剩余 10% |
| **索引选择性评估与调整** | 计算每个索引的选择性（唯一值占总行数比例），低于阈值的索引标记为低效，评估是否需要重构或替换 | 索引存在但选择性极低（如性别列上的索引） |
| **隐式转换消除** | 发现 ORM 生成的 SQL 中因类型不匹配导致索引失效的隐式转换（如 varchar 列被数字参数查询），修正列类型或查询方式 | 执行计划中出现 CONVERT_IMPLICIT |
| **碎片化治理** | 分析索引碎片率，对高碎片索引制定 REBUILD/REORGANIZE 策略，并设定维护作业 | 碎片率 >30% 的索引 |
| **填充因子调优** | 对高频写入的表，调整索引填充因子，减少页分裂 | 写入频繁且出现大量页分裂 |
| **索引压缩** | 对大表（>100万行）的索引启用行压缩或页压缩，减少 I/O | 表行数大且压缩收益明显 |

### 产出物示例

```markdown
### 表 ext_order 索引重构报告

| 原索引 | 问题 | 新索引 | 预期收益 |
|--------|------|--------|----------|
| IX_ext_order_customer_id (customer_id) | 未覆盖查询 SELECT * WHERE customer_id = @p1 AND status = @p2 | IX_ext_order_customer_status_cover (customer_id, status) INCLUDE (order_no, total_amount, created_at) | 消除 Key Lookup，I/O 降低 ~70% |
| IX_ext_order_status (status) | 选择性 0.02（仅 3 个值），几乎无用 | 删除，被复合索引覆盖 | 减少写入开销 |
| IX_ext_order_created_at (created_at) | 查询总是 created_at + status 联合过滤 | IX_ext_order_created_status (created_at DESC, status) | 满足时间范围扫描 |
```

## 2. 字段级深度优化（维度 B）

不是"标记废弃字段"，而是**让字段设计反映真实的数据语义**。

| 技术 | 具体做法 | 触发条件 |
|------|----------|----------|
| **类型语义修正** | 将存储格式与语义不匹配的字段改为正确类型：<br>- 布尔值存成 `varchar('true'/'false')` → `BIT`<br>- 日期存成字符串 → `DATETIME2`<br>- 金额存成 `FLOAT` → `DECIMAL(18,4)` | 字段类型与其承载的数据语义不匹配 |
| **NOT NULL 与 DEFAULT 策略** | 分析每个 NULL 字段的业务含义："未知"（允许 NULL）还是"应该有值但没填"（应 NOT NULL + DEFAULT）。添加 DEFAULT 约束，使 ORM 插入时无需显式提供值 | 大量插入语句必须显式提供某个固定值 |
| **长度策略重构** | 对 `NVARCHAR(MAX)` 但实际数据不超过 200 字符的字段，改为精确长度，减少溢出页和扫描开销 | 查询该表的实际数据长度分布 |
| **消除多值字段** | 发现逗号分隔的多值字段（如 `tags = 'a,b,c'`），评估是否拆分为关联表 | 查询中频繁使用 `LIKE '%value%'` 或 `STRING_SPLIT` |
| **枚举标准化** | 将字符串枚举字段统一为数值枚举或查找表，消除大小写不一致、拼写错误 | 同一字段中存在多种拼写变体表达同一含义 |
| **Unicode 策略统一** | 对不存储非 ASCII 字符的字段，从 `NVARCHAR` 改为 `VARCHAR`，节省 50% 存储 | 字段内容全部为 ASCII |
| **时区语义显式化** | 对日期时间字段，明确其语义：本地时间 vs UTC。混用的表统一策略，并考虑 `DATETIMEOFFSET` | 同一表中同时存在本地时间和 UTC 时间 |
| **软删除与查询模式对齐** | 分析软删除标记列（如 `is_deleted`）与所有查询的交互：是否每个查询都正确过滤？缺失过滤的查询列出清单 | 存在软删除标记但部分查询未过滤 |

### 产出物示例

```markdown
### 表 wform_record 字段重构报告

| 字段 | 现状 | 问题 | 重构方案 | 迁移方式 |
|------|------|------|----------|----------|
| status | VARCHAR(20) | 存在 'Approved', 'approved', 'APPROVED' 三种变体 | 改为 TINYINT (0-5 枚举)，同时建查找表 | 先 UPDATE 统一数据，再 ALTER COLUMN |
| form_data | NVARCHAR(MAX) | 80% 数据 < 5KB | 保持 MAX（有极大数据），但增加计算列存前 100 字符用于搜索 | 添加计算列 + 索引 |
| created_by | VARCHAR(50) | 实际存的是用户 GUID | 改为 UNIQUEIDENTIFIER | 先验证全部可转换，再 ALTER |
| is_delete | BIT | 存在但 20% 查询未过滤 | 在相关查询处补过滤，同时考虑过滤索引 | 代码级修改 |
| remark | NVARCHAR(2000) | 平均长度 30 字符 | 改为 NVARCHAR(500) | 先检查 MAX 值，再缩容 |
```

## 3. 约束与数据完整性的实质性提升（维度 C）

不是"补充缺失外键"这种简单描述，而是**建立完整的数据完整性防线**。

| 技术 | 具体做法 | 触发条件 |
|------|----------|----------|
| **业务唯一性约束** | 发现代码中总是先 SELECT 再 INSERT 来防止重复，但数据库没有唯一约束 → 直接加 UNIQUE INDEX/UNIQUE CONSTRAINT，从根上消灭竞态条件 | 代码中出现"查重再插入"模式 |
| **CHECK 约束补充** | 对代码中反复出现的值域校验（如金额不能为负、状态必须在某个集合内），下沉为 CHECK 约束 | ORM 代码中有大量 if 判断验证字段值 |
| **乐观并发控制** | 对无 rowversion/updated_at 字段的表，增加 `ROWVERSION` 列，配合 EF Core 的并发令牌，消除丢失更新问题 | 存在"读-改-写"模式且无并发保护 |
| **级联策略审计** | 分析每个外键的 ON DELETE 行为：默认的 NO ACTION 导致删除时必须先删子表；评估是否应改为 CASCADE 或 SET NULL，消除代码中的手动多表删除 | 删除主表前代码手动删除多张子表 |
| **默认值下沉** | 将代码中每次插入都设置的固定值下沉为数据库 DEFAULT，减少 ORM 的责任 | 多次 INSERT 语句中重复出现的常量值 |
| **计算列** | 对频繁用于过滤/排序的派生字段（如 JSON 中的某个子属性、两个字段的计算结果），创建持久化计算列并建立索引 | WHERE 条件频繁使用派生值 |

### 产出物示例

```markdown
### 表 sys_user 约束强化报告

| 约束 | 现状 | 重构 | 理由 |
|------|------|------|------|
| 用户名唯一 | 无 UNIQUE 约束，代码先查后插 | 添加 UNIQUE INDEX IX_uq_sys_user_username | 并发注册时产生重复用户名的竞态 |
| 邮箱格式 | ORM 层验证 | 添加 CHECK (email LIKE '%_@__%.__%') | 旁路 ORM 的批量插入可写入垃圾数据 |
| 状态值域 | 代码 if 判断 | CHECK (status BETWEEN 0 AND 3) | 防御性约束 |
| 乐观锁 | 无 | 添加 ROWVERSION 列 | 个人资料并发修改会丢失更新 |
| 删除策略 | 代码手动删关联表 | 外键 ON DELETE CASCADE 或软删除统一策略 | 消除手动多表删除 |
```

## 4. CRUD 路径的深度重构（维度 D）

不是"提取重复代码为私有方法"，而是**重构数据访问的架构模式**。

| 技术 | 具体做法 | 触发条件 |
|------|----------|----------|
| **N+1 查询消除** | 识别该表被循环查询的场景（如查列表后循环查详情），改为 JOIN 或 IN 批量查询，或使用 EF Core 的 Include/ThenInclude 重构 | 性能监控或代码审查发现 N+1 |
| **投影查询替代实体查询** | 对只读列表场景，将加载完整实体的查询改为 `Select` 投影到 DTO，只查询所需列，配合覆盖索引 | 列表页只展示部分字段但加载了所有列 |
| **批量操作重构** | 将循环单行 INSERT/UPDATE 改为 EF Core 的 AddRange/ExecuteUpdate，或 SqlBulkCopy | 导入/批量处理场景 |
| **事务边界精化** | 分析该表相关操作的事务：事务是否包裹了非数据库操作（I/O、HTTP 调用）导致事务过长？是否缺失事务导致部分成功？调整事务隔离级别 | 事务中包含外部调用或长时间操作 |
| **查询参数化审计** | 确认所有访问该表的查询都是参数化的，发现拼接 SQL 则修复 | 安全检查发现字符串拼接 SQL |
| **分页策略重构** | 对 OFFSET/FETCH 深分页场景（如第 100 页），改为 Keyset Pagination（基于索引的游标式分页），深页性能提升 100 倍以上 | 列表接口深分页响应极慢 |
| **异步化改造** | 将同步阻塞的数据库访问改为 async/await，释放线程池资源 | 该表访问频繁且使用同步 API |
| **只读查询优化** | 对只读查询使用 `AsNoTracking()`，消除 EF Core 变更跟踪开销 | 列表查询不需要更新 |

### 产出物示例

```markdown
### 表 ext_order CRUD 路径重构报告

| 路径 | 现状 | 问题 | 重构方案 | 性能提升 |
|------|------|------|----------|----------|
| 订单列表 | 加载 50 条完整实体 + Include 5 个导航属性 | 生成 251 条 SQL（1 主查询 + 50×5 子查询） | 投影查询到 DTO，配合覆盖索引 | SQL 从 251 条降到 1 条 |
| 订单导出 | 循环单行 INSERT 到导出表 | 10 万行导出需 30 分钟 | SqlBulkCopy 批量写入 | 30 分钟 → 30 秒 |
| 订单详情 | 分 5 次查询组装 | 5 次往返 | 单次投影查询（JOIN + DTO） | 往返从 5 次降到 1 次 |
| 订单更新 | 加载完整实体 → 修改 → 保存 | 无乐观锁 | 添加 ROWVERSION + ExecuteUpdate | 并发安全 + 避免整行加载 |
| 订单搜索 | `WHERE order_no LIKE '%' + @p + '%'` | 全表扫描 | 业务层重构：精确匹配优先 + 前缀索引 | 扫描成本降 99% |
```

## 5. ORM 映射质量重构（维度 E）

JNPF 使用 SqlSugar（或类似 ORM），映射质量直接影响所有数据访问的性能和正确性。

| 技术 | 具体做法 | 触发条件 |
|------|----------|----------|
| **导航属性审计** | 检查每个导航属性是否真的被使用。不使用的导航属性移除，减少模型复杂度；缺失的导航属性补上，消除手动 JOIN | 实体定义了从未使用的导航属性 |
| **值转换器优化** | 对枚举字段使用 ValueConverter 映射到查找表或数值，消除字符串比较 | 实体属性是字符串但语义是枚举 |
| **查询过滤器统一** | 软删除、多租户过滤应在 DbContext 层面使用 Global Query Filter 统一应用，而非在每个查询手动加 Where | 多个查询重复写 `WHERE is_deleted = 0` |
| **DbContext 范围审计** | 检查 DbContext 生命周期是否正确（Per Request 还是 Singleton），以及是否被跨线程共享 | 发现 DbContext 被注入为 Singleton |
| **关系映射验证** | 确认外键关系在 EF 模型中正确配置（Required/Optional、DeleteBehavior），与数据库实际约束一致 | 模型配置与数据库不一致 |

### 产出物示例

```markdown
### 表 ext_order ORM 映射质量报告

| 映射项 | 现状 | 问题 | 重构方案 |
|--------|------|------|----------|
| Order.Customer 导航属性 | 已定义 | 90% 查询不使用 | 移除，改为显式 JOIN（仅在需要时） |
| Order.Status 枚举映射 | 字符串存储 | 查询时需字符串比较 | 添加 ValueConverter 映射到枚举 |
| 软删除过滤器 | 每个查询手动加 `WHERE is_deleted = 0` | 遗漏风险高 | 在 DbContext 层配置 Global Query Filter |
| Order.OrderItems 集合 | 已定义但未使用 | 占用内存 | 移除或改为延迟加载 |
```

## 6. 总结：L1 行动阶段的定位

| 平庸版本（禁止） | 专家级版本（本文档） |
|------------------|----------------------|
| 补缺失索引 | 基于查询模式和选择性重新设计索引体系，包括覆盖索引、过滤索引、索引压缩 |
| 标记废弃字段 | 字段类型语义修正、枚举标准化、多值字段拆分、Unicode 策略、时区语义 |
| 修类型错误 | CHECK 约束下沉、唯一约束补强、乐观锁、级联策略、计算列 |
| 提取重复 CRUD | N+1 消除、投影查询、批量操作、事务精化、分页策略重构、异步化 |

### 每个行动必须附带

1. **证据**：执行计划对比、数据分布分析、代码引用清单
2. **风险评估**：迁移难度、回滚方案
3. **性能指标**：SQL 条数变化、I/O 变化、响应时间变化
4. **测试覆盖**：迁移前快照、迁移后验证

> **这样每一次螺旋做完一张表，系统质量就有一次可量化的跃升，而不是"清理了一些垃圾"。这才是重构的意义。**
