## 0. 与全局边界的关系（必须先行明确）

在进行任何类级重构前，每个执行者必须核对以下边界，避免重蹈"数据与领域混杂"的覆辙：

| 概念 | 归属程序集 | 说明 |
|------|-----------|------|
| `IAggregateRoot`、`AggregateRoot`、`IDomainEvent` | `Foundation.Domain.Abstractions` | 领域概念，与数据访问无关 |
| `IDomainEventDispatcher`、`IEventBus` 实现 | `Foundation.DomainEvents` | 事件机制，独立于数据库 |
| `IRepository<T>`、`IUnitOfWork` | `Foundation.Data.Abstractions` | 数据抽象，不包含业务 |
| 具体 EF Core / SqlSugar 实现 | `Foundation.Data.EntityFrameworkCore` / `SqlSugar` | 基础设施 |
| JNPF 业务实体（如 `Tenant`、`User`、`WorkflowDefinition`） | `JNPF.Domain` | 继承 Foundation 抽象 |
| 动态表单元数据、动态 DDL 等 | `JNPF.DynamicForm`（或 `Foundation.DynamicData` 的适配层） | 业务能力，不属于通用数据核心 |

**任何将上述概念混放的代码都视为违规，必须在类级螺旋中纠正。**

## 1. 类级螺旋的前置条件

1. **表级事实卡覆盖目标聚合涉及的表**：L1 已产出这些表的字段/索引/外键/CRUD 路径清单。
2. **表间依赖关系已明确**：从 L1 的外键分析和 CRUD 代码引用中，可提取"哪些表总被同一组类在同一事务中修改"。
3. **行为特征考卷（T0.3）已就绪**：所有类级改动必须通过考卷验证行为不变。
4. **数据基础设施程序集骨架已建立**：`Foundation.Data.Abstractions` 等物理项目存在，类级重构可直接使用其接口。
5. **不可逆/预授权清单已理解**：删除类、修改公共 API 签名、改变事务边界等属不可逆；内部重命名、提取接口、移动类、增加测试等属预授权。

## 2. 聚合识别的系统方法（L2 的第一步，最关键）

### 2.1 从表级事实卡识别聚合候选

L1 已为每张表记录了"哪些类操作它"。统计如下：

- **表组**：若多张表总是被同一组类（或单个类）读写，且修改发生在同一个数据库事务中，则这些表强烈暗示属于一个聚合。
- **单表孤立**：仅被一个类或很少类访问，且无强外键关联的表，可能是独立聚合或不属于核心领域（比如日志表，可单独处理）。

**执行动作**：生成"表-类-事务"三维矩阵。如下示例：

| 表 | 操作类 | 事务范围 |
|----|--------|----------|
| `sys_user` | `UserService`, `UserRepository` | 单表事务 |
| `sys_user_role` | `UserService`, `RoleService` | 通常与 `sys_user` 同事务 |
| `ext_order` | `OrderService`, `OrderRepository` | 独立事务 |
| `ext_order_item` | `OrderService`, `OrderRepository` | 与 `ext_order` 同事务 |

据此可将 `sys_user` + `sys_user_role` 视为一个聚合候选，`ext_order` + `ext_order_item` 为另一个。

### 2.2 识别聚合根

- 聚合根是聚合内**唯一入口**，外部只能通过它修改内部实体。
- 通常是事务发起者对应实体（如 `Order` 是根，`OrderItem` 是内部实体）。
- 若没有明显根（比如多张平级表互相依赖），则可能需要重新评估聚合边界，或引入一个聚合根包装。

### 2.3 识别值对象

- 从类中提取无身份、不可变的属性组。但**注意**：在 JNPF 现有代码中，很多"值对象"可能只是普通字符串/JSON 字段，不要为了 DDD 而过度提取。仅在发现**重复验证逻辑、重复属性组、且有明确业务含义**时才提取。

### 2.4 识别界限上下文

- JNPF 低代码平台中，`User` 在身份模块和审批模块可能语义不同。若发现同名类在不同命名空间下有不同属性和行为，应考虑通过接口隔离或上下文映射避免概念污染。
- 但**不要因此创建全新模型**，只用适配器或接口明确边界即可。

**注意：聚合识别只是重构的第一步，不是重新设计。产出物应基于现有代码关系，而不是凭空画出理想图。**

## 3. 类级重构技术清单（修订版）

### A. 聚合边界强化

| 技术 | 具体做法 | 触发条件 | 是否属于预授权？ |
|------|----------|----------|------------------|
| **聚合根封装** | 将原本外部直接操作内部实体的代码改为通过聚合根方法。例如 `Order.AddItem(item)` 而非直接 `orderItemRepository.Add()`。 | 外部类直接修改内部实体 | 是（内部重构） |
| **值对象提取** | 对重复出现的属性组（如地址、金额区间）提取为不可变类，实现相等比较。 | 多个类中出现结构相同属性组且伴随验证 | 是（新增类+移动代码） |
| **领域事件引入（进程内）** | 将聚合间的直接调用改为发布 `IDomainEvent`，由处理器在同一进程内异步/同步处理。**不引入外部消息队列**。 | 类 A 直接 new 类 B 调用，造成耦合 | 是（接口+实现移动） |
| **界限上下文显式化** | 用接口隔离不同上下文的同名概念，避免直接互相引用。 | 同名类在不同模块中含义不同且互相引用 | 是（提取接口） |

**禁止项**：不要将领域事件与基础设施事件混用；不要在没有明确跨聚合业务时强行引入事件。

### B. 职责分离与类结构优化

| 技术 | 具体做法 | 触发条件 | 是否属于预授权？ |
|------|----------|----------|------------------|
| **上帝类拆分** | 按职责拆分：领域实体（属性+行为）、领域服务（跨聚合规则）、应用服务（编排）、仓储（持久化）。确保领域实体不依赖 DbContext。 | 类同时包含业务规则、数据访问、事务控制等 | 是（新增类+移动方法，不改变公共行为） |
| **仓储模式规范化** | 将业务类中直接操作 DbContext/SqlSugar 的代码收敛到仓储接口。业务类只依赖 `IRepository<T>`。 | 业务类散落大量 ORM 调用 | 是（接口+实现替换） |
| **策略模式替换条件分支** | 当 `switch` 或 `if-else` 分支超过 3 个且逻辑各异，提取策略接口，通过 DI 解析。 | 条件分支过多 | 是（新增接口+实现） |
| **工厂提取** | 实体创建逻辑复杂（>5 参数或含默认值、关联初始化）时提取工厂。 | 构造函数膨胀或创建代码重复 | 是 |

**特别注意**：JNPF 中很多 Service 类可能依赖动态数据（如 `DynamicFormDataService`），拆分时不要将动态逻辑与静态实体逻辑强行混合。

### C. 依赖治理与解耦

| 技术 | 具体做法 | 触发条件 | 是否属于预授权？ |
|------|----------|----------|------------------|
| **接口隔离** | 为聚合定义最小对外接口，只暴露必要方法，放在单独命名空间或 Contract 项目。 | 外部类依赖具体实现且只用少数方法 | 是（接口提取） |
| **依赖倒置** | 对外部系统（邮件、文件、支付）抽象为端口接口，实现放基础设施层。领域层不引用具体 SDK。 | 业务类直接 new HttpClient 或第三方 SDK | 是（接口+适配器） |
| **消除循环依赖** | 使用依赖图工具找出环，通过提取接口或事件打破。 | 类 A 依赖 B，B 依赖 A | 是（接口提取或事件） |
| **静态依赖消除** | 将静态类/单例（除纯函数）替换为实例类，通过 DI 注入。 | 大量 `DateTime.Now`、`HttpContext.Current`、静态配置 | 是 |

**注意**：消除循环依赖时，**不要引入复杂的中介者模式**，优先使用接口或事件。

### D. 公共逻辑提取与设计模式

| 技术 | 具体做法 | 触发条件 | 是否属于预授权？ |
|------|----------|----------|------------------|
| **通用仓储基类** | 在 `Foundation.Data.EntityFrameworkCore` 中提供 `EfCoreRepository<T>` 基类，各聚合仓储继承。 | 多个仓储重复 CRUD | 是（使用已有基类） |
| **规约模式** | 封装查询条件为可组合对象，避免仓储接口方法爆炸。 | 仓储接口方法过多（>10 个查询方法） | 是（新增规约类） |
| **装饰器处理横切关注点** | 使用装饰器或 AOP 包装事务、日志、权限，避免散落在业务方法中。 | 每个 Service 方法重复相同横切代码 | 是（新增装饰器） |
| **模块化 DI 注册** | 将 `Startup.cs` 中散落的服务注册迁移到各模块的 `AddXxxModule()` 扩展方法。 | 启动类包含大量服务注册 | 是（代码移动） |

**注意**：装饰器可能改变执行顺序，需谨慎，确保行为不变。

### E. 事务边界与一致性设计（当前阶段限制）

类级螺旋阶段，我们**不引入分布式事务或 Outbox 模式**，只做两件事：

1. **记录事务边界**：识别现有事务范围，标记哪些操作属于一个聚合内事务，哪些跨聚合。产出"事务边界说明"文档。
2. **消减不必要的大事务**：如果发现一个事务跨越多个聚合（比如订单和库存强一致），暂时不改，但在聚合间插入领域事件占位，为后续模块化做准备。**不主动改造为最终一致性**，因为那属于模块级或服务级阶段。

**禁止**：在类级螺旋中引入 Outbox、消息队列或 Saga。

### F. 可测试性与可维护性

| 技术 | 具体做法 | 触发条件 | 是否属于预授权？ |
|------|----------|----------|------------------|
| **构造函数注入** | 所有依赖通过接口注入，禁止内部 new 具体实现。 | 类内部 new 具体服务 | 是 |
| **消除静态状态** | 将静态可变状态改为实例或通过 `IHttpContextAccessor` 等注入。 | 静态字段保存请求上下文 | 是 |
| **提取纯函数** | 将无副作用的业务规则提取为纯函数或静态小类，便于单元测试。 | 业务规则与 I/O 混合 | 是 |
| **测试替身** | 为所有端口提供 mock/fake，领域逻辑测试不依赖数据库。 | 测试需要启动真实数据库 | 是 |
| **防御性断言** | 在关键方法入口添加 `Guard.Against.Null` 等。 | 方法经常因参数 null 出错 | 是 |

**产出**：每个聚合应新增至少 3 个单元测试覆盖核心规则。

## 4. 与行为特征考卷的配合

- 类级螺旋的每次行动后，必须运行行为特征考卷，确保所有核心 API 行为不变。
- 若考卷变红，立即回退到最近提交，分析原因。
- 对于新增的领域事件、接口提取等，如果影响了外部调用，需更新考卷或增加新的特征用例。

## 5. L2 螺旋执行步骤（五步循环细化）

以单个聚合为对象：

1. **观察**：收集该聚合涉及的所有类、接口、依赖、事务代码、现有测试。
2. **判断**：基于上述技术清单，列出可改进项，按风险/收益排序，标注预授权/不可逆。
3. **行动**：仅执行预授权范围内的重构，每步可单独提交。
4. **验证**：运行行为考卷 + 单元测试 + 架构测试（依赖环检测），确认无回归。
5. **回看**：更新聚合边界图、事务边界说明，记录遗留问题，进入下一个聚合。

**聚合处理顺序**：优先处理依赖最少、最独立的聚合（如日志、文件元数据、系统配置），再处理核心业务（用户/租户/权限），最后处理复杂耦合（工作流、动态表单相关）。

---

## 6. 验收标准与产出物

每个聚合完成螺旋后，必须交付：

1. **更新后的聚合边界图**（展示根、实体、值对象、仓储接口、事件）。
2. **类结构变更报告**（新增/删除/移动的类，应用的设计模式）。
3. **依赖分析报告**（循环依赖消除情况，外部依赖抽象列表）。
4. **事务边界说明**（哪些操作同事务，哪些潜在跨聚合）。
5. **单元测试覆盖**：核心领域规则测试，数量≥3，并纳入 CI。
6. **行为考卷报告**：全绿证明。

**量化指标**：

- 聚合内聚度提升：依赖环数量降为 0（或显著下降）。
- 公共逻辑重复率下降（SonarQube 可度量）。
- 领域类不再直接依赖数据访问组件（静态检查）。

---

## 7. 特别注意：避免过度设计与重新设计

- **不要为了追求完美 DDD 而大幅改动现有模型**。只处理最痛的点（上帝类、循环依赖、静态依赖）。
- **不要引入新的复杂框架**（如 MediatR、AutoMapper）除非当前代码已有或确有强需求。
- **不要在设计阶段争论领域模型的"正确性"**，一切以现有代码行为和事实卡为准。
- **如果某个聚合边界模糊**，暂时搁置，登记为"待观察"，不强行划分。

---

## 8. 与本阶段并行任务的关系

- 与表级螺旋可能并行（但同一张表的类级重构需等该表 L1 完成）。
- 类级螺旋产出的接口和聚合边界将直接指导后续 `Foundation.Data.*` 的完善（比如通用仓储基类的接口定义）。
- 类级螺旋中发现的跨聚合事件需求，可暂以进程内事件实现，为模块级拆分埋下伏笔。

---

## 9. 结语

类级螺旋是承上启下的关键：它基于表级事实，为模块化提供清晰的领域内核。我们追求的是"**更干净、可测试、边界清晰的现有代码**"，而不是一个全新的理想模型。遵循五步螺旋和上述技术清单，可在不破坏行为的前提下，渐进式地提升系统质量。
