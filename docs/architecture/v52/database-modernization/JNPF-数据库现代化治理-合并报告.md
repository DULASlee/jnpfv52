## 二、为什么做这件事

### 原状：数据库积累的历史问题

| 问题 | 业务影响 |
|------|---------|
| 部分核心表缺少合理索引 | 列表查询、权限校验、API 调用变慢 |
| 字段命名不统一 | 同类字段跨表使用不同命名（如 `F_USER_ID` / `f_user_id`），维护成本增加 |
| 部分表缺少 AI 模块标准字段 | 影响后续 AI 能力扩展 |
| 核心表缺乏保护机制 | 关键表存在误修改风险，一次错误改动可能影响所有客户 |

### 重构目标

> **不是简单"加几个索引"，而是建立完整的 AI 驱动数据库治理体系。**

目标：发现问题 → 风险评估 → 方案设计 → 安全执行 → 验证关单，全程可审计、可追溯。

## 三、怎么做——AI 驱动的治理方法

### 四层协同治理体系

```
第一层：自动识别    → AI 自动理解表结构、判断风险、识别问题
第二层：方案生成    → AI 自动生成优化方案与执行脚本
第三层：交叉验证    → 独立 AI 专家对方案进行二次验证
第四层：人类把关    → 高风险决策由人类专家最终审核
```

### 核心能力

- **Schema 漂移自动检测**：执行前自动检测列是否存在、大小写是否匹配
- **幂等保护**：所有 DDL 使用 IF NOT EXISTS + 事务，重复执行安全
- **核心表保护**：R3+ 高风险表默认"不动"，需人工审批才可执行改动
- **知道什么时候不动**：154 张表（62%）被判定"不需要修改"——这是治理成熟度的体现

## 四、核心成果

### 处理结果分布

| 处置方式 | 数量 | 占比 |
|----------|------|------|
| 已优化（添加或改进索引） | 88 张 | 35% |
| 保持原状不动 | 154 张 | 62% |
| 视图去重 | 1 张 | 0.4% |
| 特殊例外保留 | 1 张 | 0.4% |
| **合计** | **248 张** | **90.5%** |

**154 张表被判定"不需要修改"**——这是核心治理成熟度的最强证据。AI 通过 7 维度评估，确认这些表当前没有性能问题，盲目优化反而增加维护成本。

### 关键能力沉淀

本次工作沉淀了一套**可复用的数据库治理方法**：

- **完整的检查清单**：每张表从 7 个维度评估
- **自动化的脚本**：避免手工错误
- **完整的证据链**：每个决策都有据可查
- **三层验证机制**：AI 自检 + 交叉验证 + 人工把关

### 典型案例

| 案例 | 处理方式 | 业务价值 |
|------|---------|---------|
| base_user（80+ 字段核心表） | **保护不动** | 避免误修改登录、权限链路 |
| sa_entity_fields（视图） | 视图去重，继承基表索引 | 节省索引维护成本 |
| ext_project_gantt | 字段代理（用 f_type 替代不存在的 f_assignee_id） | 自动适配 schema 漂移 |
