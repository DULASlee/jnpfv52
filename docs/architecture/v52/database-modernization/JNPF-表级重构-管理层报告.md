## 第二部分 · 为什么需要这次重构

### 原状：数据库积累的"老问题"

| 问题 | 业务影响 |
|------|---------|
| 部分核心表缺少合理索引 | 列表查询、权限校验、API 调用变慢，用户体验受影响 |
| 历史开发规范不统一 | 同类字段命名风格混杂（`F_USER_ID` vs `f_user_id`），新功能开发效率降低 |
| 同一概念字段命名差异 | `F_ApplyUser` / `F_InputPerson` / `F_Salesman` / `F_TravelMan` 等同义字段跨表不一致，维护成本增加 |
| 部分表结构缺少治理 | 风险等级未分类，重要程度靠经验判断，无统一标准 |
| 动态表与业务核心表混杂 | 架构边界不清晰，影响未来微服务拆分 |
| 视图与基础表耦合关系未识别 | 视图查询路径未优化，存在重复计算风险 |

### 重构目标

> **不是简单"加几个索引"。**

而是建立完整的数据库治理能力闭环：

```
发现问题
   ↓
风险评估（AI 自动识别）
   ↓
方案设计（AI 生成 + 人工治理）
   ↓
安全执行（事务保护 + 备份预案）
   ↓
验证关单（多维证据 + 独立验证）
```

**成果是这套能力本身**——而不是单次执行的索引数量。

## 第三部分 · AI 表级重构专家 Skill 能力

> 这部分解释"AI 替代人工到底能做到什么程度"。

### AI 重构专家工作流程（人话版）

```
1. 自动理解表结构
   └─ 连接数据库，扫描所有表和列，理解字段含义和关联关系

2. 判断表的重要程度
   └─ 区分核心业务表（如用户、订单）vs 配置表 vs 辅助表

3. 识别潜在风险
   └─ 自动发现命名不一致、字段缺失、列类型不匹配等"老问题"

4. 给出优化建议
   └─ 哪些字段需要组合索引？哪些列不适合做索引？

5. 自动生成执行方案
   └─ 输出标准 SQL，并自动应用幂等保护（IF NOT EXISTS）

6. 验证修改结果
   └─ 多维度检查：索引存在性 / 行数不变 / 事务原子性 / 跨表引用

7. 输出完整成果记录
   └─ 每张表都有证据文件，支持审计与回滚
```

### 关键能力指标

| 能力 | 表现 |
|------|------|
| 自动识别 schema 漂移 | 16+ 次在执行前发现"原计划用 A 列，实际只有 B 列" |
| 自动生成幂等 SQL | 所有 DDL 使用 IF NOT EXISTS，重复执行安全 |
| 自动事务控制 | 失败时自动回滚，不会留下半成品 |
| 自动验证机制 | 每张表独立证据文件，6 维度检查 |
| 自动路由升级 | 发现问题自动路由到人工决策 |

### 治理层级

```
Layer 0: Hook 守卫（L0 自动拦截危险操作）
Layer 1: AI Skill 自动执行（覆盖 90% 标准场景）
Layer 2: R2 独立 AI 专家验证（覆盖疑难场景）
Layer 3: R1 人工治理（覆盖 P0/P1 与争议场景）
```

```

```
