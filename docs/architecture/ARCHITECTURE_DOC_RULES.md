## 一、铁律（违反任何一条，该文档判定为不合格）

### 铁律1 · 穿透原则

- ✗ 禁止："系统采用JWT认证，通过Token验证用户身份"
- ✓ 必须："用户登录时，前端调用 POST /api/oauth/Login（服务：`OAuthService.Login`，`modularity/oauth/JNPF.OAuth/OAuthService.cs`），服务端校验 **BASE_USER** 账号密码，通过后调用 `JWTEncryption.GenerateToken()` 生成 JWT；Claims 与过期时间来自 `JWTSettingsOptions`（`Configurations/JWT.json`）。Token 缓存策略由 `CacheManager` 与 **BASE_SYS_CONFIG** 的 `singleLogin` 等项控制。前端在 axios 拦截器注入 `Authorization`。后端通过 `JwtHandler` 与 `IUserManager` 读取当前用户 Claims。"

**判定标准**：任何一个技术点，如果可以用「具体文件路径 + 类名 + 方法名 + 参数/返回值」来描述，就必须这样描述。无法给出时，必须明确标注 **【待源码验证】**。

> **本项目补充**：JNPF 大量使用 `DynamicApiController` 自动生成 API，文档中应优先引用 `modularity/` 下 `*Service` 类及其方法，而非臆造 Controller 类名。

---

### 铁律2 · 数据锚定原则

每个功能模块必须列出涉及的核心数据库表（使用 **加粗** 标注表名），并给出关键字段说明。示例：

**BASE_USER**：用户主表（v5.2 实体 `UserEntity`；勿写 v3.6 的 `sys_user`）

- F_Id (PK), F_Account, F_Password（MD5/AES，见 OAuth 登录逻辑）
- F_RealName, F_Email, F_Mobile
- F_OrganizeId, F_RoleId
- F_EnabledMark, F_DeleteMark
- F_CreatorTime, F_LastLogTime

**判定标准**：每个模块至少列出 2 张以上核心表及其关键字段。若该模块没有直接操作数据库（纯前端模块），则说明其消费的 API 接口和对应后端模块的表。

---

### 铁律3 · 图表强制原则

以下类型的图表不是「可选」，而是「必须」：

| 场景 | 必须使用的图表 |
|------|----------------|
| 涉及多步骤流程 | Mermaid flowchart / sequenceDiagram |
| 涉及多组件交互 | Mermaid sequenceDiagram |
| 涉及数据模型关系 | Mermaid erDiagram |
| 涉及架构层次 | Mermaid graph 或 ASCII 架构图 |

**图表要求**：

- 每张图必须有标题和编号（如：图2-1 RBAC权限模型ER图）
- 图中必须标注关键的类名/方法名/表名，不允许只有「服务A→数据库」
- Mermaid 代码块必须可直接渲染，语法必须正确

---

### 铁律4 · 可验证原则

- 给出的文件路径必须可直接在源码中搜索验证
- 给出的类名和方法名必须与源码中实际存在的完全一致
- 若不确定某个实现细节，必须使用以下标记：

  > 【待源码验证：该处可能为 XXXService.Process()，需在源码 `modularity/` 或 `framework/` 目录下确认】

- **绝对禁止**编造不存在的文件路径、类名或方法名

---

### 铁律5 · 禁止空泛原则

以下词汇/句式被禁止出现在文档中（除非紧跟具体实现）：

| 禁止 | 必须改为 |
|------|----------|
| ✗ "系统支持..." | 系统通过 [具体类/方法] 实现了... |
| ✗ "采用了..." | 在 [文件路径] 中，通过 [技术手段] 实现了... |
| ✗ "一般来说..." | 删除，直接说本系统的实际做法 |
| ✗ "可以实现..." | 在 [代码位置] 中，当前实现了... |
| ✗ "主要包括..." | 必须逐项列出并给出代码路径，不能笼统概括 |

## 二、文档输出格式规范

### 文档结构

- 使用 Markdown 格式
- 章节编号使用层级：1 → 1.1 → 1.1.1
- 代码路径使用行内代码块：`` `path/to/file.cs` ``
- 代码片段使用围栏代码块并标注语言
- 表格用于对比和清单类信息
- **每个章节结尾必须有**：
  - 「本节核心表清单」
  - 「本节关键代码路径索引」

### 代码片段要求

- 每个核心机制必须附带 20–50 行关键代码片段（从源码中摘录或还原）
- 代码片段必须标注来源文件路径
- 关键行使用注释标注（如 `// ★ 关键：此处注入数据权限过滤条件`）
