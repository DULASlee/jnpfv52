# ADR-016: JNPF 架构部署策略 — 逻辑微服务 + 物理单体

**状态:** Final
**日期:** 2026-06-11
**阶段:** 前端架构重构 / 知识图谱补全前置决策

---

## 背景

在启动前端架构重构、DKEE 知识图谱构建、AI 升维（顾问式 AI + 自博弈引擎）三大战略之前，需要回答一个前置问题：**JNPF 是否需要先重构为微服务架构？**

当前 JNPF V5.2 是一个 **51 项目的模块化单体**，具有清晰的 4 层架构（framework / infrastructure / modularity / application），118 个 API 通过 `IDynamicApiController` 自动生成，模块间通过 DI 接口通信。

如果微服务化是 AI 升维的前置条件，整个时间线将严重延迟。如果不是，则 AI 升维可以立即启动。

---

## 决策内容

**JNPF 不进行物理微服务化重构。**

当前及未来架构策略：

```
逻辑层（不变）：        物理层（不变）：
  modularity/              ┌──────────────────────┐
  ├── Base 模块           │   JNPF 单体容器       │
  ├── WorkFlow 模块       │   单一 Docker 镜像    │
  ├── Message 模块        │   单一进程            │
  ├── VisualDev 模块      │   共享数据库          │
  ├── TaskScheduler 模块  │   DI 内部通信         │
  ├── CodeGen 模块        │   30 秒启动           │
  └── ...                 └──────────────────────┘
```

**逻辑层的边界清晰性才是架构目标，不是物理层的独立部署。**

### 四个核心理由

1. **总架构师的蓝图不需要微服务：**
   - 顾问式 AI → 依赖大模型网关，不依赖部署拓扑
   - 低代码框架 → 需要确定性编译器，不依赖微服务
   - DKEE → 依赖知识图谱数据库，不依赖微服务
   - 自博弈引擎 → 需要沙箱容器，单体更易容器化
   - EAB + 逃生舱 → 是逻辑约束，不是物理拆分

2. **微服务化会严重延误 AI 升维：**
   - 数据库拆分（独立 Schema）→ 3-6 个月
   - API Gateway + 服务发现 → 1-2 个月
   - 分布式事务（Saga/最终一致性）→ 1-2 个月
   - 改造 118 个 API → 2-3 个月
   - 总计 **9-16 个月**，AI 升维完全停滞

3. **微服务不是护城河，AI 才是：**
   - 微服务架构是通用技术能力，任何团队都能做
   - 领域知识图谱 + 自博弈引擎是不可复制的护城河
   - 把 12 个月花在通用能力而非护城河上 → 战略错误

4. **自博弈沙箱用单体更快：**
   - 单体容器：30 秒就绪
   - 微服务集群（K8s + Service Mesh + 配置中心）：5-10 分钟就绪
   - 自博弈需要万次循环，30 秒 vs 10 分钟的差距是致命的

---

## 架构约束（EAB 的一部分）

1. **模块间通过接口通信，不直接引用实现**（当前已在 90% 的模块中满足）
2. **每个模块有独立的 API 契约和数据边界**
3. **物理部署为单体容器**，镜像大小控制在 < 500MB
4. **未来可按需渐进式抽取高负载模块**（如 IoT 数据接入）为独立服务——这是技术演进，不是架构重构

---

## 备选方案

| 方案 | 优点 | 缺点 | 为何不选 |
|---|---|---|---|
| 全面微服务化 | 独立扩缩容、技术栈自由 | 9-16 个月工期，AI 升维停滞，运维复杂度爆炸 | 战略时机不对 |
| 保持现状不提模块边界 | 零成本 | 边界模糊，新成员难以理解，AI 难以理解系统结构 | 不可持续 |
| **逻辑微服务 + 物理单体（本决策）** | 边界清晰、部署简单、AI 升维不延迟、护城河时间不被侵占 | 不支持独立扩缩容 | ✅ 选择此项 |

---

## 后果

**正面：**
- AI 升维可以立即启动，不被基础设施重构阻塞
- 沙箱环境创建速度 30 秒（单体）vs 10 分钟（微服务集群）
- 运维简单，一个容器一个进程
- 模块边界在代码层面清晰，DKEE 可以按模块构建知识图谱

**负面：**
- 无法针对单个模块独立扩缩容
- 高并发场景（如 IoT 数据接入）可能需要后续抽取
- 需定期审查模块边界是否被侵蚀（建议每季度一次）

**风险缓解：**
- 在模块边界处预留接口抽象层（Facade），使未来抽取成本最小化
- 当前数据库已通过租户隔离 + 模块前缀实现逻辑分区
- 如未来某模块确实需要独立扩展，从单体中渐进式抽取，不引发大爆炸式重构

---

## EAB 声明

> JNPF 是模块化单体架构。51 个 C# 项目编译为单一部署单元，内部通过依赖注入接口通信。每个业务模块（modularity/）是一个逻辑服务，有独立的 API 契约（通过 IDynamicApiController 自动生成）和数据边界（通过模块表前缀 BASE_/FLOW_/VISUAL_/ 等区分）。物理部署为单一 Docker 容器。未来可根据负载需求，从单体中渐进式抽取特定模块为独立服务——这是技术演进，不是架构重构。
